## 一、集合与并发容器

### 1. 并发场景下 HashMap 会出现什么问题？

**答案：**

- `HashMap` 不是线程安全容器，并发 `put` / 扩容时可能出现数据覆盖、元素丢失、链表结构异常等问题。
- JDK 1.7 使用数组 + 链表，并且扩容迁移里有头插链表反转过程，多线程竞争下可能形成环形链表，导致查询时死循环。
- JDK 1.8 改成尾插，并在链表过长时转红黑树，降低了死循环风险，但仍然不能保证并发安全。
- 并发读写场景不要用普通 `HashMap`，应根据场景选择 `ConcurrentHashMap`、不可变 Map、加锁保护或业务分片。

### 2. HashMap 在 JDK 1.7 和 JDK 1.8 有什么区别？

**答案：**

| 维度 | JDK 1.7 | JDK 1.8 |
| --- | --- | --- |
| 存储结构 | 数组 + 链表 | 数组 + 链表 + 红黑树 |
| 插入方式 | 头插法 | 尾插法 |
| 哈希扰动 | 多次扰动 | 高 16 位异或低 16 位 |
| 扩容迁移 | 容易在并发下形成环 | 保留原顺序，降低链表成环风险 |
| 性能退化 | 冲突严重时链表 O(n) | 链表过长可树化到 O(log n) |

链表转红黑树不是为了所有场景都更快，而是为了在哈希冲突严重时避免链表过长。红黑树节点更重、维护成本更高，所以不会一开始就用红黑树。

### 3. ConcurrentHashMap 在 JDK 1.7 和 JDK 1.8 的实现差异是什么？

**答案：**

- JDK 1.7 采用 `Segment` 分段锁，每个 `Segment` 内部类似一个小 `HashMap`，并发度受 `Segment` 数量限制。
- JDK 1.8 去掉 `Segment`，改成数组 + 链表 + 红黑树，写入时主要依赖 `CAS` 初始化桶，冲突桶上再用 `synchronized` 锁住桶头节点。
- JDK 1.8 的锁粒度更细，结构更贴近 `HashMap`，并发扩容时多个线程可以协助迁移。
- 面试回答可以概括为：1.7 是分段锁，1.8 是 `CAS + synchronized + 红黑树 + 协助扩容`。

## 二、锁、JUC 与线程池

### 4. synchronized 和 ReentrantLock 有什么区别？

**答案：**

- `synchronized` 是 JVM 内置锁，语法简单，退出代码块会自动释放锁。
- `ReentrantLock` 是 JUC 显式锁，需要手动 `lock()` / `unlock()`，通常要在 `finally` 中释放。
- `ReentrantLock` 支持公平锁、可中断获取锁、限时等待、多个 `Condition` 队列，功能更灵活。
- 普通互斥优先用 `synchronized`，需要中断、超时、公平性或多个条件队列时再考虑 `ReentrantLock`。

### 5. CAS 的流程是什么？有什么问题？

**答案：**

- `CAS` 全称 Compare And Swap，比较内存中的旧值是否等于期望值，如果相等就原子更新为新值。
- 它通常依赖 CPU 原子指令实现，能避免重量级锁切换，常用于无锁并发和乐观更新。
- 典型问题有三个：
  - `ABA` 问题：值从 A 变成 B 又变回 A，CAS 看不出来中间变化。
  - 自旋开销：竞争激烈时一直重试会浪费 CPU。
  - 只能原子更新单个变量，多个变量一致更新要借助封装对象或锁。
- Java 中常见解决方式包括版本号、`AtomicStampedReference`、降低热点竞争、分段更新等。

### 6. 线程池核心参数有哪些？工作流程是什么？

**答案：**

`ThreadPoolExecutor` 常见参数包括：

- `corePoolSize`：核心线程数。
- `maximumPoolSize`：最大线程数。
- `keepAliveTime`：非核心线程空闲存活时间。
- `workQueue`：任务队列。
- `threadFactory`：线程创建工厂。
- `handler`：拒绝策略。

执行流程可以这样答：

1. 线程数小于核心线程数，优先创建核心线程。
2. 核心线程已满，任务进入队列。
3. 队列满了，再创建非核心线程，直到最大线程数。
4. 线程和队列都满了，执行拒绝策略。

参数设计要看任务类型：CPU 密集型更接近 CPU 核数，IO 密集型可以适当放大，但要结合响应时间、阻塞比例、队列长度、下游承载能力一起评估。

### 7. 线程数持续增大会有什么问题？10 核机器把线程池调到 200 怎么评估？

**答案：**

- 线程不是越多越好，线程过多会带来上下文切换、栈内存占用、锁竞争和调度开销。
- CPU 密集型任务线程数远大于核数，通常只会让线程互相抢 CPU，吞吐不一定提升。
- IO 密集型任务可以适当增加线程数，但如果下游连接池、数据库、Redis 或第三方接口承载不了，会把压力转移到下游。
- 评估时看 `CPU user/sys`、load、上下文切换次数、队列堆积、任务耗时分布、GC、下游 RT 和错误率。

## 三、ThreadLocal、异步编程与 JVM 排障

### 8. ThreadLocal 的原理是什么？为什么会内存泄漏？

**答案：**

- 每个线程内部维护一个 `ThreadLocalMap`，`ThreadLocal` 对象作为 key，业务对象作为 value。
- 访问 `ThreadLocal` 时，本质是到当前线程自己的 `ThreadLocalMap` 里读写，所以不同线程互不影响。
- 泄漏风险来自两点：
  - key 是弱引用，`ThreadLocal` 外部强引用消失后 key 可能被 GC。
  - value 仍然被线程持有，在线程池线程长期存活时可能一直释放不了。
- 最稳的习惯是用完后在 `finally` 中调用 `remove()`。

### 9. FutureTask 和 CompletableFuture 有什么区别？

**答案：**

- `FutureTask` 更基础，代表一个可取消、可查询、可阻塞获取结果的异步任务。
- `FutureTask#get()` 通常是阻塞式等待，组合多个异步任务时表达能力较弱。
- `CompletableFuture` 支持回调、链式编排、异常处理、多个任务组合和 DAG 式依赖。
- 工程上简单异步任务可以用 `FutureTask` / `Future`，复杂编排、并行聚合、异步回调更适合 `CompletableFuture`。

### 10. 线上 OOM 或 GC 频繁怎么排查？

**答案：**

- 先确认现象：是堆 OOM、元空间 OOM、直接内存 OOM，还是频繁 Full GC。
- 再看指标：堆使用曲线、GC 日志、对象分配速率、老年代增长、线程数、连接数、缓存大小。
- 常用工具包括 `jstat` 看 GC、`jmap` / heap dump 看对象、`jstack` 看线程、MAT / VisualVM 分析引用链。
- 如果是内存持续上涨，要重点查缓存未淘汰、集合无限增长、ThreadLocal 未清理、消息/任务队列堆积、大对象、连接泄漏。

## 四、Spring 基础

### 11. `@Transactional` 声明式事务的底层原理是什么？

**答案：**

- `@Transactional` 主要基于 Spring AOP 实现，本质是在方法调用前后织入事务开启、提交和回滚逻辑。
- Spring 会为 Bean 创建代理对象，代理方式通常是 JDK 动态代理或 CGLIB。
- 方法进入时通过事务管理器获取连接、关闭自动提交并绑定到当前线程；方法正常返回则提交，抛出匹配的异常则回滚。
- 常见失效场景包括：同类内部方法自调用、方法不是 `public`、异常被吞掉、异常类型不匹配、事务传播行为理解错误。
