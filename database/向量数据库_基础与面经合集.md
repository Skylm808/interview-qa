## 1. 向量数据库解决什么问题？

传统数据库和搜索引擎很擅长按主键、字段条件或关键词找数据。例如搜 `ERR_CONNECTION_RESET`，倒排索引能很快找到包含这个错误码的文档。

但用户问“浏览器连不上服务器怎么办”时，相关文档可能写的是“排查连接被重置”，两段文字没有相同的词。先把文本、图片、音频或商品特征交给 embedding 模型，得到一串浮点数；语义接近的内容在向量空间里距离通常更近。向量数据库负责存储这些向量，并在大量数据中快速找出最近的 Top K。

```text
原始数据 -> embedding 模型 -> 向量 + 元数据 -> 向量数据库

用户问题 -> 同一个 embedding 模型 -> 查询向量
         -> 相似度检索 Top K -> 过滤 / 重排 -> 返回原文或业务对象
```

典型场景：

- RAG 知识库：找与问题语义相关的 chunk，作为 LLM 上下文。
- 语义搜索：用户换一种说法，也能找到相近内容。
- 推荐与召回：用用户、商品或行为序列的 embedding 找相似商品。
- 图片、音频和视频检索：用多模态模型将不同媒介映射到可比较的向量空间。

向量数据库不生成 embedding，也不替代业务主库。模型负责“怎么表示”，向量数据库负责“怎么存、怎么找”；订单、权限、原文等事实数据通常仍在 MySQL、ES 或对象存储中。

## 2. 数据模型：向量与元数据

一条向量记录通常至少有四部分：

```text
id:          chunk_10086_03
dense_vector:[0.12, -0.31, 0.76, ...]     # 例如 768 / 1024 / 1536 维
sparse_vector:{"token_12": 1.4, "token_991": 0.8}  # 可选
metadata:    tenant_id, doc_id, title, acl, version, created_at, tags ...
```

- `id` 是稳定主键，用于幂等写入、删除和回查原文。
- 向量字段参与相似度计算。
- `metadata` 是结构化字段，用于租户隔离、权限过滤、时间范围、文档版本和业务筛选。
- 原文可以和向量放在同一库，也可以只存摘要与 `doc_id`，命中后再回主库或对象存储取全文。

**不要只存向量。** 如果知识库里没有 `tenant_id`、`acl`、`doc_version`，系统很难做权限过滤、删除旧版本和排查错误来源。

### 2.1 Collection、分区和索引

不同产品叫法不同，概念大致对应：

| 概念 | 可以理解成什么 | 用途 |
| --- | --- | --- |
| Collection / Class / Index | 一张向量表或一个逻辑数据集 | 定义字段、维度和相似度度量 |
| Partition / Shard | Collection 内部的数据切分 | 扩容、隔离或缩小搜索范围 |
| Vector index | 为向量建立的近邻索引 | 不必逐条比较全部向量 |
| Scalar / payload index | 元数据字段的索引 | 加速 `tenant_id`、时间、标签等过滤 |

同一个向量字段里的维度和 embedding 模型必须一致。把 768 维和 1536 维向量混进同一索引无法查询；即使维度碰巧相同，换了模型后语义空间也可能不同。实际表里应记录 `embedding_model` 与 `embedding_version`，模型升级时双写或新建 collection，灰度验证后再切流。

## 3. 稠密向量、稀疏向量与混合检索

### 3.1 稠密向量（Dense Vector）

稠密向量维度固定，绝大多数位置都是非零浮点数，例如：

```text
[0.12, -0.31, 0.76, 0.08, -0.44, 0.59]
```

它通常由 embedding 模型生成，擅长表达语义关联。用户搜“iPhone 充电头”，即使文档标题是“苹果手机充电器”，稠密检索仍可能召回。

代价是存储和索引成本高。以 `1536` 维 `float32` 为例，一条原始向量约为 `1536 × 4 = 6144` 字节，1000 万条数据的原始向量就接近 60 GB；HNSW 图、元数据和副本会继续增加内存或磁盘占用。

### 3.2 稀疏向量（Sparse Vector）

稀疏向量的总维度可以很高，但一条记录只有少量位置有值，通常只保存“维度 ID -> 权重”：

```text
{ "苹果": 1.2, "手机": 0.8, "充电器": 1.5 }
```

传统 BM25 与倒排索引可以看作典型的稀疏检索思路；学习型稀疏模型还会为扩展词项分配权重。它擅长错误码、商品型号、接口名、人名、数字等必须精确命中的内容，而且结果更容易解释。

### 3.3 两者怎么选？

| 对比项 | 稠密向量 | 稀疏向量 |
| --- | --- | --- |
| 强项 | 同义改写、自然语言语义 | 关键词、型号、错误码、专有名词 |
| 常见索引 | HNSW、IVF、DiskANN 等 ANN 索引 | 倒排索引 |
| 可解释性 | 较弱，单维度通常没有业务含义 | 较强，可看到命中的词和权重 |
| 常见问题 | 语义泛相关，精确条件可能被忽略 | 换词后可能漏召回 |

生产中常用混合检索。稀疏侧保住 `HTTP 502`、`SKU-2026-A`、类名等精确线索；稠密侧补“换句话说”的语义召回；之后用 RRF、加权融合或 reranker 把候选重新排序。

```text
Query
  -> BM25 / sparse Top 50
  -> dense ANN Top 50
  -> 去重与融合（RRF / 加权）
  -> reranker Top 10
  -> 返回 Top 3 ~ 5
```

不要因为接入了向量检索就直接删掉 BM25。对技术文档、商品和企业知识库，混合检索往往更稳。

## 4. 相似度与向量索引

### 4.1 相似度度量

常用度量有：

- **Cosine similarity（余弦相似度）**：比较方向，常用于文本 embedding。若向量已做 L2 归一化，余弦相似度与内积排序等价。
- **Inner Product（内积）**：很多模型或推荐场景直接用它；必须确认模型训练和归一化方式。
- **L2 distance（欧氏距离）**：比较几何距离，适合明确以 L2 训练或评估的模型。

不要把度量方式随便换掉。入库向量和查询向量要用同一模型、同一预处理和同一度量；不匹配时，分数通常没有意义。

### 4.2 精确检索与 ANN

精确 kNN 会将查询向量和每条记录计算一次距离。100 万条、1536 维时成本很高，但结果可做到精确。

ANN（Approximate Nearest Neighbor）允许少量近似误差，换取更低延迟和更高吞吐。面试里可以记成：`kNN` 是“要找最近 K 个”的问题，`ANN` 是加速路线。

| 索引 | 思路 | 优点 | 代价与适用情况 |
| --- | --- | --- | --- |
| FLAT | 暴力计算全部距离 | 精确、实现简单 | 数据量小、离线评测或作为 recall 基准 |
| HNSW | 多层近邻图导航 | 低延迟、召回高，使用很广 | 建图慢、内存开销较大；要调 `ef` 类搜索参数 |
| IVF / IVFFlat | 先聚类到桶，再搜索少量桶 | 建索引和内存成本通常低于 HNSW | 需训练/选择桶数与 probes；召回依赖参数 |
| PQ / 量化 | 压缩向量或残差编码 | 大幅降低内存和磁盘占用 | 距离有误差，需评估 recall 损失 |
| DiskANN 类 | 让大部分索引和向量放 SSD | 超大规模时节省内存 | 强依赖 NVMe 与 IO 调优 |

索引没有“永远最好”的选择。先拿一组带标注的查询，对比 `Recall@K`、p95/p99、索引构建时间、内存和成本；再决定 HNSW、IVF 或量化方案。只看 QPS 很容易把“检索变快但答案变差”的问题带到线上。

## 5. 一次读请求到底怎么执行？

“读向量数据库”不等于根据主键 `get` 一条记录。最常见的是一次相似度检索，读链路如下：

```text
用户问题
  -> Query Rewrite（可选）
  -> Embedding Service：生成 query_vector
  -> 权限 / tenant / 文档状态过滤条件
  -> Vector DB：ANN 找候选 + metadata filter
  -> sparse 候选融合（可选）
  -> Reranker：精排少量候选（可选）
  -> 按 doc_id / chunk_id 补原文、标题、引用链接
  -> 返回搜索结果，或交给 LLM 生成
```

### 5.1 先过滤，再检索还是先检索，再过滤？

业务上，权限过滤必须在结果返回前严格生效。技术实现则要看产品能力与过滤选择性：有的引擎能把标量过滤和 ANN 过程结合，有的会在候选阶段再过滤。无论哪种，都要压测两个风险：

- 过滤字段没有索引时，检索会退化或变慢。
- 如果先只取很少的 ANN 候选再做严格过滤，可能过滤完一条都不剩，或召回率明显下降。

例如用户只能访问 `tenant_id=t1` 的文档，不能先在全部租户的 Top 10 中找到结果，再把不属于 `t1` 的结果返回或交给 LLM。应把 `tenant_id`、文档状态和 ACL 放进检索条件，必要时为高频过滤字段建立 payload/scalar 索引。

### 5.2 为什么还需要 reranker？

向量检索负责快速召回，常取 Top 20～100；它看的是向量距离，未必能区分“同主题但没回答问题”和“真正包含答案”的段落。reranker 将问题和少量候选一起输入更精细的模型，得到更可靠的排序，再选 Top 3～10。

例子：用户问“订单取消后库存什么时候回补”。向量检索可能同时召回“库存预扣”“支付超时”“退款”，reranker 会把同时包含“取消”和“回补规则”的段落放前面。候选不要取无限多，否则 reranker 延迟和成本会失控。

### 5.3 读接口应返回什么？

至少返回 `id`、相似度分数、`doc_id`、`chunk_id`、标题路径、文档版本和必要原文。对 RAG，还应记录 query 的模型版本、filter、召回候选、融合分数、rerank 分数与最终上下文，才能定位“没召回”“排错了”还是“模型答错了”。

## 6. Milvus：拿 MySQL 类比，理解概念、索引和查询

先记一句最重要的话：**Milvus 不是 MySQL 的替代品，而是专门解决“向量相似度 Top K”问题的检索服务。** MySQL 保存价格、库存、订单等事实数据；Milvus 保存向量和检索所需元数据，返回最相近的候选 ID。

### 6.1 先建立最直观的对应关系

| Milvus | 类比 MySQL | 作用 |
| --- | --- | --- |
| Database | Database / Schema | 较粗粒度地隔离业务，例如公司知识库和商品搜索。 |
| Collection | Table | 一组 schema 固定的向量记录。 |
| Field | Column | 主键、文本、向量、tenant_id、时间等字段。 |
| Partition | 表分区 / 逻辑分区 | 缩小数据范围或隔离；不是给每个高基数租户都建一个分区。 |
| Vector index | 特殊索引 | 加速“哪个向量和 query vector 最像”。 |
| Scalar index | 普通字段索引 | 加速 tenant_id、doc_id、状态、时间、标签等过滤。 |
| Segment | 内部数据块 | Milvus 用于写入、建索引、加载和 compaction 的存储单元，没有 MySQL 的严格一一对应。 |

例如 RAG 的 Collection 可以理解为一张 document_chunks 向量表：

~~~text
id              主键
text            chunk 原文或摘要
embedding       FLOAT_VECTOR(1024)
tenant_id       租户
doc_id          所属文档
title_path      标题路径
doc_version     文档版本
status          READY / DELETED
~~~

其中 embedding 是 MySQL 普通业务表没有的核心字段；一条记录可能把“Redis 6.0 引入网络 IO 多线程”表示为一串 1024 维浮点数。向量维度、embedding 模型和距离度量必须匹配：1024 维的查询向量不能去搜 768 维 collection；换了模型也不应把新旧向量直接比较。

### 6.2 get、query、search：最容易混淆，也最重要

可以把三种读操作记成：**知道 ID 用 get，知道条件用 query，知道语义用 search。**

| 操作 | Milvus 在做什么 | 类比 MySQL | RAG 例子 |
| --- | --- | --- | --- |
| get | 按主键取已知实体 | WHERE id = 10086 | 取已知 chunk 的内容和 metadata。 |
| query | 用标量字段过滤，不按向量距离排序 | WHERE tenant_id = 'A' AND doc_id = 'redis.pdf' | 找公司 A 的 redis.pdf 所有 chunk。 |
| search | 传 query vector，按距离取 Top K；可叠加 filter | MySQL 传统 B+ 树不擅长的高维近邻查询 | 只在公司 A 可访问文档中找“Redis 网络 IO”相关段落。 |

~~~text
用户问题：Redis 为什么能处理高并发？
  -> embedding 模型生成 query_vector
  -> Milvus search：vector + tenant_id/ACL filter + Top K
  -> 返回最相近的 chunk_id、distance、metadata
  -> reranker 精排 -> LLM 基于原文回答
~~~

所以 query 和 search 的边界要说清：query 只是 metadata 条件筛选；search 才是“向量相似度 + 可选 metadata filter”。权限、tenant、文档状态必须作为 search filter 生效，不能先返回跨租户候选，再让 LLM 自己忽略。

### 6.3 向量检索是不是一定走索引？没有索引会怎样？

对某个向量字段，Milvus 通常会用该字段配置的向量索引完成 search。若使用 FLAT，或没有可用的 ANN 近邻索引，本质上更接近暴力计算：将 query vector 与候选向量逐个算距离，再取 Top K。

~~~text
100 万条、768 维向量，FLAT：
query_vector -> 依次计算 100 万次距离 -> 排序/取 Top K
优点：精确，适合小数据和效果基线。
代价：数据量上来后，计算与延迟很高。
~~~

| 向量索引 | 核心思路 | 取舍 |
| --- | --- | --- |
| FLAT | 比较全部候选向量 | 精确，但大规模慢。 |
| HNSW | 在多层近邻图上导航 | 常用，召回高、延迟低；建图和内存开销较大。 |
| IVF | 先聚类，搜索少量最近桶 | 内存/构建成本可控；需要调桶数和 probes。 |
| DiskANN 类 | 大部分索引/向量放 SSD | 超大规模节省内存；更依赖 NVMe 和 IO 调优。 |

这不是说“没向量索引，所有字段都暴力扫”。tenant_id、doc_id、created_at 等 metadata 可以建立 scalar index 来帮助过滤。实际 search 会结合标量过滤与向量候选；过滤是先在检索阶段参与还是候选后进一步筛掉，和具体版本、索引和数据分布有关，必须压测过滤后的候选数和 Recall@K。

### 6.4 Partition、Segment 和集群读写链路

Partition 是更偏逻辑的切分；Segment 是 Milvus 内部实际写入、加载、建索引和 compaction 的数据块。一个 Partition 可以有多个 Segment。大规模多租户场景中，不要机械地做“一个 tenant 一个 Partition”；通常应让 Partition Key 将数据映射到有限数量的内部 partition，再用 tenant_id filter 做权限过滤。

~~~text
写入：
Client -> Proxy -> Streaming Node -> WAL（预写日志）
       -> Growing Segment（新写入、可查询）
       -> flush / compaction -> Sealed Segment（历史数据）
       -> Data Node 建索引 -> 对象存储

查询：
Client -> Proxy -> Streaming Node（搜新数据） + Query Node（搜历史 Segment）
       -> 合并各 Segment / shard 的 Top K -> 返回
~~~

- Proxy 是无状态入口，负责路由和结果汇总；Coordinator 管理拓扑、调度和元数据。
- Streaming Node 处理写入和新数据；Query Node 检索历史 Segment；Data Node 做 compaction 和索引构建。
- 生产关注点包括索引是否加载、Query Node 容量、segment 数量、对象存储吞吐和删除比例，而不只是 SDK 是否返回成功。

### 6.5 最小 Python 使用示例

下面是新版 pymilvus 的最小流程。vector_1 和 query_vector 必须来自同一个 embedding 模型，且长度都等于 DIM。

~~~python
# pip install -U pymilvus
from pymilvus import MilvusClient

DIM = 1024
client = MilvusClient("kb_milvus.db")  # 本地演示；生产环境改为 uri + token

client.create_collection(
    collection_name="kb_chunks",
    dimension=DIM,
    metric_type="COSINE",
)

client.insert(
    collection_name="kb_chunks",
    data=[{
        "id": 1,
        "vector": vector_1,
        "text": "Redis 连接数满时先检查 maxclients、连接池和慢客户端。",
        "tenant_id": "company_a",
        "doc_id": "redis_note",
        "status": "READY",
    }],
)

# 语义检索，并把权限/状态限制在检索条件里。
hits = client.search(
    collection_name="kb_chunks",
    data=[query_vector],
    filter='tenant_id == "company_a" and status == "READY"',
    limit=10,
    output_fields=["text", "doc_id", "status"],
)

# 纯 metadata 查询：不是向量相似度检索。
rows = client.query(
    collection_name="kb_chunks",
    filter='tenant_id == "company_a" and doc_id == "redis_note"',
    output_fields=["text", "status"],
)
~~~

快速创建适合理解 API。生产中要显式定义 schema、为高频 filter 建标量索引、按规模选择 HNSW/IVF 等索引；批量导入后确认索引和 collection 已加载。重试写入用 upsert 或业务版本控制，避免重复主键或旧版本覆盖新版本。

### 6.6 Milvus 与 MySQL 应怎样分工？

~~~text
商品修改：MySQL product（事实源）
  -> CDC / Outbox
  -> 生成或更新 embedding
  -> Milvus product_vector（检索副本）

用户搜索：“适合通勤的防水双肩包”
  -> embedding
  -> Milvus 召回 Top 200 product_id
  -> MySQL 校验仍在售、价格、库存
  -> 业务排序并返回商品卡片
~~~

| 维度 | MySQL | Milvus |
| --- | --- | --- |
| 最擅长的查询 | 主键、范围、Join、精确条件 | 高维空间里的语义相似 Top K |
| 索引 | B+ 树、联合索引等 | HNSW、IVF、量化等向量近邻索引 |
| 数据定位 | 订单、库存、价格、权限等事实源 | 向量、候选 ID 和检索 metadata 副本 |
| 一致性 | 强业务约束、事务 | 通常允许短暂最终一致，可从源数据重建 |
| 不适合做什么 | 大规模高维 ANN | 支付、扣库存、复杂事务和多表 Join |

一句话记忆：**MySQL 回答“这件商品现在能不能卖”；Milvus 回答“哪些商品和用户意图最相近”。**

## 7. RAG 中 ES 与 Milvus 怎么选？

ES 和 Milvus 都能做向量检索，差别在“谁是主能力”。ES 是搜索引擎，关键词搜索、过滤、聚合、排序和运营检索能力很完整；Milvus 是专用向量检索系统，更适合把高吞吐、大规模 ANN 召回单独做成一层。两者都必须用真实评测集比较 Recall@K、延迟和成本，不能只凭产品名选型。

| RAG 情况 | 优先 ES | 优先 Milvus |
| --- | --- | --- |
| 现有基础设施 | 已经有 ES，文档和关键词索引已在其中 | 已有 Milvus 或向量检索要独立建设 |
| 检索目标 | 关键词、型号、筛选、聚合、运营搜索与语义检索同等重要 | 语义召回、多模态或推荐是核心，向量规模/吞吐更高 |
| 混合检索 | ES 可在同一次搜索中组合全文、dense vector、sparse vector，并做 RRF 融合 | 可做稠密/稀疏或多向量检索，但关键词生态、聚合和运营检索通常不如 ES 顺手 |
| 运维取舍 | 少一个系统；适合先快速验证 RAG | 检索层可独立扩容、单独调向量索引；但要维护源数据同步和另一套集群 |
| 常见链路 | ES：BM25 + kNN -> RRF -> reranker | Milvus：dense/sparse Top K -> 应用融合/重排；原文和事实数据放主库或对象存储 |

**RAG 例子：** 企业已有 ES，用户会搜索错误码、接口名和自然语言问题。优先在 ES 内把 BM25 的精确命中和 dense_vector 的语义命中融合；它减少一次数据同步，也方便过滤 tenant、文档状态和标签。Elasticsearch 官方支持将全文、向量、过滤和混合检索组合在同一检索引擎中。[官方向量检索说明](https://www.elastic.co/docs/solutions/search/vector) [官方混合检索说明](https://www.elastic.co/docs/solutions/search/hybrid-search)

如果是图片/商品相似召回、数亿级 embedding，或者 ES 已因全文检索和聚合很忙，不希望向量索引争抢资源，则将 Milvus 作为独立召回层更合理。Milvus 的 Proxy、Query Node、Data Node 和对象存储分层支持检索与索引构建分别扩展；但“Milvus 一定比 ES 快”并不成立，过滤比例、索引参数、硬件、数据更新率和目标 recall 都会改变结果。[Milvus 架构说明](https://milvus.io/docs/architecture_overview.md)

不要一开始就同时上 ES 和 Milvus。需要双写时，以文档系统/主库为事实源，事件携带 doc_id 和 version，通过 CDC/Outbox 同步到两个检索副本；读侧在应用层融合时要能处理版本延迟、删除和权限过滤。

## 8. 常用向量数据库怎么选？

下面按典型定位比较，不把某个产品说成唯一答案。

| 方案 | 常见定位 | 适合什么情况 | 需要留意 |
| --- | --- | --- | --- |
| [Milvus](https://milvus.io/docs/overview.md) | 专用开源向量数据库 | 大规模向量检索、独立扩缩容、多索引选择 | 自建集群的资源、数据同步与运维成本 |
| [Qdrant](https://qdrant.tech/documentation/guides/) | 专用向量数据库，强调 payload filter | 需要向量检索和结构化过滤结合，想使用较直接的 collection/payload 模型 | 高频 filter 字段要建 payload index；磁盘模式依赖 NVMe |
| [Weaviate](https://docs.weaviate.io/weaviate/concepts/search) | 向量、关键词、混合检索和模块化能力 | 希望较快搭建语义/混合搜索，或使用多模态检索能力 | 仍要自己评估 embedding、filter、混合权重与成本 |
| [pgvector](https://github.com/pgvector/pgvector) | PostgreSQL 扩展 | 数据量中小、已有 Postgres、需要 SQL/事务/Join 生态 | HNSW 内存较大；IVFFlat 要调 lists/probes；超大规模需评估扩展边界。详见 [PostgreSQL 基础与面经合集](./PostgreSQL_基础与面经合集.md) |
| Elasticsearch / OpenSearch | 搜索引擎附带向量能力 | 已有 ES、关键词搜索和过滤是主需求，向量检索是补充 | 高频更新、segment merge、向量内存与索引参数需要单独压测 |

一个实用的选型顺序：

1. 已经有 ES 或 PostgreSQL，先验证现有体系能否达到目标 recall、p99 和成本。
2. 向量规模、过滤组合、吞吐或多租户隔离成为瓶颈，再评估 Milvus、Qdrant、Weaviate 这类专用系统。
3. 团队只想托管服务、希望减少运维时，再按云厂商、数据合规、地域和价格选择托管向量服务。

## 9. RAG 的完整例子

以企业内部技术文档问答为例。员工问：“Redis 连接数突然满了，先查什么？”

```text
文档上传
  -> 解析 Markdown / PDF，按标题和段落切 chunk
  -> 生成 chunk_id、doc_version、tenant_id、ACL、标题路径
  -> embedding，批量写入向量库；标题和正文同时写入 BM25 索引

用户提问
  -> 鉴权，得到 tenant_id 与 ACL
  -> 用同一 embedding 模型生成 query vector
  -> dense Top 50：语义相近的 Redis 排障段落
  -> sparse Top 50：含“连接数”“maxclients”等精确词的段落
  -> RRF 融合、去重，rerank 为 Top 5
  -> 取原文和标题路径，连同引用交给 LLM
  -> LLM 基于资料作答；资料不足时明确说明
```

这里有四个容易漏掉的点：

- ACL 应在检索条件中生效，不能让 LLM “自觉忽略”越权内容。
- chunk 要保留标题路径和版本。只存一小段正文，命中后读者不知道它属于哪篇文档。
- 文档更新后，新旧 chunk 的切换要原子化或按版本过滤，不能一直累积旧向量。
- 检索结果要保留日志。用户说“答案不对”时，先看正确 chunk 有没有被召回，再看重排和生成。

## 10. 生产设计与排障点

### 10.1 写入链路

```text
原文入库 / 对象存储
  -> 解析与切块
  -> embedding（带模型版本）
  -> 批量 insert / upsert
  -> 建索引或等待增量索引生效
  -> 记录 READY 版本并发布
```

- embedding 调用、向量写入和元数据更新跨系统时要有任务状态、幂等键、重试和死信处理。
- 大批导入宜批量写入，避免逐条 RPC；索引构建会消耗 CPU、内存和 IO，应避开线上高峰或使用独立资源。
- 删除通常是逻辑删除、tombstone 或异步 compaction。要监控删除比例，否则索引体积和查询效果可能变差。

### 10.2 读链路指标

| 指标 | 用来发现什么问题 |
| --- | --- |
| Recall@K、nDCG、人工标注集 | 召回是否真的找到了相关内容 |
| 向量检索 p50/p95/p99、rerank 耗时 | 是向量库慢，还是后处理慢 |
| filter 后候选数、空结果率 | ACL/tenant/filter 是否过严或索引异常 |
| 索引构建耗时、加载内存、磁盘/网络 IO | 容量是否接近上限，是否需要量化或扩容 |
| embedding 失败率、模型版本分布、索引新鲜度 | 新文档为何没有被搜到 |

### 10.3 常见故障定位

| 现象 | 优先检查 |
| --- | --- |
| 正确文档完全没出现 | 文档是否切块/写入成功、是否被 ACL 或版本过滤、query 与入库模型是否一致 |
| 候选里有正确文档，最终答案仍错 | 融合权重、reranker、上下文截断、LLM 引用规则 |
| 延迟突然升高 | 查询向量服务、filter 索引、HNSW/IVF 搜索参数、冷热数据、节点 CPU/内存/IO、索引加载状态 |
| 改成 ANN 后结果变差 | 搜索参数太保守、过滤后候选不足、量化误差、索引构建或模型版本有问题 |
| 用户看到了别的租户内容 | 立即检查 filter 是否在检索请求里生效、ACL 元数据是否正确、缓存 key 是否包含租户与权限版本 |

## 11. 高频面试问答

### 11.1 向量数据库和传统数据库有什么区别？

传统数据库更擅长按主键和结构化条件精确查找；向量数据库增加了“按语义距离找最近邻”的能力，并用 ANN 索引避免全量算距离。它们通常协作：业务主库保存事实数据和事务，向量库保存检索副本与向量索引。

### 11.2 为什么 HNSW 快，为什么又贵？

HNSW 把向量组织成多层近邻图，查询时从高层快速跳到目标附近，再在底层展开搜索，因此不必扫描全部向量。图的邻接关系需要额外内存，建图和更新也更重；提高搜索候选数会提高 recall，同时也会增加延迟。

### 11.3 向量检索为什么不能直接替代关键词检索？

向量擅长语义，但对错误码、型号、日期、数字和罕见专有名词不一定稳定。用户搜 `go1.24`、`ERR-1024` 或某个订单号时，关键词/稀疏检索通常更可靠，所以生产中常将稠密和稀疏候选融合。

### 11.4 元数据过滤应该怎么做？

将 `tenant_id`、ACL、状态、时间、标签等作为结构化字段保存，并为高频条件建立对应索引。权限条件必须在向量检索请求中生效；不能先把越权候选交给 LLM，再希望它不引用。过滤选择性很强时，要单独压测 recall 和延迟。

### 11.5 如何让模型升级不影响线上检索？

新建 `embedding_version` 或新 collection，先对增量/历史数据重算向量并双写；用同一评测集比较 recall、答案质量和延迟；灰度切读流量，确认稳定后再下线旧索引。不要把新旧模型向量混放后直接比较距离。

### 11.6 面试里如何用一分钟回答“向量数据库怎么读”？

> 用户问题先经同一 embedding 模型变成 query vector，查询带上 tenant、ACL、文档状态等过滤条件。向量库通过 HNSW 或 IVF 这类 ANN 索引召回 Top K，业务侧再和 BM25/稀疏结果融合，必要时用 reranker 精排，最后按 `doc_id` 或 `chunk_id` 取原文和引用。我要监控 recall、检索 p99、过滤后候选数和索引新鲜度。向量库负责召回，不负责代替权限、原文存储和最终答案判断。

## 12. RAG 发展主线：从相似度检索到可维护知识

### 12.1 先看结论：这不是六代产品依次淘汰

RAG 的全称是 **Retrieval-Augmented Generation，检索增强生成**：先从外部知识源找资料，再把资料交给大语言模型生成答案。2020 年的 RAG 论文把“模型参数中的知识”和“外部可检索知识”组合起来，后来工程界逐渐把它扩展成文档问答、企业搜索和 Agent 知识系统。[RAG 原始论文](https://arxiv.org/abs/2005.11401)

下面这条路线能帮助理解重点变化，但不能理解成严格的版本号：

```text
Vector RAG：   找语义相似的片段                similarity（相似度）
GraphRAG：     找实体、关系和全局主题          relations（关系）
LightRAG：     用更轻的图结构兼顾局部与全局    efficient graph retrieval（高效图检索）
树形索引：     按不同抽象层级逐层定位          hierarchical reasoning（分层推理）
LLM Wiki：     把反复推导的知识编译成可积累页面 curation（持续整理）
OKF：          把知识做成可移植、可审计的格式   interoperability（互操作性）
```

这里第一次出现两个词：

- **Curation（知识整理/策展）**：不是简单保存原文，而是持续做提炼、去重、关联、纠错、标注来源和淘汰过期内容。
- **Interoperability（互操作性）**：同一份知识可以被不同模型、Agent、编辑器和检索系统读写，不被某个私有数据库或 SDK 锁死。

GraphRAG、LightRAG 和树形索引在 2024 年前后是并行探索，解决的问题也不同；LLM Wiki 和 OKF 则在 2026 年把关注点从“查询时怎样搜”继续推向“知识怎样长期维护与交付”。实际系统完全可以同时使用向量库、知识图谱、层级目录、Wiki 和 Git。

### 12.2 长上下文不是一个 RAG 阶段，而是一条并行路线

**上下文窗口（context window）** 是模型一次推理最多能接收的 token 数量。Token 是模型处理文本的基本单位，可以粗略理解为字、词或词的一部分。

长上下文模型可以一次读很多材料，但“能装下”不等于“每次都应该全装进去”：

- 资料越多，输入成本和首字延迟越高。
- 无关片段、重复内容、过期规则和互相冲突的说法会干扰回答。
- 关键信息处在长文本中间时，模型可能没有充分利用它。
- 权限隔离不能靠“把全部资料给模型，再提醒它不要看”。

因此长上下文更适合处理“已经筛选后的完整章节、代码文件或少量候选资料”；RAG 负责先决定该给模型看什么。两者通常组合，而不是二选一。

下面一直使用同一个例子：公司内部有支付、订单、库存三个服务的设计文档、接口说明、变更记录和事故复盘。用户问：

> 7 月订单支付失败为什么会影响库存回补？修复方案后来改过几次？

这个问题既要找具体事故，也要跨服务追关系，还要识别修复方案的版本变化。

### 12.3 第一阶段：Vector RAG——先解决“外部知识怎么接进来”

#### 12.3.1 它是什么

Vector RAG 通常把文档切成小段，转换成向量，再按问题与文档片段的语义相似度取回 Top K。

第一次出现的名词：

- **Chunk（文本块）**：从文档切出来的一个片段，是最常见的检索单位。
- **Embedding（向量表示）**：模型把文本映射成一串数字，使语义相近的文本在向量空间里通常更接近。
- **Retriever（检索器）**：根据问题找候选资料的模块，可以是向量检索、BM25 或二者混合。
- **Generator（生成器）**：读取问题和候选资料并生成最终答案的 LLM。

```text
文档 -> 切 chunk -> embedding -> 向量索引

问题 -> embedding -> 相似度 Top K -> rerank -> LLM 回答
```

#### 12.3.2 用例子理解

问题里有“支付失败”“库存回补”。Vector RAG 可能召回：

1. 支付超时事故复盘中的一个片段；
2. 库存预扣与回补规则；
3. 订单取消状态机；
4. 另一场相似但无关的支付事故。

LLM 根据这些片段拼出答案。它擅长找“表述不同但意思接近”的内容，例如问题说“返钱”，文档写“退款”。

#### 12.3.3 这一阶段着重看什么

- **切块质量**：chunk 太小会丢上下文，太大会混入无关内容；应保留标题路径、文档 ID 和版本。
- **混合检索**：错误码、接口名、日期和版本号常由 BM25 找得更准；语义问题由向量补充。
- **元数据过滤**：租户、ACL、文档状态和版本必须在检索时过滤。
- **重排**：向量 Top K 只是粗召回，reranker 再判断哪些片段真正回答问题。
- **评测**：先看正确资料有没有进入 Top K，再看最终答案；不要把检索错和生成错混在一起。

#### 12.3.4 它的局限

向量检索主要回答“哪段文字和问题像”，不天然知道：

- 支付服务调用订单服务，订单服务再发布库存事件；
- 事故 A 和修复 PR B 是什么关系；
- 整个资料库的三大主题是什么；
- 同名服务、别名和跨文档实体是不是同一个对象。

这推动了图结构和层级结构的引入。

### 12.4 第二阶段：GraphRAG——从相似片段走向实体、关系和全局主题

#### 12.4.1 先区分两个概念

**Graph RAG** 是一类方法：用图结构辅助检索增强生成。**Microsoft GraphRAG** 是其中一个具体方案，重点解决普通 Vector RAG 不擅长的全局问题，例如“整个资料库有哪些主要主题”。

第一次出现的名词：

- **Entity（实体）**：可以被单独识别的对象，如“订单服务”“库存服务”“事故 INC-1024”。
- **Relation（关系）**：实体间的有向或无向联系，如“订单服务发布库存回补事件”。
- **Knowledge Graph（知识图谱）**：以实体为节点、关系为边组织事实的图。
- **Community（社区）**：图中联系紧密的一组节点。Microsoft GraphRAG 会对社区分层并生成摘要。
- **Global Query（全局问题）**：需要理解整个语料库主题或趋势的问题，而不是寻找一段明确事实。

Microsoft GraphRAG 的典型索引过程是：从文档抽取实体和关系，形成知识图谱；对图做社区划分并预生成社区摘要。回答全局问题时，多个社区摘要先分别生成局部答案，再汇总成最终答案。[Microsoft GraphRAG 论文](https://www.microsoft.com/en-us/research/publication/from-local-to-global-a-graph-rag-approach-to-query-focused-summarization/)

```text
原始文本
  -> 实体/关系抽取
  -> 知识图谱
  -> 社区划分
  -> 各层社区摘要

问题 -> 局部实体检索或全局社区检索 -> 汇总证据 -> LLM 回答
```

#### 12.4.2 用例子理解

图中可能出现：

```text
[INC-1024 支付事故]
    ├─ caused_by -> [支付回调重复]
    ├─ affected  -> [订单状态机]
    ├─ triggered -> [库存回补事件]
    └─ fixed_by  -> [PR-884]
                       └─ reverted_by -> [PR-901]
```

Vector RAG 可能分别找到事故、状态机和 PR 三个片段；GraphRAG 可以沿关系把它们组织成一条证据链。问“这个季度事故的共同原因是什么”时，社区摘要还能聚合多场事故的共同主题。

#### 12.4.3 这一阶段着重看什么

- **抽取质量**：实体漏抽、关系方向错误，会让后续推理建立在错图上。
- **实体消歧**：`order-service`、`订单服务`、旧名 `trade-order` 是否是同一实体。
- **局部与全局检索**：查一个接口用局部实体邻域；总结全库主题用社区摘要，不能所有问题都跑全图。
- **证据回链**：每个实体和关系都要能回到原文片段，图本身不能成为无来源的“第二真相”。
- **构建成本**：抽取实体、关系、社区和摘要需要大量 LLM 调用；语料更新时也要维护图。

#### 12.4.4 它的局限

GraphRAG 的图构建成本高，增量更新、删除和实体合并都比简单向量索引复杂。关系抽错后，错误还可能在社区摘要中被放大。因此它适合确实需要跨文档关系、全局主题和多跳证据的场景，不应为了“架构高级”替换所有 Vector RAG。

### 12.5 第三阶段：LightRAG——让图检索更轻，并兼顾局部与全局

#### 12.5.1 它是什么

LightRAG 是 2024 年提出、后来发表于 EMNLP 2025 的轻量级图 RAG 方案。它不是“把 GraphRAG 换个名字”，而是使用知识图谱与向量表示的双层结构，并把检索关键词分成低层和高层：

- **Low-level keyword（低层关键词）**：具体实体或细节，如“INC-1024”“库存回补事件”。
- **High-level keyword（高层关键词）**：主题或概念，如“跨服务一致性”“事故演进”。
- **Dual-level retrieval（双层检索）**：同时寻找具体对象和宏观关系，再合并上下文。

```text
文档 -> chunk
     -> 实体/关系抽取 -> 图存储
     -> 实体、关系、chunk 的向量索引

问题 -> 高层/低层关键词
     -> local / global / hybrid 检索
     -> 合并图上下文和原始 chunk
     -> LLM 回答
```

论文的核心目标是用较轻的方式提供图增强检索；当前开源项目又继续加入了增量插入、选择性删除和多种后端等工程能力。论文结论与后续项目功能要分开看。[LightRAG 论文](https://openreview.net/pdf?id=AibDk9Z48i) [LightRAG 官方仓库](https://github.com/HKUDS/LightRAG)

#### 12.5.2 用例子理解

对于“7 月订单支付失败为什么影响库存回补”：

- 低层检索找 `7 月事故`、`支付回调`、`库存回补事件`；
- 高层检索找 `订单一致性`、`跨服务补偿` 等关系主题；
- 两部分合并，既保留事故细节，也补足它在整个系统中的位置。

相比预先为所有图社区生成多层报告的做法，LightRAG 更强调通过双层关键词和图邻域直接组织上下文，以减少索引和查询成本。

#### 12.5.3 这一阶段着重看什么

- **四类存储的一致性**：实际项目常同时有 KV、向量、图和文档状态存储；写入失败时要能补偿或重建。
- **local/global/hybrid 模式**：具体事实用 local，全局关系用 global，两者都需要时才用 hybrid；不能默认最重模式。
- **增量更新与删除**：文档变化后，哪些实体和关系需要重算，孤立节点怎么清理。
- **抽取模型与缓存**：索引成本很大一部分来自 LLM 抽取；应缓存可复用结果并记录模型版本。
- **评测公平性**：用同一语料、同一问题集比较答案质量、索引成本、查询延迟和更新成本，不能只看展示效果。

#### 12.5.4 它的局限

“Light” 是相对图 RAG 的工程目标，不代表系统天然简单。图抽取错误、跨存储一致性、权限过滤和版本管理仍然存在。小知识库只需要关键词加向量时，引入 LightRAG 可能得不偿失。

### 12.6 并行路线：树形索引——恢复长文档的层级结构

#### 12.6.1 它是什么

**树形索引（tree-structured index）** 是一类按层级组织知识的索引，不是一个统一产品。代表方法 RAPTOR 在 2024 年发表于 ICLR：先把相近的叶子 chunk 聚类，再让 LLM 为每组生成摘要；继续对摘要聚类和总结，递归构造一棵从细节到全局的树。查询时可以同时从多个抽象层级检索。[RAPTOR 论文](https://openreview.net/pdf?id=GN921JHCRw)

第一次出现的名词：

- **Leaf node（叶子节点）**：最底层原始 chunk，信息最具体。
- **Parent node（父节点）**：对子节点内容的聚合或摘要，信息更抽象。
- **Recursive abstraction（递归抽象）**：对子块总结后，再对上一层摘要继续聚类和总结。
- **Hierarchical retrieval（层级检索）**：根据问题从不同层级取材料，而不是永远只取原始小块。

```text
根：订单系统故障与恢复总览
├─ 支付与订单一致性
│  ├─ 7 月事故摘要
│  │  ├─ 支付回调 chunk
│  │  └─ 订单状态机 chunk
│  └─ 8 月修复方案摘要
└─ 库存预扣与回补
   ├─ 回补规则 chunk
   └─ 补偿任务 chunk
```

#### 12.6.2 用例子理解

问“7 月事故的具体触发条件”时，系统需要叶子层原文；问“过去半年订单故障有哪些共同模式”时，上层摘要更有用。树形索引让系统在细节和全局摘要之间选择合适粒度。

图片中“树形索引让推理按路径导航”的说法可以作为直观理解，但不应说成所有树索引都由 Agent 从根节点一步步走到叶子。以 RAPTOR 为例，它的核心是构造多层摘要并跨层检索，而不是固定执行一条人工目录路径。

#### 12.6.3 这一阶段着重看什么

- **聚类是否合理**：无关 chunk 被聚到一起，父摘要就会混乱。
- **摘要失真**：越往上越抽象，细节、例外和否定条件越容易丢失；答案必须能回到叶子证据。
- **层级选择**：事实题偏叶子，全局题偏父节点；可以同时召回不同层级再重排。
- **更新成本**：一个叶子变化后，只应重算受影响的祖先链，而不是重建整棵树。
- **权限边界**：不能把不同权限文档先汇总成同一个父摘要，否则摘要本身可能泄露信息。

#### 12.6.4 树和图怎么选

| 对比 | 树形索引 | 图索引 |
| --- | --- | --- |
| 结构 | 一个节点通常有清晰父子层级 | 节点可有多种、多对多关系 |
| 擅长 | 长文档、目录、由细到粗的摘要 | 跨文档实体关系、多跳关联、全局主题 |
| 典型问题 | “这份长报告的结论和证据分别是什么？” | “事故、服务、负责人和修复 PR 如何关联？” |
| 主要风险 | 高层摘要丢细节 | 实体/关系抽错，图维护成本高 |

同一系统可以用树表达文档层级，用图表达跨文档关系，再用向量检索定位入口。

### 12.7 第四阶段：LLM Wiki——让理解结果可以积累

#### 12.7.1 它是什么

**LLM Wiki** 更像一种知识库模式，目前不是统一标准：LLM 不只在每次查询时临时读取原始 chunk，而是把原始资料逐步编译成结构化、互相链接、可以继续维护的 Wiki 页面。

这里的 **compile（知识编译）** 不是把 Markdown 编译成机器码，而是“读取原始材料一次，把稳定结论提炼成以后可重复使用的知识页”。Microsoft 的开源实现把知识分成三层：[LLM Wiki 架构](https://github.com/microsoft/llmwiki/blob/main/ARCHITECTURE.md)

```text
raw/：  人维护的原始资料，只读，是真正证据
wiki/： LLM 生成和维护的实体页、概念页、摘要页、索引和日志
AGENTS.md：规定页面类型、目录、frontmatter、命名、摄取和校验规则
```

第一次出现的名词：

- **Frontmatter（文档头部元数据）**：Markdown 开头由 `---` 包围的 YAML，用来声明页面类型、标题、摘要、标签、来源等。
- **Progressive disclosure（渐进式披露）**：先给 Agent 很小的目录和摘要，命中相关领域后再读详细页面，最后才展开原始证据。
- **Backlink（反向链接）**：页面 A 链接页面 B 时，B 能知道有哪些页面引用自己。
- **Lint（静态校验）**：自动检查缺失字段、坏链接、孤立页面、格式错误和可能过期的内容。

#### 12.7.2 用例子理解

第一次导入 7 月事故复盘时，系统建立：

- `incidents/inc-1024.md`：事故过程、根因、影响、来源；
- `services/order.md`：订单状态机以及与库存服务的依赖；
- `concepts/compensation.md`：补偿事务的适用边界；
- 页面之间建立普通 Markdown 链接。

后来导入 `PR-884` 和 `PR-901`，LLM 不只是新增两个 chunk，而是更新事故页，写明“首次修复后来被回滚”，补上冲突与来源。下次再问，不必从几百份材料里重新归纳同一个结论。

#### 12.7.3 为什么说它让知识“积累”

普通 RAG 的检索结果和当次推理通常不会自动变成下一次可复用的知识；LLM Wiki 把经过整理的结果保存为可读页面，后续资料会继续补充这些页面。因此积累的是“结构化理解”，不只是原始文档数量。

这不等于每次 LLM 回答都应该自动写回 Wiki。写入应区分候选修改、自动校验和人工审核，否则一次幻觉会被固化并反复引用。

#### 12.7.4 这一阶段着重看什么

- **原始资料与编译知识分层**：raw 是证据源，wiki 是可重建的派生知识。
- **来源和冲突**：每个关键结论能回链到原文；新资料与旧结论冲突时要标记，而不是静默覆盖。
- **渐进式读取**：先读 index 的标题、别名、摘要和路径，再读页面，最后打开原始证据；减少无关 token。
- **知识健康度**：检查孤立页、坏链接、重复实体、无来源结论、过期页面和未处理冲突。
- **写权限**：Agent 先生成候选 diff，通过结构、链接、来源校验和领域负责人审核后再合入。

#### 12.7.5 它的局限

- 第一次知识编译耗时且可能产生错误。
- 高频配置、交易数据和实时状态不适合由 LLM 写入 Markdown。
- 页面持续重写可能产生合并冲突，需要所有者、审查和版本策略。
- Wiki 不是搜索引擎；规模很大时仍需要 BM25、向量或图检索找到入口。

### 12.8 第五阶段：OKF——让知识能被不同 Agent 和工具共同使用

#### 12.8.1 它是什么

OKF 的全称是 **Open Knowledge Format，开放知识格式**。它不是检索算法、数据库或 Agent 协议，而是一套表示知识的开放格式：一个目录中的 Markdown 文件，加 YAML frontmatter、普通链接、索引和可选更新日志。

截至 2026 年 8 月，Google Cloud 开源仓库中的规范版本为 v0.2。它强调人可读、Agent 可解析、Git 可比较、跨工具可携带，并把来源、可信度信号、新鲜度和生命周期纳入格式。[OKF v0.2 规范](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md?plain=1)

第一次出现的名词：

- **Knowledge Bundle（知识包）**：一组自包含的 OKF 目录和文档，是交换和发布的基本单位。
- **Concept（知识概念）**：知识包中的一个 Markdown 文件，可表示表、API、指标、流程或抽象概念。
- **Provenance（来源谱系）**：一条知识由哪些原始材料产生。
- **Freshness（新鲜度）**：知识现在是否仍然有效，何时需要复核。
- **Lifecycle（生命周期）**：知识从候选、有效、废弃到归档的状态变化。

一个简化的 OKF 页面可以是：

```markdown
---
type: Incident
title: 7 月订单支付失败事故
description: 支付重复回调导致订单与库存补偿链路异常
tags: [order, payment, inventory]
status: stable
stale_after: 2026-12-31T00:00:00Z
sources:
  - id: inc-1024
    resource: incident-report/INC-1024
    title: INC-1024 事故复盘
  - id: pr-901
    resource: pull-request/PR-901
    title: PR-901 修复记录
---

# 结论

首次修复 PR-884 后来被 PR-901 回滚并替代。[^pr-901]

# 依赖

订单状态变更通过[库存回补事件](../events/inventory-release.md)触发补偿。

[^pr-901]: PR-901 修复记录
```

规范只强制每个普通概念文档具有可解析 frontmatter 和非空 `type`；标题、描述、来源、状态等字段按规范和团队需要使用。上面的业务类型与内容是示例，不是 OKF 强制 Schema。

#### 12.8.2 为什么图片里把 frontmatter 称为“控制面”

这是一种很有用的工程类比，不是 OKF 规范中的正式分层：

- **控制面（control plane）** 决定知识怎么被发现和治理：类型、标题、别名、摘要、负责人、来源、状态、有效期、依赖。
- **数据面（data plane）** 承载完整背景、规则、例外、证据链接和推理所需上下文，也就是 Markdown 正文。

Agent 先读取控制面进行路由，只有命中后才展开数据面。这样既保留自由文本的表达能力，也避免把每一句话拆成僵硬的数据库字段。

#### 12.8.3 Git 给知识增加了什么

- **Branch（分支）**：Agent 在独立分支生成候选知识变更，不直接覆盖权威版本。
- **Diff（差异）**：审查者只看新增、删除和修改内容。
- **Pull Request / PR（合并请求）**：把结构校验、链接校验、依赖校验、自动测试和人工评审放到发布流程中。
- **Blame（逐行溯源）**：查看一段知识由哪次提交、谁在何时修改。
- **Revert（回滚）**：发现错误后完整撤销某次更新。
- **Tag（标签版本）**：把一组知识固定为可发布、可复现的版本。

所以 Git 管的不是模型的“记忆”，而是知识变更的生命周期：谁提出、改了什么、谁审核、何时发布、能否回退。

#### 12.8.4 用例子理解

订单团队可以把上面的事故、服务、事件和修复方案打成一个知识包。IDE Agent、数据分析 Agent 和运维 Agent 都能读取同样的 Markdown、frontmatter 和链接；其中任意工具都可以把内容再导入 ES、Milvus 或图数据库，而无需先理解某个私有知识库 SDK。

当源代码接口变化时，Agent 只在分支上提交受影响页面的候选 diff。CI 检查格式、链接、来源和依赖，领域负责人审核后合并。线上检索索引随后从已发布版本重建。

#### 12.8.5 这一阶段着重看什么

- **最小格式契约**：哪些字段必须统一，哪些允许业务扩展；消费者必须容忍未知类型和字段。
- **来源、信任与新鲜度**：机器生成不代表已验证，过期页面不能继续被当作当前事实。
- **链接与依赖**：链接必须可解析，删除或改名要检查下游页面。
- **发布流程**：候选、校验、评审、合入、打 tag、重建索引和回滚要可追踪。
- **格式与运行时解耦**：OKF 负责“知识长什么样”，搜索、同步、权限、推理和冲突合并仍由外部系统负责。

#### 12.8.6 它不解决什么

OKF 不负责：

- 搜索引擎和向量召回；
- 实时数据同步；
- 自动判断内容真假；
- 多人修改时自动解决语义冲突；
- 数据库事务、细粒度 ACL 和高频写入；
- 保证某个 LLM 一定正确理解正文。

因此它更适合相对稳定、需要解释和审查的知识，如 API 说明、指标口径、架构决策、运行手册和事故经验；实时库存、监控指标和用户会话仍应放数据库、消息系统或时序系统。

### 12.9 把六种路线放回同一个系统

回到最初的问题：“7 月订单支付失败为什么会影响库存回补？修复方案后来改过几次？”

| 层次 | 负责什么 | 在例子中做什么 |
| --- | --- | --- |
| Vector RAG | 找相似原文 | 找到事故复盘、状态机和库存回补片段 |
| GraphRAG | 找实体关系和全局主题 | 连接事故、服务、事件、PR 与回滚关系 |
| LightRAG | 较轻地联合局部与全局图检索 | 同时召回具体事故和“跨服务补偿”主题 |
| 树形索引 | 按抽象层级定位 | 先看订单域摘要，再下钻事故和代码证据 |
| LLM Wiki | 保存经过整理、可继续更新的理解 | 维护事故页、服务页和补偿概念页，记录冲突 |
| OKF | 规定知识如何交换和治理 | 用统一 frontmatter、链接、来源和生命周期发布知识包 |

最终比较合理的组合是：

```text
数据库 / 代码 / 事故报告                         原始事实
          ↓
LLM Wiki / OKF Markdown                         可读、可审查的知识层
          ↓
BM25 + 向量索引 + 图索引 + 层级索引             可重建的检索层
          ↓
Agent 按目录摘要 -> 相关页面 -> 原始证据逐层读取  推理与执行层
```

不要把最下面的检索索引当唯一事实源。Wiki 页面可以从原始来源重新编译，ES/Milvus/图索引又可以从页面和原文重新构建。权限、来源、版本和发布状态必须贯穿每一层。

### 12.10 每个阶段到底怎么选

| 你的主要问题 | 优先起点 | 什么时候再升级 |
| --- | --- | --- |
| FAQ、手册问答、数据量中小 | BM25 + Vector RAG | 出现大量跨文档关系或全局主题问题 |
| 实体关系、多跳问题、全库主题总结 | GraphRAG | 图构建和更新成本过高时评估 LightRAG 或缩小图范围 |
| 既要图关系，又关注成本和增量更新 | LightRAG | 先证明普通混合检索不够，再承担多存储复杂度 |
| 超长文档、报告、代码库有清晰层级 | 树形/层级索引 | 跨文档多对多关系明显时再补图 |
| 同一结论被反复归纳，希望长期积累 | LLM Wiki | 必须同时建立来源、校验、审核和过期治理 |
| 多种 Agent/工具要交换知识 | OKF | 它只解决表示格式，仍需按规模选择检索与同步系统 |

最常见的落地顺序仍然是：先做可评测的混合 Vector RAG；只有测试集证明关系、全局主题或长文结构确实是主要失败原因，再增加图或树；只有知识会反复更新和跨工具复用，才建设 Wiki/OKF 的治理链路。

### 12.11 面试复盘题

#### 🟢 初级：Vector RAG、GraphRAG 和树形索引分别解决什么问题？

> 考察点：能否区分相似度、关系和层级。

回答提纲：Vector RAG 按语义和关键词找局部证据；GraphRAG 显式组织实体关系，适合跨文档和全局问题；树形索引保存从细节到摘要的层级，适合长文档和多粒度检索。三者可以组合。

#### 🟢 初级：LLM Wiki 为什么不等于“把所有文档放进长上下文”？

> 考察点：知识编译与渐进式披露。

回答提纲：长上下文每次仍要重新读取原始材料；LLM Wiki 把稳定结论、关系和冲突编译成可复用页面，先读目录摘要再逐层展开，并保留到原始来源的链接。

#### 🟡 中级：为什么用了 GraphRAG，还可能需要向量检索？

> 考察点：召回入口和图关系的互补。

回答提纲：图擅长关系扩展，但用户问题未必直接命中实体 ID；向量/BM25 先找到相关实体、关系或原文入口，图再做邻域和多跳扩展，最后回原文验证。图不是全文检索的替代品。

#### 🟡 中级：LLM Wiki 或 OKF 如何避免把一次幻觉固化成长期知识？

> 考察点：来源、状态、验证、发布和回滚。

回答提纲：原始资料保持只读；Agent 只生成候选 diff；关键结论带来源和生成信息；CI 做结构、链接、依赖检查；高风险知识由领域负责人审核；发布版本可 tag，可通过 Git revert 回滚；过期时间触发复核。

#### 🔴 高级：设计一个同时使用 Vector RAG、图和 OKF 的企业知识系统，事实源放在哪里？

> 考察点：分层、可重建索引、一致性和治理取舍。

回答提纲：业务数据库、代码和原始文档是事实源；OKF/LLM Wiki 是经过审核的知识层；ES、Milvus 和图数据库是可重建检索副本。变更先进入候选分支，审核发布后用版本事件更新索引；查询必须携带 ACL 与知识版本；监控索引新鲜度，并能从已发布知识快照回滚重建。
