## 1. 向量数据库解决什么问题？

传统数据库和搜索引擎很擅长按主键、字段条件或关键词找数据。例如搜 `ERR_CONNECTION_RESET`，倒排索引能很快找到包含这个错误码的文档。

但用户问“浏览器连不上服务器怎么办”时，相关文档可能写的是“排查连接被重置”，两段文字没有相同的词。先把文本、图片、音频或商品特征交给 embedding 模型，得到一串浮点数；语义接近的内容在向量空间里距离通常更近。向量数据库负责存储这些向量，并在大量数据中快速找出最近的 Top K。

```text
原始数据 -> embedding 模型 -> 向量 + 元数据 -> 向量数据库

用户问题 -> 同一个 embedding 模型 -> 查询向量
         -> 相似度检索 Top K -> 过滤 / 重排 -> 返回原文或业务对象
```

典型场景：

- RAG 知识库：找与问题语义相关的 chunk，作为 LLM 上下文。
- 语义搜索：用户换一种说法，也能找到相近内容。
- 推荐与召回：用用户、商品或行为序列的 embedding 找相似商品。
- 图片、音频和视频检索：用多模态模型将不同媒介映射到可比较的向量空间。

向量数据库不生成 embedding，也不替代业务主库。模型负责“怎么表示”，向量数据库负责“怎么存、怎么找”；订单、权限、原文等事实数据通常仍在 MySQL、ES 或对象存储中。

## 2. 数据模型：向量与元数据

一条向量记录通常至少有四部分：

```text
id:          chunk_10086_03
dense_vector:[0.12, -0.31, 0.76, ...]     # 例如 768 / 1024 / 1536 维
sparse_vector:{"token_12": 1.4, "token_991": 0.8}  # 可选
metadata:    tenant_id, doc_id, title, acl, version, created_at, tags ...
```

- `id` 是稳定主键，用于幂等写入、删除和回查原文。
- 向量字段参与相似度计算。
- `metadata` 是结构化字段，用于租户隔离、权限过滤、时间范围、文档版本和业务筛选。
- 原文可以和向量放在同一库，也可以只存摘要与 `doc_id`，命中后再回主库或对象存储取全文。

**不要只存向量。** 如果知识库里没有 `tenant_id`、`acl`、`doc_version`，系统很难做权限过滤、删除旧版本和排查错误来源。

### 2.1 Collection、分区和索引

不同产品叫法不同，概念大致对应：

| 概念 | 可以理解成什么 | 用途 |
| --- | --- | --- |
| Collection / Class / Index | 一张向量表或一个逻辑数据集 | 定义字段、维度和相似度度量 |
| Partition / Shard | Collection 内部的数据切分 | 扩容、隔离或缩小搜索范围 |
| Vector index | 为向量建立的近邻索引 | 不必逐条比较全部向量 |
| Scalar / payload index | 元数据字段的索引 | 加速 `tenant_id`、时间、标签等过滤 |

同一个向量字段里的维度和 embedding 模型必须一致。把 768 维和 1536 维向量混进同一索引无法查询；即使维度碰巧相同，换了模型后语义空间也可能不同。实际表里应记录 `embedding_model` 与 `embedding_version`，模型升级时双写或新建 collection，灰度验证后再切流。

## 3. 稠密向量、稀疏向量与混合检索

### 3.1 稠密向量（Dense Vector）

稠密向量维度固定，绝大多数位置都是非零浮点数，例如：

```text
[0.12, -0.31, 0.76, 0.08, -0.44, 0.59]
```

它通常由 embedding 模型生成，擅长表达语义关联。用户搜“iPhone 充电头”，即使文档标题是“苹果手机充电器”，稠密检索仍可能召回。

代价是存储和索引成本高。以 `1536` 维 `float32` 为例，一条原始向量约为 `1536 × 4 = 6144` 字节，1000 万条数据的原始向量就接近 60 GB；HNSW 图、元数据和副本会继续增加内存或磁盘占用。

### 3.2 稀疏向量（Sparse Vector）

稀疏向量的总维度可以很高，但一条记录只有少量位置有值，通常只保存“维度 ID -> 权重”：

```text
{ "苹果": 1.2, "手机": 0.8, "充电器": 1.5 }
```

传统 BM25 与倒排索引可以看作典型的稀疏检索思路；学习型稀疏模型还会为扩展词项分配权重。它擅长错误码、商品型号、接口名、人名、数字等必须精确命中的内容，而且结果更容易解释。

### 3.3 两者怎么选？

| 对比项 | 稠密向量 | 稀疏向量 |
| --- | --- | --- |
| 强项 | 同义改写、自然语言语义 | 关键词、型号、错误码、专有名词 |
| 常见索引 | HNSW、IVF、DiskANN 等 ANN 索引 | 倒排索引 |
| 可解释性 | 较弱，单维度通常没有业务含义 | 较强，可看到命中的词和权重 |
| 常见问题 | 语义泛相关，精确条件可能被忽略 | 换词后可能漏召回 |

生产中常用混合检索。稀疏侧保住 `HTTP 502`、`SKU-2026-A`、类名等精确线索；稠密侧补“换句话说”的语义召回；之后用 RRF、加权融合或 reranker 把候选重新排序。

```text
Query
  -> BM25 / sparse Top 50
  -> dense ANN Top 50
  -> 去重与融合（RRF / 加权）
  -> reranker Top 10
  -> 返回 Top 3 ~ 5
```

不要因为接入了向量检索就直接删掉 BM25。对技术文档、商品和企业知识库，混合检索往往更稳。

## 4. 相似度与向量索引

### 4.1 相似度度量

常用度量有：

- **Cosine similarity（余弦相似度）**：比较方向，常用于文本 embedding。若向量已做 L2 归一化，余弦相似度与内积排序等价。
- **Inner Product（内积）**：很多模型或推荐场景直接用它；必须确认模型训练和归一化方式。
- **L2 distance（欧氏距离）**：比较几何距离，适合明确以 L2 训练或评估的模型。

不要把度量方式随便换掉。入库向量和查询向量要用同一模型、同一预处理和同一度量；不匹配时，分数通常没有意义。

### 4.2 精确检索与 ANN

精确 kNN 会将查询向量和每条记录计算一次距离。100 万条、1536 维时成本很高，但结果可做到精确。

ANN（Approximate Nearest Neighbor）允许少量近似误差，换取更低延迟和更高吞吐。面试里可以记成：`kNN` 是“要找最近 K 个”的问题，`ANN` 是加速路线。

| 索引 | 思路 | 优点 | 代价与适用情况 |
| --- | --- | --- | --- |
| FLAT | 暴力计算全部距离 | 精确、实现简单 | 数据量小、离线评测或作为 recall 基准 |
| HNSW | 多层近邻图导航 | 低延迟、召回高，使用很广 | 建图慢、内存开销较大；要调 `ef` 类搜索参数 |
| IVF / IVFFlat | 先聚类到桶，再搜索少量桶 | 建索引和内存成本通常低于 HNSW | 需训练/选择桶数与 probes；召回依赖参数 |
| PQ / 量化 | 压缩向量或残差编码 | 大幅降低内存和磁盘占用 | 距离有误差，需评估 recall 损失 |
| DiskANN 类 | 让大部分索引和向量放 SSD | 超大规模时节省内存 | 强依赖 NVMe 与 IO 调优 |

索引没有“永远最好”的选择。先拿一组带标注的查询，对比 `Recall@K`、p95/p99、索引构建时间、内存和成本；再决定 HNSW、IVF 或量化方案。只看 QPS 很容易把“检索变快但答案变差”的问题带到线上。

## 5. 一次读请求到底怎么执行？

“读向量数据库”不等于根据主键 `get` 一条记录。最常见的是一次相似度检索，读链路如下：

```text
用户问题
  -> Query Rewrite（可选）
  -> Embedding Service：生成 query_vector
  -> 权限 / tenant / 文档状态过滤条件
  -> Vector DB：ANN 找候选 + metadata filter
  -> sparse 候选融合（可选）
  -> Reranker：精排少量候选（可选）
  -> 按 doc_id / chunk_id 补原文、标题、引用链接
  -> 返回搜索结果，或交给 LLM 生成
```

### 5.1 先过滤，再检索还是先检索，再过滤？

业务上，权限过滤必须在结果返回前严格生效。技术实现则要看产品能力与过滤选择性：有的引擎能把标量过滤和 ANN 过程结合，有的会在候选阶段再过滤。无论哪种，都要压测两个风险：

- 过滤字段没有索引时，检索会退化或变慢。
- 如果先只取很少的 ANN 候选再做严格过滤，可能过滤完一条都不剩，或召回率明显下降。

例如用户只能访问 `tenant_id=t1` 的文档，不能先在全部租户的 Top 10 中找到结果，再把不属于 `t1` 的结果返回或交给 LLM。应把 `tenant_id`、文档状态和 ACL 放进检索条件，必要时为高频过滤字段建立 payload/scalar 索引。

### 5.2 为什么还需要 reranker？

向量检索负责快速召回，常取 Top 20～100；它看的是向量距离，未必能区分“同主题但没回答问题”和“真正包含答案”的段落。reranker 将问题和少量候选一起输入更精细的模型，得到更可靠的排序，再选 Top 3～10。

例子：用户问“订单取消后库存什么时候回补”。向量检索可能同时召回“库存预扣”“支付超时”“退款”，reranker 会把同时包含“取消”和“回补规则”的段落放前面。候选不要取无限多，否则 reranker 延迟和成本会失控。

### 5.3 读接口应返回什么？

至少返回 `id`、相似度分数、`doc_id`、`chunk_id`、标题路径、文档版本和必要原文。对 RAG，还应记录 query 的模型版本、filter、召回候选、融合分数、rerank 分数与最终上下文，才能定位“没召回”“排错了”还是“模型答错了”。

## 6. Milvus：拿 MySQL 类比，理解概念、索引和查询

先记一句最重要的话：**Milvus 不是 MySQL 的替代品，而是专门解决“向量相似度 Top K”问题的检索服务。** MySQL 保存价格、库存、订单等事实数据；Milvus 保存向量和检索所需元数据，返回最相近的候选 ID。

### 6.1 先建立最直观的对应关系

| Milvus | 类比 MySQL | 作用 |
| --- | --- | --- |
| Database | Database / Schema | 较粗粒度地隔离业务，例如公司知识库和商品搜索。 |
| Collection | Table | 一组 schema 固定的向量记录。 |
| Field | Column | 主键、文本、向量、tenant_id、时间等字段。 |
| Partition | 表分区 / 逻辑分区 | 缩小数据范围或隔离；不是给每个高基数租户都建一个分区。 |
| Vector index | 特殊索引 | 加速“哪个向量和 query vector 最像”。 |
| Scalar index | 普通字段索引 | 加速 tenant_id、doc_id、状态、时间、标签等过滤。 |
| Segment | 内部数据块 | Milvus 用于写入、建索引、加载和 compaction 的存储单元，没有 MySQL 的严格一一对应。 |

例如 RAG 的 Collection 可以理解为一张 document_chunks 向量表：

~~~text
id              主键
text            chunk 原文或摘要
embedding       FLOAT_VECTOR(1024)
tenant_id       租户
doc_id          所属文档
title_path      标题路径
doc_version     文档版本
status          READY / DELETED
~~~

其中 embedding 是 MySQL 普通业务表没有的核心字段；一条记录可能把“Redis 6.0 引入网络 IO 多线程”表示为一串 1024 维浮点数。向量维度、embedding 模型和距离度量必须匹配：1024 维的查询向量不能去搜 768 维 collection；换了模型也不应把新旧向量直接比较。

### 6.2 get、query、search：最容易混淆，也最重要

可以把三种读操作记成：**知道 ID 用 get，知道条件用 query，知道语义用 search。**

| 操作 | Milvus 在做什么 | 类比 MySQL | RAG 例子 |
| --- | --- | --- | --- |
| get | 按主键取已知实体 | WHERE id = 10086 | 取已知 chunk 的内容和 metadata。 |
| query | 用标量字段过滤，不按向量距离排序 | WHERE tenant_id = 'A' AND doc_id = 'redis.pdf' | 找公司 A 的 redis.pdf 所有 chunk。 |
| search | 传 query vector，按距离取 Top K；可叠加 filter | MySQL 传统 B+ 树不擅长的高维近邻查询 | 只在公司 A 可访问文档中找“Redis 网络 IO”相关段落。 |

~~~text
用户问题：Redis 为什么能处理高并发？
  -> embedding 模型生成 query_vector
  -> Milvus search：vector + tenant_id/ACL filter + Top K
  -> 返回最相近的 chunk_id、distance、metadata
  -> reranker 精排 -> LLM 基于原文回答
~~~

所以 query 和 search 的边界要说清：query 只是 metadata 条件筛选；search 才是“向量相似度 + 可选 metadata filter”。权限、tenant、文档状态必须作为 search filter 生效，不能先返回跨租户候选，再让 LLM 自己忽略。

### 6.3 向量检索是不是一定走索引？没有索引会怎样？

对某个向量字段，Milvus 通常会用该字段配置的向量索引完成 search。若使用 FLAT，或没有可用的 ANN 近邻索引，本质上更接近暴力计算：将 query vector 与候选向量逐个算距离，再取 Top K。

~~~text
100 万条、768 维向量，FLAT：
query_vector -> 依次计算 100 万次距离 -> 排序/取 Top K
优点：精确，适合小数据和效果基线。
代价：数据量上来后，计算与延迟很高。
~~~

| 向量索引 | 核心思路 | 取舍 |
| --- | --- | --- |
| FLAT | 比较全部候选向量 | 精确，但大规模慢。 |
| HNSW | 在多层近邻图上导航 | 常用，召回高、延迟低；建图和内存开销较大。 |
| IVF | 先聚类，搜索少量最近桶 | 内存/构建成本可控；需要调桶数和 probes。 |
| DiskANN 类 | 大部分索引/向量放 SSD | 超大规模节省内存；更依赖 NVMe 和 IO 调优。 |

这不是说“没向量索引，所有字段都暴力扫”。tenant_id、doc_id、created_at 等 metadata 可以建立 scalar index 来帮助过滤。实际 search 会结合标量过滤与向量候选；过滤是先在检索阶段参与还是候选后进一步筛掉，和具体版本、索引和数据分布有关，必须压测过滤后的候选数和 Recall@K。

### 6.4 Partition、Segment 和集群读写链路

Partition 是更偏逻辑的切分；Segment 是 Milvus 内部实际写入、加载、建索引和 compaction 的数据块。一个 Partition 可以有多个 Segment。大规模多租户场景中，不要机械地做“一个 tenant 一个 Partition”；通常应让 Partition Key 将数据映射到有限数量的内部 partition，再用 tenant_id filter 做权限过滤。

~~~text
写入：
Client -> Proxy -> Streaming Node -> WAL（预写日志）
       -> Growing Segment（新写入、可查询）
       -> flush / compaction -> Sealed Segment（历史数据）
       -> Data Node 建索引 -> 对象存储

查询：
Client -> Proxy -> Streaming Node（搜新数据） + Query Node（搜历史 Segment）
       -> 合并各 Segment / shard 的 Top K -> 返回
~~~

- Proxy 是无状态入口，负责路由和结果汇总；Coordinator 管理拓扑、调度和元数据。
- Streaming Node 处理写入和新数据；Query Node 检索历史 Segment；Data Node 做 compaction 和索引构建。
- 生产关注点包括索引是否加载、Query Node 容量、segment 数量、对象存储吞吐和删除比例，而不只是 SDK 是否返回成功。

### 6.5 最小 Python 使用示例

下面是新版 pymilvus 的最小流程。vector_1 和 query_vector 必须来自同一个 embedding 模型，且长度都等于 DIM。

~~~python
# pip install -U pymilvus
from pymilvus import MilvusClient

DIM = 1024
client = MilvusClient("kb_milvus.db")  # 本地演示；生产环境改为 uri + token

client.create_collection(
    collection_name="kb_chunks",
    dimension=DIM,
    metric_type="COSINE",
)

client.insert(
    collection_name="kb_chunks",
    data=[{
        "id": 1,
        "vector": vector_1,
        "text": "Redis 连接数满时先检查 maxclients、连接池和慢客户端。",
        "tenant_id": "company_a",
        "doc_id": "redis_note",
        "status": "READY",
    }],
)

# 语义检索，并把权限/状态限制在检索条件里。
hits = client.search(
    collection_name="kb_chunks",
    data=[query_vector],
    filter='tenant_id == "company_a" and status == "READY"',
    limit=10,
    output_fields=["text", "doc_id", "status"],
)

# 纯 metadata 查询：不是向量相似度检索。
rows = client.query(
    collection_name="kb_chunks",
    filter='tenant_id == "company_a" and doc_id == "redis_note"',
    output_fields=["text", "status"],
)
~~~

快速创建适合理解 API。生产中要显式定义 schema、为高频 filter 建标量索引、按规模选择 HNSW/IVF 等索引；批量导入后确认索引和 collection 已加载。重试写入用 upsert 或业务版本控制，避免重复主键或旧版本覆盖新版本。

### 6.6 Milvus 与 MySQL 应怎样分工？

~~~text
商品修改：MySQL product（事实源）
  -> CDC / Outbox
  -> 生成或更新 embedding
  -> Milvus product_vector（检索副本）

用户搜索：“适合通勤的防水双肩包”
  -> embedding
  -> Milvus 召回 Top 200 product_id
  -> MySQL 校验仍在售、价格、库存
  -> 业务排序并返回商品卡片
~~~

| 维度 | MySQL | Milvus |
| --- | --- | --- |
| 最擅长的查询 | 主键、范围、Join、精确条件 | 高维空间里的语义相似 Top K |
| 索引 | B+ 树、联合索引等 | HNSW、IVF、量化等向量近邻索引 |
| 数据定位 | 订单、库存、价格、权限等事实源 | 向量、候选 ID 和检索 metadata 副本 |
| 一致性 | 强业务约束、事务 | 通常允许短暂最终一致，可从源数据重建 |
| 不适合做什么 | 大规模高维 ANN | 支付、扣库存、复杂事务和多表 Join |

一句话记忆：**MySQL 回答“这件商品现在能不能卖”；Milvus 回答“哪些商品和用户意图最相近”。**

## 7. RAG 中 ES 与 Milvus 怎么选？

ES 和 Milvus 都能做向量检索，差别在“谁是主能力”。ES 是搜索引擎，关键词搜索、过滤、聚合、排序和运营检索能力很完整；Milvus 是专用向量检索系统，更适合把高吞吐、大规模 ANN 召回单独做成一层。两者都必须用真实评测集比较 Recall@K、延迟和成本，不能只凭产品名选型。

| RAG 情况 | 优先 ES | 优先 Milvus |
| --- | --- | --- |
| 现有基础设施 | 已经有 ES，文档和关键词索引已在其中 | 已有 Milvus 或向量检索要独立建设 |
| 检索目标 | 关键词、型号、筛选、聚合、运营搜索与语义检索同等重要 | 语义召回、多模态或推荐是核心，向量规模/吞吐更高 |
| 混合检索 | ES 可在同一次搜索中组合全文、dense vector、sparse vector，并做 RRF 融合 | 可做稠密/稀疏或多向量检索，但关键词生态、聚合和运营检索通常不如 ES 顺手 |
| 运维取舍 | 少一个系统；适合先快速验证 RAG | 检索层可独立扩容、单独调向量索引；但要维护源数据同步和另一套集群 |
| 常见链路 | ES：BM25 + kNN -> RRF -> reranker | Milvus：dense/sparse Top K -> 应用融合/重排；原文和事实数据放主库或对象存储 |

**RAG 例子：** 企业已有 ES，用户会搜索错误码、接口名和自然语言问题。优先在 ES 内把 BM25 的精确命中和 dense_vector 的语义命中融合；它减少一次数据同步，也方便过滤 tenant、文档状态和标签。Elasticsearch 官方支持将全文、向量、过滤和混合检索组合在同一检索引擎中。[官方向量检索说明](https://www.elastic.co/docs/solutions/search/vector) [官方混合检索说明](https://www.elastic.co/docs/solutions/search/hybrid-search)

如果是图片/商品相似召回、数亿级 embedding，或者 ES 已因全文检索和聚合很忙，不希望向量索引争抢资源，则将 Milvus 作为独立召回层更合理。Milvus 的 Proxy、Query Node、Data Node 和对象存储分层支持检索与索引构建分别扩展；但“Milvus 一定比 ES 快”并不成立，过滤比例、索引参数、硬件、数据更新率和目标 recall 都会改变结果。[Milvus 架构说明](https://milvus.io/docs/architecture_overview.md)

不要一开始就同时上 ES 和 Milvus。需要双写时，以文档系统/主库为事实源，事件携带 doc_id 和 version，通过 CDC/Outbox 同步到两个检索副本；读侧在应用层融合时要能处理版本延迟、删除和权限过滤。

## 8. 常用向量数据库怎么选？

下面按典型定位比较，不把某个产品说成唯一答案。

| 方案 | 常见定位 | 适合什么情况 | 需要留意 |
| --- | --- | --- | --- |
| [Milvus](https://milvus.io/docs/overview.md) | 专用开源向量数据库 | 大规模向量检索、独立扩缩容、多索引选择 | 自建集群的资源、数据同步与运维成本 |
| [Qdrant](https://qdrant.tech/documentation/guides/) | 专用向量数据库，强调 payload filter | 需要向量检索和结构化过滤结合，想使用较直接的 collection/payload 模型 | 高频 filter 字段要建 payload index；磁盘模式依赖 NVMe |
| [Weaviate](https://docs.weaviate.io/weaviate/concepts/search) | 向量、关键词、混合检索和模块化能力 | 希望较快搭建语义/混合搜索，或使用多模态检索能力 | 仍要自己评估 embedding、filter、混合权重与成本 |
| [pgvector](https://github.com/pgvector/pgvector) | PostgreSQL 扩展 | 数据量中小、已有 Postgres、需要 SQL/事务/Join 生态 | HNSW 内存较大；IVFFlat 要调 lists/probes；超大规模需评估扩展边界。详见 [PostgreSQL 基础与面经合集](./PostgreSQL_基础与面经合集.md) |
| Elasticsearch / OpenSearch | 搜索引擎附带向量能力 | 已有 ES、关键词搜索和过滤是主需求，向量检索是补充 | 高频更新、segment merge、向量内存与索引参数需要单独压测 |

一个实用的选型顺序：

1. 已经有 ES 或 PostgreSQL，先验证现有体系能否达到目标 recall、p99 和成本。
2. 向量规模、过滤组合、吞吐或多租户隔离成为瓶颈，再评估 Milvus、Qdrant、Weaviate 这类专用系统。
3. 团队只想托管服务、希望减少运维时，再按云厂商、数据合规、地域和价格选择托管向量服务。

## 9. RAG 的完整例子

以企业内部技术文档问答为例。员工问：“Redis 连接数突然满了，先查什么？”

```text
文档上传
  -> 解析 Markdown / PDF，按标题和段落切 chunk
  -> 生成 chunk_id、doc_version、tenant_id、ACL、标题路径
  -> embedding，批量写入向量库；标题和正文同时写入 BM25 索引

用户提问
  -> 鉴权，得到 tenant_id 与 ACL
  -> 用同一 embedding 模型生成 query vector
  -> dense Top 50：语义相近的 Redis 排障段落
  -> sparse Top 50：含“连接数”“maxclients”等精确词的段落
  -> RRF 融合、去重，rerank 为 Top 5
  -> 取原文和标题路径，连同引用交给 LLM
  -> LLM 基于资料作答；资料不足时明确说明
```

这里有四个容易漏掉的点：

- ACL 应在检索条件中生效，不能让 LLM “自觉忽略”越权内容。
- chunk 要保留标题路径和版本。只存一小段正文，命中后读者不知道它属于哪篇文档。
- 文档更新后，新旧 chunk 的切换要原子化或按版本过滤，不能一直累积旧向量。
- 检索结果要保留日志。用户说“答案不对”时，先看正确 chunk 有没有被召回，再看重排和生成。

## 10. 生产设计与排障点

### 10.1 写入链路

```text
原文入库 / 对象存储
  -> 解析与切块
  -> embedding（带模型版本）
  -> 批量 insert / upsert
  -> 建索引或等待增量索引生效
  -> 记录 READY 版本并发布
```

- embedding 调用、向量写入和元数据更新跨系统时要有任务状态、幂等键、重试和死信处理。
- 大批导入宜批量写入，避免逐条 RPC；索引构建会消耗 CPU、内存和 IO，应避开线上高峰或使用独立资源。
- 删除通常是逻辑删除、tombstone 或异步 compaction。要监控删除比例，否则索引体积和查询效果可能变差。

### 10.2 读链路指标

| 指标 | 用来发现什么问题 |
| --- | --- |
| Recall@K、nDCG、人工标注集 | 召回是否真的找到了相关内容 |
| 向量检索 p50/p95/p99、rerank 耗时 | 是向量库慢，还是后处理慢 |
| filter 后候选数、空结果率 | ACL/tenant/filter 是否过严或索引异常 |
| 索引构建耗时、加载内存、磁盘/网络 IO | 容量是否接近上限，是否需要量化或扩容 |
| embedding 失败率、模型版本分布、索引新鲜度 | 新文档为何没有被搜到 |

### 10.3 常见故障定位

| 现象 | 优先检查 |
| --- | --- |
| 正确文档完全没出现 | 文档是否切块/写入成功、是否被 ACL 或版本过滤、query 与入库模型是否一致 |
| 候选里有正确文档，最终答案仍错 | 融合权重、reranker、上下文截断、LLM 引用规则 |
| 延迟突然升高 | 查询向量服务、filter 索引、HNSW/IVF 搜索参数、冷热数据、节点 CPU/内存/IO、索引加载状态 |
| 改成 ANN 后结果变差 | 搜索参数太保守、过滤后候选不足、量化误差、索引构建或模型版本有问题 |
| 用户看到了别的租户内容 | 立即检查 filter 是否在检索请求里生效、ACL 元数据是否正确、缓存 key 是否包含租户与权限版本 |

## 11. 高频面试问答

### 11.1 向量数据库和传统数据库有什么区别？

传统数据库更擅长按主键和结构化条件精确查找；向量数据库增加了“按语义距离找最近邻”的能力，并用 ANN 索引避免全量算距离。它们通常协作：业务主库保存事实数据和事务，向量库保存检索副本与向量索引。

### 11.2 为什么 HNSW 快，为什么又贵？

HNSW 把向量组织成多层近邻图，查询时从高层快速跳到目标附近，再在底层展开搜索，因此不必扫描全部向量。图的邻接关系需要额外内存，建图和更新也更重；提高搜索候选数会提高 recall，同时也会增加延迟。

### 11.3 向量检索为什么不能直接替代关键词检索？

向量擅长语义，但对错误码、型号、日期、数字和罕见专有名词不一定稳定。用户搜 `go1.24`、`ERR-1024` 或某个订单号时，关键词/稀疏检索通常更可靠，所以生产中常将稠密和稀疏候选融合。

### 11.4 元数据过滤应该怎么做？

将 `tenant_id`、ACL、状态、时间、标签等作为结构化字段保存，并为高频条件建立对应索引。权限条件必须在向量检索请求中生效；不能先把越权候选交给 LLM，再希望它不引用。过滤选择性很强时，要单独压测 recall 和延迟。

### 11.5 如何让模型升级不影响线上检索？

新建 `embedding_version` 或新 collection，先对增量/历史数据重算向量并双写；用同一评测集比较 recall、答案质量和延迟；灰度切读流量，确认稳定后再下线旧索引。不要把新旧模型向量混放后直接比较距离。

### 11.6 面试里如何用一分钟回答“向量数据库怎么读”？

> 用户问题先经同一 embedding 模型变成 query vector，查询带上 tenant、ACL、文档状态等过滤条件。向量库通过 HNSW 或 IVF 这类 ANN 索引召回 Top K，业务侧再和 BM25/稀疏结果融合，必要时用 reranker 精排，最后按 `doc_id` 或 `chunk_id` 取原文和引用。我要监控 recall、检索 p99、过滤后候选数和索引新鲜度。向量库负责召回，不负责代替权限、原文存储和最终答案判断。
