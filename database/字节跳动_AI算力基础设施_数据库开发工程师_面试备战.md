## 1. 岗位画像与能力地图

这份 JD 同时包含四层工作，面试通常会从你最熟悉的一层切入，然后向上下游追问。

```text
业务 / Agent / RAG
    ├─ 记忆、知识库、工具调用、多轮工作流
    ↓
检索与查询层
    ├─ ES / BM25、向量检索、混合召回、rerank、SQL
    ↓
存储与索引层
    ├─ MySQL / PostgreSQL、对象存储、Milvus / pgvector、缓存
    ↓
基础设施与治理层
    ├─ 分片副本、资源调度、监控、AIOps、容量、故障恢复
```

| JD 关键词 | 面试官真正想确认的能力 | 你现有的切入点 |
| --- | --- | --- |
| Agent RAG / ContextSearch | 能否把“问一句话”拆成检索、上下文组织、生成、评测闭环 | ES 检索、MySQL 元数据、Redis 缓存 |
| Mem0 / Agent Memory | 能否区分聊天记录、短期上下文和可长期复用的事实；能否做隔离与删除 | MySQL 事实表、Redis 短期状态、ES/向量召回 |
| Serverless PG / Supabase | 能否理解 PostgreSQL 作为带事务、SQL、权限能力的 AI 应用底座 | MySQL 的事务/索引/主从基础可迁移；补 pgvector、RLS 概念 |
| 向量检索算法 × 系统 × 硬件 | 不只会调 SDK，知道召回率、延迟、内存/SSD、过滤之间的取舍 | ES 的倒排、分片、查询调优；补 ANN/HNSW/IVF |
| AI for DB / AIOps | 先用数据和安全护栏做建议，再小流量执行与回滚 | MySQL EXPLAIN、慢日志、ClickHouse 分析、监控 |

**面试优先级建议：**

1. 先守住基础：MySQL 索引/事务/锁，Redis 缓存与热点，Linux、网络、并发、算法。
2. 再弄懂 RAG 的一条完整链路，以及 ES 和向量检索为什么常常要一起用。
3. 最后准备“规模化、隔离、评测、回滚”这四个工程词。它们比背出十个 AI 框架更有辨识度。

### 2.2 来自字节 AI / Agent 方向的直接信号

牛客一篇字节 AI Agent 秋招一面公开帖中，出现了以下问题：MySQL 索引何时失效、AI Agent 中消息队列的作用、Redis 缓存策略、父子索引、BM25 与向量检索融合、ReAct 消息格式、工具响应角色、短期/长期记忆设计。对本岗位的相关性很高。[原帖](https://api-cdn.nowcoder.com/feed/main/detail/8b2b5df61184235bc4210760250663e?sourceSSR=dynamic)

| 公开题目 | 你要回答到的点 | 可继续追问 |
| --- | --- | --- |
| MySQL 索引在什么情况下会失效？`LIKE` 呢？ | 最左前缀、范围条件后的列、函数/计算/隐式类型转换、低选择性、优化器成本选择；`LIKE '%xx'` 无法利用普通 B+Tree 前缀 | 如何用 `EXPLAIN ANALYZE` 验证？全文/倒排/向量分别何时合适？ |
| AI Agent 为什么用 MQ，不直接通过数据库通信？ | 解耦生产消费、削峰、异步长任务、重试与背压；数据库是事实状态，不宜当高吞吐事件总线 | 如何做到不丢、不重、按 session 有序？ |
| Redis 在 Agent 系统中做什么？ | 会话短期状态、限流、幂等、热点结果/embedding 缓存、任务状态；不能把它当唯一长期记忆 | 热 key、过期、缓存穿透、断连怎么办？ |
| RAG 为什么要有父子索引？ | 小 chunk 适合精确召回，大块父文档适合补足上下文；子块命中后回取父块/相邻块 | 如何避免父文档太大把上下文撑爆？ |
| BM25 和向量检索如何融合？ | 两路召回，各取候选；用 RRF 或归一化加权融合；再由 reranker 精排 | 错误码、型号、数字为什么不能只用向量？ |
| ReAct 的工程消息如何建模？ | 明确 `system/user/assistant/tool` 角色、`tool_call_id`、输入输出、状态、超时、可追踪 ID；工具输出不可信且要限长 | 重试工具时如何保证幂等？ |
| Agent 的短期/长期记忆怎样设计？ | 短期是当前会话的有限上下文/摘要；长期是经抽取和去重的偏好、事实、决策，按用户/租户/Agent 过滤检索 | 用户删除记忆、记忆冲突、越权召回怎么处理？ |

另一篇近期公开的 Agent 面经，直接问到“多 Agent 如何通信”“多个 Agent 同时操作数据库或文件如何处理”。[原帖](https://www.nowcoder.com/discuss/877151327091027968) 这意味着除了 LLM 概念，**并发控制与资源隔离**仍是后端/数据库方向的硬考点。

## 3. 把已有技术栈迁移到 AI 数据库

你不是从零开始。把已有知识换一个位置即可：

| 你会的组件 | 在传统系统中的角色 | 在 AI 数据链路中的角色 | 面试中可以怎么说 |
| --- | --- | --- | --- |
| MySQL | 订单、用户等结构化事实和事务 | 文档/记忆元数据、权限、版本、任务状态、评测集、审计 | “事实与事务仍放关系库；向量库更像可重建的检索索引副本。” |
| Redis | 缓存、会话、分布式锁、限流 | 短期会话、提示词/embedding 缓存、任务去重、热门检索缓存 | “Redis 只加速，不作为唯一真相；关键写入要回到持久存储。” |
| Elasticsearch | 倒排、全文检索、日志搜索 | BM25/关键词召回、过滤、混合检索的一路候选 | “报错码、型号、版本号、精确词更适合关键词检索，不能被向量完全替代。” |
| ClickHouse | 日志、OLAP、报表 | 检索/生成链路日志、离线评测、容量预测、AIOps 特征分析 | “在线链路做决策，CH 用于离线分析和回放，避免把重分析压在在线库。” |

### 3.1 一个最重要的认知：向量库不是“替代 MySQL 的新数据库”

一条知识通常分散在不同系统中：

```text
对象存储：原始 PDF / 网页 / 图片
MySQL / PG：doc_id、租户、ACL、状态、版本、任务状态（事实真相）
ES：关键词与 BM25 索引（可重建）
向量库：chunk embedding 与 ANN 索引（可重建）
Redis：缓存、会话与限流（可丢失）
ClickHouse：检索日志、质量和容量分析（离线/准实时）
```

你在任何设计题里先讲清这张分工图，就已经避开了很多新人常犯的错误：把原文、权限和向量全堆在一个向量库里；或把 Redis 当长期记忆的唯一存储。

### 3.2 Milvus 到底需要先学什么？

先理解概念，再看 API：

| 概念 | 类比 | 第一轮够用的解释 |
| --- | --- | --- |
| Embedding | 文本/图片的特征表示 | 同一模型把内容和问题编码成定长向量；语义近的向量通常距离更近 |
| Collection | 一张向量表 | 定义主键、向量维度、标量字段和索引 |
| ANN | 近似索引查询 | 不和每条向量完整比较，以小量准确率换明显的延迟/成本收益 |
| HNSW | 多层邻居图 | 高层快速导航、底层局部搜索；低延迟高召回，但图索引占内存、写入/建索引较重 |
| IVF | 先分桶再桶内搜 | 用聚类中心缩小候选范围；`nprobe` 越大通常召回越高、延迟越高 |
| Metadata filter | `WHERE tenant_id = ?` | 检索时就必须带租户、ACL、版本等过滤，不能先召回越权内容再让 LLM 自觉忽略 |

Milvus 官方将向量检索和标量过滤都作为索引选型的一部分；HNSW、IVF、DiskANN 等索引的取舍需要结合召回、内存、SSD 与过滤比例压测，而不是凭产品名决定。[Milvus Index Explained](https://milvus.io/docs/index-explained.md)

已有仓库中还有一份更完整的基础材料：[向量数据库基础与面经合集](向量数据库_基础与面经合集.md)。本篇只聚焦岗位与面试，不重复展开所有索引细节。

## 4. 新人必须补齐的最小知识集

### 4.1 RAG：先会画出这条链路

```text
离线写入：文档上传 -> 解析/OCR -> 切分 chunk -> embedding
        -> MySQL 记录文档版本和 ACL
        -> ES 建关键词索引 + 向量库建 ANN 索引

在线查询：问题 -> 鉴权/改写 -> embedding
        -> ES(BM25) 与向量库(ANN) 并行召回
        -> 融合 -> rerank -> 取原文/父块 -> LLM -> 带引用回答
        -> 记录检索、模型与反馈日志到 ClickHouse
```

每一个箭头都可能被追问：

- **切分为什么不能固定 500 字？** 要看文档结构、语义完整性、模型上下文和评测结果；标题、表格、代码块应尽量保留结构。
- **混合检索为什么有效？** 稠密向量解决同义表达；BM25 对关键字、错误码、数字、版本号更稳。两路候选可用 RRF 融合，再重排。
- **为什么还要 rerank？** 召回模型快但粗，Top 50 里有“同主题而不回答问题”的段落；reranker 只精排小候选集，平衡质量与延迟。
- **如何判断 RAG 差在哪里？** 记录 query、filter、各路候选、融合分数、重排分数、最终 chunk、答案和用户反馈。先分辨“没召回”“召回了但没排前面”“上下文不完整”“模型幻觉”，再优化。

### 4.2 Agent Memory：它不是聊天记录数据库

一个实用划分：

| 类型 | 示例 | 存储与生命周期 |
| --- | --- | --- |
| 短期记忆 | 当前会话最近几轮、工作流中间结果 | Redis 或会话表；限大小、TTL、摘要压缩 |
| 长期事实记忆 | “用户偏好中文回答”“该项目使用 PG” | SQL 事实表 + 向量索引；可更新、去重、可删除 |
| 知识库 | 产品文档、代码、制度 | 对象存储/元数据 + ES/向量索引；有文档版本与权限 |
| 过程/审计日志 | Agent 调了什么工具、参数和结果 | OLTP/日志系统 + ClickHouse；可追溯、脱敏、保留期明确 |

Mem0 的公开文档也采用类似分层：SQL 保存事实和元数据作为 source of truth，向量数据库保存 embedding 做语义检索，并要求用 `user_id`、`agent_id`、`run_id` 等过滤范围，避免不同用户或任务的记忆混淆。[Mem0 How It Works](https://github.com/mem0ai/mem0/blob/main/docs/core-concepts/how-it-works.mdx)

### 4.3 PostgreSQL / Supabase：知道“为什么它会出现在 JD 里”即可

Supabase 的向量能力基于 PostgreSQL 的 `pgvector` 扩展，可以在关系模型、SQL、事务和权限体系里保存与查询 embedding；这很适合中小规模、强事务或已有 PG 的 AI 应用。规模/吞吐/独立扩缩容要求更高时，再评估专用向量库。[Supabase Vector Columns](https://supabase.com/docs/guides/ai/vector-columns)

这不是“Milvus 和 PG 谁更好”的二选一。面试中应按问题选：

| 情况 | 更自然的起点 | 原因 |
| --- | --- | --- |
| 新业务、数据量还小、事务和 SQL 很多 | PostgreSQL + pgvector | 少一个分布式系统，事务与权限在同一处 |
| 大规模向量、高 QPS、多索引、检索集群要独立扩容 | Milvus 等专用向量库 | 检索层的性能与资源能独立治理 |
| 已有成熟 ES，关键词和过滤更重要 | ES 向量能力 / ES + 向量库 | 复用全文检索与运维能力，按压测结果决定 |

## 5. JD 高概率场景题与答题框架

> 本节是依据 JD 推导的练习题，不是声称出现在公开面经中的真题。每题都按“目标 -> 数据 -> 链路 -> 一致性/异常 -> 指标 -> 取舍”回答。

### 场景 1：为多租户企业知识库设计 RAG 检索服务

**题目：** 10 万企业租户上传 PDF、网页、表格；要求按权限问答，文档可更新/删除，峰值 2 万 QPS，回答需要附引用。如何设计？

**推荐回答骨架：**

1. **先澄清：** 文档数、平均大小、chunk 数、读写比例、SLA、单租户是否会极热、ACL 粒度（文档/部门/用户）、是否允许最终一致。
2. **数据分工：** 原文在对象存储；MySQL/PG 保存 `document`、`chunk`、`acl`、`version` 和导入任务；ES 为 BM25；Milvus/pgvector 存 `chunk_id + vector + tenant_id + version + status`；Redis 缓存热点查询与权限结果；CH 记录效果和延迟日志。
3. **写入链路：** 上传产生 `ingest_task`，经 MQ 异步解析、切分和 embedding。每一步有 `task_id` 与幂等键 `(doc_id, version, chunk_no)`；成功后原子切换当前 `version`，旧向量异步回收。不能直接覆盖旧索引，否则读请求会混到半新半旧数据。
4. **读链路：** 鉴权后把 `tenant_id`、允许的 ACL、`status=active`、当前版本作为**检索请求中的 filter**；ES 和向量库并行召回，RRF 融合、rerank，按 `chunk_id` 获取正文和引用。先做权限过滤，不能让越权 chunk 进入 LLM 上下文。
5. **热点与故障：** 热租户单独限流/配额与缓存；embedding/rerank 超时则降级为关键词检索或少量向量候选；向量库不可用时返回“搜索模式降级”而不是编造答案；MQ 积压时优先保证新文档任务可观察、可重试。
6. **指标：** 检索 p95/p99、各阶段耗时、空召回率、候选数、过滤后候选数、Recall@K/NDCG、引用命中率、答案正确率、索引新鲜度、跨租户泄露事件数。

**一句话亮点：** “向量库是可重建的检索副本，权限和版本要以关系库为真相，并在召回前过滤。”

### 场景 2：给 Agent 做长期记忆，如何避免串用户、越存越脏？

**题目：** 对话 Agent 需要记住用户偏好、项目决定和待办；多 Agent 共享部分项目记忆，但不能把用户 A 的信息召回给 B。怎样设计写入、检索、更新和删除？

**推荐回答：**

```text
对话事件 -> 敏感信息检测/脱敏 -> 记忆抽取器
         -> 去重/冲突检查 -> SQL Memory（事实真相）
         -> outbox / MQ -> embedding -> 向量索引

下一次提问 -> 根据 user_id + tenant_id + agent_id + scope 鉴权
           -> 向量检索 + metadata filter -> 只取少量相关记忆 -> prompt
```

- **不是全文入库：** 只抽取长期可复用的偏好、事实、决定；原始对话另有保留策略。抽取结果要有来源 `source_message_id`、置信度、创建/更新时间、过期时间。
- **隔离模型：** `tenant_id` 是每次读取的硬条件；`user_id`、`agent_id`、`project_id`/`run_id` 定义作用域。共享项目记忆必须显式授权，默认不共享。
- **一致性：** SQL 先提交 memory 状态，outbox 可靠投递向量更新。检索时只接受 `status=active`、当前 `embedding_version`；索引最终一致是可接受的，但删除要先阻断读取、后异步物理清理。
- **冲突与遗忘：** 新偏好与旧偏好冲突时保留版本或以时间/用户确认决策，不让 LLM 静默覆盖；支持用户查看、修正、删除；敏感数据默认不写入长期记忆。
- **评测：** 记忆命中率不等于好。还要看错误记忆率、过期记忆率、跨 scope 召回数、删除传播延迟和 token 节省。

### 场景 3：向量检索从百万级增长到十亿级，p99 变差、成本过高怎么办？

**先不要直接回答“上 HNSW”。** 先问向量维度、QPS、TopK、召回目标、写入更新比例、过滤选择性、内存/SSD 比例、租户分布和 SLA。

**完整思路：**

- 以 `(tenant/业务域, embedding_model, version)` 做逻辑隔离；分片策略要同时避免巨型租户和小租户碎片化。
- 用小规模 exact `FLAT` 或离线暴力检索作为质量基线，评估 Recall@K；不要只看接口有没有返回结果。
- 内存充足且追求低延迟/高召回时优先评估 HNSW；内存紧张、可以接受更多扫描/量化误差时评估 IVF/PQ、DiskANN 等。任何选型都应基于真实 filter 和真实 query 压测。
- 提高 HNSW `efSearch` 或 IVF `nprobe` 通常能提高召回，也会增加延迟/CPU；用分级服务或动态参数而非把所有请求打满。
- 过滤极窄时，先缩小候选集合或针对高频 metadata 建索引；否则 ANN 找到大量候选后再过滤，可能出现“候选不够”或尾延迟恶化。
- embedding 模型升级采用新 collection/新版本双写、离线回填、影子流量评测、灰度切读、可回滚；绝不混放不同语义空间的向量。
- 按热/温/冷分层，定期压缩与回收过期/旧版本索引；副本数按读流量和可用性定，而不是所有数据盲目三副本。

### 场景 4：设计“AI 自动索引推荐”，怎样避免把线上库调坏？

这是 JD 中 AI for DB 的经典陷阱题。高分答案不是“让 LLM 看 SQL 自动建索引”，而是：

```text
慢日志 / query digest / EXPLAIN / 表统计
    -> 特征提取与候选生成（规则 + 模型）
    -> 影子评估 / 成本估计 / 人审或策略门禁
    -> 灰度创建索引 -> 观测收益与写放大 -> 自动回滚 / 下线
```

- **数据源：** SQL 模板、频率、扫描行数、p95/p99、表大小、基数、现有索引、写入 QPS、锁等待、业务优先级。
- **候选：** 规则先给出可解释候选，例如高频 `WHERE + JOIN + ORDER BY` 组合；模型可帮助聚类/排序，但不能拥有无约束 DDL 权限。
- **安全护栏：** SQL 脱敏与权限隔离；限定白名单库表、DDL 窗口、索引数量、磁盘预算、并发构建；先在影子环境/回放流量上验证。
- **收益函数：** 不只看单条查询变快，还要扣除索引空间、写放大、构建成本、其他查询计划退化风险。设置观察期，没有整体收益就回滚。
- **解释性：** 给出“推荐哪几个列、覆盖哪类 query、预期减少多少扫描、为何不推荐另一个索引”，让 DBA/业务能审核。

### 场景 5：如何做数据库 AIOps 的异常检测与根因分析？

**不要只说“把指标扔给 LLM”。** LLM 可以做摘要和辅助归因，检测与执行必须可验证。

1. **采集：** QPS、错误率、p99、连接池、CPU、内存、IO、网络、复制延迟、锁等待、慢 SQL、缓存命中率、索引命中、向量 recall/延迟、MQ lag。
2. **检测：** 静态阈值用于硬保护；按时段的季节性基线处理周期波动；多指标关联判断异常，减少“单指标告警风暴”。
3. **关联：** 用 request/trace ID 串起网关、检索、rerank、DB、缓存；把发布、参数变更、热点租户、分片迁移等事件纳入时间线。
4. **归因与动作：** 先输出候选假设与证据，例如“某租户 filter 后候选不足导致 `efSearch` 拉高，CPU 与 p99 同时上升”；低风险动作可限流/扩容/降级，高风险动作必须走审批和回滚预案。
5. **闭环：** 记录告警的 precision、误报/漏报、MTTD、MTTR、自动动作收益；数据放 ClickHouse 便于长期回放与训练。

### 场景 6：多个 Agent 并发修改同一个项目资料库，怎么保证正确性？

- 每个 Agent 生成 `operation_id` 和幂等键；写数据库采用唯一约束/条件更新或乐观锁 `version`，而不是“先查再写”。
- 把“修改原文、更新元数据、生成 embedding、更新 ES/向量索引”拆成状态机；主库事务提交后通过 outbox/MQ 异步同步索引。
- 同一文档/项目按 `doc_id` 或 `project_id` 路由到有序分区；跨文档无需强行追求全局顺序。
- 冲突返回给编排器，让 Agent 根据版本重新读取、合并或请用户确认；不能让两个 Agent 静默覆盖。
- 写入成功后不承诺索引立即可见，接口应返回版本和索引状态；读侧只取已发布的稳定版本。

## 6. 高频问答速练

### 6.1 向量数据库和 ES / MySQL 有什么区别？

> MySQL 擅长事务、结构化条件和精确查找；ES 擅长倒排、关键词和全文相关性；向量数据库擅长在高维向量中做近似最近邻搜索。它们不是互斥关系：MySQL/PG 保存权限、版本和业务事实，ES 处理关键词，向量库补充语义召回。生产 RAG 通常先并行召回、融合并重排，而不是让某一库包办所有事情。

### 6.2 为什么 RAG 不直接“向量 TopK 后喂给 LLM”？

> TopK 只代表向量距离近，不代表真正回答了问题。要考虑 ACL、文档版本、关键词精确命中、重复 chunk、上下文长度和引用可追溯。通常会增加 metadata filter、BM25 融合、rerank、父文档回取和无答案拒答；还要用评测集确认改动真的提升质量。

### 6.3 HNSW 和 IVF 如何选？

> HNSW 是多层邻居图，低延迟、高召回常见，但内存和构建更新成本偏高；IVF 先聚类分桶，查询只探测部分桶，`nprobe` 控制延迟/召回，配合 PQ 可压缩内存但会损失精度。先用真实数据量、过滤条件和 Recall@K/p99 压测；如果数据很小，先用 FLAT 做准确率基线。

### 6.4 向量索引里的 `tenant_id` 为什么重要？

> 它既是多租户隔离条件，也是性能条件。必须在检索请求中生效，不能先把所有租户的候选送入 LLM 再期望模型不泄漏。过滤太强时还要注意 ANN 候选不足和延迟变化，必要时做分区、标量索引或调整搜索预算。

### 6.5 文档更新后如何避免旧内容一直被召回？

> 用 `doc_id + version + status` 管理。先写新版本并完成解析/embedding/索引，校验通过后把活动版本原子切到新版本；读请求只检索 `active` 版本；旧版本延迟清理。同步过程通过任务状态、幂等键和 outbox/MQ 保证可重试、可观察。

### 6.6 为什么 Agent Memory 不全放 Redis？

> Redis 很适合短期上下文、缓存、限流和去重，但它不是长期事实的唯一真相：存在 TTL、淘汰、持久化与审计限制。长期记忆需要可查询、可修正、可删除、可审计的事实表；向量索引是语义检索副本，Redis 只是加速层。

### 6.7 怎样评估检索系统好不好？

> 分两层。检索层看 Recall@K、MRR/NDCG、空召回率、权限过滤正确率、p95/p99、索引新鲜度；回答层看引用正确率、答案正确率、无答案拒答准确率、人工偏好/用户反馈。离线评测和线上灰度都要有，不能只看模型主观感觉。

### 6.8 如果完全没用过 Milvus，现场怎么诚实回答？

> 我还没有在生产使用过 Milvus，但我理解它解决的是高维向量的 ANN 检索与标量过滤。我的学习顺序是先用 FLAT 建质量基线，再比较 HNSW/IVF 在 Recall@K、p99、内存和写入成本上的取舍；数据模型会保存 `tenant_id`、`acl`、`doc_version`、`embedding_version`，并把向量索引视为可从原文和元数据重建的副本。我的 ES 经验也让我会先验证关键词检索、过滤和混合召回，而不是盲目替换现有链路。

这段回答的关键不是伪装“会”，而是展示你已经具备正确的系统设计方法。

## 7. 两周学习与项目路线

### 7.1 两周最小计划

| 时间 | 学习目标 | 可交付成果 |
| --- | --- | --- |
| 第 1–2 天 | 复盘 MySQL 索引、事务、MVCC、慢 SQL；Redis 缓存一致性、热点 key | 各写 10 个追问的口述答案 |
| 第 3–4 天 | 学 embedding、余弦/内积/L2、FLAT、HNSW、IVF、Recall@K | 手画一次向量写入与查询链路 |
| 第 5–6 天 | 学 RAG：切分、BM25、混合检索、RRF、rerank、评测 | 设计 30 条带标准引用的小评测集 |
| 第 7–8 天 | 用现有 ES 做关键词检索；选择 pgvector 或 Milvus 跑一个最小向量检索 | 做出“关键词 vs 向量 vs 混合”对比表 |
| 第 9–10 天 | 加文档版本、ACL、异步入库、幂等与失败重试 | 画出状态机与数据表 |
| 第 11–12 天 | 加 Agent Memory、会话缓存和任务日志 | 能说明短期/长期记忆的隔离与删除 |
| 第 13 天 | 做压测与观测：p95/p99、Recall@K、失败注入、降级 | 一页性能/质量复盘 |
| 第 14 天 | 模拟面试：项目深挖 + 两道系统设计 + 两道算法 | 录音复盘，压缩成 3 分钟项目介绍 |

### 7.2 最值得做的一个项目：可评测的企业知识库 RAG

比起做一个“能聊天”的 Demo，更建议完成一个能回答工程问题的项目：

```text
上传 Markdown/PDF
  -> 对象存储（原文） + MySQL（文档、ACL、版本、任务）
  -> MQ / worker（解析、切分、embedding）
  -> ES（BM25） + pgvector 或 Milvus（向量）
  -> 混合召回/RRF + rerank + 引用返回
  -> Redis（查询/embedding 缓存、限流）
  -> ClickHouse（检索日志、离线评测）
```

**最低可用的功能清单：**

- 多租户字段和 ACL filter；故意做一个越权测试，证明检索层没有返回它。
- `doc_id/version/status/embedding_version`，实现文档更新后旧版本不再被读到。
- 两路检索与 RRF；给出至少 20～30 个问题的 Recall@K/引用命中率对比。
- 异步任务可重试、幂等写入、失败状态可查询。
- 记录一次查询经过哪些 chunk、分数和耗时，能定位“检索错”还是“生成错”。

**项目介绍的 90 秒版本：**

> 我做的是一个可评测的多租户知识库 RAG。原始文档放对象存储，MySQL 保存文档版本、权限和任务状态，ES 负责关键词召回，向量库负责语义召回。查询时先鉴权，并把 `tenant_id`、ACL、活动版本带进两个检索请求；两路候选用 RRF 融合后 rerank，最后返回带引用的回答。文档更新通过版本切换而不是覆盖旧索引，写入用幂等任务和异步队列，保证失败可重试。我们记录每次检索候选、分数和延迟，用 Recall@K、引用命中率、p99 和索引新鲜度评估效果；向量服务异常时会降级到关键词检索并拒绝编造答案。

### 7.3 不要陷入的学习误区

- 不要只背“RAG = 向量库 + LLM”。重点是权限、版本、混合检索、评测和降级。
- 不要同时浅尝 Mem0、Milvus、Supabase、所有 Agent 框架。先做一条完整链路，再替换组件对比。
- 不要把“LLM 自动调参”当万能答案。线上数据库变更必须有数据、门禁、灰度、回滚和审计。
- 不要因为没有 Milvus 经验而回避这个岗位。能把 MySQL/ES/Redis/ClickHouse 的边界说清楚，已经是很强的工程起点。

### 8.1 场景题万能答题顺序

遇到没做过的场景，按下面顺序思考并说出来：

1. **目标与边界：** QPS、数据量、读写比、SLA、一致性、隔离和成本。
2. **数据真相在哪：** 哪个库保存事务事实，哪些索引/缓存可重建。
3. **主链路：** 写入、读取、异步任务、幂等与顺序。
4. **异常：** 超时、重试、重复、热点、版本切换、降级、回滚。
5. **验证：** 质量、性能、安全、成本分别看什么指标，怎么灰度。
6. **取舍：** 为什么不是另一种方案，在哪个规模/约束下会改。

如果被追问一个没接触过的技术，不要只说“不会”。可以说：

> 我没有直接用过这个产品，所以不会虚构线上经验；但我会先明确数据规模、更新比例、过滤条件、召回目标和 SLA，再用真实数据压测质量、p99、资源成本与故障恢复。按这些约束，我当前会优先验证……，如果……则切换到……。
