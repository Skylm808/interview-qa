# 后端开发面经合集 - gRPC（答案版）

> 数据来源：牛客网、Go语言中文网等中文求职社区

## gRPC

### 1. gRPC 是什么？它和普通 REST API 的核心区别是什么？

**答案：**

- gRPC 是一种现代 RPC 框架，常见实现是基于 `HTTP/2 + Protocol Buffers`。
- REST 更偏资源风格，很多时候对外暴露 HTTP/JSON 接口；gRPC 更偏服务调用，接口定义通常更强、更明确。
- gRPC 在服务间调用里很常见，因为它序列化更紧凑、协议能力更强。
- 所以一句话说：**REST 更适合开放接口，gRPC 更适合内部高性能服务通信。**

---

### 2. gRPC 为什么通常比 HTTP + JSON 更适合服务间通信？

**答案：**

- 第一，Protobuf 比 JSON 更紧凑，序列化和反序列化开销通常更小。
- 第二，gRPC 基于 HTTP/2，天然支持多路复用，连接利用率更高。
- 第三，接口通过 `.proto` 明确定义，跨语言协作和代码生成都更规范。
- 但这不是说 gRPC 一定全面碾压 HTTP/JSON，而是说它在 **内部服务调用** 这类场景里通常更合适。

---

### 3. Protobuf 为什么适合拿来做 RPC 接口定义？

**答案：**

- 它既是序列化格式，也是接口描述语言的一部分。
- 你可以先在 `.proto` 里定义消息结构和服务方法，再自动生成多语言代码。
- 它的二进制编码更紧凑，字段演进也更规范，比较适合长期维护的接口。
- 所以 Protobuf 的价值不只是“比 JSON 小”，更重要的是 **强约束、可生成、跨语言一致**。

---

### 3A. Protobuf 序列化到底有什么好处？和 Dubbo2 常用的 Hessian2 怎么对比？

**答案：**

先区分两件事：`.proto` 是接口合同，定义有哪些服务、方法和字段；Protobuf 序列化是把这份合同里的对象编码成二进制字节。gRPC 根据 `.proto` 生成客户端和服务端代码，调用方不需要手写“把对象转字节、再从字节还原对象”的代码。

例如订单服务返回用户信息：

```proto
message User {
  int64 id = 1;
  string name = 2;
  string phone = 3;
}
```

传输 `User{id: 1001, name: "Tom"}` 时，Protobuf 主要编码字段号和字段值，不会把 `id`、`name` 这些字段名反复写进每一条消息。接收方已经通过同一份 `.proto` 知道字段 `1` 是 `id`、字段 `2` 是 `name`，因此消息通常比 JSON 更小，解析也不需要按字符串 key 查找。

#### Protobuf 的实际价值

1. **体积更小、CPU 开销通常更低**：字段号是数字，整数可用变长编码；生成代码面对的是明确类型，不需要像 JSON 那样反复解析文本和字段名。具体收益取决于数据结构，不能脱离压测承诺固定倍数。
2. **接口更严格**：字段类型、是否重复、RPC 方法和返回值都在 `.proto` 中声明。Go、Java、Python 客户端由同一份合同生成，减少“一个字段在不同语言里被理解成不同类型”的问题。
3. **更容易演进**：新增字段时分配新的字段号，旧客户端会忽略不认识的字段，新客户端读取旧消息时使用默认值；因此可以灰度升级。删除字段后不要复用原字段号，应标记为 `reserved`，避免旧数据被错误解释。
4. **工具链完整**：能自动生成 Stub、Mock、文档和校验代码，接口评审也可以直接审 `.proto` 的变更。

**字段演进例子：**用户服务后来要增加邮箱：

```proto
message User {
  int64 id = 1;
  string name = 2;
  string phone = 3;
  string email = 4;
}
```

先发布能识别 `email` 的服务端，再逐步发布新客户端。旧客户端收到带 `email` 的响应会忽略字段 4，不会因为多一个字段而反序列化失败。这就是它适合长期 RPC 合同的原因。

#### 和 Dubbo2 的 Hessian2 对比

Dubbo 2.x 的序列化可配置，传统 Java 服务中常见/默认的是 Hessian2。Hessian2 也是二进制序列化，但它更偏“把 Java 对象传过去”；Protobuf 则更偏“先定义跨语言的数据合同，再生成类型代码”。

| 维度 | Protobuf（gRPC 常用） | Hessian2（传统 Dubbo2 常用） |
| --- | --- | --- |
| 接口来源 | `.proto` 先定义合同，再生成代码 | 常见做法是 Java 接口和 POJO 驱动 |
| 编码方式 | 字段号 + 类型 + 值，接收方依赖 schema | 二进制对象序列化，可携带对象/类相关描述 |
| 跨语言协作 | 官方多语言代码生成，合同一致性强 | 支持多语言，但传统 Dubbo2 实践更偏 Java 生态 |
| 演进约束 | 字段号不可复用、演进规则明确 | 更依赖 Java 类、字段和序列化兼容策略 |
| 性能与体积 | 对稳定、类型明确的消息通常更紧凑 | 也比 JSON 紧凑，但对象模型和兼容信息可能带来额外开销 |
| 适合场景 | 多语言、高频内部 RPC、长期公共合同 | 已有 Dubbo2/Java 服务、历史接口兼容优先 |

不要把它答成“Protobuf 永远比 Hessian2 快”。消息很小、网络或业务处理才是瓶颈时，差异可能不明显；真正要看的是 p99、CPU、GC、带宽和兼容成本。也不要认为 Protobuf 自带加密或校验：它解决的是编码和合同问题，传输安全仍要靠 TLS，参数合法性仍要由业务或校验层处理。

**选型例子：**一个新建的地图服务需要同时给 Go 路径引擎、Java 推荐服务和 Python 离线任务提供 RPC。用 Protobuf 定义 `RouteRequest`、`RouteResponse`，三端生成代码，后续增加 `avoid_toll` 字段时按新字段号演进，最省跨语言沟通成本。反过来，若公司已有大量 Java Dubbo2 服务并且接口已经稳定，短期继续使用 Hessian2 通常比整体迁移更稳；新接口再根据跨语言和协议统一需求逐步引入 Protobuf/Triple/gRPC。

**面试回答：**

> Protobuf 的价值不只在消息更小。它用 `.proto` 把接口和数据结构固定下来，再生成多语言代码；字段用数字标签编码，通常比 JSON 更紧凑，新增字段也能向后兼容。传统 Dubbo2 常用 Hessian2，它更贴近 Java 对象序列化，适合已有 Java/Dubbo 体系；Protobuf 更适合多语言和长期治理的 RPC 合同。性能不是绝对结论，我会结合真实消息大小、CPU、p99 和改造成本压测后选型。

### 4. gRPC 的四种调用模式分别是什么？

**答案：**

- `Unary RPC`：最常见，一次请求对应一次响应。
- `Server Streaming RPC`：客户端发一次请求，服务端返回一个流。
- `Client Streaming RPC`：客户端发一个流，服务端最终回一个结果。
- `Bidirectional Streaming RPC`：双向都是流，双方可以持续收发。
- 面试里如果想说得更稳，可以补一句：**流式 RPC 很适合实时推送、增量返回、长连接交互。**

---

### 5. gRPC 为什么依赖 HTTP/2？HTTP/2 给了它哪些能力？

**答案：**

- HTTP/2 支持多路复用，所以多个请求可以共用一条连接，减少队头阻塞问题。
- 它还支持头部压缩和双向流，这些能力都很适合 RPC 场景。
- gRPC 的流式调用，本质上也是建立在 HTTP/2 的流模型之上。
- 所以可以简单理解成：**HTTP/2 提供了连接层和传输层能力，gRPC 在上面补了接口定义、序列化和调用语义。**

---

### 6. gRPC 里超时、取消、重试这些能力一般怎么理解？

**答案：**

- 超时本质上是在告诉下游：这次调用最多等多久，避免请求无限挂住。
- 取消一般用于调用方已经不需要结果了，或者上游请求已经结束，希望把取消信号继续往下传。
- 重试不能乱开，要先看接口是否幂等，否则可能把一次请求执行成多次。
- 所以工程上常见原则是：**超时一定要有，取消要能传递，重试要建立在幂等前提下。**

---

### 7. gRPC 服务注册与发现一般怎么做？

**答案：**

- gRPC 本身不强制使用某一种注册中心，工程上通常配合 `etcd`、Consul 或 Nacos 做服务注册与发现。
- 服务启动时注册 `IP + Port + Metadata`，并持续上报心跳或续租；客户端调用前获取可用实例，再按轮询、随机、权重或一致性哈希选择实例。
- 服务宕机后，注册中心通过超时、Lease 失效或主动注销摘除实例；客户端更新列表后，不再把请求发给故障节点。
- **注册发现解决“调用谁”，不保证“调用一定成功”。**线上仍需配合超时、重试、熔断和幂等设计。

### 8. HTTP 和 RPC 有什么区别？什么时候用 HTTP，什么时候用 RPC？可以用 gRPC 解释吗？

**答案：**

先澄清一个容易混淆的点：HTTP 和 RPC 不是同一层的两个完全互斥选项。

- **HTTP** 是传输协议，定义请求、响应、连接、状态码、Header 等通信规则。
- **RPC** 是调用模型，目标是让调用方像调用本地函数一样调用远程服务，并补充接口定义、序列化、超时、取消、错误码、服务发现等工程能力。
- gRPC 就是一个典型 RPC 框架，通常使用 **HTTP/2 传输 + Protobuf 编码 + `.proto` 接口合同 + Stub 代码生成**。
- REST/JSON 也可以运行在 HTTP 上；gRPC 也运行在 HTTP/2 上。所以正确说法是“HTTP 是协议，RPC 是调用方式/框架模型”，而不是“HTTP 和 RPC 完全二选一”。

#### 一、一次调用的直观区别

**HTTP/REST：**

```text
客户端 -> HTTP 请求（URL、Method、JSON、Header）
       -> 网关/服务
       -> HTTP 响应（状态码、JSON、Header）
```

例如查询用户：

```http
GET /api/v1/users/1001 HTTP/1.1
Accept: application/json
```

```json
{"id":1001,"name":"Tom"}
```

**gRPC：**

```proto
service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
```

客户端调用生成的 `GetUser(ctx, req)` Stub，框架负责把请求按 Protobuf 编码，通过 HTTP/2 发给服务端，再把响应解码成强类型对象。

#### 二、HTTP/REST 更适合什么场景？

1. **浏览器、移动端和第三方开放 API**：浏览器原生支持 HTTP，JSON 易调试，跨语言和接入门槛低。
2. **外部合作方接口**：对方未必能生成 gRPC Stub，HTTP/JSON 更容易被各种语言、脚本和网关消费。
3. **资源型 CRUD 和公共 Web API**：URL、Method、状态码、缓存语义比较直观，配合 OpenAPI 可以形成文档和 SDK。
4. **需要经过现有 CDN、WAF、API Gateway 或企业代理**：这些基础设施通常对 HTTP/JSON 支持最好。
5. **调试和人工排查优先**：curl、浏览器和日志系统直接查看 HTTP 请求更方便。

HTTP 也不是只能做简单接口。通过 HTTP/2、SSE 或 WebSocket 可以支持流式返回；只是如果内部服务之间有严格接口合同、双向流和高调用频率，通常 gRPC 的工程体验更好。

#### 三、RPC/gRPC 更适合什么场景？

1. **内部微服务之间的高频调用**：服务数量多、接口稳定，Protobuf 的强类型和代码生成可以减少手写胶水代码。
2. **多语言服务协作**：用一份 `.proto` 生成 Go、Java、Python 等客户端和服务端，字段类型和方法签名更一致。
3. **低延迟、带宽敏感场景**：二进制 Protobuf 通常比 JSON 更紧凑；HTTP/2 多路复用可减少连接和请求管理开销，但最终仍要压测确认。
4. **流式和长连接调用**：gRPC 原生支持 Unary、服务端流、客户端流和双向流，适合实时推送、文件分片、持续事件交互。
5. **需要统一治理的内部调用**：超时、取消、Metadata、状态码、重试策略、拦截器、Tracing 和负载均衡可以纳入统一框架。

#### 四、什么时候不要盲目选 gRPC？

- 直接给浏览器调用时，标准 gRPC 需要额外的 gRPC-Web 或 BFF，不能假设浏览器能像普通 HTTP 一样直接使用。
- 对外接口需要长期兼容、人工调试和第三方接入时，JSON/HTTP 往往更友好。
- 团队没有 `.proto` 版本治理、兼容检查、证书和可观测性基础时，直接上 gRPC 可能只是把复杂度转移到运维。
- 消息很小、业务耗时主要在数据库或下游，Protobuf 的编码优势可能不是主要瓶颈；应通过真实的 CPU、带宽、p99 和故障恢复压测决策。
- 不能因为 gRPC 有重试就对写接口无脑重试。重试前要确认方法幂等，并设置超时预算、退避和最大次数。

#### 五、典型架构：外部 HTTP，内部 gRPC

```text
浏览器 / 第三方客户端
          |
       HTTPS + JSON
          v
      API Gateway / BFF
          |
       gRPC + Protobuf
          v
订单服务 -> 库存服务 -> 支付服务
```

- 外部层用 HTTP/JSON，方便认证、限流、文档、兼容和调试。
- BFF 或网关把外部请求校验、聚合成内部强类型 RPC 调用。
- 内部服务使用 gRPC，统一传递 deadline、trace ID、用户身份和幂等键；服务端通过拦截器做日志、指标、Tracing 和错误转换。
- 对外 HTTP 状态码与内部 gRPC status code 不要机械一一映射，要按业务语义转换，例如 `NOT_FOUND` 映射为 404，超时映射为 504，参数错误映射为 400。

#### 六、选型决策表

| 维度 | HTTP/REST + JSON | RPC/gRPC |
| --- | --- | --- |
| 主要目标 | 开放、兼容、资源访问 | 内部服务调用、强合同和治理 |
| 数据格式 | 文本 JSON，易读易调试 | Protobuf 二进制，强类型、通常更紧凑 |
| 传输 | HTTP/1.1 或 HTTP/2 | 通常 HTTP/2 |
| 接口约束 | OpenAPI/约定，可强可弱 | `.proto` + 代码生成，约束更强 |
| 流式能力 | 需 SSE/WebSocket 等组合 | 原生四种 Streaming 模式 |
| 浏览器/第三方 | 直接支持，接入门槛低 | 常需 gRPC-Web、网关或 SDK |
| 典型位置 | 网关、BFF、开放 API | 微服务内部、低延迟链路 |

**面试里推荐这样答：**

> HTTP 是通信协议，RPC 是远程调用模型，gRPC 是基于 HTTP/2 和 Protobuf 的 RPC 框架。对浏览器、第三方和开放 API，我通常选 HTTPS + JSON，因为兼容、调试和接入更简单；对内部微服务，如果接口稳定、调用频繁、需要多语言代码生成、超时取消和流式能力，我会选 gRPC。实际架构经常是外部 HTTP/JSON、内部 gRPC，通过网关或 BFF 转换。选型不会只看性能，还要看客户端能力、接口演进、治理成本、可观测性和幂等重试边界。
