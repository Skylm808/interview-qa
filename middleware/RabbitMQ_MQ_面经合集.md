# RabbitMQ / MQ 面经合集（答案版）

> 来源补充：`fzh/` 下腾讯、美团、淘天天猫等公司面经中抽取的非项目类 MQ 基础题。

---

## 一、MQ 选型与调用方式

### 1. 什么时候用 HTTP/RPC，什么时候用 MQ？

**答案：**

- 需要同步结果、强依赖返回值、链路短且可控时，用 HTTP / RPC 更直接。
- 需要异步解耦、削峰填谷、最终一致、失败重试、事件广播时，用 MQ 更合适。
- 不要为了“用了 MQ”而引入 MQ：如果调用方必须马上知道结果，MQ 只会增加状态管理和补偿复杂度。

面试里可以这样答：

> RPC 适合同步调用，MQ 适合异步事件。选择标准不是技术偏好，而是调用方是否必须立即拿到结果，以及业务是否需要解耦、削峰、重试和最终一致。

### 2. 为什么有些业务选 RabbitMQ，而不是 Kafka？

**答案：**

RabbitMQ 更偏传统消息队列，Kafka 更偏分布式日志和高吞吐流式系统。

| 维度 | RabbitMQ | Kafka |
| --- | --- | --- |
| 核心优势 | 低延迟、路由灵活、确认机制成熟 | 高吞吐、可回放、日志存储强 |
| 消费模型 | push 为主，ACK 语义直观 | pull 为主，按分区维护位点 |
| 典型场景 | 订单事件、延迟任务、业务异步解耦 | 日志采集、埋点、数据管道、流处理 |
| 顺序能力 | 队列内有序 | 分区内有序 |

如果业务更关注低延迟、灵活路由、延迟队列、可靠投递，RabbitMQ 很常见；如果更关注海量吞吐、长期留存和回放，Kafka 更常见。

## 二、可靠性、重试与消费语义

### 3. RabbitMQ 如何尽量保证消息不丢？

**答案：**

需要覆盖生产者、Broker、消费者三段：

1. 生产者开启 confirm，确保消息到达 Broker。
2. 需要路由失败感知时开启 return callback 或 mandatory。
3. Exchange、Queue、Message 都要持久化。
4. 消费者手动 ACK，业务处理成功后再确认。
5. 消费失败要有重试、死信队列、告警和补偿任务。

一句话：消息可靠性不是 MQ 单点能力，而是生产、存储、消费、补偿一整条链路共同保证。

### 4. MQ 的 consumer 方法至少要实现哪些功能？

**答案：**

- 参数校验和幂等判断，避免重复消费造成脏数据。
- 核心业务处理，且保证业务成功后再 ACK。
- 异常分类：可重试异常进入重试，不可重试异常进入死信或人工补偿。
- 日志、监控和 trace，能定位消息 ID、业务 ID、重试次数和失败原因。
- 限流或并发控制，避免消费者把下游打垮。

### 5. MQ 消费失败怎么处理？

**答案：**

- 短暂网络抖动、下游超时这类可恢复异常，可以延迟重试。
- 参数非法、业务状态不允许这类不可恢复异常，不应该无限重试，要进入死信队列或人工处理。
- 重试必须配合幂等，否则重复执行会引入更大的问题。
- 如果某一类消息持续失败，要告警并隔离，避免一条坏消息阻塞整个队列。

## 三、顺序、延迟任务与幂等

### 6. MQ 怎么保证顺序消费？如何在保证顺序的同时提高吞吐？

**答案：**

- MQ 一般只能保证单队列或单分区内有序，不能天然保证全局有序。
- 业务上通常按 `orderId`、`userId`、`skuId` 等维度做路由，让同一业务实体的消息进入同一个队列或同一个分区。
- 吞吐优化的思路是“局部有序 + 多路并行”：不同业务 key 分散到多个队列 / 分区并行消费，同一个 key 内部保持顺序。
- 如果消费者并发处理，还要注意同 key 串行、版本号校验或状态机校验，避免乱序写入。

### 7. 15 分钟未支付自动取消订单，可以怎么做？

**答案：**

常见方案有：

- 延迟队列 / 死信队列：下单后投递延迟消息，到期检查订单状态再取消。
- 时间轮：适合大量定时任务，能更精细地控制触发时间。
- 定时任务扫描：实现简单，但精度较低，扫描压力和延迟要评估。
- Redis ZSet：用过期时间作为 score，到期扫描处理。

面试里要补一句：到期消息触发后不能直接无脑取消，要再次查询订单状态，只有仍未支付时才执行取消和库存回补。

### 8. 加分布式锁就一定能解决幂等吗？

**答案：**

不能。分布式锁解决的是一段时间内的互斥执行，幂等解决的是同一个业务请求重复到达时最终效果只发生一次。

- 锁可能超时、误删、续期失败，也可能只覆盖了局部代码段。
- 幂等通常要靠业务唯一键、状态机流转、去重表、唯一索引、消息消费记录等机制。
- 分布式锁可以作为辅助手段，但不能替代幂等设计。
