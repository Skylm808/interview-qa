## Kafka 可靠性专题

### Kafka 的生产者可靠性和消费者可靠性分别怎么保证？二者有什么关系？

**先说结论：**

生产者可靠性解决的是：**业务产生的事件，能不能可靠、尽量只写一次地进入 Kafka 日志**；消费者可靠性解决的是：**Kafka 中已有的事件，能不能可靠地转化为业务结果，并正确推进消费进度**。

它们通过“Kafka 日志中的消息”连接，但属于两个独立的故障边界，谁也不能替代谁。完整链路可以抽象成：

```text
业务事务             生产者                  Broker                 消费者
┌──────────┐    ┌──────────────┐    ┌────────────────┐    ┌────────────────────┐
│订单落库   │ -> │重试 + 幂等发送 │ -> │副本 + ISR      │ -> │业务成功 + 幂等处理   │
│Outbox事件 │    │acks=all      │    │持久化 Kafka 日志│    │再提交 offset       │
└──────────┘    └──────────────┘    └────────────────┘    └────────────────────┘
      │                                                        │
      └─ 防止“业务成功但没发消息”             防止重复副作用、错误推进进度 ─┘
```

#### 一、生产者可靠性：保证消息可靠进入 Kafka

不能只背一个 `acks=all`，应该从“业务事件有没有产生”一直看到“Broker 有没有持久化”：

| 层次 | 可能的问题 | 主要手段 |
| --- | --- | --- |
| 业务系统到 Producer | 订单已提交，服务却在发送 Kafka 前宕机 | 关键事件使用 **Transactional Outbox / 本地消息表 + CDC 或补偿任务** |
| Producer 发送 | 网络抖动、Leader 切换导致发送失败或响应丢失 | `retries`、合理的 `delivery.timeout.ms`、检查异步发送回调或 Future |
| Producer 重试 | Broker 已写入但 ACK 丢了，重试产生重复消息 | `enable.idempotence=true`；同时保留业务 `event_id` |
| Broker 持久化 | Leader 刚写入就宕机，副本尚未同步 | `acks=all`、足够的副本数、合理的 `min.insync.replicas` |
| 顺序性 | 失败重试后，同一业务的消息发生乱序 | 相同业务 Key 落到同一 Partition；开启幂等，并控制并发飞行请求 |

一组常见的生产者配置思路是：

```properties
acks=all
enable.idempotence=true
retries=适当的大值
delivery.timeout.ms=按业务可接受时延设置
```

Topic 侧还需要配合副本，例如 `replication.factor=3`，并设置 `min.insync.replicas=2`。生产者使用 `acks=all` 时，当前 ISR 中的全部副本都要确认；如果 ISR 数量已经少于 2，Broker 会拒绝写入。也就是说，系统宁可让本次发送失败，也不在可同步副本不足时冒险写入。

这里有三个边界要说清楚：

1. **必须检查发送结果。** Kafka Producer 通常异步发送；如果调用 `send()` 后不等待结果，也不处理回调异常，配置再可靠，应用也可能不知道消息最终失败。
2. **Producer 幂等只解决发送重试导致的重复写入。** 应用重启后重新构造并发送同一个业务事件，不应只依赖 Producer 幂等，仍要携带全局唯一的 `event_id`。
3. **`acks=all` 不解决数据库与 Kafka 的双写。** 订单事务提交后、调用 Kafka 前宕机，Kafka 根本收不到消息；高可靠场景要在同一个数据库事务里写订单和 Outbox，再由 CDC 或后台任务投递。

根据 Kafka 官方配置说明，幂等生产要求 `acks=all`、允许重试，并将 `max.in.flight.requests.per.connection` 控制在不超过 5；这些条件冲突时，幂等可能无法启用。可参考 [Kafka Producer 配置](https://kafka.apache.org/41/configuration/producer-configs/)。

#### 二、消费者可靠性：保证消息可靠转化为业务结果

消费者最关键的不是“能否 poll 到消息”，而是处理结果与 offset 的提交顺序：

```text
错误顺序：poll -> 提交 offset -> 写数据库
                         └─ 此处宕机：Kafka 认为已经消费，业务结果却没有，造成丢处理

推荐顺序：poll -> 本地事务：业务写入 + event_id 去重记录 -> 提交事务 -> 提交 offset
                                                           └─ 此处宕机：会重放，但幂等后只生效一次
```

具体需要做好以下几件事：

1. **关闭自动提交，业务成功后再提交 offset。** 常见做法是 `enable.auto.commit=false`，只有业务事务提交成功后，才手动提交相应 Partition 的 offset。Kafka 提交的 offset 表示“下一条要读取的位置”。
2. **消费者必须有业务幂等。** 在同一个本地事务中写业务表和消费记录表，并给 `(consumer_group, event_id)` 建唯一约束；消息重放时发现已处理，就不再重复扣款、加积分或扣库存。
3. **失败时不能悄悄推进 offset。** 临时故障应有限重试并退避；无法处理的毒消息可进入重试 Topic 或 DLQ，同时告警和保留人工补偿入口，避免永久阻塞一个 Partition。
4. **正确处理 Rebalance 和并行消费。** 单条处理时间不要超过 `max.poll.interval.ms`；发生分区撤销时停止接新任务，完成或安全中止在途任务，再提交已经连续处理完成的 offset。一个 Partition 内并发处理时，不能因为 offset 12 先完成，就跳过仍在处理的 offset 11。
5. **事务消息只读已提交数据。** 上游使用 Kafka Transaction 时，下游可配置 `isolation.level=read_committed`，避免读到后来被回滚的事务消息。

消费者的核心伪代码如下：

```text
for record in poll():
    begin database transaction
        insert consumed_event(group, record.event_id)  // 唯一键去重
        update business_state(...)                     // 真正业务操作
    commit database transaction

    commit Kafka offset                                // 业务成功后再提交
```

如果数据库事务成功、offset 提交前宕机，消息会再次投递，这就是 **at-least-once**。重放不可怕，真正危险的是业务没有幂等，导致同一订单被重复扣款。Kafka 官方设计文档也明确区分了“发布消息的持久性”和“消费处理保证”，可参考 [Kafka Design：Delivery Semantics](https://kafka.apache.org/41/design/design/#messagesemantics)。

#### 三、生产者与消费者有什么关系？

二者共同组成端到端可靠性，但保护的是不同阶段：

```text
事件 E 可靠进入 Kafka                 E 只产生一次业务效果 F(E)
┌──────────────────┐                  ┌──────────────────────┐
│ Producer 可靠性   │ -- offset=N --> │ Consumer 可靠性       │
└──────────────────┘                  └──────────────────────┘
```

| 故障窗口 | 只靠哪一端也不够 | 正确处理 |
| --- | --- | --- |
| 订单已写库，事件还没发出就宕机 | 消费者再可靠也读不到消息 | Outbox / CDC / 补偿 |
| Broker 已写入，Producer 没收到 ACK | 消费者幂等不能阻止 Kafka 日志出现重复记录 | Producer 重试 + Producer 幂等 |
| 消费者写库成功，提交 offset 前宕机 | Producer 幂等不能阻止消息被重新消费 | 业务 `event_id` 去重 + 成功后提交 offset |
| 消费者先提交 offset，业务处理前宕机 | Producer 可靠也无法补回被跳过的业务处理 | 禁止提前提交 offset |

所以，**生产者幂等和消费者幂等不是一回事**：

- Producer 幂等是 Kafka 协议层能力，主要防止一次发送过程因重试而在日志中重复追加。
- Consumer 幂等是业务层能力，防止消息重投、Rebalance 或进程宕机后重复执行外部副作用。

实际系统常常两个都要开，并给消息设计稳定的 `event_id`，让生产、消费、追踪和对账使用同一个业务身份。

#### 四、能否做到端到端 Exactly Once？

需要先说明“恰好一次”的范围：

- **Kafka -> 计算 -> Kafka：** 可以使用 Kafka Transaction，把“写入下游 Topic”和“提交上游 offset”放在同一个事务中；下游使用 `read_committed`，可实现 Kafka 范围内的 Exactly Once。
- **Kafka -> MySQL / 支付 / 短信：** Kafka 事务不能自动覆盖外部系统。工程上通常采用 `at-least-once + 业务幂等 + Outbox + 对账补偿`，保证最终只产生一次有效业务结果。

因此线上常见的可靠性组合是：

```text
生产端：Outbox + event_id + acks=all + retries + Producer 幂等
Broker：多副本 + min.insync.replicas + ISR/副本异常监控
消费端：手动提交 offset + 本地事务 + event_id 唯一约束 + 重试/DLQ
全链路：Lag、最老消息年龄、发送失败率、重试率、DLQ 和对账监控
```

#### 五、订单积分例子

假设订单服务产生 `OrderPaid(event_id=E1001, order_id=1001)`，积分服务消费后加 100 积分：

1. 订单服务在一个数据库事务内更新订单为已支付，并插入 Outbox 事件 `E1001`。
2. 投递任务把 `E1001` 发送到 Kafka，等待 `acks=all`；超时可重试，Producer 幂等避免发送重试造成重复追加。
3. 积分服务消费消息，在同一数据库事务内插入消费记录 `E1001` 并增加积分；消费记录有唯一索引。
4. 本地事务成功后提交 offset。即使此时宕机并重放 `E1001`，唯一索引也会识别出“已经加过积分”。
5. Outbox 长时间未投递、Kafka 消费 Lag 异常或消息进入 DLQ 时触发告警，并通过订单与积分流水对账补偿。

这样各层允许“重试和重放”，但最终业务效果只生效一次，比假设网络永不超时更可靠。

#### 常见追问

1. **基础：为什么不能开启自动提交 offset？** 说明自动提交与业务成功没有天然原子关系，以及提前提交造成的丢处理窗口。
2. **进阶：`acks=all` 是否代表绝对不丢？** 说明副本、ISR、磁盘故障和数据库-Kafka 双写边界。
3. **进阶：Producer 幂等开启后，消费者还需要幂等吗？** 需要；两者防护的重复来源和作用范围不同。
4. **高级：并发处理一个 Partition 时如何安全提交 offset？** 只能提交已经连续完成的最大位置，可维护完成区间/水位线，不能跨过尚未完成的消息。
5. **高级：Kafka 事务为何不能保证 MySQL 恰好一次？** 因为 MySQL 不在 Kafka 事务协调器的原子提交范围内，需要外部系统配合。

**面试里推荐这样答：**

> 生产者可靠性保证消息可靠进入 Kafka，主要靠 Outbox 兜住业务双写，再用 `acks=all`、重试、Producer 幂等以及 Broker 多副本保证发送和存储；消费者可靠性保证消息可靠变成业务结果，主要靠业务成功后手动提交 offset、本地事务和 `event_id` 唯一约束实现幂等，并配合有限重试、DLQ 和 Rebalance 处理。两者通过 Kafka 日志衔接但不能互相替代：生产端可靠而消费者提前提交会丢业务处理，消费端可靠而生产端没写入则根本无消息。Kafka 到 Kafka 可用事务实现限定范围的 Exactly Once；涉及数据库或外部接口时，通常采用 at-least-once 加业务幂等、Outbox 和对账补偿。

## Kafka

### 1. Kafka 的核心架构是什么？Topic、Partition、Broker 分别是什么？

**答案：**

- Kafka 的核心链路可以先这样理解：

```text
Producer -> Topic -> Partition -> Broker -> Consumer Group -> Consumer
```

- `Producer` 是生产者，负责把消息发送到 Kafka。
- `Topic` 是消息的逻辑主题，比如订单消息、支付消息、日志消息，可以把它理解成“消息类别”。
- `Partition` 是 Topic 的物理分片。一个 Topic 可以拆成多个 Partition，每个 Partition 本质上都是一条追加写日志。
- `Broker` 是 Kafka 集群里的节点服务器。Partition 会分布在不同 Broker 上存储，所以 Kafka 才能横向扩容。
- `Consumer` 是消费者，负责从 Kafka 拉取消息并处理。
- `Consumer Group` 是消费者组，用来做消费端的负载均衡。**同一个分区，在同一个消费组里，同一时刻只会被一个消费者消费。**
- `Offset` 这里最好分成两层理解：
  - `message offset`：消息在某个 Partition 里的位置编号，这是分区自己的；
  - `consumer group offset`：某个消费组在某个 Partition 上消费到哪里了，这是消费进度。

**这几个概念之间的关系，可以这样讲：**

- 一个 Topic 可以有多个 Partition，目的是提升吞吐和并行能力。
- 多个 Partition 会分布到多个 Broker 上，目的是做扩展和高可用。
- 生产者发消息时，最终是把消息写入某个 Topic 的某个 Partition。
- 消费者消费时，不是直接“消费 Topic 这个抽象概念”，而是消费 Topic 下的各个 Partition。
- Consumer Group 的意义是：把多个 Partition 分给组内多个消费者并行消费。

**为什么 Kafka 要这么设计？**

- 用 `Topic` 做业务隔离；
- 用 `Partition` 做并行和扩展；
- 用 `Broker` 做分布式存储；
- 用 `Consumer Group` 做消费端扩展和负载均衡；
- 用 `Offset` 做消费进度管理。

**消费者组还可以顺手这样理解：**

- 如果两个消费者属于 **同一个 Consumer Group**，那它们是“分工消费”，常用于提升消费能力。
- 如果两个消费者属于 **不同的 Consumer Group**，那它们是“各自独立消费一份消息”，常用于一个 Topic 被多个下游系统分别使用。
- 所以 Kafka 天然支持“一份消息被多个系统订阅”，也支持“一个系统内部多实例并行消费”。

**这里可以举一个很典型的业务例子：**

- 假设有一个 Topic 叫 `order_created`，里面放的是“订单创建成功”的消息。
- 这个 Topic 下有一个分区 `Partition-0`，其中一条消息是：

```text
offset 100 -> order_id=1001
```

- 这时有三个下游系统都想消费它：
  - 库存系统：`stock-group`
  - 积分系统：`points-group`
  - 数据分析系统：`analytics-group`
- 那么这三个 **不同的 Consumer Group**，都可以各自消费到 `offset 100` 这条消息。
- 也就是说，**同一个分区里的同一条消息，可以被多个不同消费者组分别消费**；它们互不冲突，因为每个组维护的是自己的消费进度。

**但如果是同一个 Consumer Group 内部，就不是这样了：**

- 假设 `Partition-0` 只属于 `order-group` 这个消费组。
- 如果 `order-group` 里有两个消费者 `consumer-1` 和 `consumer-2`，那这个分区同一时刻只会分给其中一个，比如只分给 `consumer-1`。
- `consumer-2` 不能同时再来消费这个分区，否则同组内就会重复消费，顺序也会乱。

**容易混淆的一点：Kafka 里其实有两种 offset：**

- 第一种是 **消息 offset**，它属于 Partition，用来标识消息在分区日志里的位置，比如 `0、1、2、3...`。
- 第二种是 **消费进度 offset**，它属于 Consumer Group，用来标识“这个组在这个分区上读到哪了”。
- 所以更准确地说，不是“offset 在消费者手里，而不在分区上”，而是：
  - 分区自己有消息 offset，负责定义顺序；
  - 消费组有消费位点，负责记录进度。
- 消费组提交的消费位点通常会存到 Kafka 的内部主题 `__consumer_offsets` 里。

**面试里比较完整但不啰嗦的回答可以这样说：**

> Kafka 本质上是一个分布式消息队列，也是一个分布式日志系统。生产者把消息发到 Topic，Topic 再拆成多个 Partition，每个 Partition 是一条有序追加日志，这些 Partition 分布在不同 Broker 上存储。消费者不是直接消费 Topic，而是按 Consumer Group 去消费各个 Partition，同一个分区在同一个消费组里只会分给一个消费者处理。这样 Kafka 就同时具备了业务隔离、水平扩展、高吞吐和消费端并行能力。

### 2. Kafka 为什么吞吐量高？

**答案：**

先记一句话：Kafka 的高吞吐不是单点优化，而是 **顺序写 + Page Cache + 批处理 + 零拷贝** 叠加的结果；再配合分区并行，把磁盘 IO、网络 IO 和 CPU 都利用起来。

#### 一、顺序写磁盘

**随机写和顺序写的区别：**

```text
随机写：数据分散在磁盘各处，机械硬盘需要不断移动磁头寻道。

磁盘: [数据 A][空][数据 B][空][数据 C][空]
          ^          ^          ^
       磁头来回跳，寻道成本高

顺序写：只在文件末尾追加。

磁盘: [数据 A][数据 B][数据 C][数据 D] ->
                                      ^
                                持续向后追加
```

- Kafka 的一个 Partition 本质上是一条按 offset 递增的追加日志。生产者把消息发给 Leader 后，Broker 通常只需写到当前日志段文件的末尾。
- 一条日志段目录大致如下：

```text
topic: order-events
└── partition-0/
    ├── 00000000000000000000.log       <- 消息持续追加到这里
    ├── 00000000000000000000.index     <- offset 索引
    └── 00000000000000000000.timeindex <- 时间索引
```

- 传统数据库经常需要按主键或索引定位后原地更新，随机写更多；Kafka 消息写入后通常不修改，消费者只按 offset 顺序读，天然适合连续 IO。
- 对机械硬盘，顺序写能明显减少寻道；对 SSD，顺序写同样更容易获得稳定吞吐，并降低大量小块随机写的额外开销。

**容易被追问：顺序写是否等于每条消息都已经刷盘？**

不是。Broker 的 `write()` 往往先写入操作系统 Page Cache；生产者何时收到成功响应还取决于 `acks` 和副本确认。顺序追加提高的是写入路径效率，可靠性仍要看副本数、ISR、`acks` 和刷盘策略。

#### 二、Page Cache

**如果每条消息都直接 `fsync` 到磁盘：**

```text
Producer -> Kafka -> fsync -> 磁盘
                         ^
                    每条都等磁盘，吞吐低
```

**Kafka 的实际写入路径更接近：**

```text
Producer -> Kafka -> write() -> Page Cache -> 操作系统后台刷盘 -> 物理磁盘
                                  ^
                            先进入内核缓存
```

- Kafka 复用操作系统的 Page Cache。Broker 追加日志时，数据通常先进入内核页缓存，内核再按合适的时机批量回写磁盘。
- 消费者读取刚写入的热消息时，往往也能从 Page Cache 直接读取，不必再次访问物理磁盘。
- Kafka 没有把整套消息缓存都压在 JVM 堆中，这能减少大对象和堆内缓存带来的 GC 压力，把文件缓存和刷盘调度交给操作系统处理。

```text
用户空间
Kafka JVM
    | write()
    v
内核空间: [Page Cache: 消息 1][消息 2][消息 3] ...
                   |
                   v
             后台 flush 到磁盘
```

**注意：** Page Cache 不是“数据只在内存里”。缓存会被回收，冷数据仍会从磁盘读取；它的价值是让近期读写尽量走内存路径，并把刷盘集中为更高效的批量 IO。

#### 三、批量处理

**生产者批量发送：**

```text
单条发送：消息 1 -> 等 ACK -> 消息 2 -> 等 ACK -> ...

批量发送：[消息 1, 消息 2, ..., 消息 100] -> 一次请求 -> 等一次 ACK
```

- Producer 会先按 Topic-Partition 攒 batch，再序列化、压缩并发送。这样一次网络请求、协议解析和系统调用可以承载多条消息。
- `batch.size` 控制单批的目标大小，`linger.ms` 控制为了凑批最多等待多久。例如：

```java
props.put("batch.size", 16384);        // 单批目标 16 KB
props.put("linger.ms", 5);             // 最多等待 5 ms 再发送
props.put("compression.type", "gzip"); // 批内消息一起压缩
```

- 批次更大时，网络包数量、请求次数、包头和上下文切换都会下降；相似消息放在一起压缩，压缩率通常也更高。

**消费者批量拉取：**

```text
单条拉取：fetch 1 -> 处理 -> fetch 1 -> 处理
批量拉取：fetch 多条 -> 批量处理 -> 批量提交 offset
```

```java
props.put("fetch.min.bytes", 50000);  // 尽量攒够 50 KB 再返回
props.put("fetch.max.wait.ms", 500);  // 最多等待 500 ms
```

- Consumer 的 `poll` 本身就是批量拉取；应用侧也可以批量处理、批量提交 offset，避免每条消息都和 Broker 往返一次。
- 批量不是越大越好。batch 太大或等待太久会提高端到端延迟，消费单批太大也可能占用更多内存、拉长单次处理时间。参数要按消息大小、QPS、延迟目标和下游处理能力权衡。

#### 四、零拷贝

消费者读取日志文件后，传统 `read/write` 链路通常需要把数据复制到 Kafka 用户态缓冲区，再复制到 Socket 缓冲区：

```text
磁盘 -> Page Cache -> Kafka 用户态缓冲区 -> Socket 缓冲区 -> 网卡
         DMA             CPU                 CPU             DMA
```

Kafka 在适合的文件传输场景可使用 Java NIO 的 `transferTo()`，底层对应 Linux 的 `sendfile()` 等能力：

```java
fileChannel.transferTo(position, count, socketChannel);
```

```text
磁盘 -> Page Cache ------------------------------> 网卡
         DMA              sendfile / 内核路径      DMA
```

- 数据不必先复制到 Broker 的 JVM 用户态再转发，减少用户态 CPU 拷贝和用户态/内核态切换。
- 对已经命中 Page Cache 的数据，Broker 更像高效的日志转发器，CPU 可以留给协议处理、压缩、副本复制和更多连接。
- “零拷贝”是工程简称，不应理解为机器完全不做数据搬运：DMA 仍可能参与；TLS、消息转换或某些压缩处理也可能无法完全走这条路径。它优化的是 Broker 向消费者传输日志的复制成本。

#### 五、四种机制怎样协同

```text
Producer
  -> 按 Partition 攒 batch
  -> 批量压缩、发送
  -> Broker 顺序追加日志
  -> 写入 Page Cache，后台批量刷盘

Consumer
  -> 批量 fetch
  -> 热数据优先命中 Page Cache
  -> 文件到 Socket 尽量走 sendfile
  -> 批量处理、提交 offset
```

- **分区并行** 是横向扩展基础：多个 Partition 可分布到多个 Broker，生产和消费都能并行；每个分区内部仍保持顺序追加。
- **批量压缩** 会同时减少网络带宽和磁盘占用，进一步放大批处理收益。

**面试里推荐这样答：**

> Kafka 把消息设计成 Partition 上的追加日志，所以写入是顺序追加，避免随机写的寻道和定位成本；Broker 复用操作系统 Page Cache，近期读写大多走内存路径，后台再批量刷盘；生产和消费都按 batch 工作，摊薄网络、协议和系统调用开销；消费者拉取日志时可通过 `sendfile` 等零拷贝能力减少 Broker 用户态复制。再加上 Partition 可以跨 Broker 并行，Kafka 最终形成了 **顺序 IO + Page Cache + 批处理 + 零拷贝 + 分区并行** 的高吞吐链路。实际配置时仍要在吞吐、延迟和可靠性之间取舍。

### 3. Kafka 里 Partition、Replica、Leader、Follower、ISR 分别是什么？

**答案：**

- `Partition` 是分片，解决扩展性问题。
- `Replica` 是副本，解决高可用问题。
- 一个分区在同一时刻只有一个 `Leader` 对外提供读写，其他副本是 `Follower`，负责跟随同步。
- `ISR` 全称是 `In-Sync Replicas`，表示“当前和 Leader 保持同步、状态足够健康”的副本集合。
- 这里要注意，**ISR 不是所有副本的全集**。如果某个 Follower 同步太慢、延迟太大，它可能暂时掉出 ISR。
- 所以当我们说 `acks=all` 时，等的不是“所有副本都确认”，而是“当前 ISR 里的副本确认”。
- 面试里常见追问是：**真正决定可用性的不是副本数本身，而是 ISR 里还有没有足够健康的副本。**

### 4. 生产者发送消息时，Kafka 怎么决定消息进哪个分区？

**答案：**

- 如果消息显式指定了 partition，那就直接进指定分区。
- 如果没指定 partition，但指定了 key，通常会根据 key 做哈希，让同一个 key 尽量落到同一个分区。
- 如果 key 也没有，通常会走轮询或 sticky 分区策略，尽量把批量发送做得更高效。
- 所以常见面试回答就是：**指定分区优先；否则 key 决定路由；再否则走默认分区器策略。**

**如果继续追问：哈希是不是一定不会冲突？为什么这里不用 MD5 / SHA-256？**

- 先说结论：**哈希一定可能冲突。**
- 只要输入空间远大于输出空间，就不可能做到绝对无冲突。区别只在于：
  - 冲突概率高不高
  - 工程上能不能接受
- 像 `MD5`、`SHA-256` 这种更多是**密码学哈希**，强调抗碰撞、抗篡改和安全性。
- Kafka 按 key 选分区，本质只是做**路由分发**，目标是：
  - 同一个 key 尽量稳定落到同一个分区
  - 算得快
  - 分布尽量均匀
- 所以这里更关注的是**速度和分布性**，不是密码学安全，没必要上 `MD5` / `SHA-256` 这种更重的哈希。
- 另外要注意，即使不同 key 哈希后落到同一个分区，这也不叫“数据错了”，只是它们被路由到了同一个桶里。Kafka 只要求“同 key 稳定路由”，不要求“不同 key 绝对分开”。

**面试里可以这样答：**

> Kafka 按 key 选分区时，本质是做路由，不是做安全校验，所以不需要 MD5 这类密码学哈希。哈希本身一定可能冲突，但这里工程上能接受，因为目标只是让同一个 key 稳定落到同一个分区，并尽量把数据分散得比较均匀。只要分区器足够快、分布性足够好，就能满足需求。

### 5. Kafka 怎么保证消息不丢？

**答案：**

- 这题不能只答 Broker，最好按 **生产者、Broker、消费者** 三段来讲。
- 核心思路是：**发的时候别假成功，存的时候别单点，消费的时候别没处理完就提交 offset。**

**1）生产者侧：保证“真的发成功了”**

- 关键配置是 `acks=all`。这里的 Leader 指的是**目标 Partition 的 Leader 副本**。Producer 会先把消息发给这个 Partition 的 Leader。
- 如果配置了 `acks=all`，Leader 不能只在自己写成功后就立刻返回，而是要等 **当前 ISR 里的副本** 也同步完成后，再给 Producer 返回成功。
- 这里一定要注意：`acks=all` 等的是 **ISR**，不是“所有副本的绝对全集”。如果某个 Follower 太慢、已经掉出 ISR，它不会参与这次确认。
- 只说 `acks=all` 还不够，通常还要配合 `retries`，应对网络抖动这类临时失败。
- 但一重试就可能重复发，所以还要开启幂等性 `enable.idempotence=true`，避免因为重试造成重复写入。

**2）Broker 侧：保证“存下来后不轻易丢”**

- Kafka 靠多副本机制保证高可用。一个 Partition 不只一份数据，Leader 挂了还能从 Follower 里选新的 Leader。
- 这里有个很关键的点是 `min.insync.replicas`。它的意思不是“总副本数至少几个”，而是：**当生产者用 `acks=all` 写入时，ISR 里最少要有几个副本可用，这次写入才允许成功。**
- 如果只配了 `acks=all`，但 ISR 里只剩 Leader 一个节点，那 `acks=all` 实际上就会退化得很危险，因为它等来等去也只等到了 Leader 自己。
- 所以高分回答通常会补一句：**`acks=all` 要和 `min.insync.replicas >= 2` 一起看**。这样当 ISR 副本数不够时，Broker 会直接拒绝写入，宁可报错，也不冒险接收一条可能马上丢失的数据。

**举个最常见的例子：**

- 假设一个 Partition 有 3 个副本：`1 个 Leader + 2 个 Follower`
- 此时配置：
  - `acks=all`
  - `replication.factor=3`
  - `min.insync.replicas=2`
- 如果当前 ISR 里有 3 个副本，写入当然可以成功。
- 如果有一个 Follower 掉线了，但 ISR 里还剩 `Leader + 1 个 Follower`，也就是 2 个副本，那仍然可以写。
- 但如果再坏一点，只剩下 Leader 自己还在 ISR 里，那这时写入就应该被拒绝，而不是假装成功。

**所以这三个概念要分清：**

- `replication.factor`：这个 Partition 一共配了几份副本
- `ISR`：这些副本里，当前真正健康、同步得上的那几份
- `min.insync.replicas`：当你用 `acks=all` 写入时，ISR 至少得剩几份，这次写入才允许成功

**3）消费者侧：保证“处理成功后再提交进度”**

- 如果消费者一拉到消息就自动提交 offset，但本地业务还没执行完就崩了，Kafka 会以为这条消息已经消费过了，这才是真正可怕的“业务丢消息”。
- 所以核心做法是关闭自动提交 `enable.auto.commit=false`，改成手动提交。
- 只有当本地业务逻辑真的执行成功，比如数据库事务提交成功了，再去提交 offset。
- 这里最好再补一句：为了应对重复消费，消费逻辑本身通常还要做幂等。

**所以更完整的总结是：**

- 生产者侧：`acks=all + retries + idempotence`
- Broker 侧：`replication + min.insync.replicas`
- 消费者侧：`手动提交 offset + 消费幂等`

**面试里可以直接这样答：**

> Kafka 保证消息不丢，不能只看 Broker，而要做端到端保障。生产者侧我会配置 `acks=all`，配合重试和幂等，保证消息真的写成功；Broker 侧依靠多副本机制，并结合 `min.insync.replicas`，避免副本不够时还错误地接收写入；消费者侧关闭自动提交，只有本地业务真正处理成功后再手动提交 offset。再往前走一步，消费逻辑本身还要做幂等。严格来说，工程上更准确的说法不是“绝对 0 丢失”，而是尽量做到端到端可靠和可恢复。

### 6. Kafka 怎么保证消息有序？

**答案：**

- Kafka 只能保证 **单分区内有序**，不能天然保证一个 Topic 所有分区的全局有序。
- 如果业务要求同一类消息严格有序，常见做法是让同一个业务 key 始终进入同一个分区。
- 消费端也要注意：一个分区最好只被一个消费者线程按顺序处理，否则应用层自己也可能打乱顺序。
- 所以面试时最好直接说：**Kafka 能保证的是单分区顺序，不是全局顺序。**

---

### 7. Consumer Group 和 Rebalance 是什么？为什么大家都怕 Rebalance？

**答案：**

- `Consumer Group` 是 Kafka 的消费组机制：一个分区同一时刻只会被组内一个消费者消费。
- 同组内是“分工关系”，不同组之间是“各自独立消费”。所以一个 Topic 的同一条消息，既可以被一个系统内部多实例并行处理，也可以被多个下游系统分别订阅。
- 举个例子：`order_created` 这个 Topic 里的同一条消息，可以同时被 `stock-group`、`points-group`、`analytics-group` 三个组分别消费；但在 `stock-group` 内部，这条分区消息同一时刻只能分给一个消费者实例处理。
- `Rebalance` 就是消费组成员变化、订阅变化、分区变化时，Kafka 重新分配分区归属。
- 大家怕 Rebalance，是因为它发生时通常会带来短暂停顿，严重时会影响消费延迟，甚至引发重复消费。
- 所以工程上一般会尽量减少不必要的频繁重平衡，比如控制消费者抖动、合理设置心跳和超时参数。

---

### 8. Kafka 出现消息堆积时，怎么排查和处理？

**答案：**

- 我会先判断是“生产太快了”还是“消费变慢了”。
- 如果是消费变慢，还要继续拆：是消费者挂了、下游接口慢了、单条消息太重了，还是分区数不够。
- 临时止血常见做法有：扩消费者、扩分区、批量消费、隔离慢下游、必要时降级非核心逻辑。
- 根因治理则是：优化单条消息处理耗时、提高幂等和重试能力、避免坏消息把整个消费链路拖死。

### 9. Kafka 和传统 MQ 有什么区别？应该怎么选？

**答案：**

先纠正一个容易被面试官追问的说法：**Kafka 本身也是消息中间件**。大家口中的“Kafka 和传统 MQ”，通常是在比较两种不同的设计重心：

- Kafka 更像一个可反复读取的**分布式提交日志**，擅长高吞吐、事件流、数据管道和消息回放。
- 传统 MQ 更像一个负责把任务准确交给消费者的**消息路由与投递中心**，擅长灵活路由、单条确认、重试、死信和延迟任务。

下面主要用 RabbitMQ 代表传统 MQ 来比较。RocketMQ 同样具备分区、顺序存储和高吞吐等能力，处在两者之间，所以不能把所有 MQ 产品一概而论。

#### 一、先看两者最核心的模型

**传统 MQ：重点是“把这条消息交给谁”**

```text
                                  ┌─> [库存队列] ─> 库存消费者 ─ACK─> 消息删除
生产者 ─> Exchange（按规则路由） ─┼─> [短信队列] ─> 短信消费者 ─ACK─> 消息删除
                                  └─> [风控队列] ─> 风控消费者 ─ACK─> 消息删除
                                      │
                                      └─失败 / 超时─> 重试队列或死信队列
```

- 生产者把消息交给 Broker，Broker 根据路由规则投递到一个或多个队列。
- 消费者处理成功后发送 `ACK`，消息通常就可以从队列中删除。
- 消费失败可以 `NACK`、重新入队，或者进入死信队列，控制粒度通常落在单条消息上。

**Kafka：重点是“把事件按顺序记下来，读者自己记录读到哪里”**

```text
                         Topic: order_created
                  ┌──────────────────────────────┐
生产者 ─追加写入─> │ P0: [0][1][2][3][4][5] ... │
                  │ P1: [0][1][2][3] ...       │
                  └──────────────────────────────┘
                         │       │       │
                         │       │       └─> analytics-group：offset=2
                         │       └─────────> points-group：offset=4
                         └─────────────────> stock-group：offset=5

消息是否保留：由保留时间 / 保留大小决定
消费到了哪里：由每个 Consumer Group 的 offset 决定
```

- Producer 只管把事件追加到 Topic 的某个 Partition，不会为每个下游复制一套原始日志。
- 不同 Consumer Group 各自维护 offset，互不影响；同一条消息可以被多个系统独立读取。
- 消费成功不会立刻物理删除消息。只要消息仍在保留期内，消费者就能重置 offset 后重新回放。

**一句话抓住本质：**传统 MQ 以“队列、路由、投递状态”为中心；Kafka 以“分区日志、offset、保留策略”为中心。

#### 二、关键区别对比

| 对比维度 | Kafka | 传统 MQ（以 RabbitMQ 为例） |
| --- | --- | --- |
| 核心定位 | 分布式日志、事件流平台 | 业务消息路由与任务队列 |
| 数据组织 | Topic 拆成多个 Partition，每个分区追加写 | Exchange 按规则把消息路由到一个或多个 Queue |
| 消费方式 | Consumer 主动批量拉取，自己维护 offset | Broker 通常向 Consumer 推送，Consumer 用 ACK/NACK 确认 |
| 消息生命周期 | 消费后仍按保留策略保存，可重复读取 | 消费并 ACK 后通常从队列删除 |
| 多下游订阅 | 每个 Consumer Group 独立读取同一份日志 | 通常为每个下游绑定独立队列，各自保存一份待消费消息 |
| 顺序保证 | 保证单 Partition 内有序 | 单 Queue 可有序，但多消费者并发、重试也可能打乱处理顺序 |
| 吞吐特点 | 批量、顺序 IO、Page Cache、分区并行，适合海量数据 | 更强调低延迟投递和业务控制；吞吐能力取决于具体产品和配置 |
| 失败处理 | 提交 offset；重试常通过重试 Topic、暂停分区或应用逻辑实现 | ACK/NACK、重新入队、死信队列等机制通常更直接 |
| 消息回放 | 原生支持，重置 offset 即可回放保留期内的数据 | 通常不是默认模型，往往需要重新发布或额外保存消息 |
| 业务特性 | 流处理、Connector、消息回放更自然 | 复杂路由、优先级、死信、延迟任务等通常更贴近业务 |
| 扩展方式 | 增加 Broker 和 Partition；消费并行度受 Partition 数限制 | 增加消费者、队列或节点；具体扩展方式依赖产品 |

这里不要机械地说“Kafka 一定比传统 MQ 快”。更准确的说法是：**Kafka 的存储、批量和分区模型更容易在大数据量下获得很高的整体吞吐；传统 MQ 则通常把更多能力放在路由和单条消息控制上。**

#### 三、用一个电商例子理解

假设订单服务产生一条事件：

```text
order_created(orderId=1001, userId=88, amount=299)
```

库存、积分、短信、数据分析四个系统都要处理它。

**方案 A：使用 Kafka**

```text
                         ┌─> stock-group      扣库存
订单服务 ─> order_created├─> points-group     加积分
          Topic          ├─> sms-group        发短信
                         └─> analytics-group  实时统计
```

四个系统使用四个 Consumer Group，所以都能读到同一条订单事件，各自维护消费进度。如果数据团队后来发现统计逻辑写错了，可以修复程序，再把 `analytics-group` 的 offset 重置到昨天的位置，重新计算昨天的数据。

这个例子里 Kafka 的优势是：

- 订单量很大时，可以用多个 Partition 提升写入和消费吞吐。
- 四个下游互不干扰，某个消费组宕机只会让自己的 lag 增长。
- 历史事件在保留期内仍然存在，适合审计、回放和重新计算。

但如果短信消费者处理失败，Kafka 不会自动替你完成复杂的“第 1 次等 10 秒、第 2 次等 1 分钟、最后进死信队列”流程，通常要设计 `sms_retry_10s`、`sms_retry_1m`、`sms_dlq` 等 Topic，或者在应用层实现重试调度。

**方案 B：使用传统 MQ（以 RabbitMQ 为例）**

```text
                                      ┌─> stock.queue     ─> 扣库存 ─ACK
订单服务 ─> order.exchange ─路由复制─┼─> points.queue    ─> 加积分 ─ACK
                                      ├─> sms.queue       ─> 发短信 ─ACK
                                      └─> analytics.queue ─> 统计   ─ACK

sms.queue 处理失败 ─> 重试队列 ─> 再次投递 ─> 仍失败 ─> sms.dlq
```

Exchange 把同一条订单消息路由到四个队列，每个系统只关心自己的队列。短信处理成功就 ACK；失败可以 NACK、重新入队或转入死信队列。这个模型非常适合“把一项业务任务可靠地交给某个服务完成”。

这个例子里传统 MQ 的优势是：

- 每条消息的成功、失败、重试和死信状态更直观。
- 按 routing key 灵活分发消息更方便。
- 订单超时关闭、失败重试、任务优先级等业务需求通常更容易表达。

代价是：已 ACK 的消息通常不再保留在原队列中。如果一个新上线的分析系统想重放过去七天的全部订单事件，就需要提前把数据保存在别处，或者让生产者重新发布，不能像 Kafka 那样简单重置 offset。

#### 四、怎么选？

```text
消息量很大，要做日志采集、埋点、实时计算、CDC 或历史回放？
  └─ 是：优先考虑 Kafka

更关心复杂路由、单条 ACK/NACK、延迟任务、死信和细粒度重试？
  └─ 是：优先考虑 RabbitMQ / RocketMQ 等业务型 MQ

两种需求都很强？
  └─ 不必二选一：核心事件流进 Kafka，业务命令和延迟任务走业务型 MQ
```

典型场景可以这样记：

- **Kafka：**用户行为埋点、日志采集、数据库 CDC、实时数仓、风控事件流、多个下游订阅和回放。
- **传统 MQ：**订单超时关闭、短信或邮件任务、支付结果通知、失败重试、复杂路由、工作队列。
- **混合使用：**订单状态变化写 Kafka 供数据、推荐和风控订阅；30 分钟未支付自动关单走延迟消息。

选择时还要考虑团队现有技术栈、消息规模、运维能力和生态，不能只看某一项跑分。Kafka 的 Partition 数、Consumer Group 和 offset 管理有学习成本；传统 MQ 的队列、路由规则和堆积容量也同样需要治理。

**面试里推荐这样答：**

> Kafka 本身也是 MQ，但它的核心抽象是可保留、可回放的分区日志，更强调批量、顺序 IO、分区并行和高吞吐；传统 MQ 更强调把消息按规则投递到队列，并对单条消息进行 ACK、重试和死信处理。消费成功后，Kafka 的消息仍按保留策略存在，不同消费组靠各自的 offset 独立消费；传统 MQ 的消息 ACK 后通常就从队列删除。因此日志、埋点、CDC、实时计算和多下游回放我会优先选 Kafka，复杂路由、延迟任务和细粒度失败处理我会优先选业务型 MQ。最终不是比较谁绝对更强，而是看业务更需要“事件日志”还是“任务投递”。

### 10. Kafka 是怎么做到削峰填谷的？

**答案：**

削峰填谷不是 Kafka 把流量“变没了”，而是把高峰时来不及处理的请求先可靠地存下来，再让下游按自己能承受的速度慢慢处理。

可以把 Kafka 想成订单服务和库存服务之间的一个大型等候区：

```text
高峰期：用户下单 -> 订单服务快速写 Kafka -> 立即返回“排队处理中”
平峰期：库存/优惠券/通知消费者 -> 按稳定速度从 Kafka 取消息处理
```

**例子：**某场直播带货开始后的 10 秒里涌入 10 万个下单请求，但库存服务只能稳定处理每秒 2000 个扣库存操作。

如果订单服务同步调用库存服务，瞬间每秒 1 万请求会把库存服务、数据库连接池和 Redis 打满，最后所有用户都超时。接入 Kafka 后：

1. 订单服务先完成轻量校验和订单预创建，把 `order_created` 事件写入 Kafka。
2. 写入成功就告诉用户“订单处理中”，不在请求线程里等待库存、积分、通知全部完成。
3. 库存消费者以每秒约 2000 条的稳定速度消费；高峰来的消息暂时积压在 Kafka 中。
4. 积分、短信、推荐等非核心消费者各自用独立消费组处理，不会拖慢库存主链路。
5. 高峰过去后，生产速度低于消费速度，消费者继续处理积压消息，延迟逐步回落，这就是“填谷”。

Kafka 能承担这个等候区，是因为消息会持久化保留一段时间，消费者宕机或扩容后还能从上次提交的位置继续消费。它不是无限队列：如果消费者长期慢于生产者，积压会持续增长，最终触及磁盘、保留时长和业务时效的边界。

所以完整方案还要有三件事：入口限流防止 Kafka 本身被打爆；消费者监控积压量和最老消息延迟；当积压过大时优先扩消费者、优化慢逻辑或降级非核心处理。对库存扣减、订单创建等场景，消费端还必须幂等，因为失败重试或重平衡可能使同一消息再次到达。

**面试回答：**

> Kafka 削峰填谷的核心是把“同步调用下游”改成“先持久化事件、再异步消费”。高峰时订单服务只负责快速把订单事件写入 Kafka，库存服务按自己能承受的速度稳定消费；消息暂时积压在 Kafka，不会直接把库存数据库打垮。高峰过去后消费者继续处理积压，延迟回落。前提是队列有容量边界、消费者有积压监控，并且关键消费逻辑支持幂等和补偿。

### 11. 业务里为什么要用 MQ？什么时候会想到 Kafka？

**答案：**

- 我不会答成“为了用中间件而用”，而是会先看业务是不是有这几个问题：
  
  - 主链路太重，需要异步化
  - 上下游耦合太紧，需要解耦
  - 突发流量太大，需要削峰填谷
  - 任务不能在进程内直接丢，需要持久化

- 如果这些问题都比较明显，就会想到 MQ。

**Kafka 更适合什么时候：**

- 吞吐要求高
- 消息量大
- 更偏日志流、埋点流、异步处理流
- 消费端可能有多个下游系统各自消费

**为什么不是直接开 goroutine：**

- goroutine 适合轻量异步
- 但进程一挂，内存里的任务就没了
- Kafka 能把任务持久化下来，服务重启后还能继续消费

**面试里推荐这样答：**

> 业务里用 MQ，核心通常是为了解耦、异步化、削峰和持久化。Kafka 更适合高吞吐、分布式日志流和多个消费组并行消费的场景；如果只是单机内的轻量异步，goroutine 也许够用，但一旦任务比较重、不能接受丢任务，消息队列就更合适。

### 12. 生产者发送 Kafka 失败了怎么办？

**答案：**

- 先不要只答“重试”，更完整的思路是分层看：
1. **先保证发送可靠性**
   
   - `acks=all`
   - 开启重试
   - 开启幂等 `enable.idempotence=true`

2. **失败时做分类**
   
   - 网络抖动：可重试
   - Broker 暂时不可用：可重试
   - 参数错误 / 消息非法：通常不是重试能解决的

3. **重试也要有边界**
   
   - 不能无限重试
   - 避免把下游压垮

4. **业务上还要兜底**
   
   - 本地消息表
   - 补偿任务
   - 告警和死信处理

**面试里推荐这样答：**

> 生产者发送 Kafka 失败时，我会先用 `acks=all + retries + idempotence` 提高发送可靠性。失败后要先区分是临时性故障还是参数类错误，临时性故障可以有限重试；如果消息对业务特别关键，还要用本地消息表或补偿任务兜底，不能把“发送失败”完全丢给应用日志。

### 13. Kafka 的 at-most-once、at-least-once、exactly-once 三种投递语义分别是什么？

**答案：**

三种语义描述的是“消息端到端可能被处理几次”，不是单看 Broker 是否保存了消息。核心取舍是：先提交进度可能丢消息，后提交进度可能重复；想同时避免两者，需要事务边界或业务幂等。

| 语义 | 含义 | 常见提交顺序 | 结果 | 适用场景 |
| --- | --- | --- | --- | --- |
| `at-most-once`（至多一次） | 一条消息最多处理一次，允许丢失 | 先提交 offset，再执行业务 | 不重复，但崩溃窗口会丢 | 指标采样、可丢日志 |
| `at-least-once`（至少一次） | 一条消息至少处理一次，允许重复 | 业务成功后再提交 offset | 不易丢，但崩溃窗口会重放 | 订单、库存等绝大多数业务 |
| `exactly-once`（恰好一次） | 在定义好的处理边界内，只对外产生一次可见结果 | 事务性写入 + 事务性提交 offset | 不丢、不重，但有条件和成本 | Kafka 流式计算、Kafka 到 Kafka 的处理链路 |

**用“订单创建后发积分”举例：**

1. `at-most-once`：消费者拿到 `order_created(orderId=1001)` 后，先提交 offset，进程随后在“加积分”前崩溃。Kafka 不会重发，订单 1001 永远少了积分。这种做法换来低重复率，却牺牲可靠性。
2. `at-least-once`：消费者先在数据库给订单 1001 加积分，再提交 offset。若加积分成功后、提交 offset 前进程崩溃，重启后会再次拿到同一消息。因此写库必须以 `order_id` 或 `event_id` 做唯一约束，重复处理时返回已完成而不是再加一次。
3. `exactly-once`：若消费者读取 `order_created` 后只需要写入另一个 Kafka Topic，例如生成 `points_granted`，可用 Kafka Transaction 把“输出消息”和“输入 offset”放进同一个事务。事务提交后两者同时可见；中断则两者都不可见。下游消费者配置 `isolation.level=read_committed`，只读取已提交事务。

Kafka 的 EOS 不会自动让“写 MySQL、调用支付、发送短信”也恰好一次：外部系统通常不参与 Kafka 事务。跨系统场景仍然要做业务幂等、Outbox / CDC、状态机和对账补偿。面试中把 `exactly-once` 说成“全世界绝不重复”是不准确的。

**`at-least-once` 的消费者处理顺序：**

```text
poll 消息
  -> 在本地事务内写业务表 + 消费记录表（event_id 唯一）
  -> 本地事务提交成功
  -> 手动提交 Kafka offset
```

消费记录表可建立唯一约束：`UNIQUE(consumer_name, event_id)`。若插入冲突，说明这条事件已经成功处理过，直接提交 offset 即可。对于“扣库存”这类可直接表达为状态转换的业务，也可把 `event_id` 存入业务流水表，依靠唯一索引把去重和业务写入放在同一个本地事务里。

**面试回答：**

> 至多一次是先提交 offset 再处理，可能丢但不会因重放而重复；至少一次是业务成功后再提交，可能重放，所以消费者必须幂等；恰好一次依赖事务，把处理结果和 offset 一起提交，但它主要解决 Kafka 内部的 read-process-write。真正写数据库或调用外部服务时，我仍会用唯一业务键、消费记录、Outbox 和补偿保证最终一次生效。线上默认通常选 at-least-once 加业务幂等，因为成本和可靠性最平衡。
