# AI Coding 面试：后端工程师为什么能应聘全栈，以及如何借助 AI 交付前后端

> 这篇只回答面试问题：**后端为什么应聘全栈？AI 怎么参与前后端交付？大家都会用 AI，你凭什么更可靠？怎样 Review AI 写的代码？**

## 0. 面试官真正担心什么

这不是在考你会不会写 CSS 动画，而是在确认你能否：从用户界面一路负责到数据与服务；不把 AI 当不受控生成器；能判断代码正确性；交付可 review、可上线、可回滚的改动。

回答主线是：**后端能力守住系统正确性；AI 补足 UI 实现和跨层迭代速度；规格、边界、验证与上线判断由我负责。**

---

## 1. “你是后端，为什么来应聘全栈？”

### 60～90 秒参考回答

> 我做后端时积累的核心能力是领域建模、接口契约、权限、状态机、数据一致性和可观测性。这些不只属于后端，它们决定一个用户功能最终能不能正确交付。
>
> 我应聘全栈不是因为把前端当成让 AI 写页面，而是因为一个需求的最小交付单位是一条用户旅程：用户怎么操作、接口如何校验、后台如何处理、失败怎样反馈、数据怎样审计。只负责其中一个 API，很多时候不能真正解决问题。
>
> 我的方式是先把领域规则、API 契约和验收路径定清楚，再用 AI 加速前端组件、表单状态、typed client、mock、测试和页面细节；后端我重点把住权限、幂等、事务和异步一致性。最后用接口测试、浏览器 E2E、日志/指标和独立 review 验证整条链路。AI 提升实现速度，但不会降低正确性门槛。

### 追问“你的前端能力体现在哪？”

| 环节 | 我负责什么 | AI 加速什么 |
| --- | --- | --- |
| 交互与状态 | 页面状态、输入校验、loading/empty/error、权限可见性 | 组件初稿、样式、边界态补全 |
| 前后端契约 | Schema、错误码、分页、兼容性 | typed client、mock、请求封装 |
| 后端逻辑 | 状态机、权限、事务、幂等、缓存/消息一致性 | 样板代码、测试、代码搜索与重构建议 |
| 验证交付 | 验收标准、风险判断、发布/回滚 | 浏览器回归、独立 review、证据整理 |

**关键表达：**我不承诺成为视觉设计师；我承诺能交付从页面到数据、失败时也可预期的一条完整业务链路。

## 2. “你具体怎样借助 AI 写前后端代码？”

不要说“提一个 Prompt，AI 就做完了”。画出可控链路：

```text
用户故事 / 验收标准
  → 领域规则与 API Contract
  → AI 只读探索已有模式
  → 前后端按同一 Contract 实现
  → 单测 / 集成测试 / 浏览器 E2E
  → AI 独立 Review + 人工验收
  → 监控、灰度、回滚
```

### 用“管理员禁用短链接”讲完整

业务需求：管理员只能禁用本租户的 `ACTIVE` 短链接；重复点击幂等；禁用后跳转访问为 404；页面二次确认；写审计日志并失效缓存。

#### 第一步：人先定义规格，AI 不猜业务

```text
目标：管理员可禁用本租户的 ACTIVE 短链接。
非目标：本次不做恢复、不做批量操作。
规则：重复禁用返回当前状态；跨租户资源返回 404，不泄露其存在性。
契约：POST /api/links/{id}/disable → { id, status, disabledAt }。
验收：403/404/重复提交/超时都有页面反馈；API、集成测试、E2E 都通过。
风险：缓存失效与审计日志不可遗漏。
```

这一步决定业务规则、错误语义和验收；否则 AI 很容易写出“能跑但不对”的页面和接口。

#### 第二步：先让 AI Explore，再允许改动

```text
只读探索，不改文件。请定位：短链接状态迁移、租户鉴权入口、
同类禁用操作、缓存失效与审计实现、对应前端页面和测试模式。
输出文件路径、关键符号、证据、最小修改计划和不确定项。
```

我先核对它是否理解已有权限、错误处理和组件约定；复杂任务让一个 Agent 只探索、另一个只 review，不让多个 Agent 同时改同一批文件。

#### 第三步：Contract first，让前端和后端不互相猜

```text
状态机 / 领域模型
        ↓
OpenAPI / JSON Schema / 示例响应
   ┌────┴────┐
   ▼         ▼
Backend      Frontend
handler      typed client + mock + 确认弹窗
   └────┬────┘
        ▼
contract test + E2E
```

AI 可基于已确认的 Contract 生成 handler 骨架、客户端类型、mock 和表单状态；我会 review 状态迁移、错误码、越权语义和兼容性。这样前端不需要猜字段，后端也不会为页面临时做不稳定接口。

#### 第四步：按纵向切片实现，用证据验收

我要求 AI 一次只实现这个功能，同时报告修改文件、运行命令、测试结果与未解决风险。验收从两端进行：

| 视角 | 必查项 |
| --- | --- |
| 后端 | 租户隔离、状态机、幂等、事务、缓存/消息一致性、错误码 |
| 前端 | 二次确认、重复点击、loading/empty/error、状态刷新、可访问性 |
| 用户链路 | 创建资源 → 禁用 → 列表状态变化 → 访问 404 → 审计可查 |
| 运营 | 日志含 request/resource/tenant 标识；可观测失败率与延迟；可灰度/回滚 |

OpenAI Docs 说明 Codex CLI 可以在仓库中探索、编辑、运行工具、配置权限，并针对改动进行不修改工作区的 review；但它们应纳入上述验收门，不能替代人对结果负责。[OpenAI Docs：Codex CLI](https://learn.chatgpt.com/docs/codex/cli)

## 3. “都会用 AI，你比其他候选人好在哪？”

### 参考回答

> 我不把 AI 当自动补全，也不把它当最后责任人。我更关注怎样让它在工程约束里稳定工作：输入必须是可验收规格，输出必须有测试和可回放证据，风险操作必须有权限与人工关卡，失败要沉淀为可复用规则。
>
> 所以差异不在谁能生成更多代码，而在谁更快判断它缺什么 Context、哪里不可信、该用什么验证。对前端我看用户状态和 Contract；对后端我看不变量和故障边界；对上线我看观测、灰度和回滚。我交付的是可维护结果，不是一次性代码片段。

| 普通用法 | 我的做法 | 价值 |
| --- | --- | --- |
| 给 AI 一个大需求 | 拆成范围、规则、非目标、契约、验收和风险 | 降低误解与过度实现 |
| 听 AI 说“完成了” | 要求 diff、测试命令、运行结果、截图/日志和剩余风险 | 用证据代替自述 |
| 只让 AI 写代码 | Explore → Plan → Implement → Test → 独立 Review | 每一步可纠偏、可回滚 |
| 出错再改 Prompt | 归因到规格、Context、工具、测试或架构，写入规则/CI | 经验成为团队能力 |

### 让仓库对人和 AI 都可读

```text
AGENTS.md                 # 运行方式、边界、目录导航、必须验证项
docs/domain/*.md          # 状态机、不变量、错误码、业务术语
openapi.yaml              # 前后端契约的单一事实来源
scripts/verify.sh         # 可重复的最小验证入口
docs/runbooks/*.md        # 故障排查、恢复与升级条件
```

OpenAI 的 harness engineering 经验同样强调：让 Agent 能逐层发现仓库中的权威信息，比堆一份巨大的说明书更有效；知识应可发现、版本化并能被验证。[OpenAI：Harness engineering](https://openai.com/index/harness-engineering/)

## 4. “你怎么 Review AI 写的代码是否正确？”

**结论：不能只读 diff，也不能只看测试绿。**我从规格、契约、领域不变量、运行行为和上线风险五层交叉验证。

```text
规格 / 验收
   ↓
代码结构与 diff ─→ 单测 / 集成测试 ─→ 浏览器 / API 运行验证
   ↓                       ↓                    ↓
权限、状态机、事务       边界与回归           日志、指标、灰度、回滚
```

| 层 | 我问什么 | 典型反例 |
| --- | --- | --- |
| 规格一致性 | 是否实现目标，也没有越过非目标？ | 只需禁用，AI 却顺手增加删除/恢复/批量接口 |
| Contract | 字段、状态码、空值、分页、兼容性与前端是否一致？ | 后端改为 409，前端仍按 200 处理 |
| 领域不变量 | 权限、状态迁移、幂等、事务、并发、数据归属是否正确？ | 仅按 id 更新，造成跨租户越权；先查后改导致竞态 |
| 运行行为 | 超时、重复、空数据、失败重试、降级是否可预期？ | 页面只有成功态，没有 403、404、网络错误 |
| 上线风险 | migration、缓存、消息、资源、日志、监控、回滚是否齐备？ | 缓存未失效；新增字段无索引；日志没有关联 ID |

### Review 的实际步骤

1. 先读规格，再读 diff；逐条勾选验收和非目标。
2. 让 AI 解释关键决定并定位证据，例如“租户过滤在哪层强制”“重复请求为什么幂等”。
3. 从不变量反推反例测试：跨租户 ID、并发双击、状态已变、下游失败、缓存仍有旧值。
4. 独立执行 API 集成测试和浏览器 E2E；必要时找只读 Agent 做 adversarial review。
5. 看运行证据：真实请求日志、DB 记录、事件、cache key、trace，确认副作用符合预期。
6. 涉及权限、金额、迁移、异步一致性或生产操作时，增加人工 review、灰度与回滚预案。

### 可直接复述的例子

> AI 生成“禁用短链接”后，我不会只看按钮能不能点。我先用规格确认它没有误做恢复或删除；再检查 API 的 404 是否避免跨租户资源泄露；看 service 是否用条件更新或状态机保证重复/并发请求幂等；检查审计与缓存失效的边界；最后以两租户、并发双击、缓存命中和 API 超时写集成/E2E 用例。上线前确认日志、指标、灰度和回滚。测试绿只是证据之一，不是正确性的定义。

## 5. 高频追问与参考答案

### 🟢 Q1：AI 生成的前端页面和后端接口对不上，怎么办？

> 考察点：前后端契约、协作与调试。

我以 OpenAPI/JSON Schema 和示例响应作为单一事实来源，先确认差异是字段、枚举、错误码还是接口语义。前端 typed client 和 mock 都由契约生成或校验，后端增加 contract test；不让双方靠口头或 AI 猜字段。接口演进时做显式版本或向后兼容，不悄悄改变响应。

### 🟢 Q2：AI 写得很快，为什么还需要你做全栈？

> 考察点：工程责任与角色边界。

AI 可以快速生成局部实现，却不会天然知道业务不变量、组织权限、线上数据语义和发布风险。我的价值是将模糊问题定义成可验收边界，选择架构和验证手段，并对最终副作用负责。AI 提升产出速度，让我把时间投入到系统设计、故障边界和用户体验闭环。

### 🟡 Q3：AI 写的测试都通过了，你为什么还不信？

> 考察点：测试局限、独立验证、对抗性思维。
> Tradeoff：测试越全面，交付越慢；按变更风险分层投入。

AI 可能同时写实现和测试，测试只证明它满足自己假设的行为，未必覆盖真实规格。我会从验收和不变量导出独立反例：越权、并发、重复、超时、旧数据、版本兼容和回滚。低风险 UI 文案可依赖单测和截图；权限、金额、迁移和跨服务一致性必须增加集成测试、E2E、数据核对和人工 review。

### 🟡 Q4：AI 生成了一段 SQL 或数据库迁移，怎么确认不会出事故？

> 考察点：数据安全、性能与回滚。
> Tradeoff：不能承诺零风险，只能通过预演、限制和回滚缩小爆炸半径。

我会先确认读写范围、影响表/行和锁表/长事务风险；在代表性数据上检查执行计划、扫描量和耗时。迁移必须有版本、备份或回退方案，按 `expand → backfill → switch → contract` 演进，避免一次删除或改类型；上线采用小流量/分批数据校验。AI 可以生成草案和协助分析，但没有直接在生产执行的权限。

### 🔴 Q5：如果团队所有人都会用 AI，如何让整体质量变高而不是 bug 变多？

> 考察点：规模化工程体系。

我会把个人技巧沉淀成团队护栏：统一的规格/验收模板、版本化 API 契约、仓库内领域规则、可复用验证脚本、风险分级权限、CI 质量门和 bad case 回归集。比如 AI 常遗漏租户过滤或迁移回退时，不是下次再提醒，而是写成测试、lint 或发布检查。这样 AI 提升团队吞吐，质量由可执行的工程机制守住。

## 6. 容易失分的说法

| 不建议这样说 | 更好的表达 |
| --- | --- |
| “AI 基本把前端都写了。” | “AI 加速页面和样板实现；我通过 Contract、E2E 和用户状态验收整条链路。” |
| “我会写 Prompt，让它一次性生成整个系统。” | “我拆成可验收切片，先探索和计划，再实现、测试与独立 review。” |
| “测试过了就说明没问题。” | “测试是证据之一；权限、状态机、并发和线上副作用还需独立验证。” |
| “我什么都能做。” | “我对端到端交付负责，但高风险架构/发布会明确升级、评审和回滚。” |
| “前端是 AI 的事，后端是我的事。” | “前后端以用户旅程与 Contract 协作；我负责跨层一致性与可用性。” |

## 7. 最后的答题原则

不要把自己包装成“比 AI 更会写每一行代码的人”。更可信的定位是：**我是能让 AI 在工程边界内产生可靠结果的后端型全栈工程师。**

回答时尽量落到真实功能，以“规格 → Contract → 实现 → 独立验证 → 灰度/回滚”的顺序讲。面试官听到的就不再是“我会用 AI”，而是你具备完整的交付判断力。
