# AI Coding：后端工程师借助 Codex 做到全栈的实战路线

> 目标不是把后端工程师变成“什么都手写一点的人”，而是把你已有的后端优势——领域建模、接口契约、可靠性、可观测性和交付纪律——扩展成能独立交付一条完整用户链路的能力。AI Coding Agent 负责加速探索、实现、测试与 review；你仍要负责需求边界、架构取舍和最终验收。

## 0. 先换一个工作单位：从“写接口”到“交付一条用户旅程”

后端开发常以接口或服务为边界；全栈交付以用户能完成的事情为边界。

```text
用户旅程：登录 → 创建短链接 → 查看访问数据 → 修改/禁用链接
                 │
                 ▼
产品验收：页面可用、错误可理解、数据正确、权限正确、可观测、可部署
                 │
                 ▼
工程拆解：页面/交互 + API 契约 + 领域逻辑 + 数据模型 + 测试 + 监控
```

你的后端经验不是短板：它决定系统是否真的正确。前端、页面交互、样式和 E2E 测试是可以借助 Agent 快速补齐的层；但“哪个状态允许什么动作、失败怎样恢复、数据口径如何定义”必须由你定清楚。

## 1. 角色分工：人做判断，Agent 做可验证的执行

| 工作 | 你负责 | 适合交给 Codex / Agent |
| --- | --- | --- |
| 需求 | 用户目标、范围、不做什么、验收标准 | 追问歧义、整理成 PRD/场景清单 |
| 架构 | 领域边界、状态机、数据一致性、权限、关键取舍 | 对比方案、画图、查代码、做风险清单 |
| 前后端契约 | 资源模型、错误码、分页、鉴权、兼容策略 | 生成 OpenAPI 草稿、客户端类型、mock |
| 实现 | 关键不变量和复杂逻辑的最终判断 | CRUD、页面、表单、测试、迁移、重构 |
| 验证 | 什么才算正确、哪些风险不能接受 | 跑测试、浏览器验证、代码 review、生成证据 |
| 交付 | 是否合并/发布/回滚 | 整理 changelog、PR 描述、发布检查单 |

最重要的原则是：**不要给 Agent 一句“做个后台管理系统”。给它一个能验收的、纵向切开的用户故事。**

```text
坏任务：做一个订单后台。

好任务：管理员可在订单列表按状态和创建时间筛选；点击详情能看到退款状态；
接口返回分页、总数和稳定错误码；无权限用户返回 403；补齐 API、单测和一个浏览器 E2E 流程。
```

## 2. 后端到全栈：推荐的“纵向切片”路线

不要先学完 React、CSS、DevOps 再做项目。每一阶段交付一个完整、可运行的小切片。

| 阶段 | 做一个什么东西 | 强化什么能力 | Agent 最适合承担的部分 |
| --- | --- | --- | --- |
| 1. 单页 CRUD | 待办/链接/订单列表：查、增、改、删 | 前后端请求、表单、表格、错误态 | 脚手架、组件、表单校验、接口 client |
| 2. 真实业务切片 | 短链接：创建、跳转、禁用、基础统计 | 状态机、缓存、鉴权、迁移 | 管理端 UI、OpenAPI client、测试样例 |
| 3. 异步与可观测 | 导入任务/报表：提交、进度、失败重试 | MQ、任务状态、幂等、日志/指标 | 任务页、轮询/SSE、Dashboard、E2E |
| 4. 可交付产品 | 多租户知识库或轻量工单系统 | ACL、RAG、部署、审计、成本 | 页面细节、文档、回归测试、review |

每个阶段都从一个用户旅程开始，到一条 E2E 测试结束。这比让 Agent 一次生成一个巨大项目更稳，因为每一步都有真实反馈。

## 3. 一条功能的 AI-native 开发流程

下面是一条后端工程师可以稳定复用的流程。它对应 Codex 能做的探索、编辑、运行工具和本地 review，但把关键判断保留给人。OpenAI Docs 说明 Codex CLI 可在本地仓库中检查、修改、运行命令、设置权限，并在提交前运行独立 review。[OpenAI Docs：Codex CLI](https://learn.chatgpt.com/docs/codex/cli)

```text
需求卡 → 领域规则/验收 → API Contract → 可点的页面骨架
       → 后端垂直切片 → 单测/集成测 → 浏览器 E2E → Agent review → 人验收
```

### Step 1：先写一页“可交付规格”，再让 Agent 开工

规格不需要长，但至少要有：

```md
目标：管理员能禁用短链接，禁用后访问返回 404。
非目标：本次不做恢复、不做批量操作。
领域规则：只能禁用本租户的 ACTIVE 链接；重复禁用返回当前状态，不报错。
API：POST /api/links/{id}/disable → { id, status, disabledAt }。
验收：页面有二次确认；成功后列表状态更新；403/404 有明确提示；
      后端单测 + API 集成测试 + 一条浏览器 E2E 都通过。
风险：缓存失效与审计日志必须在同一业务动作中处理。
```

**小巧思 1：把“不做什么”写进规格。**它是控制 Agent 过度实现最廉价、也最有效的方法。

### Step 2：Explore，不要立刻改代码

先让 Agent 只读探索，并要求引用文件和证据：

```text
只读探索这个仓库，不要改文件。请找出：
1) 链接状态定义和状态迁移的位置；2) 当前鉴权/租户隔离入口；
3) 同类禁用操作的 API、前端页面和测试模式；4) 可能受影响的缓存或事件。
给出文件路径、关键符号、证据和最小改动计划；不确定项单列。
```

你检查它是否真正理解了代码路径，再批准计划。复杂任务可让一个子 Agent 专门探索、另一个只做 review；不要让多个 Agent 同时改同一组文件。

### Step 3：Contract first，让前端和后端并行

先确定 OpenAPI/JSON Schema、错误码和状态，而不是等后端做完再让 Agent 猜页面需要什么。

```text
领域模型/状态机
        ↓
OpenAPI / JSON Schema / 示例响应
   ┌────┴────┐
   ▼         ▼
Backend      Frontend
handler      typed client + mock + 页面
   └────┬────┘
        ▼
contract test + E2E
```

**小巧思 2：让前端先针对 mock 的契约完成可点击页面。**后端可独立实现同一契约，随后用 contract test 接上。这样你不会被“等接口好了才能做 UI”卡住。

### Step 4：一次只实施一个纵向切片

给 Agent 的实现任务要包含边界和验证命令：

```text
按已确认规格实现“禁用短链接”这一个纵向切片。
遵循现有的 handler/service/repository 分层与错误处理方式；不要重构无关代码。
先补后端失败测试，再实现；然后补前端确认弹窗与成功/失败状态。
运行 <单测命令>、<集成测试命令>、<前端检查命令>；报告修改文件、每项验证证据和未解决风险。
```

### Step 5：用两种视角验证

| 视角 | 你要验证什么 | 工具/方法 |
| --- | --- | --- |
| 后端视角 | 状态机、权限、幂等、事务、错误码、缓存/事件 | 单测、集成测试、DB/日志检查 |
| 用户视角 | 页面是否可操作、loading/empty/error 是否合理、状态是否同步 | 本地运行、浏览器、截图、E2E |

**小巧思 3：将“用户旅程”写成黄金路径和失败路径。**例如“禁用成功”“无权限”“已禁用重复提交”“后端超时”。让 Agent 以这四条路径写 E2E，而不是只测按钮存在。

### Step 6：让 Agent 做独立 Review，再由你做业务验收

```text
只做代码 review，不修改文件。重点检查：
1) 租户隔离和越权；2) 状态迁移、并发与幂等；3) API 兼容性；
4) 缓存/异步事件一致性；5) 前端错误态和可访问性；6) 测试是否只覆盖 happy path。
按严重等级给出可复现证据；无问题不要凑数。
```

OpenAI Docs 中的 Codex CLI 支持在未提交改动、commit 或 base branch 上进行不修改工作区的独立 review。[OpenAI Docs：Codex CLI](https://learn.chatgpt.com/docs/codex/cli)

## 4. 给后端工程师的全栈能力清单

不需要追求炫技；先掌握下面“能交付”的最小能力。

| 层 | 你应该能做什么 | 一个可靠的学习动作 |
| --- | --- | --- |
| 需求/交互 | 写用户旅程、状态、空态/错态、验收标准 | 先画 3～5 个页面状态，再写代码 |
| 前端 | 页面、表单、请求状态、路由、组件复用 | 从设计系统/现有组件库组装，不从零造组件库 |
| API | 契约、错误码、分页、版本兼容 | Schema 先行，生成 typed client 和 mock |
| 领域服务 | 状态机、权限、事务、幂等、缓存 | 把不变量写成测试和注释，而非只埋在实现里 |
| 数据 | migration、索引、数据修复、审计 | 每次 schema 改动都写升级/回退/校验计划 |
| 异步 | 任务、重试、死信、进度、可观测 | 给用户可见的任务状态，不让前端猜结果 |
| 交付 | CI、环境配置、日志/指标/trace、回滚 | 每个功能定义最低验证命令和一个 dashboard 查询 |

**你对全栈最有价值的贡献，不是 CSS 像设计师一样漂亮，而是让 UI 到数据的一整条路径可预测、可观察、可恢复。**视觉细节可以让 Agent 配合截图迭代；跨租户越权、重复扣款和错误口径不能靠“看起来没问题”。

## 5. 让仓库对 Agent 也“可读”：少而准的项目说明

Agent 的能力很大程度取决于它能否快速找到事实。OpenAI 关于 harness engineering 的案例强调：与其给一个巨大的说明书，不如给 Agent 一个小而稳定的入口和逐层可发现的信息；项目知识应当是版本化、可检索的系统记录。[OpenAI：Harness engineering](https://openai.com/index/harness-engineering/)

建议在仓库中维护这几类小文件：

```text
AGENTS.md                 # 入口：运行方式、边界、目录导航、必须验证项
docs/architecture.md      # 组件边界、调用链、关键取舍
docs/domain/*.md          # 状态机、核心术语、不变量、错误码
docs/runbooks/*.md        # 常见故障与验证/恢复步骤
openapi.yaml              # 前后端契约的单一事实来源
scripts/verify.sh         # 一条可重复的最小验证入口
```

`AGENTS.md` 适合写：如何运行、如何测试、禁止的改动、关键目录以及“遇到 X 去读哪个文档”。不适合塞入全部架构细节。

**小巧思 4：每修一个 Agent 容易犯的错，就把预防它的规则写进仓库并让 CI 校验。**例如 API 契约变更必须更新 OpenAPI；新增迁移必须有回退策略；新增 endpoint 必须有鉴权测试。让经验变成系统能力，而不是下一次 Prompt 再说一遍。

## 6. 适合练手的三个后端全栈项目

### 6.1 短链接管理台：最小但完整

```text
React/Next 管理台 → Go/Java API → MySQL
                    ├→ Redis（跳转/限流）
                    └→ 访问日志 → 异步聚合 → 统计页面
```

- 第一切片：创建、列表、跳转；
- 第二切片：禁用、租户隔离、审计；
- 第三切片：访问统计、异步聚合、图表；
- 重点：状态机、幂等、缓存失效、分页、图表数据口径。

### 6.2 异步导入与任务中心：最像企业系统

```text
上传 CSV → 校验/入库任务 → MQ/Worker → 进度与错误明细
     ↑                                      ↓
     └──────── 前端轮询或 SSE 任务中心 ──────┘
```

- 重点：任务状态、失败重试、幂等、部分成功、错误下载、权限、可观测性；
- 前端重点：进度、取消、失败详情、重新执行；
- Agent 很适合帮你生成测试数据、错误场景、管理端页面和 E2E。

### 6.3 内部知识助手：把后端、RAG 和产品闭环结合

```text
文档上传 → 解析/切块/索引 → ACL → 检索 + 引用回答
                                  ↑
                        管理台：来源、版本、重建、权限
```

- 重点：不要只做聊天框；做文档版本、chunk 来源、ACL、引用、重建任务和评测集；
- 可把 [agent开发.md](agent开发.md) 中的 RAG 排障漏斗实际做成 dashboard。

## 7. 一周一个小闭环的学习计划

| 周期 | 交付物 | 刻意练习 |
| --- | --- | --- |
| 第 1 周 | 一个 CRUD 用户旅程 + OpenAPI + E2E | 用 Agent 先 explore、再实现；学会看 diff 和测试证据 |
| 第 2 周 | 加鉴权、错误态、分页、状态机 | 从用户失败路径倒推 API 与页面设计 |
| 第 3 周 | 加异步任务、日志、metrics/trace | 让 Agent 根据日志定位一个自己制造的故障 |
| 第 4 周 | Agent review、部署、复盘文档 | 让 Agent 评审一次改动；把 bad case 写入 AGENTS/docs/测试 |

每周结束只问四个问题：用户能完成什么？失败时会怎样？如何证明数据正确？下次 Agent 如何更快、更少犯错？

## 8. 使用 Codex 的安全与效率边界

Codex 可在仓库中探索、编辑、执行本地命令，并允许按任务设置权限和 sandbox 边界；对陌生仓库先探索、对有副作用命令保留审批、对每个任务保留 Git checkpoint。详见 [OpenAI Docs：Codex CLI](https://learn.chatgpt.com/docs/codex/cli)。

- **小任务交互式做**：探索、debug、小修复；用同一会话连续追问，快速校正方向。
- **大任务拆成可验收子任务**：设计/探索、实现、测试、review 分开，避免一个超长 Prompt。
- **并行只用于独立工作**：一个 Agent 探索、一个审查可以；多个 Agent 同改同一文件不可以。
- **把权限当作产品能力**：默认只读；编辑、运行命令、访问网络、发布、删数据按风险逐级开放。
- **证据比自述重要**：要求输出修改文件、命令、测试结果、截图/日志与剩余风险；不要只接受“已完成”。
- **Git 是安全网，不是事后补救**：开始前和关键节点创建 checkpoint；高风险变更走 PR、CI、review 和可回滚发布。

## 9. 结尾：AI Coding 的真正升级点

AI 没有取消工程纪律，反而放大了它的价值。Agent 让实现速度变快后，稀缺的是：把模糊需求变成可验收规格、让仓库和系统可被理解、把正确性写进契约和测试、用证据决定是否交付。

先从一条小而完整的用户旅程开始。你会发现自己并不是在“学一点前端”，而是在练习以产品结果为边界的完整工程能力。
