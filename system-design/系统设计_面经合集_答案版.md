### 1. 如何设计一个秒杀系统？如何限流、削峰？

**答案：**

**系统架构：**

```
                    CDN
                     ↓
客户端 → 负载均衡 → API网关(限流) → 秒杀服务 → Redis → 数据库
                                    ↓
                                 消息队列
                                    ↓
                                 订单服务
```

**核心设计：**

| 阶段      | 策略             |
| ------- | -------------- |
| **前端**  | 按钮置灰、验证码、答题    |
| **网关**  | 限流、IP黑名单       |
| **服务层** | 内存预减库存、队列削峰    |
| **数据库** | Redis预扣库存、异步落库 |

**限流方案：**

```go
// 1. 令牌桶
limiter := rate.NewLimiter(1000, 2000)  // 1000 QPS, 桶容量2000
if !limiter.Allow() {
    return "系统繁忙"
}

// 2. 滑动窗口
func slidingWindowLimit(key string, limit int, window time.Duration) bool {
    now := time.Now().UnixNano()
    pipe := redis.Pipeline()
    pipe.ZRemRangeByScore(key, "0", strconv.FormatInt(now-window.Nanoseconds(), 10))
    pipe.ZAdd(key, redis.Z{Score: float64(now), Member: now})
    pipe.ZCard(key)
    pipe.Expire(key, window)
    results, _ := pipe.Exec()
    count := results[2].(*redis.IntCmd).Val()
    return count <= int64(limit)
}
```

**削峰方案：**

```go

func seckill(userID, productID string) {
    // 1. 参数校验、限流

    // 2. Redis预扣库存

    if stock < 0 {
        redis.Incr("stock:" + productID)  // 回滚

    // 3. 发送到消息队列
```

**答案：**

**表结构设计：**

```sql
-- 用户表
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50)

-- 关注关系表
CREATE TABLE follows (
    user_id BIGINT,
    follower_id BIGINT,
    PRIMARY KEY (user_id, follower_id)

-- 动态表（Feed）
CREATE TABLE feeds (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    content TEXT,
    created_at DATETIME,
    INDEX idx_user_time (user_id, created_at)
);

-- 时间线表（推模式）
CREATE TABLE timelines (
    user_id BIGINT,
    feed_id BIGINT,
    created_at DATETIME,
    PRIMARY KEY (user_id, created_at, feed_id)
);
```

**推拉模式选择：**

| 模式       | 写放大       | 读放大       | 适用   |
| -------- | --------- | --------- | ---- |
| **推模式**  | 高（写入所有粉丝） | 低         | 粉丝少  |
| **拉模式**  | 低         | 高（聚合关注的人） | 粉丝多  |
| **推拉结合** | 中         | 中         | 实际使用 |

**推拉结合策略：**

```go
func publishFeed(userID string, feed Feed) {
    // 1. 写入动态表
    db.Insert("feeds", feed)

    // 2. 获取粉丝列表
    followers := getFollowers(userID)

    // 3. 活跃粉丝推送，非活跃拉取
    for _, f := range followers {
        if isActiveUser(f) {
            redis.ZAdd("timeline:"+f, feed.CreatedAt, feed.ID)
        }
    }
}

func getTimeline(userID string) []Feed {
    // 1. 从Redis获取推送的
    pushed := redis.ZRevRange("timeline:"+userID, 0, 20)

    // 2. 拉取关注的大V的动态
    bigVFeeds := pullBigVFeeds(userID)

    // 3. 合并排序
    return merge(pushed, bigVFeeds)
}
```

### 4. 多个consumer只让一个消费，如何实现？

**答案：**

**Consumer Group机制（Kafka示例）：**

```
生产者 → Topic(3个分区) → Consumer Group
                          ├─ Consumer1 (处理分区0)
                          ├─ Consumer2 (处理分区1)
                          └─ Consumer3 (处理分区2)
```

**关键点：**

1. 同一Consumer Group中的消费者不会消费同一分区
2. 每个分区只会被组内一个消费者消费
3. 消费者数量不应超过分区数量

**Go实现（使用Sarama）：**

```go
config := sarama.NewConfig()
config.Consumer.Group.Rebalance.Strategy = sarama.BalanceStrategyRoundRobin

group, _ := sarama.NewConsumerGroup(brokers, "my-group", config)

handler := &ConsumerGroupHandler{}
for {
    group.Consume(ctx, []string{"topic"}, handler)
}

type ConsumerGroupHandler struct{}

func (h *ConsumerGroupHandler) ConsumeClaim(session sarama.ConsumerGroupSession, claim sarama.ConsumerGroupClaim) error {
    for msg := range claim.Messages() {
        // 处理消息
        session.MarkMessage(msg, "")
    }
    return nil
}
```

### 5. 如何保证消息不被重复消费？如何保证消息的顺序性？

**答案：**

**防止重复消费（幂等性）：**

| 方案          | 实现               |
| ----------- | ---------------- |
| **数据库唯一键**  | INSERT时利用唯一索引去重  |
| **Redis去重** | SETNX消息ID，已存在则跳过 |
| **业务幂等**    | 状态机，已完成的不再处理     |

```go
func consume(msg Message) error {
    // 1. Redis去重
    ok, _ := redis.SetNX(ctx, "msg:"+msg.ID, "1", time.Hour).Result()
    if !ok {
        return nil // 已处理
    }

    // 2. 处理业务
    if err := process(msg); err != nil {
        redis.Del(ctx, "msg:"+msg.ID)  // 处理失败，删除
        return err
    }

    return nil
}
```

**保证顺序性：**

| 方案       | 说明             |
| -------- | -------------- |
| **单分区**  | 同一分区内有序（牺牲并行度） |
| **业务分区** | 相同业务ID发到同一分区   |
| **版本号**  | 消费时检查版本，乱序则等待  |

```go
// 业务分区
func produce(orderID string, msg []byte) {
    partition := hash(orderID) % partitionCount
    producer.Send(topic, partition, msg)
}

// 版本号机制
func consume(msg Message) error {
    for {
        currentVersion := getVersion(msg.ID)
        if msg.Version == currentVersion + 1 {
            process(msg)
            setVersion(msg.ID, msg.Version)
            return nil
        }
        time.Sleep(100 * time.Millisecond)  // 等待前序消息
    }
}
```

### 6. 分布式事务有哪些解决方案？

**答案：**

| 方案        | 原理                 | 优点   | 缺点      |
| --------- | ------------------ | ---- | ------- |
| **2PC**   | 协调者统一提交/回滚         | 强一致  | 同步阻塞、单点 |
| **3PC**   | 增加PreCommit阶段      | 减少阻塞 | 网络分区问题  |
| **TCC**   | Try-Confirm-Cancel | 业务控制 | 代码侵入大   |
| **Saga**  | 事件驱动补偿             | 长事务  | 隔离性差    |
| **本地消息表** | 消息+定时任务            | 简单可靠 | 延迟      |
| **最终一致性** | 消息队列               | 解耦   | 最终一致    |

**TCC示例：**

```go
// Try阶段：预留资源
func try(orderID string) error {
    // 冻结库存
    db.Exec("UPDATE stock SET frozen = frozen + 1 WHERE product_id = ?")
    // 冻结余额
    db.Exec("UPDATE account SET frozen = frozen + 100 WHERE user_id = ?")
    return nil
}

// Confirm阶段：确认执行
func confirm(orderID string) error {
    db.Exec("UPDATE stock SET quantity = quantity - 1, frozen = frozen - 1")
    db.Exec("UPDATE account SET balance = balance - 100, frozen = frozen - 100")
    return nil
}

// Cancel阶段：取消预留
func cancel(orderID string) error {
    db.Exec("UPDATE stock SET frozen = frozen - 1")
    db.Exec("UPDATE account SET frozen = frozen - 100")
    return nil
}
```

### 7. CAP定理是什么？两阶段提交、三阶段提交的区别？

**答案：**

**CAP定理：**
分布式系统不可能同时满足以下三个特性：

- **C（Consistency）**：一致性，所有节点数据相同
- **A（Availability）**：可用性，每个请求都能响应
- **P（Partition Tolerance）**：分区容错性，网络分区时仍能运行

**由于P必须保证，实际选择是CP或AP：**
| 选择 | 特点 | 系统 |
|------|------|------|
| **CP** | 保证一致性，可能不可用 | ZooKeeper、etcd、Redis Cluster |
| **AP** | 保证可用性，最终一致 | Cassandra、Eureka |

**2PC vs 3PC：**

| 特性       | 2PC              | 3PC                              |
| -------- | ---------------- | -------------------------------- |
| **阶段**   | Prepare → Commit | CanCommit → PreCommit → DoCommit |
| **阻塞**   | 协调者故障时阻塞         | 超时可继续                            |
| **数据一致** | 可能不一致            | 改善但未解决                           |

**2PC流程：**

```
协调者         参与者A    参与者B
   |──Prepare───>|           |
   |──Prepare────────────────>|
   |<──Yes───────|           |
   |<──Yes───────────────────-|
   |──Commit────>|           |
   |──Commit─────────────────>|
```

### 8. 如何设计分布式锁？

**答案：**

**实现方式对比：**

| 方式            | 优点      | 缺点     |
| ------------- | ------- | ------ |
| **数据库**       | 简单      | 性能差、单点 |
| **Redis**     | 高性能     | 主从切换丢锁 |
| **ZooKeeper** | 强一致、可靠  | 性能较差   |
| **etcd**      | 强一致、高性能 | 学习成本   |

**Redis实现（Redlock）：**

```go
// 单节点版本
func Lock(key, value string, ttl time.Duration) bool {
    return redis.SetNX(ctx, key, value, ttl).Val()
}

func Unlock(key, value string) bool {
    script := `
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end`
    return redis.Eval(ctx, script, []string{key}, value).Val().(int64) == 1
}

// Redlock（多节点）
func RedlockLock(key, value string, ttl time.Duration) bool {
    n := len(redisClients)
    quorum := n/2 + 1
    successCount := 0

    for _, client := range redisClients {
        if client.SetNX(ctx, key, value, ttl).Val() {
            successCount++
        }
    }

    return successCount >= quorum
}
```

### 10. DDD和三层架构对比？

**答案：**

**三层架构：**

```
表现层(Controller)
       ↓
业务层(Service)
       ↓
数据层(DAO/Repository)
```

**DDD架构：**

```
用户接口层(Controller/API)
       ↓
应用层(Application Service)
       ↓
领域层(Domain)  ←── 核心业务逻辑
       ↓
基础设施层(Infrastructure)
```

| 对比       | 三层架构     | DDD            |
| -------- | -------- | -------------- |
| **关注点**  | 技术分层     | 业务领域           |
| **业务逻辑** | Service层 | 领域层（实体、值对象）    |
| **数据库**  | 直接操作     | 通过Repository抽象 |
| **复杂度**  | 简单       | 较复杂            |
| **适用场景** | CRUD为主   | 复杂业务           |

**DDD核心概念：**

- **实体（Entity）**：有唯一标识的对象
- **值对象（Value Object）**：无标识，通过属性定义
- **聚合（Aggregate）**：一组相关对象的集合
- **聚合根（Aggregate Root）**：聚合的入口
- **领域服务（Domain Service）**：跨实体的业务逻辑
- **仓储（Repository）**：聚合的持久化抽象

### 11. 为什么使用JWT，不使用session和cookie？

我选择 JWT，不是因为它一定比 session 更高级，而是因为它更适合前后端分离和微服务场景。Session 模式下，服务端要维护会话状态，通常要有共享存储，比如 Redis；而 JWT 是无状态的，请求里带上 token 后，各服务只要验证签名就能识别用户身份，减少了中心化会话依赖。另一方面，浏览器跨域场景下 cookie 的配置会更麻烦，比如 SameSite、credentials、跨域传递这些问题，而 JWT 放在 Authorization 头里通常更直接。  
当然 JWT 也有代价，比如主动注销、封禁、立即失效没 session 那么方便，所以实际项目里一般会配合短期 access token、refresh token，必要时再加黑名单机制。”

### 12. 四种限流算法怎么选？

**答案：**

- 固定窗口最简单，但窗口切换点容易出现瞬时双倍流量。
- 滑动窗口更平滑，统计更准确，但实现和存储成本更高。
- 漏桶适合把流量整形成稳定速率，令牌桶适合“整体限速，但允许一定突发”，工程里最常见的通常是令牌桶。
- 所以这题最好的回答不是背定义，而是说清楚：**要不要允许突发、要不要绝对平滑、实现成本能不能接受**。

### 13. 消息队列出现消息堆积时，怎么排查和处理？

**答案：**

- 我会先判断是“生产突然变快了”，还是“消费变慢了”。如果是后者，还要继续拆：是消费者挂了、下游接口慢了，还是分区不够、单条消息太重。
- 排查时重点看 backlog、消费速率、异常重试、下游响应时间和消费者线程状态。
- 临时止血的手段通常有：扩消费者、扩分区、批量消费、非核心链路先降级，必要时把特别慢的下游先隔离出去。
- 根因治理则是：提升消费幂等、减少单条消息耗时、做好重试和死信队列，避免一条坏消息把整个消费链路拖死。

### 14. 如何保证消息不丢？为什么“只靠 MQ”做不到绝对不丢？

**答案：**

- 真正的不丢是端到端问题，至少要把生产者、Broker、消费者三段都考虑进去。
- 生产者侧要有发送确认和重试，Broker 侧要有持久化和副本，消费者侧要在业务真正处理成功后再确认，并且做好幂等。
- 但即便这样，也很难说“绝对 0 丢失”，因为还会有应用崩溃、网络分区、人为误操作这些问题。
- 所以工程上更准确的说法是：**尽量做到可恢复、可重试、可补偿**，而不是轻易承诺绝对不丢。

### 15. 高热活动或热点帖子流量暴涨时，如何防止主链路被打垮？如果二级消费者阻塞怎么办？

**答案：**

- 先做热点隔离：热点数据单独缓存、提前预热、静态化能静态化，入口再配合限流、排队、削峰，避免所有请求直接打到数据库。
- 核心链路和非核心链路一定要拆开。比如主流程只保证发帖/下单成功，积分、通知、推荐这些二级逻辑走异步，不要互相拖累。
- 如果二级消费者阻塞，我会优先保证主链路，把慢消费者独立 consumer group、独立 topic 或单独线程池，不让它反压核心业务。
- 面试里一句话概括就是：**主链路保核心成功，次链路异步化 + 隔离 + 可降级**。

### 16. 支付 / 订单状态机怎么设计？

**答案：**

状态机的重点是“状态可枚举、流转受约束、重复事件幂等”。

- 常见状态：待支付、支付中、支付成功、支付失败、已取消、已退款、已关闭。
- 每个外部事件只能触发合法流转，例如待支付可以变支付成功或取消，支付成功不能再变待支付。
- 支付回调可能重复到达，所以要用业务单号、支付单号、唯一索引和状态判断保证幂等。
- 回调处理要验签、校验金额、校验商户订单号，再更新本地状态。

### 17. 如何防止重复支付或重复提交？

**答案：**

- 前端按钮置灰只能减少误触，不能作为核心保证。
- 后端要用请求号、业务唯一键、支付单唯一索引、状态机判断保证幂等。
- 对外部支付回调，要以支付平台交易号和本地订单号做唯一约束。
- 如果引入分布式锁，也只能作为并发互斥辅助手段，最终仍要靠状态机和唯一约束兜底。

### 18. 分布式事务有哪些常见方案？

**答案：**

- 2PC / XA：一致性强，但阻塞和性能成本高。
- TCC：Try / Confirm / Cancel，业务侵入强，但控制力高。
- Saga：长事务拆成多个本地事务，每步失败后执行补偿。
- 本地消息表 / 事务消息：本地事务和消息投递绑定，再由消费者最终一致处理。
- 最大努力通知：适合支付回调、通知类场景，靠重试和对账兜底。

面试里不要只背名词，要说明选择取决于一致性要求、业务可补偿性、链路时延和实现成本。

### 19. DDD 的核心是什么？

**答案：**

DDD 的核心不是多套几层目录，而是围绕业务领域建模，把复杂业务规则放到领域模型里。

- 通过统一语言让业务和技术对同一概念达成一致。
- 通过限界上下文划清模型边界，避免一个概念在不同业务里混用。
- 通过实体、值对象、聚合、领域服务、仓储表达业务规则。
- 适合复杂业务，简单 CRUD 不一定需要重 DDD。

### 20. 配置热更新如何避免新实例 miss 消息和错误配置直发线上？

**答案：**

- Pub/Sub 这类通知机制不保证离线补发，新实例启动时要主动拉取全量配置。
- 配置中心要持久化配置版本，实例收到通知后按版本拉取，而不是只依赖消息内容。
- 错误配置要通过校验、灰度、审批、回滚版本和生效范围控制来治理。
- 高风险配置最好支持分环境、分租户、分机器灰度，并能快速回滚。

### 21. Feed 流的推、拉、推拉结合模式如何实现？

**答案：**

以“用户发布一条动态，粉丝看到时间线”为例：

- **推模式（fan-out on write）**：作者发帖后，把动态 ID 异步写入每个粉丝的收件箱 `inbox:{fanoutUserId}`。读时间线只需读取自己的 inbox 再批量取详情，读快；但大 V 发帖会产生海量写放大。
- **拉模式（fan-out on read）**：只保存作者自己的发件箱 `outbox:{authorId}`。用户打开首页时，查询关注列表，分别取每位作者最近动态后按时间或评分归并。写轻；但关注多的用户读放大明显。
- **推拉结合**：普通作者的粉丝规模可控，采用推；大 V 只写自己的 outbox，读者拉取时再合并。用粉丝数阈值、动态热度和在线活跃度决定走哪条路径。

一个可落地的混合流程：

```text
作者发布 -> DB / 内容存储落库 -> Kafka: feed_created
    -> 普通作者分发消费者：批量写粉丝 inbox（可重试、按 event_id 幂等）
    -> 大 V：只维护作者 outbox

用户读首页 -> 读 inbox
    -> 取关注大 V 的 outbox
    -> 合并、去重、按时间/推荐分排序 -> 分页返回
```

工程细节：inbox 通常只保存 `feed_id`、时间和排序字段，内容详情单独存并缓存；分发要异步化且按批次处理；关注/取关、删除动态需要可重放事件或版本号来修正收件箱；分页应使用游标而不是深度 `offset`；热门作者和热点内容还需本地缓存、限流与降级。

**面试回答：**

> 推模式写放大、读快，适合普通用户；拉模式写轻、读放大，适合大 V；生产上通常混合。用户发帖先可靠落库再发事件，普通用户的动态异步 fan-out 到粉丝收件箱，大 V 只维护发件箱；读首页时把 inbox 和大 V 的 outbox 合并排序。这样避开了大 V 的写爆炸，同时保持普通用户读路径足够快。

### 22. 用户量从 100 万增长到 1 亿，架构如何演进？

**答案：**

不要只回答“分库分表、加缓存”。架构演进应围绕可观测数据逐层定位瓶颈，并让每一阶段保留下一阶段的扩展边界：

| 阶段 | 重点动作 | 需要提前留下的能力 |
| --- | --- | --- |
| 100 万级 | 单体或模块化服务、主从/读写分离、索引优化、Redis 缓存、监控告警 | 无状态服务、配置中心、请求 ID、限流与降级 |
| 千万级 | 按领域拆服务，CDN 和静态化，异步化非核心链路，热点隔离，MQ 削峰 | 幂等、重试、死信、容量压测、全链路观测 |
| 亿级 | 按业务和数据热点分片，独立库存/订单/搜索等核心域，多机房容灾，分级缓存 | 路由层、全局 ID、数据迁移方案、跨分片查询治理、灾备演练 |

演进顺序一般是先做低风险收益项：慢 SQL 和索引、读写分离、缓存命中率、异步化、扩容；确认单库或单表已经成为长期瓶颈后，再做分库分表。服务拆分也不是按技术名词拆，而是按业务边界、团队边界和故障隔离来拆。核心下单/支付链路要比推荐、通知、报表有更高的资源优先级和独立限流/线程池，避免次要功能拖垮主链路。

### 23. 分库分表时 sharding key 怎么选？数据迁移怎么做？

**答案：**

分片键的第一原则是贴合主要访问路径，其次才是均匀分布。订单表如果最常按用户查历史订单，可选 `user_id`；若最常按商家处理订单，可选 `merchant_id`；库存表通常按 `sku_id` 聚合。不能只看哈希是否均匀，还要评估热点、跨分片查询、扩容、关联关系和数据生命周期。

常见路由方式：

- `hash(user_id) % N`：分布较均匀，但直接扩容会导致大面积迁移；
- 一致性哈希或虚拟分片：扩容迁移范围更小；
- 范围分片：利于按时间归档和范围查询，但容易形成时间热点；
- 目录/路由表：灵活但多一次路由查询，需要高可用和缓存。

在线迁移以“先扩容、双写/变更同步、回填、校验、切流、保留回滚窗口”为主线：

```text
1. 创建新分片并上线按版本路由能力
2. 从旧库全量回填历史数据
3. 用 binlog CDC 持续同步回填期间的增量
4. 对新旧库做行数、校验和与抽样业务校验
5. 小流量灰度读新库 -> 双读比对 -> 全量切流
6. 保留旧库只读与回滚窗口，确认稳定后再下线
```

迁移期间，每条写请求要带稳定的路由版本或由路由层统一决策，避免同一条数据写到两个不一致位置；跨分片事务优先通过订单状态机、事务消息和补偿实现最终一致，而不是把分布式强事务当默认方案。

### 24. 用 Go 实现一个高并发限流器，令牌桶和漏桶怎么选？

**答案：**

先用“门票”理解令牌桶：桶里有若干张门票，请求进来要拿一张；系统每秒补固定数量的门票，但桶满了就不再补。这样既能限制平均速度，也允许短时间内把桶里积攒的门票一次用掉。

例如商品详情接口规定“平均每秒最多 5 次，但允许用户刚打开页面时连续点 10 次”：桶最多放 10 张门票，每秒补 5 张。用户连续请求 10 次都能通过；第 11 次因为没有门票被拒绝；等 1 秒后又补回 5 张。

下面是教学版的 Go 实现。为方便理解，按整秒补票；生产环境可以改为按毫秒精确计算。

```go
type TokenBucket struct {
	mu           sync.Mutex
	tokens       int       // 当前剩余门票
	maxTokens    int       // 桶最多放多少张门票
	addPerSecond int       // 每秒补多少张门票
	lastAddTime  time.Time // 上次补票的时间
}

func (b *TokenBucket) Allow() bool {
	b.mu.Lock()
	defer b.mu.Unlock()

	now := time.Now()
	passedSeconds := int(now.Sub(b.lastAddTime).Seconds())
	if passedSeconds > 0 {
		b.tokens += passedSeconds * b.addPerSecond
		if b.tokens > b.maxTokens {
			b.tokens = b.maxTokens
		}
		b.lastAddTime = now
	}

	if b.tokens == 0 {
		return false
	}
	b.tokens--
	return true
}
```

这里的 `Mutex` 是为了防止两个请求同时看到“还有最后一张票”，然后都通过。真实服务里不会只维护一个桶，而是按用户 ID、IP 或接口分别维护；否则一个恶意用户会耗尽所有正常用户的额度。

漏桶则更像银行的单窗口：所有请求先排队，窗口每秒只处理固定数量。它适合保护很慢的下游，例如数据库写入或第三方支付。但队列必须设上限，满了就明确拒绝；无限排队只会把“请求太多”变成“用户等很久后超时”。

**完整例子：**秒杀开始的一秒内来了 3 万请求，而订单数据库只能稳定处理 5000 次写入。

1. 网关先给每个用户发门票，重复点击和脚本请求会被拦在入口。
2. 通过的请求进入一个最多容纳 1 万任务的队列，订单服务按自身能力慢慢处理。
3. 队列满后直接提示“人数过多，请稍后重试”，而不是继续接收请求。
4. 如果服务部署多台，单机内存中的门票无法限制全站总量；这时把总配额放到网关或 Redis，由所有机器共同扣减。

**面试回答：**

> 令牌桶解决“谁能进来”：平均速度受控，但允许少量突发；漏桶解决“进去以后按多快处理”：把下游处理速度压平。秒杀里我会先按用户做令牌桶，再给订单服务一个有上限的排队区。队列满就快速拒绝，不能无限堆积。单机实现保护本机，多实例的全站配额再交给网关或 Redis 统一控制。

### 25. 百万级 Goroutine 的进程内存暴涨，如何排查？

**答案：**

先明确一点：Goroutine 比线程轻，但不是免费。每个 Goroutine 至少有自己的栈、调度信息和它引用的对象；100 万个 Goroutine 即使每个只占很少内存，累计也会很大。更常见的问题不是“业务确实需要 100 万个活跃协程”，而是连接断了、任务结束了，但协程没有退出，数量不断累积。

排查可以按“先看数量，再看谁没退出，最后看它占住了什么”进行：

1. 每隔一分钟记录 `runtime.NumGoroutine()` 和进程内存。正常流量下降后，协程数也应回落；只涨不回落就是泄漏信号。
2. 打开 pprof 后抓 goroutine 快照。它相当于给所有协程拍照：相同调用栈出现几十万次，说明这批协程都卡在同一个地方。
3. 再抓 heap 快照，确认内存是协程栈、channel 里的积压消息，还是协程闭包一直引用着大对象。
4. 对比故障前后的两份快照，比单独看一份更容易确认“到底哪一类协程在持续增加”。

**完整例子：**长连接服务为每个连接启动读、写、心跳三个 goroutine。客户端断网后：

- 读协程因为网络错误退出；
- 写协程还在向一个没人接收的 channel 发送消息，因此一直卡住；
- 心跳协程还在运行，ticker 也没有停止。

连接不断重连，旧连接留下两个协程。10 万次重连后，虽然在线用户没有增加，Goroutine 却从 10 万涨到几十万甚至百万，内存和调度开销自然持续上涨。pprof 快照里会看到大量相同的 `chan send` 或 ticker 等待调用栈。

修复时，让同一连接的协程共享一个 `ctx`：连接关闭时调用 `cancel()`，每个协程都同时监听“有任务可做”和“连接已取消”。ticker 要显式停止：

```go
func heartbeat(ctx context.Context) {
	ticker := time.NewTicker(time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-ticker.C:
			sendPing()
		case <-ctx.Done():
			return
		}
	}
}
```

向 channel 发送消息也不能无限等待，应同时监听 `ctx.Done()`。批量任务不要一次启动几十万个 goroutine，而是固定数量的 worker 从任务队列领取工作；这样任务再多，同时存在的协程数量也有上限。

**面试回答：**

> 百万 Goroutine 先不要急着调 GC，我先判断它们是不是应该存在。先看协程数是否随流量回落，再用 goroutine 快照找大量重复的卡点，用 heap 快照确认它们持有什么对象。长连接里最常见的是连接断了，但写协程、心跳协程没有退出；我会用同一个 context 统一取消、停止 ticker，并让 channel 操作可以因取消而返回。批任务则用固定 worker 数量，防止任务量直接变成协程数量。

### 26. 如何设计一个支撑 10 万 QPS 的路径规划服务？

**答案：**

先确认边界：10 万 QPS 是全局还是单城市，目标 p99、实时路况时效、地图更新频率、是否有货车限行或多途经点等个性化约束。不同答案会导致完全不同的容量和缓存设计。

```text
客户端 -> Gateway（鉴权、限流、城市路由）
       -> 区域路径规划集群（无状态横向扩容）
       -> 静态路网快照 + 实时路况 Overlay
       -> 本地/分布式路径缓存

地图编辑/路况流 -> Kafka -> 区域状态服务 -> 版本化快照与 Overlay
```

- 静态道路拓扑按城市或地理网格分片，版本化后加载到本地内存或 mmap；路径引擎按区域横向扩容。
- 实时路况通过 Kafka 更新到对应区域的内存 Overlay，不每次请求都查数据库。
- 使用分层/预处理算法，例如主干路索引、Contraction Hierarchies 或 MLD，把在线搜索限制在局部区域和少量候选路径。
- 缓存 key 至少包含起终点网格、出发时间桶、`map_version` 和 `traffic_version`；命中旧版本不能直接返回。
- 热点城市独立资源池；依赖或路况流异常时可降级为静态路况、较粗路线或短 TTL 缓存结果。

**例子：**早高峰北京到上海的跨城路线请求非常集中。入口先按城市与网格路由，命中“起点网格 + 终点网格 + 5 分钟时间桶”的缓存；未命中才进入路径引擎。事故事件只更新受影响区域的 traffic overlay 并递增 `traffic_version`，相关缓存自然失效，不需要全量清空。这样热点请求主要在缓存层完成，路径引擎只处理长尾和个性化请求。

**面试回答：**

> 10 万 QPS 的关键不是单纯加机器，而是区域分片、静态路网本地化、实时路况流式 Overlay、版本化缓存和热点隔离。读链路尽量不查 DB；在线算法只做必要的局部搜索，热点 OD 对走缓存。我要持续看 p99、缓存命中率、路况版本延迟、单城市流量倾斜和路线成功率，并准备静态路况降级。

### 27. gRPC 的流控机制是什么？服务端处理慢时，客户端怎样不被打爆？

**答案：**

gRPC 建在 HTTP/2 上，HTTP/2 有连接级和 Stream 级 flow control。接收方消费数据后通过 `WINDOW_UPDATE` 归还窗口；窗口耗尽时发送方会被阻塞，因此它能提供传输层背压。

但 HTTP/2 流控不等于“业务已处理完成”。服务端框架可能已从网络读入消息，而业务 handler 仍在排队，所以还需要应用层保护：

- **服务端**：限制每个方法的并发数和队列长度；满载时尽快返回 `RESOURCE_EXHAUSTED`，不要无限堆队列。设置最大消息大小、最大并发 Stream、deadline，并隔离慢依赖。
- **客户端**：每个调用都带 deadline；限制 in-flight 请求数；重试只用于幂等请求，并使用指数退避和抖动。收到 `RESOURCE_EXHAUSTED` 或超时后要退避，不要立即重试。
- **流式 RPC**：服务端每次 `Send`、客户端每次 `Recv` 都要监听 `ctx.Done()`；若业务要求“处理一条再发下一条”，设计应用层 ACK/credit，不能只依赖 HTTP/2 窗口。

**例子：**路线服务向推荐服务发 gRPC server stream，每秒可推 5000 条路况事件，但推荐服务只能处理 1000 条。服务端设置最大并发 stream 和每个订阅的有界队列，队列满时丢弃过期的中间路况，只保留最新版本；客户端限制同时订阅数，并在 `RESOURCE_EXHAUSTED` 后指数退避。这样慢消费者只影响自身，不会撑满发送端内存。

**面试回答：**

> HTTP/2 的 connection 和 stream window 提供基础背压，但我不会把它当成业务流控。服务端要有并发上限、有界队列、deadline 和快速拒绝；客户端要限制 in-flight、设置超时、只对幂等调用退避重试。流式调用还要有 ctx 取消和业务 ACK/credit，才能在慢消费者场景下避免内存和重试风暴。

### 28. 分布式系统中，如何保证地图数据最终一致性？

**答案：**

最终一致性不是“发一条 MQ 就结束”，而是可靠投递、顺序/版本、消费幂等、版本发布和对账的闭环。地图编辑数据以主库为事实源，实时路况以事件流为事实源；两类数据都要显式带版本。

```text
地图编辑事务：主库更新 + Outbox 事件同一事务提交
  -> CDC / Relay 投递 Kafka
  -> 索引、缓存、搜索、路径引擎分别消费
  -> 按 feature_id + version 幂等更新
  -> 构建完成后原子切换 map_version
```

- Outbox/CDC 解决“数据库已提交但消息没发出”的双写问题。
- Kafka 按 `feature_id` 分区，保证同一道路要素的事件顺序；消息包含 `event_id`、`feature_id`、`version`、操作类型和时间。
- 消费者用去重表或唯一约束去重，只接受更高版本；删除使用 tombstone，避免旧消息把已删除道路重新写回。
- 地图索引构建完成后通过 manifest/版本指针原子发布，读服务在一个请求内固定使用同一 `map_version`，不能读到半新半旧数据。
- 失败事件进入重试/死信队列；定时用主库快照与索引、缓存、下游数据做行数、版本和抽样路径对账。

**例子：**一条道路在 10:00 被封闭，主库把 `road_123` 更新为 `version=42`，并写入 Outbox。CDC 投递 Kafka 后，路径引擎先构建带 `version=42` 的区域 overlay，校验成功才切换版本指针。重复消息因为版本相同被忽略；若旧的 `version=41` 迟到，也会被版本比较丢弃。直到新版本发布前，用户仍会读旧快照，但不会读到一半新、一半旧的路线数据。

**面试回答：**

> 我会以主库和版本化事件为事实依据：主库更新与 Outbox 同事务提交，CDC 可靠投递 Kafka；消费者按要素 ID 保序、按事件 ID 去重、按版本单调更新；索引和缓存按 map_version 原子发布。失败走重试、死信和对账。这样允许短暂读旧数据，但保证最终收敛，并避免重复、乱序和半版本发布。
