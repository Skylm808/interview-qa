## 第一部分：高并发保护的基本功

这一部分先讲系统设计题反复使用的基础能力。可以把它们理解成一条完整的防线：

```text
请求进入
  -> 限流：超过系统容量的请求不要继续进入
  -> 隔离：不同接口、租户或依赖不要互相拖垮
  -> 超时：一次调用最多等多久
  -> 重试：只对短暂故障做少量、有退避的重试
  -> 熔断：下游持续失败时暂时停止调用
  -> 降级：核心功能继续工作，非核心功能返回简化结果
```

它们解决的问题不同，不能互相替代。限流处理“流量太多”，熔断处理“下游已经不健康”，降级决定“出故障后返回什么”，隔离限制“故障能影响多大范围”。

### 1. 面对高并发，为什么不能只靠加机器？应该先做什么？

**难度：初级**

先确定系统的容量上限，再谈方案。假设订单服务有 20 个实例，每个实例稳定处理 500 QPS，那么应用层大约能处理 1 万 QPS；但数据库只能稳定完成 6000 次写入，整条链路的上限仍然是 6000 QPS。继续增加订单服务实例，只会让更多请求同时争抢数据库连接。

高并发保护通常按以下顺序考虑：

1. **算清容量**：看峰值 QPS、p99、CPU、连接池、数据库写入能力和 MQ 消费速度。
2. **入口限流**：把超过容量的流量尽早拒绝，避免请求进入系统后才超时。
3. **核心与非核心拆开**：创建订单是核心；积分、推荐、短信可以异步或降级。
4. **保护依赖**：为数据库、Redis、第三方接口分别设置并发上限、超时和熔断。
5. **保证可恢复**：写操作要幂等，异步任务要能重试、补偿和对账。

**例子：**直播开始后流量从 3000 QPS 突然升到 2 万 QPS。网关只放行订单链路能承受的 6000 QPS；订单创建成功后写入 Kafka，积分和短信异步处理；推荐服务故障时直接不返回推荐信息。这样用户可能看不到推荐，但下单能力仍然可用。

**面试回答：**

> 高并发不是简单加机器，因为系统容量由最慢的共享资源决定。我会先通过压测确认应用、连接池、缓存、数据库和下游各自的容量，再在入口限流，拆分核心与非核心链路，并给依赖加超时、隔离和熔断。最后用幂等、异步、补偿保证系统在过载后还能恢复。

### 2. 固定窗口、滑动窗口、令牌桶和漏桶怎么选？如何用 Go 实现？

**难度：中级**

先用生活中的例子区分四种算法：

| 算法 | 怎么理解 | 优点 | 主要问题 | 适合场景 |
| --- | --- | --- | --- | --- |
| 固定窗口 | 每分钟最多 100 次 | 最简单 | 分钟交界处可能瞬间通过 200 次 | 后台接口、低成本粗限流 |
| 滑动窗口 | 始终统计最近 60 秒 | 比固定窗口准确 | 需要保存更多时间片或请求记录 | 登录、短信等精确配额 |
| 令牌桶 | 先拿票，有票才能进入 | 限制平均速率，同时允许小突发 | 下游若要求绝对匀速仍可能被瞬时冲击 | API 网关、用户/IP 限流 |
| 漏桶 | 请求先排队，再匀速流出 | 输出速度稳定 | 队列会增加等待时间，满后必须拒绝 | 数据库写入、慢第三方接口 |

#### 线程安全的教学版令牌桶

假设平均每秒发 5 张票，桶最多存 10 张。空闲两秒后桶里能积累 10 张票，所以短时间可以连续通过 10 个请求；长期平均速度仍然不超过每秒 5 个。

```go
type TokenBucket struct {
	mu       sync.Mutex
	rate     float64   // 每秒补多少个令牌
	capacity float64   // 桶容量，决定允许多大突发
	tokens   float64
	last     time.Time
}

func NewTokenBucket(rate, capacity int) *TokenBucket {
	now := time.Now()
	return &TokenBucket{
		rate:     float64(rate),
		capacity: float64(capacity),
		tokens:   float64(capacity),
		last:     now,
	}
}

func (b *TokenBucket) Allow() bool {
	b.mu.Lock()
	defer b.mu.Unlock()

	now := time.Now()
	// 按实际经过的时间补票，不需要额外启动定时 goroutine。
	b.tokens += now.Sub(b.last).Seconds() * b.rate
	if b.tokens > b.capacity {
		b.tokens = b.capacity
	}
	b.last = now

	if b.tokens < 1 {
		return false
	}
	b.tokens--
	return true
}
```

`Mutex` 保证多个 goroutine 不会同时拿走最后一个令牌。这个桶只保护当前进程；服务有 20 个实例时，全局配额会被放大 20 倍。全局限流通常放在 API 网关，或者用 Redis + Lua 原子扣减；本地令牌桶仍可作为实例级的最后一道保护。

#### 有界队列实现漏桶效果

漏桶不一定要真的计算“水位”。工程上常用“有界队列 + 固定速率消费者”实现：提交请求只负责入队，后台每个时间间隔取一个任务。队列满时立即拒绝，不能无限等待。

```go
type Job func()

type LeakyBucket struct {
	queue chan Job
	tick  *time.Ticker
}

func NewLeakyBucket(queueSize int, perSecond int) *LeakyBucket {
	return &LeakyBucket{
		queue: make(chan Job, queueSize),
		tick:  time.NewTicker(time.Second / time.Duration(perSecond)),
	}
}

func (b *LeakyBucket) Submit(job Job) bool {
	select {
	case b.queue <- job:
		return true
	default:
		return false // 队列已满，快速失败
	}
}

func (b *LeakyBucket) Run(ctx context.Context) {
	defer b.tick.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-b.tick.C:
			select {
			case job := <-b.queue:
				job()
			default:
			}
		}
	}
}
```

**例子：**订单入口允许少量突发，所以使用令牌桶：平均 5000 QPS，桶容量 8000。数据库写入只能稳定处理 3000 QPS，因此通过限流的请求进入有上限的队列，再按稳定速度消费。入口令牌桶负责“谁能进”，有界队列负责“按多快处理”。

生产环境不要只看“被拒绝了多少请求”，还要监控当前 QPS、限流率、队列长度、排队时间和最老任务年龄。排队时间已经超过请求 deadline 时，即使队列还有位置也应该拒绝。

**面试回答：**

> 需要允许小突发时用令牌桶，需要把下游输入压成稳定速率时用漏桶；固定窗口适合简单配额，滑动窗口适合更准确的时间范围统计。单机桶保护当前实例，全局配额应放到网关或 Redis。所有排队都必须有长度和等待时间上限，满了就快速失败。

### 3. 熔断是什么？如何用 Go 写一个容易理解的熔断器？

**难度：中级**

熔断器类似家里的空气开关。连续调用下游都失败时，继续请求只会占满 goroutine、连接池并触发更多重试，所以先“断开”一段时间，直接返回失败或降级结果。冷却时间结束后，放少量探测请求；探测成功再恢复，失败则继续断开。

常见三个状态：

- `Closed`：正常调用，并统计失败；
- `Open`：直接拒绝，不再访问故障下游；
- `Half-Open`：冷却结束后允许少量请求探测。

下面用一个简化版说明核心逻辑。它按连续失败次数熔断，适合学习；生产中通常还要按时间窗口统计失败率、限制半开探测并发，并使用成熟组件。

```go
type Breaker struct {
	mu            sync.Mutex
	failures      int
	threshold     int
	openUntil     time.Time
	coolDown      time.Duration
	probeInFlight bool // 半开状态只允许一个探测请求
}

func (b *Breaker) Allow() bool {
	b.mu.Lock()
	defer b.mu.Unlock()

	if b.openUntil.IsZero() {
		return true // Closed
	}
	if time.Now().Before(b.openUntil) || b.probeInFlight {
		return false // Open，或者已经有探测请求
	}

	b.probeInFlight = true // Half-Open
	return true
}

func (b *Breaker) Record(success bool) {
	b.mu.Lock()
	defer b.mu.Unlock()

	if success {
		b.failures = 0
		b.openUntil = time.Time{}
		b.probeInFlight = false
		return
	}

	b.probeInFlight = false
	b.failures++
	if b.failures >= b.threshold {
		b.openUntil = time.Now().Add(b.coolDown)
	}
}
```

**例子：**订单页需要调用推荐服务。推荐服务故障后，连续 20 次调用失败，熔断器打开 10 秒。这 10 秒里订单服务不再等待推荐接口，直接返回订单信息和空推荐列表。10 秒后先尝试少量请求；成功则恢复，仍失败就继续熔断。

熔断阈值不能只凭感觉设置。应结合调用量、正常错误率、超时比例和恢复时间，并监控熔断次数、熔断时长、半开探测结果。业务参数错误这类确定性失败通常不应计入下游故障率。

**面试回答：**

> 熔断用于下游持续失败时阻止故障扩散。关闭状态正常调用，失败率或连续失败达到阈值后打开并快速失败；冷却后进入半开，只放少量探测请求，成功再恢复。熔断后必须有明确的降级结果，否则只是把慢失败变成快失败。

### 4. 降级和隔离分别解决什么问题？怎么落到 Go 服务里？

**难度：中级**

**降级解决“资源不够或依赖故障时，少做什么”。**例如商品详情页保留价格和库存，暂时不展示推荐、评论摘要；路线服务拿不到实时路况时，退回静态路况路线。

**隔离解决“一个故障最多影响哪里”。**例如推荐接口和下单接口使用不同并发配额；大客户和普通客户分资源池；慢第三方接口使用独立 worker pool，不能占满整个服务的 goroutine 和连接池。

Go 中可以用带缓冲的 channel 做并发舱壁。下面限制推荐调用最多同时执行 100 个；名额用完时直接走降级，不再创建更多等待中的 goroutine。

```go
type Bulkhead struct {
	slots chan struct{}
}

func NewBulkhead(maxConcurrent int) *Bulkhead {
	return &Bulkhead{slots: make(chan struct{}, maxConcurrent)}
}

func (b *Bulkhead) TryEnter() bool {
	select {
	case b.slots <- struct{}{}:
		return true
	default:
		return false
	}
}

func (b *Bulkhead) Leave() {
	<-b.slots
}

func GetRecommendations(ctx context.Context, b *Bulkhead) []Item {
	if !b.TryEnter() {
		return nil // 推荐不是核心功能，满载时降级为空列表
	}
	defer b.Leave()

	items, err := callRecommend(ctx)
	if err != nil {
		return nil
	}
	return items
}
```

**例子：**订单服务总共能承受 1000 个并发请求。如果推荐接口变慢，而所有调用共用一个无限队列，1000 个请求可能全卡在推荐上，真正的下单请求也进不来。把推荐并发限制为 100 后，最坏只有 100 个请求受影响；其余请求跳过推荐，仍能完成下单。

隔离不是把线程池或 channel 调得越多越好。资源池过多会浪费连接和内存，过小又会降低吞吐。需要根据压测结果设置，并监控占用率、拒绝数和等待时间。

**面试回答：**

> 降级决定故障时返回什么，隔离限制故障影响范围。我会先区分核心与非核心功能，再为慢依赖设置独立的并发上限和有界队列；资源耗尽时非核心功能快速返回缓存、默认值或空结果，不能让它占满整条主链路。

### 5. 超时、重试、幂等为什么必须一起设计？

**难度：高级**

调用超时只能说明“调用方没等到结果”，不能证明“服务端没有执行”。例如支付请求在服务端扣款成功后，响应包丢失，客户端看到超时。如果客户端直接重试，而服务端没有幂等保护，就可能重复扣款。

一个安全的调用通常包含：

1. **总 deadline**：整个请求最多花多长时间；下游超时必须小于上游剩余时间。
2. **幂等键**：同一个业务请求重试多次，只产生一次结果。
3. **有限重试**：只重试网络抖动、临时不可用等可恢复错误。
4. **指数退避和随机抖动**：避免大量客户端同时重试形成重试风暴。
5. **重试预算**：例如重试流量不得超过正常流量的 10%，防止故障时流量翻倍。

```go
func CallInventory(ctx context.Context, orderID string) error {
	for attempt := 0; attempt < 3; attempt++ {
		callCtx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
		err := inventoryClient.Deduct(callCtx, orderID) // orderID 是幂等键
		cancel()

		if err == nil {
			return nil
		}
		if !isTemporary(err) || ctx.Err() != nil {
			return err
		}

		backoff := time.Duration(50*(1<<attempt)) * time.Millisecond
		select {
		case <-time.After(backoff):
		case <-ctx.Done():
			return ctx.Err()
		}
	}
	return errors.New("inventory temporarily unavailable")
}
```

库存服务应对 `orderID` 建唯一约束或保存处理结果。第一次调用其实已经成功时，后续重试读取并返回第一次的结果，而不是再次扣库存。

**例子：**上游 deadline 是 800ms，却给三个串行下游各设置 500ms 超时，理论最坏耗时已经超过上游预算。更合理的做法是按剩余时间分配预算，例如库存 200ms、优惠 100ms、支付 300ms，并给本地处理和网络波动留出余量。非核心优惠接口超时可降级，支付结果不明确则查询状态或进入对账，不能盲目重试。

**面试回答：**

> 超时不代表服务端没执行，所以写请求重试前必须先有幂等键。重试只用于短暂故障，要限制次数，采用指数退避和抖动，并服从整个请求的 deadline 和重试预算。持续故障交给熔断，非核心功能交给降级，不能用无限重试解决所有错误。

### 6. 多个consumer只让一个消费，如何实现？

**答案：**

**Consumer Group机制（Kafka示例）：**

```
生产者 → Topic(3个分区) → Consumer Group
                          ├─ Consumer1 (处理分区0)
                          ├─ Consumer2 (处理分区1)
                          └─ Consumer3 (处理分区2)
```

**关键点：**

1. 同一Consumer Group中的消费者不会消费同一分区
2. 每个分区只会被组内一个消费者消费
3. 消费者数量不应超过分区数量

**Go实现（使用Sarama）：**

```go
config := sarama.NewConfig()
config.Consumer.Group.Rebalance.Strategy = sarama.BalanceStrategyRoundRobin

group, _ := sarama.NewConsumerGroup(brokers, "my-group", config)

handler := &ConsumerGroupHandler{}
for {
    group.Consume(ctx, []string{"topic"}, handler)
}

type ConsumerGroupHandler struct{}

func (h *ConsumerGroupHandler) ConsumeClaim(session sarama.ConsumerGroupSession, claim sarama.ConsumerGroupClaim) error {
    for msg := range claim.Messages() {
        // 处理消息
        session.MarkMessage(msg, "")
    }
    return nil
}
```

### 7. 如何保证消息不被重复消费？如何保证消息的顺序性？

**答案：**

**防止重复消费（幂等性）：**

| 方案          | 实现               |
| ----------- | ---------------- |
| **数据库唯一键**  | INSERT时利用唯一索引去重  |
| **Redis去重** | SETNX消息ID，已存在则跳过 |
| **业务幂等**    | 状态机，已完成的不再处理     |

```go
func consume(msg Message) error {
    // 1. Redis去重
    ok, _ := redis.SetNX(ctx, "msg:"+msg.ID, "1", time.Hour).Result()
    if !ok {
        return nil // 已处理
    }

    // 2. 处理业务
    if err := process(msg); err != nil {
        redis.Del(ctx, "msg:"+msg.ID)  // 处理失败，删除
        return err
    }

    return nil
}
```

**保证顺序性：**

| 方案       | 说明             |
| -------- | -------------- |
| **单分区**  | 同一分区内有序（牺牲并行度） |
| **业务分区** | 相同业务ID发到同一分区   |
| **版本号**  | 消费时检查版本，乱序则等待  |

```go
// 业务分区
func produce(orderID string, msg []byte) {
    partition := hash(orderID) % partitionCount
    producer.Send(topic, partition, msg)
}

// 版本号机制
func consume(msg Message) error {
    for {
        currentVersion := getVersion(msg.ID)
        if msg.Version == currentVersion + 1 {
            process(msg)
            setVersion(msg.ID, msg.Version)
            return nil
        }
        time.Sleep(100 * time.Millisecond)  // 等待前序消息
    }
}
```

### 8. 分布式事务有哪些解决方案？

**答案：**

| 方案        | 原理                 | 优点   | 缺点      |
| --------- | ------------------ | ---- | ------- |
| **2PC**   | 协调者统一提交/回滚         | 强一致  | 同步阻塞、单点 |
| **3PC**   | 增加PreCommit阶段      | 减少阻塞 | 网络分区问题  |
| **TCC**   | Try-Confirm-Cancel | 业务控制 | 代码侵入大   |
| **Saga**  | 事件驱动补偿             | 长事务  | 隔离性差    |
| **本地消息表** | 消息+定时任务            | 简单可靠 | 延迟      |
| **最终一致性** | 消息队列               | 解耦   | 最终一致    |

**TCC示例：**

```go
// Try阶段：预留资源
func try(orderID string) error {
    // 冻结库存
    db.Exec("UPDATE stock SET frozen = frozen + 1 WHERE product_id = ?")
    // 冻结余额
    db.Exec("UPDATE account SET frozen = frozen + 100 WHERE user_id = ?")
    return nil
}

// Confirm阶段：确认执行
func confirm(orderID string) error {
    db.Exec("UPDATE stock SET quantity = quantity - 1, frozen = frozen - 1")
    db.Exec("UPDATE account SET balance = balance - 100, frozen = frozen - 100")
    return nil
}

// Cancel阶段：取消预留
func cancel(orderID string) error {
    db.Exec("UPDATE stock SET frozen = frozen - 1")
    db.Exec("UPDATE account SET frozen = frozen - 100")
    return nil
}
```

### 9. CAP定理是什么？两阶段提交、三阶段提交的区别？

**答案：**

**CAP定理：**
分布式系统不可能同时满足以下三个特性：

- **C（Consistency）**：一致性，所有节点数据相同
- **A（Availability）**：可用性，每个请求都能响应
- **P（Partition Tolerance）**：分区容错性，网络分区时仍能运行

**由于P必须保证，实际选择是CP或AP：**
| 选择 | 特点 | 系统 |
|------|------|------|
| **CP** | 保证一致性，可能不可用 | ZooKeeper、etcd、Redis Cluster |
| **AP** | 保证可用性，最终一致 | Cassandra、Eureka |

**2PC vs 3PC：**

| 特性       | 2PC              | 3PC                              |
| -------- | ---------------- | -------------------------------- |
| **阶段**   | Prepare → Commit | CanCommit → PreCommit → DoCommit |
| **阻塞**   | 协调者故障时阻塞         | 超时可继续                            |
| **数据一致** | 可能不一致            | 改善但未解决                           |

**2PC流程：**

```
协调者         参与者A    参与者B
   |──Prepare───>|           |
   |──Prepare────────────────>|
   |<──Yes───────|           |
   |<──Yes───────────────────-|
   |──Commit────>|           |
   |──Commit─────────────────>|
```

### 10. 如何设计分布式锁？

**答案：**

**实现方式对比：**

| 方式            | 优点      | 缺点     |
| ------------- | ------- | ------ |
| **数据库**       | 简单      | 性能差、单点 |
| **Redis**     | 高性能     | 主从切换丢锁 |
| **ZooKeeper** | 强一致、可靠  | 性能较差   |
| **etcd**      | 强一致、高性能 | 学习成本   |

**Redis实现（Redlock）：**

```go
// 单节点版本
func Lock(key, value string, ttl time.Duration) bool {
    return redis.SetNX(ctx, key, value, ttl).Val()
}

func Unlock(key, value string) bool {
    script := `
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end`
    return redis.Eval(ctx, script, []string{key}, value).Val().(int64) == 1
}

// Redlock（多节点）
func RedlockLock(key, value string, ttl time.Duration) bool {
    n := len(redisClients)
    quorum := n/2 + 1
    successCount := 0

    for _, client := range redisClients {
        if client.SetNX(ctx, key, value, ttl).Val() {
            successCount++
        }
    }

    return successCount >= quorum
}
```

### 12. DDD和三层架构对比？

**答案：**

**三层架构：**

```
表现层(Controller)
       ↓
业务层(Service)
       ↓
数据层(DAO/Repository)
```

**DDD架构：**

```
用户接口层(Controller/API)
       ↓
应用层(Application Service)
       ↓
领域层(Domain)  ←── 核心业务逻辑
       ↓
基础设施层(Infrastructure)
```

| 对比       | 三层架构     | DDD            |
| -------- | -------- | -------------- |
| **关注点**  | 技术分层     | 业务领域           |
| **业务逻辑** | Service层 | 领域层（实体、值对象）    |
| **数据库**  | 直接操作     | 通过Repository抽象 |
| **复杂度**  | 简单       | 较复杂            |
| **适用场景** | CRUD为主   | 复杂业务           |

**DDD核心概念：**

- **实体（Entity）**：有唯一标识的对象
- **值对象（Value Object）**：无标识，通过属性定义
- **聚合（Aggregate）**：一组相关对象的集合
- **聚合根（Aggregate Root）**：聚合的入口
- **领域服务（Domain Service）**：跨实体的业务逻辑
- **仓储（Repository）**：聚合的持久化抽象

### 13. 为什么使用JWT，不使用session和cookie？

JWT、Session 和 Cookie 不是同一层的概念：Session 是服务端保存会话状态的方案，JWT 是令牌格式，Cookie 是浏览器保存并自动携带数据的机制。JWT 也可以放在 Cookie 中，所以不能简单回答“用了 JWT 就不用 Cookie”。

- Session 容易主动失效和封禁，但多实例通常需要 Redis 等共享会话存储。
- JWT 各服务可本地验签，减少集中查会话的开销，但签发后很难立即撤销，还要考虑密钥轮换、令牌泄漏和过期时间。
- 浏览器应用若把令牌放在 `HttpOnly + Secure + SameSite` Cookie 中，可降低 JavaScript 读取令牌造成的风险；放在 `Authorization` 头中则需要客户端自己管理令牌。

**面试回答：**

> 我不会把 JWT、Session 和 Cookie 当作三选一。需要强制下线、细粒度会话控制时，服务端 Session 更直接；多服务只需验证身份、能接受短时间失效延迟时，可以使用短期 JWT，并配合 refresh token、密钥轮换和必要的撤销列表。浏览器如何携带令牌还要单独考虑 XSS、CSRF 和跨域策略。

### 14. 消息队列出现消息堆积时，怎么排查和处理？

**答案：**

- 我会先判断是“生产突然变快了”，还是“消费变慢了”。如果是后者，还要继续拆：是消费者挂了、下游接口慢了，还是分区不够、单条消息太重。
- 排查时重点看 backlog、消费速率、异常重试、下游响应时间和消费者线程状态。
- 临时止血的手段通常有：扩消费者、扩分区、批量消费、非核心链路先降级，必要时把特别慢的下游先隔离出去。
- 根因治理则是：提升消费幂等、减少单条消息耗时、做好重试和死信队列，避免一条坏消息把整个消费链路拖死。

### 15. 如何保证消息不丢？为什么“只靠 MQ”做不到绝对不丢？

**答案：**

- 真正的不丢是端到端问题，至少要把生产者、Broker、消费者三段都考虑进去。
- 生产者侧要有发送确认和重试，Broker 侧要有持久化和副本，消费者侧要在业务真正处理成功后再确认，并且做好幂等。
- 但即便这样，也很难说“绝对 0 丢失”，因为还会有应用崩溃、网络分区、人为误操作这些问题。
- 所以工程上更准确的说法是：**尽量做到可恢复、可重试、可补偿**，而不是轻易承诺绝对不丢。

### 16. 配置热更新如何避免新实例 miss 消息和错误配置直发线上？

**答案：**

- Pub/Sub 这类通知机制不保证离线补发，新实例启动时要主动拉取全量配置。
- 配置中心要持久化配置版本，实例收到通知后按版本拉取，而不是只依赖消息内容。
- 错误配置要通过校验、灰度、审批、回滚版本和生效范围控制来治理。
- 高风险配置最好支持分环境、分租户、分机器灰度，并能快速回滚。

### 17. 分库分表时 sharding key 怎么选？数据迁移怎么做？

**答案：**

分片键的第一原则是贴合主要访问路径，其次才是均匀分布。订单表如果最常按用户查历史订单，可选 `user_id`；若最常按商家处理订单，可选 `merchant_id`；库存表通常按 `sku_id` 聚合。不能只看哈希是否均匀，还要评估热点、跨分片查询、扩容、关联关系和数据生命周期。

常见路由方式：

- `hash(user_id) % N`：分布较均匀，但直接扩容会导致大面积迁移；
- 一致性哈希或虚拟分片：扩容迁移范围更小；
- 范围分片：利于按时间归档和范围查询，但容易形成时间热点；
- 目录/路由表：灵活但多一次路由查询，需要高可用和缓存。

在线迁移以“先扩容、双写/变更同步、回填、校验、切流、保留回滚窗口”为主线：

```text
1. 创建新分片并上线按版本路由能力
2. 从旧库全量回填历史数据
3. 用 binlog CDC 持续同步回填期间的增量
4. 对新旧库做行数、校验和与抽样业务校验
5. 小流量灰度读新库 -> 双读比对 -> 全量切流
6. 保留旧库只读与回滚窗口，确认稳定后再下线
```

迁移期间，每条写请求要带稳定的路由版本或由路由层统一决策，避免同一条数据写到两个不一致位置；跨分片事务优先通过订单状态机、事务消息和补偿实现最终一致，而不是把分布式强事务当默认方案。

### 18. 百万级 Goroutine 的进程内存暴涨，如何排查？

**答案：**

先明确一点：Goroutine 比线程轻，但不是免费。每个 Goroutine 至少有自己的栈、调度信息和它引用的对象；100 万个 Goroutine 即使每个只占很少内存，累计也会很大。更常见的问题不是“业务确实需要 100 万个活跃协程”，而是连接断了、任务结束了，但协程没有退出，数量不断累积。

排查可以按“先看数量，再看谁没退出，最后看它占住了什么”进行：

1. 每隔一分钟记录 `runtime.NumGoroutine()` 和进程内存。正常流量下降后，协程数也应回落；只涨不回落就是泄漏信号。
2. 打开 pprof 后抓 goroutine 快照。它相当于给所有协程拍照：相同调用栈出现几十万次，说明这批协程都卡在同一个地方。
3. 再抓 heap 快照，确认内存是协程栈、channel 里的积压消息，还是协程闭包一直引用着大对象。
4. 对比故障前后的两份快照，比单独看一份更容易确认“到底哪一类协程在持续增加”。

**完整例子：**长连接服务为每个连接启动读、写、心跳三个 goroutine。客户端断网后：

- 读协程因为网络错误退出；
- 写协程还在向一个没人接收的 channel 发送消息，因此一直卡住；
- 心跳协程还在运行，ticker 也没有停止。

连接不断重连，旧连接留下两个协程。10 万次重连后，虽然在线用户没有增加，Goroutine 却从 10 万涨到几十万甚至百万，内存和调度开销自然持续上涨。pprof 快照里会看到大量相同的 `chan send` 或 ticker 等待调用栈。

修复时，让同一连接的协程共享一个 `ctx`：连接关闭时调用 `cancel()`，每个协程都同时监听“有任务可做”和“连接已取消”。ticker 要显式停止：

```go
func heartbeat(ctx context.Context) {
	ticker := time.NewTicker(time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-ticker.C:
			sendPing()
		case <-ctx.Done():
			return
		}
	}
}
```

向 channel 发送消息也不能无限等待，应同时监听 `ctx.Done()`。批量任务不要一次启动几十万个 goroutine，而是固定数量的 worker 从任务队列领取工作；这样任务再多，同时存在的协程数量也有上限。

**面试回答：**

> 百万 Goroutine 先不要急着调 GC，我先判断它们是不是应该存在。先看协程数是否随流量回落，再用 goroutine 快照找大量重复的卡点，用 heap 快照确认它们持有什么对象。长连接里最常见的是连接断了，但写协程、心跳协程没有退出；我会用同一个 context 统一取消、停止 ticker，并让 channel 操作可以因取消而返回。批任务则用固定 worker 数量，防止任务量直接变成协程数量。

### 19. gRPC 的流控机制是什么？服务端处理慢时，客户端怎样不被打爆？

**答案：**

gRPC 建在 HTTP/2 上，HTTP/2 有连接级和 Stream 级 flow control。接收方消费数据后通过 `WINDOW_UPDATE` 归还窗口；窗口耗尽时发送方会被阻塞，因此它能提供传输层背压。

但 HTTP/2 流控不等于“业务已处理完成”。服务端框架可能已从网络读入消息，而业务 handler 仍在排队，所以还需要应用层保护：

- **服务端**：限制每个方法的并发数和队列长度；满载时尽快返回 `RESOURCE_EXHAUSTED`，不要无限堆队列。设置最大消息大小、最大并发 Stream、deadline，并隔离慢依赖。
- **客户端**：每个调用都带 deadline；限制 in-flight 请求数；重试只用于幂等请求，并使用指数退避和抖动。收到 `RESOURCE_EXHAUSTED` 或超时后要退避，不要立即重试。
- **流式 RPC**：服务端每次 `Send`、客户端每次 `Recv` 都要监听 `ctx.Done()`；若业务要求“处理一条再发下一条”，设计应用层 ACK/credit，不能只依赖 HTTP/2 窗口。

**例子：**路线服务向推荐服务发 gRPC server stream，每秒可推 5000 条路况事件，但推荐服务只能处理 1000 条。服务端设置最大并发 stream 和每个订阅的有界队列，队列满时丢弃过期的中间路况，只保留最新版本；客户端限制同时订阅数，并在 `RESOURCE_EXHAUSTED` 后指数退避。这样慢消费者只影响自身，不会撑满发送端内存。

**面试回答：**

> HTTP/2 的 connection 和 stream window 提供基础背压，但我不会把它当成业务流控。服务端要有并发上限、有界队列、deadline 和快速拒绝；客户端要限制 in-flight、设置超时、只对幂等调用退避重试。流式调用还要有 ctx 取消和业务 ACK/credit，才能在慢消费者场景下避免内存和重试风暴。
