## 业务系统与真实故障场景

### 1. 百万 QPS 秒杀系统怎么设计？

**面试官真正想听什么：**

- 你能不能先抓住目标，而不是上来就背 Redis 锁
- 你知不知道秒杀的核心矛盾是“瞬时高流量”和“极少库存”
- 你会不会讲削峰、库存控制、异步化、补偿闭环

**先定目标：**

- 不能超卖
- 主链路不能被打垮
- 用户结果要尽快返回
- 失败链路要能收口，不能把库存卡死

**典型链路：**

1. 活动页静态化，尽量把流量挡在后端之前
2. 入口做限流、验证码、风控、黑名单、用户资格预校验
3. 库存不直接查数据库，而是先在 Redis 里做原子预扣
4. 预扣成功后写 MQ，异步创建订单
5. 订单支付成功再最终确认库存，未支付超时则回补库存
6. 全链路要有幂等和补偿任务

**为什么这样设计：**

- 如果每个请求都直接打数据库，数据库一定先挂
- Redis 预扣的价值不只是快，更关键是把“库存判断”放到一个高并发可承受的位置
- MQ 的价值不只是解耦，更重要的是削峰，把突发流量摊平

**关键难点：**

- Redis 预扣成功但 MQ 投递失败怎么办
- 订单创建成功但支付超时怎么办
- 重试导致重复下单怎么办
- 热点商品一个 key 被打爆怎么办

**对应处理：**

- 预扣和消息投递之间要有失败补偿，比如本地消息表、事务消息或重试队列
- 下单逻辑必须幂等，通常用用户 ID + 商品 ID 作为业务唯一约束
- 超时未支付要异步回补库存
- 对热点商品可以做本地缓存、分片库存、队列前置隔离

**面试里推荐这样答：**

> 秒杀系统我会先围绕四个目标设计：不超卖、不把主链路打垮、尽快返回用户结果、失败可补偿。整体链路上，入口先做静态化和限流，库存层通过 Redis 原子预扣避免直接打数据库，预扣成功后写 MQ 异步创建订单，再通过支付超时回补、幂等约束和补偿任务保证最终一致。这个题的关键不在于某个组件，而在于削峰、预扣、异步、补偿这四件事形成闭环。

#### 如果是百万 QPS，怎样从网关到数据库分层设计？

先明确容量含义：百万 QPS 通常是活动开始瞬间的入口请求，不应该让这百万请求都进入库存、订单和数据库链路。真正的目标是把绝大多数无效流量挡在边缘或网关，让进入核心交易链路的请求接近可售库存和系统处理能力。

```text
用户
  -> CDN / 静态化页面 / 防刷挑战
  -> API Gateway（鉴权、资格、令牌桶、黑名单、WAF）
  -> 秒杀接入层（活动校验、幂等、排队令牌）
  -> Redis 集群（资格、库存、去重、原子预扣）
  -> Kafka / MQ（削峰、订单事件）
  -> 订单服务（消费、落库、幂等）
  -> MySQL（订单事实、最终库存、唯一约束）
  -> 支付 / 超时关单 / 回补库存 / 对账补偿
```

**1. CDN 和前端层：先减少“根本不该进来”的请求。**

- 活动页、商品图、规则和倒计时全部静态化并下沉 CDN；活动开始前通过预热把热点资源推到边缘节点。
- 下单接口不直接暴露为固定 URL。用户先通过活动页、验证码或滑块、人机风控获得短时有效的动态路径或一次性 token，避免脚本直接重放接口。
- 客户端点击后立即置灰，避免正常用户重复点击；但服务端不能依赖前端防重，所有关键判断仍必须在后端完成。

**2. 网关层：限流、风控和快速拒绝。**

- 网关先校验登录、活动时间、商品 ID、签名、动态 token、黑名单和用户资格；无资格请求直接返回，不访问 Redis 或数据库。
- 限流至少分层：全局保护集群、按商品保护热点、按用户/IP/设备防刷。限流结果要可观测，不能只看“接口报错”。
- 网关只做轻量、无状态判断，策略、黑名单和资格结果可从本地缓存或 Redis 获取；不要让网关同步调用多个下游服务，否则网关会变成新的瓶颈。

**令牌桶怎么设计：**

令牌桶适合“限制平均速率，同时允许一个有限突发”。桶容量 `B` 决定最多能突发多少请求，补充速率 `R` 决定每秒允许多少请求通过。每个请求需要一个令牌；令牌不足立即拒绝或返回“系统繁忙”。

```text
每个商品一个桶：capacity = 20,000，refill = 5,000 tokens/s

活动开始瞬间：最多放行 20,000 个突发请求
之后稳定放行：每秒最多 5,000 个请求
其余请求：快速失败或进入有限等待队列
```

- **本地令牌桶**：网关实例用内存计数，性能最高，但多实例下需要按实例配额或由配置中心动态下发配额；适合第一层粗限流。
- **Redis + Lua 令牌桶**：用 Redis 保存剩余令牌和上次补充时间，Lua 脚本内完成“按时间补令牌 + 尝试扣令牌”，能在集群中得到一致判断；适合商品级全局限流。
- **分片与分层**：热点商品不能所有请求都打同一个 Redis key。可先在网关做本地桶，再让少量通过的请求进入 Redis 全局桶；必要时按用户 hash 分桶，并让桶总配额受活动总预算控制。
- 不应无限排队。秒杀请求的业务价值通常随时间快速衰减，队列长度、等待时长和过期时间都要有上限；超限后应快速失败，避免把排队压力传给 MQ 和数据库。

**多 Pod 下，容量和每秒补多少令牌？不能直接按百万 QPS 配。**

先分清三个数字：`入口峰值` 是百万 QPS，`Redis 可承受的资格/预扣检查量` 可能只有每秒几千到几万，`最终可卖库存` 只有 100 或 1000。令牌桶的目标是保护下一层，不是把百万请求等比例放行；库存正确性仍由 Redis Lua 的原子预扣保证，令牌桶不能代替库存。

下面假设：活动持续 60 秒，有 200 个无状态 Gateway Pod；一个用户只允许成功一次；网关本地校验、Redis 集群和订单消费者已分别压测出安全上限。

| 层级 | 100 个奖品示例 | 1000 个奖品示例 | 目的 |
| --- | --- | --- | --- |
| 单用户 / IP 小桶 | `B=2, R=0.2/s` | `B=2, R=0.2/s` | 允许一次点击和一次短暂重试，抑制连点、脚本重放 |
| 每 Pod 本地粗桶 | `B=1,000, R=500/s` | `B=2,000, R=1,000/s` | 200 Pod 全局最多约 10 万 / 20 万 QPS 进入 Redis 前的下一层，不让百万请求直接打共享存储 |
| 商品级 Redis 全局桶 | `B=2,000, R=1,000/s` | `B=10,000, R=5,000/s` | 控制实际进入 Redis Lua 预扣的总请求量，给 Redis 和 MQ 留裕量 |
| 库存 Lua | 初始库存 100 | 初始库存 1000 | 最终裁决；库存为 0 后立即返回售罄，不再发 MQ |

这些数字不是“库存 100 就每秒只放 100 个”。100 个奖品若只放 100 个请求，网络抖动、资格失败、重复 token 或个别请求中途失败都会降低售罄率；相反也不能让百万请求同时进入 Redis。上例允许少量、受控的竞争请求进入库存 Lua：通常在几十到几百毫秒内卖完，随后通过“售罄标记 + 本地缓存”让后续请求在网关快速失败。

**如何把全局配额分给 200 个 Pod：**

```text
全局 Redis 商品桶：B=2,000, R=1,000/s
200 个 Gateway Pod

每个 Pod 初始配额：B_local = 10，R_local = 5/s
```

- 上面的均分只适合流量均匀。真实流量会倾斜，不能把所有配额固定死在 Pod 上，否则某些 Pod 空闲、另一些 Pod 已耗尽。
- 更实用的做法是 **本地大桶做粗限流 + Redis 商品全局桶做最终准入**：例如每 Pod 允许 500/s 通过基础校验，但只有 Redis Lua 全局商品桶给到令牌的请求才执行库存预扣。
- 如果 Redis 商品全局桶成为热点，可由活动控制面按 5～10 秒窗口向各 Pod 下发“令牌租约”，例如一次租 50 个、有效期 1 秒；Pod 用完再申请。这样大多数请求在本地判断，Redis 不必每次都参与限流，且未使用租约过期后自然回收。
- 不要让 Pod 自己随意估算全局桶。如果只在每台机器放 `B=2,000, R=1,000/s`，200 台机器会放大为 `B=400,000, R=200,000/s`，这正是多实例限流最常见的错误。

**100 个奖品的实际过程：**

```text
00:00 活动开始，100 万 QPS 先到 CDN / Gateway
00:00~00:01 网关本地桶和风控把大量无效流量拒绝
          Redis 商品桶最多放 2,000 个短时竞争请求
          Redis Lua 只有前 100 个合法且未重复的用户能预扣成功
00:01 发现库存为 0，写 sold_out 标记并广播 / 本地缓存
00:01 以后 请求直接返回“已售罄”，不再访问 Redis Lua、MQ 或 MySQL
```

**1000 个奖品的实际过程：**

- 1000 个库存可以提高商品级桶的 burst 和 refill，例如 `B=10,000, R=5,000/s`；前提是 Redis、MQ 和订单消费端确实能稳定承受这 5000/s 的有效预扣请求。
- 如果业务要求“尽量在 10 秒内卖完”，可从目标反推：每秒至少需要约 100 个**成功预扣**。考虑资格失败和网络失败后，允许进入 Lua 的尝试量可以是成功目标的数十倍，例如 5000/s；具体倍率应来自历史活动的有效请求率，而不是拍脑袋。
- 数据库订单消费速率可以低于入口预扣速率，例如稳定写入 1000/s，MQ 负责缓冲；但 reservation 的超时时间、MQ 积压上限和订单完成时限必须一起设计，不能无限堆积。

**令牌桶 Lua 的关键字段：**

```text
key: seckill:bucket:{activity_id}:{sku_id}
fields: tokens, last_refill_ms

refilled = min(capacity, tokens + elapsed_ms * refill_per_ms)
if refilled < 1: reject
else: tokens = refilled - 1; allow
```

桶更新、令牌扣减和库存预扣可以放在同一段 Redis Lua 中，避免“先拿到令牌、再扣库存”之间出现并发窗口；但高热点下更常把本地粗限流、Redis 全局限流和库存预扣分层，缩短单次 Lua 的工作量。无论采用哪种形式，都要监控每层的拒绝率、令牌租约浪费率、Lua p99、售罄耗时、MQ 积压和最终下单成功率，再按压测和真实有效率调参。

**3. 秒杀接入与 Redis：把库存判断放在高并发原子层。**

- 活动开始前把库存、商品状态、用户资格规则预热到 Redis；库存 key 按商品维度管理，热点极高时可用库存分片或库存令牌池分散写压力。
- 资格校验、重复购买判断、库存扣减和写入待下单标记应在一个 Lua 脚本中完成，避免“先查库存再扣库存”的并发竞态。

```text
Lua 原子逻辑：
1. 活动是否有效、用户是否有资格
2. user_id + sku_id 是否已成功抢购
3. 库存是否大于 0
4. 扣减库存，写入用户抢购标记
5. 返回成功，并生成 request_id
```

- 一人一单要有两层保证：Redis 的抢购标记用于快速拒绝，MySQL 的 `(user_id, sku_id)` 唯一索引用于最终兜底。
- Redis 预扣的是“可售名额”，不是永久事实库存。预扣后必须创建可追踪的 reservation，并为未支付订单设置超时回补。

**4. MQ：只负责削峰和可靠传递，不替代业务正确性。**

- Redis 预扣成功后发送 `seckill_reserved` 事件到 Kafka/RocketMQ。订单服务按可承受的并发消费，入口百万 QPS 会被压成数据库能够稳定处理的写入速率。
- 消息应包含 `request_id`、`user_id`、`sku_id`、活动版本、预扣时间和幂等键；按 `sku_id` 或订单键路由到分区，兼顾热点和局部顺序。
- Redis 扣减成功但消息发送失败时，不能直接当成功。可采用 Outbox/本地消息表、可靠重试或扫描待下单 reservation 补发事件；最终由对账任务保证“每个成功预扣要么有订单，要么已回补”。
- 消费失败进入重试队列；超过阈值进死信队列并告警。不要无限重试，否则故障下游会被放大。

**5. 订单服务和数据库：数据库只处理被筛选后的有效请求。**

- 订单消费者先按 `request_id` 做幂等，再开启短事务写订单、订单明细和库存预留/扣减记录；对 `(user_id, sku_id)` 建唯一索引兜底一人一单。
- 数据库库存扣减可用条件更新：`update stock set available = available - 1 where sku_id = ? and available > 0`。但在百万 QPS 场景，它应是最终事实层，不是入口抢库存的第一道闸门。
- 如果库存按分仓、规格或分库分表拆分，订单路由键要提前设计，避免秒杀时跨库事务；跨资源一致性更适合用状态机、事件和补偿，而不是把长事务扩散到全链路。

**6. 支付、超时和补偿：形成不超卖的闭环。**

```text
预扣成功 -> 创建待支付订单 -> 支付成功确认
                         -> 超时未支付：关单 + 回补 Redis 名额和数据库预留
```

- 支付回调要幂等，订单状态机只能单向流转，例如 `RESERVED -> PAID` 或 `RESERVED -> CLOSED`；不能让超时任务和支付回调互相覆盖状态。
- 定时任务扫描超时 reservation，使用状态抢占或条件更新确保只回补一次。
- 定期对账 Redis 预扣记录、MQ 事件、订单表和实际库存：缺订单则补发或回补，重复订单走人工/自动修正。极端故障下宁可少卖、稍后补偿，也不能超卖。

**关键监控和降级：**

- 监控网关放行率与拒绝率、验证码命中、Redis Lua 延迟、库存剩余、MQ 积压、订单消费延迟、DB 连接池和 p99、支付回调延迟、回补次数。
- Redis、MQ 或数据库异常时，入口要能熔断并直接返回“活动繁忙”；不要继续接受请求并无限积压。
- 按商品隔离资源池、限流配额和消费者组，避免一个爆款拖垮所有普通商品。

**面试里可用的完整回答：**

> 百万 QPS 秒杀的核心不是让数据库扛百万请求，而是分层过滤，把进入交易链路的请求控制在库存和下游能力范围内。CDN 先承接静态流量，网关做动态 token、风控和分层令牌桶限流；通过的请求在 Redis Lua 中一次完成资格、一人一单和库存预扣；预扣成功后写 MQ 削峰，订单服务按可承受速率消费并用数据库唯一索引和条件更新做最终兜底。支付超时通过状态机回补库存，Redis 预扣、消息、订单和库存之间靠可靠投递、幂等与对账补偿闭环。令牌桶我会做本地粗限流加 Redis Lua 全局商品限流，并限制等待队列，避免热点把压力传到 MQ 和 DB。

### 2. 视频点赞系统怎么设计？

**面试官真正想听什么：**

- 你能不能把“用户行为”与“统计计数”拆开
- 你知不知道点赞这种场景的难点不在写库，而在热点和一致性
- 你会不会讲取消点赞、幂等、热点隔离
- 热点隔离：热点 key 隔离不一定只等于“单独放一个 Redis 节点”，本质是把超热点流量和普通流量拆开治理。常见做法包括独立 Redis 实例、独立热点分片、应用层特殊路由，以及在上层增加本地缓存，避免热点 key 把整套缓存系统打爆。

**先定语义：**

- 是否允许重复点赞
- 是否支持取消点赞
- 点赞数是否必须实时精确
- 用户端看到的“已点赞状态”和总数是否允许短暂不一致

**常见拆法：**

1. 用户行为链路
   负责回答“这个用户到底点没点过赞”
2. 总数统计链路
   负责回答“这条视频当前有多少赞”

**典型实现：**

- 用户行为可以落 Redis Set / Bitmap / DB 明细表 / MQ 异步落库
- 总数统计可以先写缓存，再异步汇总刷库
- 热门视频的总数不能只靠单 key 原地自增，容易打爆

**为什么不能简单地“点赞就 update count=count+1”：**

- 高频写直接打 DB，热点视频很容易形成行锁竞争
- 同时还要解决取消点赞、重复点击、重试幂等
- 点赞状态和点赞总数从本质上是两类数据

**关键难点：**

- 重复点赞怎么防
- 取消点赞怎么保证状态一致
- 热门视频单 key 热点怎么扛
- 总数展示和明细状态短时间不一致能否接受

**常见做法：**

- 用业务唯一键或状态机防止重复点赞
- 行为明细和计数异步解耦
- 热门视频做分片计数，最后聚合
- 前台展示允许短时间最终一致

**面试里推荐这样答：**

> 点赞系统我会拆成两条链路：一条是用户行为链路，解决‘这个用户是否点过赞’；另一条是计数链路，解决‘这条内容现在有多少赞’。因为这两个问题的关注点不一样，行为链路更强调状态正确性和防重，计数链路更强调高并发下的吞吐和热点抗压。
>
> 行为链路上，我一般会先确定唯一关系，也就是 (user_id, target_id) 这一对。落地时可以根据规模选型：如果要强一致和可追溯，可以落 MySQL 明细表，并对 (user_id, target_id) 建唯一索引；如果更关注高性能判断用户有没有点过赞，可以在 Redis 里放 Set 或 Bitmap。这样用户点进详情页时，就能快速判断当前用户是否已点赞。
>
> 计数链路上，我不会每次都直接 update DB 的点赞数字，因为热点内容会把数据库行打成瓶颈。更常见做法是先把计数写到 Redis，比如做原子自增；再通过异步任务或者 MQ，把增量批量刷回数据库。这样主链路快，数据库压力也更平滑。
>
> 如果是热门视频，还要考虑热点 key 问题。单个 Redis key 虽然比数据库强很多，但极热点场景下仍可能成为瓶颈，所以可以做分片计数，比如把一个视频的点赞计数拆成多个 shard key，写入时按用户或随机路由到不同分片，读取时再聚合。这样可以把单 key 压力打散。
>
> 另外，点赞和取消点赞不能只看计数，还要保证行为和计数一致。比如用户重复点赞，不能把计数重复加一；取消点赞时，也不能减成负数。所以行为侧必须有幂等判断，可以先判断用户状态，再决定是否更新计数。工程上常见做法是：先原子更新行为状态，再异步发计数变更事件，消费端做幂等汇总。
>
> 如果面试官继续追问异常场景，我会补两点：第一，如果 Redis 计数更新成功但 MQ 投递失败，要有补偿机制，比如本地消息表或者重试；第二，如果缓存计数和数据库计数短暂不一致，我会接受最终一致，因为点赞数本身通常允许短暂延迟，只要用户自己的点赞状态尽量实时准确即可。

### 4. 群聊 / 聊天室怎么设计？

**面试官真正想听什么：**

- 你知不知道聊天系统的核心不是“发消息”，而是长连接、路由、顺序、离线消息
- 你会不会区分单聊、群聊、广播场景
- 你能不能讲清消息链路

**先定需求：**

- 是单聊还是群聊
- 是否要求强顺序
- 是否有离线消息
- 是否需要未读数、撤回、禁言、审核
- 延迟目标是多少

**核心链路建议这样讲：**

1. 长连接接入层
   用户通过 WebSocket / 长连接网关接入
2. 连接管理层
   维护用户 ID 和连接的映射关系
3. 路由层
   按会话 ID 或群 ID 做路由，尽量让同一会话落到同一逻辑分片
4. 存储层
   在线消息实时推送，离线消息持久化
5. 消息扩展能力
   未读数、撤回、禁言、审核、历史拉取

- 主要是为了降低同一会话的乱序处理成本
- 如果消息到处乱飞，顺序、一致性和状态同步都会变复杂

- 海量连接如何维护
- 消息顺序如何保证
- 用户离线后如何补消息
- 未读数怎么统计
- 敏感词和审核链路放在哪

**一个更像后端的回答方式：**

- 在线用户走实时推送
- 不在线则写离线消息表或消息队列
- 同会话消息尽量经过同一路由分片
- 历史消息和实时推送分开考虑，不要混成一套

**面试里推荐这样答：**

> 聊天系统我会拆成长连接网关、连接管理、消息路由、消息存储和离线投递五层。核心难点不是能不能把消息发出去，而是顺序、离线补投递、未读数和海量连接管理。工程上我会按会话 ID 或群 ID 做路由，尽量把同一会话消息收敛到同一路径处理，这样更容易控制顺序和状态一致性。

### 5. 朋友圈 / Feed 流系统怎么设计？推、拉、推拉结合如何实现？

**答案：**

先把数据分成三类：关注关系回答“我关注了谁”，动态表保存“作者发布了什么”，时间线只保存“我的首页应该出现哪些动态 ID”。时间线不要复制完整正文，否则修改、删除动态时要更新大量副本。

```sql
CREATE TABLE follows (
    user_id BIGINT,
    followee_id BIGINT,
    PRIMARY KEY (user_id, followee_id)
);

CREATE TABLE feeds (
    id BIGINT PRIMARY KEY,
    author_id BIGINT,
    content TEXT,
    created_at DATETIME,
    INDEX idx_author_time (author_id, created_at)
);

CREATE TABLE timelines (
    user_id BIGINT,
    feed_id BIGINT,
    score BIGINT,
    PRIMARY KEY (user_id, score, feed_id)
);
```

读取首页时先从时间线取一页 `feed_id`，再批量读取动态详情；热门详情可以放 Redis 或本地缓存。分页使用 `score + feed_id` 游标，避免数据不断新增时深分页产生重复或漏读。

以“用户发布一条动态，粉丝看到时间线”为例，分发有三种选择：

- **推模式（fan-out on write）**：作者发帖后，把动态 ID 异步写入每个粉丝的收件箱 `inbox:{fanoutUserId}`。读时间线只需读取自己的 inbox 再批量取详情，读快；但大 V 发帖会产生海量写放大。
- **拉模式（fan-out on read）**：只保存作者自己的发件箱 `outbox:{authorId}`。用户打开首页时，查询关注列表，分别取每位作者最近动态后按时间或评分归并。写轻；但关注多的用户读放大明显。
- **推拉结合**：普通作者的粉丝规模可控，采用推；大 V 只写自己的 outbox，读者拉取时再合并。用粉丝数阈值、动态热度和在线活跃度决定走哪条路径。

一个可落地的混合流程：

```text
作者发布 -> DB / 内容存储落库 -> Kafka: feed_created
    -> 普通作者分发消费者：批量写粉丝 inbox（可重试、按 event_id 幂等）
    -> 大 V：只维护作者 outbox

用户读首页 -> 读 inbox
    -> 取关注大 V 的 outbox
    -> 合并、去重、按时间/推荐分排序 -> 分页返回
```

工程细节：inbox 通常只保存 `feed_id`、时间和排序字段，内容详情单独存并缓存；分发要异步化且按批次处理；关注/取关、删除动态需要可重放事件或版本号来修正收件箱；分页应使用游标而不是深度 `offset`；热门作者和热点内容还需本地缓存、限流与降级。

**面试回答：**

> 推模式写放大、读快，适合普通用户；拉模式写轻、读放大，适合大 V；生产上通常混合。用户发帖先可靠落库再发事件，普通用户的动态异步 fan-out 到粉丝收件箱，大 V 只维护发件箱；读首页时把 inbox 和大 V 的 outbox 合并排序。这样避开了大 V 的写爆炸，同时保持普通用户读路径足够快。

### 6. 大文件上传怎么设计？

**面试官真正想听什么：**

- 你知不知道大文件上传不是“一个接口传完”那么简单
- 你能不能讲分片、断点续传、校验、合并和失败恢复
- 你有没有安全意识

**先定目标：**

- 上传过程可恢复
- 网络波动不需要整文件重传
- 服务端能感知上传进度
- 合并过程安全且幂等

**典型设计：**

1. 客户端把文件切成多个 chunk
2. 每个 chunk 带文件 ID、分片号、校验值上传
3. 服务端记录分片上传状态
4. 所有分片到齐后触发合并
5. 合并完成后做二次校验和异步后处理

**为什么要断点续传：**

- 大文件最怕中途中断
- 如果每次都重传全量，用户体验和带宽成本都很差

**关键难点：**

- 分片重复上传怎么处理
- 合并操作如何做到幂等
- 上传中断后怎么快速恢复
- 恶意文件、超大文件、病毒文件怎么管控

**工程补充点：**

- 上传状态最好落 DB 或稳定存储，不要只放内存
- 合并操作建议异步化
- 需要配合文件类型校验、大小限制、权限校验

**面试里推荐这样答：**

> 大文件上传我会设计成分片上传加断点续传。客户端按 chunk 上传，服务端记录每个 chunk 的状态和校验值，全部完成后异步合并。这样既能处理网络中断，也能避免整文件重传。这个题的关键点不只是分片本身，而是上传状态管理、合并幂等、失败恢复和安全校验。

### 7. 预约通知 / 延迟通知怎么设计？

**面试官真正想听什么：**

- 你会不会把“定时触发”和“通知发送”拆开
- 你知不知道通知系统的重点是可靠性，不是把消息发出去就算完
- 你能不能讲幂等、重试、取消预约

**先定目标：**

- 到点尽量准时触发
- 重复通知不能发生
- 失败后能重试
- 用户取消预约后不能误发

**核心链路：**

1. 用户预约时，先落预约记录
2. 同时把触发时间交给延迟任务系统
3. 到点后任务系统把事件投递给通知服务
4. 通知服务根据渠道发送站内信 / Push / 短信
5. 发送结果回写，失败重试，超过阈值进入死信或补偿

**延迟任务系统怎么选：**

- 量不大可以定时扫描
- 吞吐更高可以用时间轮
- 已有 MQ 体系时可用延迟队列

**关键难点：**

- 用户取消预约后任务如何失效
- 通知服务超时重试会不会重复发
- 多渠道通知如何保证状态可追踪

**工程回答要补：**

- 每条通知任务都要有唯一 ID，发送逻辑必须幂等
- “预约记录”和“任务状态”要能关联，方便取消和补偿

**面试里推荐这样答：**

> 预约通知我会拆成四段：预约存储、延迟触发、通知执行、失败补偿。用户发起预约时，先落一条预约记录，里面至少包含用户 ID、业务对象 ID、预约触发时间、通知渠道、任务状态和唯一任务 ID；同时把这个任务交给延迟任务系统，比如定时扫描、时间轮，或者基于 MQ 的延迟队列。到触发时间后，延迟系统不直接发通知，而是只负责把“该任务已到期”这个事件投递给通知服务。通知服务收到后，会先根据任务 ID 查状态，做一次幂等校验，确认这个任务没有被取消、没有发送成功过，然后再调用具体渠道去发站内信、Push 或短信。发送成功后回写发送结果和状态；如果发送失败，就按重试策略继续重试，超过阈值进入死信队列或补偿表，后面由人工或补偿任务处理。这样设计的关键点是把“什么时候触发”和“怎么发送”彻底解耦：前者解决定时问题，后者解决渠道可靠性问题。对于用户取消预约，我会把预约记录改成已取消，并让后续执行时再做一次状态校验，这样即使延迟任务已经出队，也不会误发。对于下游超时或重复投递，我会依赖任务唯一 ID 和发送幂等来保证‘最多只成功一次’，并把整个链路的状态都落库，保证后续可查、可重试、可补偿

### 8. 缓存一致性怎么保证？

**面试官真正想听什么：**

- 你知不知道这题没有银弹
- 你会不会先谈一致性目标，再谈方案
- 你能不能讲出极端情况下的补偿

**第一句话就要说：**

- 绝大多数互联网业务追求的是**最终一致**，不是强一致

**为什么这点重要：**

- 如果你一上来说“保证绝对一致”，面试官通常会继续追到你答不下去
- 正确做法是先问清楚业务能接受多大延迟、读旧值后果多严重

**常见方案：**

1. `cache-aside`
   - 读：先查缓存，miss 再查 DB，再回填
   - 写：先写 DB，再删缓存
2. 延迟双删
   - 适合处理并发读写窗口问题
3. MQ 异步补偿
4. 订阅 binlog / CDC 驱动缓存更新

**关键难点：**

- 删缓存失败怎么办
- 并发读写时会不会把旧值重新写回缓存
- 缓存和 DB 分别成功 / 失败的组合场景怎么收口

**更稳的回答方式：**

- 主方案是 cache-aside
- 再根据业务写频率、一致性要求和链路复杂度决定是否加延迟双删、MQ 补偿或 binlog 驱动
- 最后一定补一句：TTL 是兜底，不是主策略

**面试里推荐这样答：**

> 缓存一致性这题我会先确认业务要的是强一致还是最终一致。大部分互联网业务我会优先用 cache-aside，也就是先写库再删缓存；如果并发读写窗口比较明显，再加延迟双删、消息补偿或者 binlog 驱动更新。这个题的重点不是背某一个方案，而是你能不能说清楚一致性要求、失败场景和补偿策略。

### 9. 热点 key 怎么治理？

**面试官真正想听什么：**

- 你是不是知道热点 key 不只是 Redis 问题，而是整条链路问题
- 你会不会把热点识别、流量分散、缓存层次都讲出来

**热点 key 的本质：**

- 某个 key 的访问量远高于其他 key，导致单点成为瓶颈

**治理手段可以分四类讲：**

1. 提前识别
   监控热点 key、热榜数据、活动流量
2. 多级缓存
   本地缓存 + Redis + DB
3. 流量分散
   key 分片、热点隔离、读副本
4. 流量治理
   限流、降级、预热

**为什么本地缓存常常有效：**

- 很多热点流量其实是同一批数据被反复读取
- 如果每次都打 Redis，Redis 本身就会变成热点中心

**关键难点：**

- 本地缓存带来一致性问题
- key 分片后聚合更复杂
- 热点变化快，预热可能跟不上

**面试里推荐这样答：**

> 热点 key 治理我不会只盯 Redis。更完整的思路是：先通过监控识别热点，再用本地缓存和多级缓存兜住最热流量，必要时做 key 分片和热点隔离，最后配合限流和降级守住主链路。这个题的关键是把“热点识别、流量分散、缓存层次、失败兜底”连成一套。**

### 10. 多机房 / 多实例流量怎么均匀分配？

**面试官真正想听什么：**

- 你会不会区分“实例负载均衡”和“跨机房调度”
- 你知不知道“绝对均匀”不一定最优
- 你能不能讲出健康检查和故障切流

**先分两个层次：**

1. 单机房内实例调度
2. 多机房之间流量调度

**常见手段：**

- 四层 / 七层负载均衡
- 权重路由
- 就近接入
- 健康检查和自动摘除
- 一致性哈希
- 会话亲和

**为什么不一定追求绝对均匀：**

- 如果业务有本地缓存、会话状态或连接状态，过于随机的均匀分布反而会降低命中率
- 所以很多场景要在“均匀分布”和“局部粘性”之间平衡

**关键难点：**

- 机房故障切流时如何避免雪崩
- 跨机房延迟和数据一致性怎么权衡
- 有状态连接如何迁移

**面试里推荐这样答：**

> 多机房流量分配我会先分成实例级和机房级两层来看。实例层更关注负载均衡和健康检查，机房层更关注就近接入、权重调度和故障切流。如果业务有本地缓存或长连接，我不会一味追求绝对随机均匀，而是会适度保留会话亲和，在命中率和负载均衡之间做取舍。

### 11. 服务超时、网络波动、重试风暴怎么处理？

**面试官真正想听什么：**

- 你知不知道重试不是免费午餐
- 你会不会把超时、幂等、退避、熔断一起讲
- 你有没有“避免故障放大”的思维

**先讲原则：**

- 重试是恢复手段，不是默认加速器
- 没有边界的重试，往往会把小故障放大成大故障

**一套完整方案应该包括：**

1. 明确的超时控制
   每一层调用都有边界
2. 幂等设计
   不然重试本身就会造成副作用
3. 指数退避和抖动
   避免一窝蜂重试
4. 熔断
   下游明显异常时，不再持续压测它
5. 降级
   关键功能保主链路，非关键功能先让步
6. 限流
   防止系统在故障期间被进一步打穿

**关键难点：**

- 超时值设太小，误伤正常请求
- 超时值设太大，线程 / goroutine 被长时间占住
- 没幂等时重试会重复扣款、重复下单、重复发消息

**面试里推荐这样答：**

> 面对服务超时和网络波动，我不会只说“加重试”。更完整的思路是：先给每层调用设清晰超时边界，再保证请求幂等，然后用指数退避重试、熔断、限流和降级一起控制故障扩散。重试只能在“可重试 + 幂等 + 有边界”的前提下使用，否则它本身就会变成故障放大器。

### 12. 登录业务怎么保证通信安全和数据安全？

**面试官真正想听什么：**

- 你会不会区分通信安全、身份认证、数据存储、风控审计
- 你会不会答成“上 HTTPS 就完了”

**推荐拆成四层：**

1. 通信安全
   HTTPS / TLS，避免窃听和中间人攻击
2. 身份认证
   token / session / 签名 / 多因素认证
3. 数据安全
   密码加盐强哈希，敏感字段加密与脱敏
4. 风控与审计
   验证码、限流、设备指纹、异地登录提醒、审计日志

**密码存储一定要答到位：**

- 绝不能明文存储
- 也不建议简单做 `md5(password)`
- 更稳的做法是使用带盐的强哈希算法，比如：
  - `bcrypt`
  - `scrypt`
  - `Argon2`

**关键难点：**

- 登录接口本身就是暴露面最大的入口之一
- 除了密码，还要关注 token 泄露、撞库、暴力破解、会话劫持

**面试里推荐这样答：**

> 登录安全我会分成通信安全和数据安全两层来讲。通信层通过 HTTPS 保证链路不被窃听和篡改；数据层里，密码必须用带盐的强哈希算法存储，不能明文也不能简单 md5。除此之外，还要配合限流、验证码、设备指纹、异地登录提醒和审计日志。这个题的高分点是把“传输、认证、存储、风控、审计”连成一套，而不是只说一个 HTTPS。

### 13. 支付 / 订单状态机怎么设计？

**答案：**

状态机的重点是“状态可枚举、流转受约束、重复事件幂等”。

- 常见状态：待支付、支付中、支付成功、支付失败、已取消、已退款、已关闭。
- 每个外部事件只能触发合法流转，例如待支付可以变支付成功或取消，支付成功不能再变待支付。
- 支付回调可能重复到达，所以要用业务单号、支付单号、唯一索引和状态判断保证幂等。
- 回调处理要验签、校验金额、校验商户订单号，再更新本地状态。

### 14. 如何防止重复支付或重复提交？

**答案：**

- 前端按钮置灰只能减少误触，不能作为核心保证。
- 后端要用请求号、业务唯一键、支付单唯一索引、状态机判断保证幂等。
- 对外部支付回调，要以支付平台交易号和本地订单号做唯一约束。
- 如果引入分布式锁，也只能作为并发互斥辅助手段，最终仍要靠状态机和唯一约束兜底。

### 15. 项目里并发很大、订单量突然上来时，你会怎么扛？

**面试官真正想听什么：**

- 你会不会先讲瓶颈分析，而不是一上来就说“加机器”
- 你能不能把流量入口、应用层、缓存层、数据库层拆开讲
- 你知不知道“先止血，再扩容，再重构”的思路

**先定目标：**

- 先保证核心链路不挂
- 先保写入成功，再谈复杂功能
- 避免局部热点拖垮整个系统

**回答顺序建议这样讲：**

1. **先定位瓶颈在哪一层**

   - 网关扛不住
   - 应用线程池 / goroutine 爆了
   - Redis 热 key
   - MySQL 慢 SQL / 锁竞争
   - MQ 积压

2. **入口先做止血**

   - 限流
   - 熔断
   - 降级
   - 非核心功能先关掉

3. **把重操作异步化**

   - 下单、发券、通知、统计尽量解耦到 MQ
   - 主链路只保最关键成功结果

4. **热点隔离**

   - 热门商品、热门用户、热点配置单独隔离
   - 防止单点热点把整个系统拖垮

5. **数据库层做兜底**

   - 补索引
   - 限制大事务
   - 读写分离
   - 必要时做分库分表

**trade-off 要主动补一句：**

- 不是所有问题都该靠数据库硬扛
- 也不是所有问题都能马上靠分库分表解决
- 很多时候第一步是削峰、限流、异步化，而不是直接做大手术

**面试里推荐这样答：**

> 如果订单量突然上来，我不会直接说加机器，而是先按层定位瓶颈：入口、应用、缓存、数据库、消息队列分别看。短期先靠限流、降级、异步化和热点隔离止血，优先保住下单主链路；中期再补数据库索引、优化慢 SQL、拆大事务；如果增长是长期的，再考虑分库分表和更大的架构调整。这个题的关键不只是扩容，而是知道先保什么、先挡什么、先拆什么。

### 16. 如果用户量本身很大，系统要怎么设计得更稳？

**面试官真正想听什么：**

- 你会不会把“高并发”和“高用户量”区分开
- 你知不知道读多写少和写多读多的治理方式不同
- 你会不会讲容量规划和分层设计

**先定问题：**

用户量大，不一定等于每时每刻并发都大。
所以这题要先拆成：

- 总用户量大
- 在线用户量大
- 瞬时并发大

**系统设计思路：**

1. **分层承压**

   - 静态资源走 CDN
   - 热读请求优先走缓存
   - 重写操作尽量异步化

2. **存储分层**

   - 热数据和冷数据分开
   - 在线查询链路和历史归档链路分开

3. **服务拆分**

   - 核心链路和非核心链路拆开
   - 用户系统、订单系统、搜索系统不要混成一个大服务

4. **容量规划**

   - 不是“用户量 1000 万”就结束
   - 要继续估：
     - 日活
     - 峰值 QPS
     - 单用户请求频率
     - 数据增长速度

不要从单体一步跳到“全套微服务 + 分库分表”。更合理的演进是每个阶段先解决已经被监控和压测证明的瓶颈：

| 阶段 | 先做什么 | 为什么 |
| --- | --- | --- |
| 100 万用户 | 索引优化、主从读写分离、Redis 缓存、应用无状态扩容 | 此时通常先解决慢 SQL、热点读和单机容量 |
| 1000 万用户 | 按业务边界拆服务，非核心链路异步化，增加 CDN、热点隔离和容量压测 | 流量和团队规模上升后，需要隔离故障与发布影响 |
| 1 亿用户 | 按访问路径做数据分片，建设路由层、全局 ID、冷热分离和多机房容灾 | 单库容量、热点分片和机房故障开始成为长期约束 |

**例子：**一个订单系统从日活 20 万增长到 2000 万。第一阶段先把订单列表的慢 SQL 和索引修好，再用缓存承担重复查询；峰值写入增加后，把短信、积分、推荐从下单事务拆到 MQ；确认单库订单表已经成为持续瓶颈后，才按 `user_id` 分片，并提前设计路由版本、增量同步和灰度切流。这个顺序比一开始就分库分表风险更低，也更容易定位每次改造带来的收益。

**高分点：**

- 真正大规模系统不是靠单点参数调优扛出来的
- 而是靠“缓存、异步、隔离、分层、容量规划”一起做

**面试里推荐这样答：**

> 用户量大时，我会先把“总量、在线量、瞬时并发”拆开看，因为它们对应的架构压力不一样。整体设计上会走分层承压：静态资源走 CDN，热点请求走缓存，重操作异步化；数据上做冷热分离，服务上做核心链路和非核心链路拆分。真正稳定的大规模系统，不是靠某一个数据库参数或线程池参数解决，而是靠分层、隔离和容量规划一起兜住。

### 17. 面试官让你讲“系统的数据量、设备量、上传频率、传输路径”，你怎么答更像工程师？

**面试官真正想听什么：**

- 你是不是只会说“数据量很大”
- 你能不能把量级、链路、瓶颈和优化点一起讲

**推荐回答结构：**

1. **先讲量级**

   - 日上传文件数
   - 平均文件大小
   - 峰值上传并发
   - 每天新增多少索引数据

2. **再讲链路**

   - 客户端上传
   - 服务端接收
   - 对象存储落盘
   - 元数据入库
   - 异步处理
   - 检索索引更新

3. **最后讲瓶颈**

   - 上传链路更吃带宽和对象存储
   - 处理链路更吃 CPU、Embedding 服务和 ES 写入
   - 检索链路更吃 ES 查询延迟和模型响应时间

**如果没有真实超大规模数据怎么办？**

- 不要编很夸张的数字
- 可以说当前量级有限，但设计时已经按“上传、处理、检索”三条链路拆开，预留了扩展点

**面试里推荐这样答：**

> 我不会只说“数据量很大”，而是会按量级、链路、瓶颈三层来讲。比如每天多少上传、平均文件大小、峰值并发大概多少；上传后经过对象存储、元数据入库、异步解析、向量化和索引更新；其中上传链路更吃带宽，处理链路更吃 CPU 和外部模型服务，检索链路更吃 ES 和生成延迟。这样讲面试官更容易判断你有没有真实做过容量分析。

### 18. 如果文件非常大、内存有限，你会怎么处理？

**面试官真正想听什么：**

- 你知不知道“不能把整个文件一次性读进内存”
- 你会不会讲分块、流式处理、外部排序这类思路

**核心原则：**

- 不要一次性全量读入内存
- 要按块处理
- 中间结果必要时落磁盘

**常见做法：**

1. **流式读取**

   - 一边读一边处理
   - 适合日志解析、文本扫描、哈希计算

2. **分块处理**

   - 把大文件拆成多个 chunk
   - 每块单独处理，再汇总结果

3. **外部算法**

   - 如果数据量远超内存，就用外部排序、分桶、临时文件归并

**高分点：**

- 你要主动说明：这类题本质上是“用磁盘换内存”
- 不要假装所有问题都能靠内存 map 解决

**面试里推荐这样答：**

> 文件特别大、内存有限时，核心原则就是不要整文件读进内存，而是改成流式读取和分块处理。如果问题需要全局排序或全局聚合，就要接受“用磁盘换内存”，采用外部排序、分桶或归并的思路。这个题考的不是 API，而是你有没有大数据量下的资源约束意识。

### 19. 500G 文件、内存只有 8G，这类海量数据题怎么回答才不慌？

**面试官真正想听什么：**

- 你能不能先判断“内存肯定不够”
- 你会不会讲外部排序、分桶、哈希拆分、归并
- 你能不能先说思路，再看具体题型

**万能回答框架：**

1. **先判断约束**

   - 500G 远超 8G，不能全量进内存

2. **再判断题型**

   - 如果是排序：外部排序
   - 如果是去重 / 聚合：分桶 + 局部处理
   - 如果是查 TopK：小根堆 + 分块扫描
   - 如果是匹配组合：哈希分片后局部求解

3. **最后讲工程细节**

   - 临时文件怎么落盘
   - 分桶规则怎么定
   - 如何保证最终归并正确

**举一个最通用的说法：**

> 这类海量文件题我会先承认“内存一定不够”，所以不能按常规算法直接做，而要转成外部算法。排序就做外部排序，先分块排序再归并；如果是查找或聚合，就先按哈希或范围做分桶，把大问题拆成多个内存可处理的小问题。核心思想是分而治之，用磁盘换内存。

**面试里推荐这样答：**

> 500G 文件配 8G 内存，这种题第一反应不是想“怎么调参数塞进去”，而是立刻切换到外部算法思路。先按题型分类：排序就外部排序，聚合就分桶，TopK 就分块扫描配堆，匹配组合就先哈希拆分。高分点在于你先明确资源约束，再给出分治和落盘方案，而不是直接写普通内存算法。

### 20. 定时任务怎么设计，才能让面试官觉得你考虑得比较完整？

**面试官真正想听什么：**

- 你会不会把“触发”与“执行”拆开
- 你知不知道多实例部署下不能重复跑
- 你会不会讲幂等、重试和失败补偿

**先定目标：**

- 到点尽量触发
- 多实例下不要重复执行
- 执行失败能重试
- 任务状态可追踪

**一套完整思路可以这样讲：**

1. **任务定义层**

   - 任务 ID
   - 执行时间
   - 执行参数
   - 当前状态

2. **调度层**

   - 负责判断“什么时候该触发”
   - 可以是定时扫描、时间轮、延迟队列

3. **执行层**

   - 真正跑任务逻辑
   - 要做幂等，避免重复执行出副作用

4. **补偿层**

   - 失败重试
   - 超过重试次数进告警 / 死信 / 人工处理

**多实例下怎么避免重复跑：**

- 分布式锁
- 数据库状态抢占
- 调度中心分配

但无论哪种方案，都要补一句：

> 即使已经做了互斥，执行逻辑本身最好仍然幂等，因为线上永远可能出现重复触发或补偿重试。

**面试里推荐这样答：**

> 定时任务我会拆成任务定义、调度、执行、补偿四层。调度层负责“什么时候触发”，执行层负责“真正把事做掉”，两者不要耦死。多实例场景下要通过分布式锁、状态抢占或调度中心避免重复跑；同时任务执行本身也要幂等，失败要能重试和告警。这个题的重点不是定时器 API，而是可靠触发、避免重复和失败收口。

### 21. 如何设计一个支撑 10 万 QPS 的路径规划服务？

**答案：**

先确认边界：10 万 QPS 是全局还是单城市，目标 p99、实时路况时效、地图更新频率、是否有货车限行或多途经点等个性化约束。不同答案会导致完全不同的容量和缓存设计。

```text
客户端 -> Gateway（鉴权、限流、城市路由）
       -> 区域路径规划集群（无状态横向扩容）
       -> 静态路网快照 + 实时路况 Overlay
       -> 本地/分布式路径缓存

地图编辑/路况流 -> Kafka -> 区域状态服务 -> 版本化快照与 Overlay
```

- 静态道路拓扑按城市或地理网格分片，版本化后加载到本地内存或 mmap；路径引擎按区域横向扩容。
- 实时路况通过 Kafka 更新到对应区域的内存 Overlay，不每次请求都查数据库。
- 使用分层/预处理算法，例如主干路索引、Contraction Hierarchies 或 MLD，把在线搜索限制在局部区域和少量候选路径。
- 缓存 key 至少包含起终点网格、出发时间桶、`map_version` 和 `traffic_version`；命中旧版本不能直接返回。
- 热点城市独立资源池；依赖或路况流异常时可降级为静态路况、较粗路线或短 TTL 缓存结果。

**例子：**早高峰北京到上海的跨城路线请求非常集中。入口先按城市与网格路由，命中“起点网格 + 终点网格 + 5 分钟时间桶”的缓存；未命中才进入路径引擎。事故事件只更新受影响区域的 traffic overlay 并递增 `traffic_version`，相关缓存自然失效，不需要全量清空。这样热点请求主要在缓存层完成，路径引擎只处理长尾和个性化请求。

**面试回答：**

> 10 万 QPS 的关键不是单纯加机器，而是区域分片、静态路网本地化、实时路况流式 Overlay、版本化缓存和热点隔离。读链路尽量不查 DB；在线算法只做必要的局部搜索，热点 OD 对走缓存。我要持续看 p99、缓存命中率、路况版本延迟、单城市流量倾斜和路线成功率，并准备静态路况降级。

### 22. 分布式系统中，如何保证地图数据最终一致性？

**答案：**

最终一致性不是“发一条 MQ 就结束”，而是可靠投递、顺序/版本、消费幂等、版本发布和对账的闭环。地图编辑数据以主库为事实源，实时路况以事件流为事实源；两类数据都要显式带版本。

```text
地图编辑事务：主库更新 + Outbox 事件同一事务提交
  -> CDC / Relay 投递 Kafka
  -> 索引、缓存、搜索、路径引擎分别消费
  -> 按 feature_id + version 幂等更新
  -> 构建完成后原子切换 map_version
```

- Outbox/CDC 解决“数据库已提交但消息没发出”的双写问题。
- Kafka 按 `feature_id` 分区，保证同一道路要素的事件顺序；消息包含 `event_id`、`feature_id`、`version`、操作类型和时间。
- 消费者用去重表或唯一约束去重，只接受更高版本；删除使用 tombstone，避免旧消息把已删除道路重新写回。
- 地图索引构建完成后通过 manifest/版本指针原子发布，读服务在一个请求内固定使用同一 `map_version`，不能读到半新半旧数据。
- 失败事件进入重试/死信队列；定时用主库快照与索引、缓存、下游数据做行数、版本和抽样路径对账。

**例子：**一条道路在 10:00 被封闭，主库把 `road_123` 更新为 `version=42`，并写入 Outbox。CDC 投递 Kafka 后，路径引擎先构建带 `version=42` 的区域 overlay，校验成功才切换版本指针。重复消息因为版本相同被忽略；若旧的 `version=41` 迟到，也会被版本比较丢弃。直到新版本发布前，用户仍会读旧快照，但不会读到一半新、一半旧的路线数据。

**面试回答：**

> 我会以主库和版本化事件为事实依据：主库更新与 Outbox 同事务提交，CDC 可靠投递 Kafka；消费者按要素 ID 保序、按事件 ID 去重、按版本单调更新；索引和缓存按 map_version 原子发布。失败走重试、死信和对账。这样允许短暂读旧数据，但保证最终收敛，并避免重复、乱序和半版本发布。

### 23. RAG 系统怎么做文档分块、标签、候选排查和效果测评？

**面试官真正想听什么：**

- 你是否把 RAG 看成“数据处理 + 检索 + 生成 + 评测”的完整系统，而不只是调用向量数据库。
- 你能否解释 chunk 为什么这样切、metadata 如何参与过滤、候选文档错了如何定位，以及如何用数据证明改动有效。

#### 一、先讲完整链路

```text
文件上传
  -> 解析（PDF / Word / HTML / Markdown）
  -> 清洗与结构恢复
  -> 分块 Chunking
  -> 生成 metadata 和 embedding
  -> 写入 ES / 向量库 + 倒排索引

用户提问
  -> Query 清洗 / 改写 / 意图识别
  -> 权限过滤
  -> 向量召回 + BM25 关键词召回
  -> 候选合并与去重
  -> Reranker 重排
  -> 选 TopK 拼接上下文
  -> LLM 生成答案与引用
  -> 记录检索和生成指标
```

#### 二、具体怎么分块？

**1. 不要一上来只按固定字符数切。**

- 先识别文件类型和结构：标题、章节、段落、列表、表格、代码块、问答对、页码和图片 OCR 结果。
- Markdown/HTML 优先按标题层级切；技术文档保留“章节标题 + 正文”，不要把标题和解释拆到不同 chunk。
- 表格尽量按完整表格或行组切，并把列名带入每个行组；代码按函数、类或配置块切，不要从中间截断。
- PDF 需要保留页码、坐标和文档版本，方便答案引用和人工回看；扫描 PDF 先 OCR，并记录 OCR 置信度。

**2. 结构化切分，再做长度兜底。**

```text
文档
└── 2.2 Redis 持久化
    ├── 2.2.1 RDB
    │   └── 段落 A + 代码/表格
    └── 2.2.2 AOF
        └── 段落 B + 注意事项
```

- 第一层按语义边界切，第二层再把过长段落按句子或 token 长度拆开。
- 常见起点是每个 chunk 约 300～800 tokens，overlap 约 10%～20%；具体值要结合 embedding 模型、文档密度、问题长度和 LLM 上下文窗口压测，不要把它当固定标准。
- overlap 只用于避免边界丢上下文，不宜过大，否则会产生大量重复向量，降低索引和检索效率。
- 每个 chunk 都带父级标题或路径，例如 `Go > GC > 三色标记`，这样单块检索时也知道语境。

**例子：**一段“库存扣减”文档不能简单每 1000 字截断。更好的 chunk 是：

```text
标题路径：电商系统 > 库存 > Redis 预扣
正文：先用 Lua 原子判断库存，再写 reservation；订单超时后回补。
```

如果正文超过长度，再在句子边界拆成两个 chunk，但两个 chunk 都保留标题路径和文档版本。

#### 三、每个 chunk 应该打什么标签？

建议把 metadata 分成四类，既服务权限过滤，也服务召回、重排、溯源和删除。

| 类别 | 示例字段 | 作用 |
| --- | --- | --- |
| 来源与版本 | `doc_id`、`file_name`、`file_md5`、`version`、`page_no`、`chunk_id` | 去重、引用、增量更新、定位原文 |
| 结构语义 | `title_path`、`section`、`heading_level`、`content_type` | 结构过滤、标题加权、上下文拼接 |
| 业务分类 | `tenant_id`、`project_id`、`department`、`doc_type`、`tags`、`language` | 租户隔离、业务过滤、分领域检索 |
| 权限与质量 | `owner_id`、`acl`、`status`、`publish_time`、`source_quality`、`ocr_confidence` | 防越权、只检索已发布内容、质量降权 |

- `chunk_id` 最好由 `doc_id + version + chunk_index` 稳定生成，文档重新切分时能判断哪些 chunk 需要删除或重建。
- 权限字段必须在召回过滤阶段执行，不能先召回私有文档、再依赖 LLM 忽略它们；否则会有越权风险。
- 标签不要全部塞进自然语言正文。可用于过滤的字段单独建 keyword/date/numeric 字段，可全文检索的内容单独建 text 字段，向量单独建 dense_vector 字段。
- 标签要有字典和校验规则，例如 `doc_type=runbook`、`language=zh`，不要让同一个概念出现“故障手册 / 运维手册 / run-book”三种不可控值。

#### 四、候选文档出了问题，怎么排查？

先把问题拆成“没有召回”“召回了但排序错”“上下文拼错”“模型答错”四类，不能只看最终答案。

```text
Query
  -> 权限过滤日志
  -> BM25 召回结果
  -> 向量召回结果
  -> 合并/去重后的候选
  -> Reranker 分数与排序
  -> 最终注入 LLM 的 chunks
  -> 最终答案与引用
```

**1. 先确认数据是否正确入库。**

- 用 `doc_id + version + chunk_id` 查原始内容、embedding 是否存在、文本是否为空、metadata 是否完整。
- 检查解析、OCR、编码、去除页眉页脚和表格转换是否把关键信息丢掉。
- 检查旧版本 chunk 是否删除；同一文档多版本并存会让候选看起来“相似但过期”。

**2. 判断是召回问题还是排序问题。**

- 相关文档根本不在 TopK：优先看 query embedding、分块边界、向量维度/距离、过滤条件、召回 `k` 和索引刷新。
- 相关文档在初始候选中但没进最终 TopK：看 BM25/向量融合权重、归一化、Reranker 输入和排序分数。
- 关键词、错误码、类名召回差：增强 BM25、同义词和字段权重；专有名词不能只依赖向量语义。
- 语义问题召回差：检查 embedding 模型、query 改写、chunk 是否太短或上下文不完整。

**3. 排查过滤和权限。**

- 记录每一步过滤前后的候选数量；重点检查 `tenant_id`、用户 ACL、文档状态、语言和时间范围。
- 如果“候选为空”，先关闭非必要过滤在隔离环境重放，确认是过滤误配还是索引没有数据；生产环境不能为了排查而绕过权限返回给用户。

**4. 排查上下文构建和生成。**

- 最终送给 LLM 的内容必须可审计：记录 chunk ID、分数、顺序、截断长度和 prompt 版本，不要只记录最终文本。
- 如果候选正确但答案错，检查去重、排序、上下文窗口截断、引用映射、Prompt 指令和模型是否把无关 chunk 当成依据。
- 用“只给参考资料、要求逐条引用、资料不足时拒答”的测试区分检索错误和模型幻觉。

#### 五、RAG 怎么测评？

测评要分离 **检索质量、答案质量、系统性能和安全性**，不能只看“用户觉得好不好”。

**1. 建立带标注的离线数据集。**

每条样本至少包含：问题、用户/租户、期望答案或关键事实、相关 `doc_id/chunk_id`、允许引用范围、不可回答标记。覆盖事实问答、多跳问题、关键词问题、版本问题、无答案问题和越权问题。

**2. 检索指标。**

- `Recall@K`：相关 chunk 是否进入前 K，衡量“有没有捞到”。
- `Precision@K`：前 K 个里有多少相关，衡量候选噪声。
- `MRR` / `nDCG@K`：相关 chunk 排得是否靠前。
- `Hit Rate`：至少命中一个可回答 chunk 的比例。
- 对权限场景额外测越权召回率，目标必须为 0。

**3. 生成指标。**

- **Faithfulness/事实一致性**：答案中的声明是否能被引用资料支持。
- **Answer Relevance**：答案是否真正回答问题，而不是只复述文档。
- **Citation Accuracy**：引用的 chunk 是否支持对应句子，引用是否完整。
- **Completeness**：多条件问题是否覆盖全部要点。
- 无答案问题测拒答准确率，避免系统在没有证据时编造。
- 自动评测可用 LLM-as-a-Judge，但要抽样人工复核，并固定评测 prompt、模型和评分标准，避免评测漂移。

**4. 性能和稳定性指标。**

- 端到端 p50/p95/p99、向量召回延迟、BM25 延迟、Reranker 延迟、LLM 首 token 和总耗时。
- embedding/索引成本、候选数量、上下文 token 数、缓存命中率、索引新鲜度和失败率。
- 对峰值查询、长问题、空结果、Reranker 超时和向量库不可用做降级演练。

**5. 用回归集驱动迭代。**

每次修改 chunk size、overlap、embedding、混合检索权重或 Reranker，都在同一套数据集上对比：Recall@K、nDCG、Faithfulness、p99 和成本。保留失败样本和线上用户反馈，按“解析失败、切块失败、召回失败、排序失败、生成失败、权限失败”分类，避免只优化平均分。

**面试里推荐这样答：**

> RAG 我会拆成数据处理、检索、生成和评测四层。分块优先按标题、段落、表格和代码等语义边界切，再用 token 长度和小比例 overlap 兜底；每个 chunk 带文档版本、标题路径、租户、ACL、页码和质量字段，权限在召回前过滤。候选错误时沿着“入库 -> BM25/向量召回 -> 合并重排 -> 最终上下文 -> 生成”逐层记录 chunk ID 和分数，判断到底是没召回、排序错、上下文拼错还是模型幻觉。测评上离线看 Recall@K、MRR/nDCG 和越权率，生成看事实一致性、答案相关性、引用准确率和拒答率，线上再看 p99、成本、索引新鲜度和用户反馈。

### 24. TB 级文件如何合并？文件之间无序、每个文件内部有序怎么办？

**先确认题意：**

- 文件之间无序，表示不能简单按文件名拼接；例如 `file-01` 的最大值可能比 `file-02` 的最小值大。
- 每个文件内部有序，表示每个文件都是一个已排序的 run，例如按用户 ID、时间戳或整数升序。
- TB 级数据无法整体读入内存，因此本质是 **多路归并（k-way merge）+ 流式读取 + 外部存储**。

#### 一、核心思路：维护每个文件的当前最小值

假设有 1000 个文件，每个文件内部按 `user_id` 升序：

```text
file A: 1, 10, 20, 50, ...
file B: 2,  8, 30, 40, ...
file C: 3,  7, 25, 60, ...
```

不能先读完 A 再读 B，因为输出会变成 `1, 10, 20, 50, 2...`，全局不再有序。正确做法是从每个文件读一条记录，放进一个大小为 `k` 的最小堆：

```text
初始堆: [A:1, B:2, C:3]

弹出 A:1 -> 写入结果文件 -> 从 A 再读 10 -> 入堆
弹出 B:2 -> 写入结果文件 -> 从 B 再读 8  -> 入堆
弹出 C:3 -> 写入结果文件 -> 从 C 再读 7  -> 入堆

结果: 1, 2, 3, 7, 8, 10, 20, 25, 30, 40, 50, 60 ...
```

- 每次堆顶一定是所有“尚未输出数据”中最小的一条，因此顺序正确。
- 弹出一条后，只需要从同一个文件再读一条补回堆，不会把整个文件读到内存。
- 时间复杂度是 `O(N log k)`，`N` 是总记录数，`k` 是参与归并的文件数；堆本身只占 `O(k)` 条记录的内存。

#### 二、TB 数据落地时的完整流程

```text
多个已排序输入文件
  -> 每文件一个顺序读 buffer
  -> 最小堆维护各文件当前记录
  -> 大 buffer 顺序写临时结果文件
  -> 多轮归并
  -> 最终全局有序文件
```

**1. 一次不要打开过多文件。**

- 1000、1 万个文件直接同时打开，可能超过文件描述符上限，也会让每个 buffer 太小、磁盘随机读增多。
- 设置归并路数 `k`，例如内存、文件描述符和磁盘吞吐允许时每轮合并 64 或 128 个文件。
- 第一轮将原文件分成若干组，每组归并出一个临时有序文件；第二轮再归并这些临时文件，直到只剩一个结果文件。

**2. 读写都用大 buffer，避免逐行系统调用。**

- 每个输入文件使用顺序读取 buffer，例如 1～8 MB；输出文件也使用较大的顺序写 buffer。
- 具体 buffer 和 `k` 的大小按可用内存、FD 上限、磁盘类型和压测结果确定。可用内存不能只除以 `k`，还要给堆、解析对象、输出 buffer 和系统页缓存留余量。
- 归并过程几乎都是顺序读和顺序写，适合磁盘吞吐；不要在循环中反复 seek 或频繁打开关闭文件。

**3. 数据格式决定解析和稳定性。**

- 固定长度二进制记录可直接按 key 读取，CPU 开销小；CSV/JSON 需要解析字段，可能先转换为更适合归并的中间格式。
- key 相同怎么办要提前定义：保留全部记录、按时间戳二次排序、去重保留最新版本，还是聚合计数。
- 如果需要稳定排序，堆比较器除业务 key 外再比较 `source_file_id + sequence_no`，保证相同 key 的输出顺序可预测。

#### 三、Go 风格伪代码

```go
type Item struct {
    Key      int64
    Value    []byte
    FileID   int
    Sequence int64
}

// heap 中每个元素都是一个文件当前尚未输出的最小记录。
for _, file := range files {
    if item, ok := readNext(file); ok {
        heap.Push(h, item)
    }
}

for h.Len() > 0 {
    item := heap.Pop(h).(Item)
    writeBuffered(output, item)

    if next, ok := readNext(files[item.FileID]); ok {
        heap.Push(h, next)
    }
}
```

生产代码还要处理文件校验、解析错误、临时文件命名、磁盘满、进度 checkpoint 和中断恢复，不能只写这段核心循环。

#### 四、失败恢复与工程边界

- 每轮归并输出到临时路径，写完后校验记录数、字节数、首尾 key 或 checksum，再原子 rename 为完成文件；不要直接覆盖最终结果。
- manifest 记录输入文件列表、归并轮次、临时输出、checkpoint 和校验值。任务失败后可从上一个完成轮次恢复，不必从 TB 原始文件重新开始。
- 输入文件若仍在追加，必须先按版本/水位线冻结快照，否则“合并期间文件继续变大”会让结果不可重复。
- 多磁盘、多机器时可以先按 key range 做分区，每个分区独立归并；边界 key 要统一规则，最终再按分区顺序拼接。若输入不按 range 切分，分布式 shuffle 的成本可能远高于本地归并。

**面试里推荐这样答：**

> 每个文件内部有序但文件之间无序时，我会做 k 路外部归并。每个文件只顺序读一个 buffer，把各文件当前最小记录放到最小堆；每次弹出堆顶写入输出，再从同一文件补一条。这样全局顺序正确，时间复杂度是 `O(N log k)`，内存只需要 `O(k)` 条记录和读写 buffer。TB 级数据不能无限打开文件，所以会按 64 或 128 路分批归并、多轮产出临时文件；同时用 manifest、checksum 和原子 rename 做断点恢复。相同 key 的去重或稳定顺序要在比较器和业务规则中提前定义。
