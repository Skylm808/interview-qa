## 常用名词速查

> 先看这张表即可；后文首次使用这些缩写时不再反复展开。命令、SQL 关键字和状态名会在各题的上下文中说明。

| 名词 | 通俗含义 |
| --- | --- |
| QPS | 每秒请求数（Queries/Requests Per Second），衡量流量大小。 |
| SKU | 最小库存单位。例如“iPhone 17、黑色、256G”和“白色、256G”是两个 SKU，各有自己的库存。 |
| CDN | 内容分发网络：把图片、静态页面等放到离用户更近的节点，减少源站压力。 |
| LB / Ingress / Gateway | 都在流量入口：LB/Ingress 把请求分发进集群，Gateway（网关）再做鉴权、限流、路由等业务入口处理。 |
| Pod | Kubernetes 中一个服务实例的运行单元；“Gateway × 100”表示网关运行 100 个实例。 |
| Redis / MySQL | Redis 是内存型高速缓存或数据结构服务；MySQL 常作为订单、库存等需要持久保存的业务账本。 |
| Lua | 可在 Redis 内一次性执行多步操作的小脚本，用于避免“先判断、再扣减”被并发请求插队。 |
| MQ / Kafka | 消息队列；Kafka 是常用实现。把请求先排队，消费者按可承受速度处理，起到削峰和解耦作用。 |
| Outbox / CDC | Outbox（本地消息表）与业务数据在同一数据库事务中写入；CDC（变更数据捕获）读取数据库变更后再投递事件，二者都用于避免“数据已写、消息丢失”。 |
| TTL / L1 / KV | TTL 是缓存过期时间；L1 是应用进程内的一级缓存；KV 是按“键 → 值”读取的数据模型。 |
| SDK / API / RPC | SDK 是业务调用的客户端工具包；API 是服务提供的调用接口；RPC 是服务间的远程方法调用。 |
| Trace / Span / p99 | Trace 是一次请求的完整调用链，Span 是链路中的一个步骤；p99 是 99% 请求不超过的耗时，用于观察长尾慢请求。 |
| WebSocket | 浏览器与服务端保持长连接、双方都能主动推消息的协议，常用于聊天和直播。 |
| S3 / OSS / COS | 三种对象存储服务的代表：AWS S3、阿里云 OSS、腾讯云 COS；都适合保存大文件。 |
| 分片 / 时间桶 / fanout | 分片是把一份热点数据或任务拆到多处；时间桶是按时间段分组；fanout（扇出）是把一条消息发给大量连接或下游。 |
| offset / sequence / lag | offset 是消息在分区内的位置；sequence 是业务顺序号；lag 是生产速度超过消费速度后积压的消息量。 |
| ZSET / Top K | ZSET 是 Redis 的有序集合，适合按分数取排行榜；Top K 指排名前 K 名。 |
| checksum / hash / ETag / STS | checksum、hash 是校验内容是否被篡改或损坏的摘要；ETag 是对象存储返回的分片版本/校验标识；STS 是短时有效的临时访问凭证。 |
| OLTP / 宽表 / Overlay / OD | OLTP 指面向订单等在线事务的数据库；宽表把常一起查询的字段展开；Overlay 是叠加在基础地图上的实时变化层；OD 指起点到终点的一对路线请求。 |
| Prometheus / Grafana / Metrics | Prometheus 采集和查询监控指标，Grafana 展示图表和告警；Metrics 就是 QPS、延迟、错误率等数值指标。 |
| 幂等 / 状态机 / 事实源 | 幂等是同一请求重试多次，结果仍只生效一次；状态机规定状态可如何迁移；事实源是最终以哪份可靠数据为准，例如订单通常以 MySQL 为准。 |
| Hot key / Top N / 高基数 | Hot key 是访问特别集中的缓存键；Top N 是排名前 N 项；高基数指标签取值过多，例如把每个完整用户 ID 都做成监控标签会压垮监控系统。 |

## 近期大厂场景题补充（2025 年公开面经线索）

### 1. 弹幕系统怎么设计？（Bilibili / 直播、视频内容方向高频）

**先澄清需求：**

- 视频弹幕按播放时间轴出现；直播弹幕按实时房间广播。
- 用户能发、能看到、能举报；审核违规内容，主播可配置屏蔽词、等级和开关。
- 播放高峰不能把所有历史弹幕一次性下发；同一条弹幕允许最终一致，但不能重复展示、不能明显乱序。

**先拆成两条链路，不要把点播和直播混在一起：**

```text
点播：发弹幕 -> 写入/审核 -> 按视频时间轴查询 -> 客户端调度展示
直播：发弹幕 -> 风控/审核 -> 房间分区 -> WebSocket 广播 -> 在线用户
```

点播的核心是“按视频时间范围高效读取”，直播的核心是“一个房间向大量在线连接扇出”。两者的存储、缓存和容量模型不同，但审核、幂等、反垃圾和观测能力可以复用。

#### 一、数据模型与分片

一条弹幕至少包含：

```text
danmu_id, video_id / room_id, user_id,
video_time_ms, send_time, content, color, mode,
status, audit_version, client_msg_id
```

- `client_msg_id` 由客户端生成，用于重试去重；服务端对 `(user_id, client_msg_id)` 建唯一约束或幂等记录。
- 点播按 `video_id + 时间桶` 分片，例如 5 秒或 10 秒一个 bucket；查询某段播放进度只读相邻几个 bucket。
- 直播按 `room_id` 做一致性哈希或显式路由，使同一房间的实时消息进入同一逻辑分区，保证该分区内顺序。
- 热门视频、超级直播间不能只靠一个分片：点播继续按时间桶拆；直播按“房间 + 广播分片”拆成多个 fanout worker。

#### 二、发送链路：先校验，再异步持久化和分发

```text
Client
  -> Gateway：登录态、设备/IP 限频、长度和协议校验
  -> Danmu Write Service：幂等、禁言、房间/视频状态校验
  -> 内容风控：词库、规则、模型（同步快速判定 + 异步复审）
  -> Kafka：按 video_id / room_id 分区
  -> Persist Consumer：OLTP / 宽表 / 对象存储归档
  -> Dispatch Consumer：直播房间广播；点播缓存失效/增量索引
```

- 网关限流按用户、设备、IP、房间分别做，异常用户直接丢弃或进入更严格审核，不能让一个脚本占满热门房间带宽。
- 发送接口成功的语义要说清：可以先返回“已接收/审核中”，消息进入可靠 MQ 后再异步落库；只有需要即时展示的直播白名单弹幕才走快速审核通道。
- Kafka key 选 `room_id` 或 `video_id + bucket`，保证同 key 有序；消费者写库使用 `danmu_id` 唯一键，允许至少一次投递。

#### 三、点播读取：按播放进度拉取，不全量加载

客户端播放到 `t` 时，预取 `[t, t + 30s]` 的弹幕，并在本地按 `video_time_ms` 放入小根堆/时间轮，到点渲染。

```text
Player -> Danmu Read API(video_id, start_ms, end_ms)
       -> Redis：video_id:bucket 缓存
       -> Danmu Store：按 video_id + bucket 范围扫描
```

- 热门视频的最近时间桶放 Redis/CDN 边缘缓存，内容变更通过版本号或短 TTL 处理；冷数据放宽表、KV 或列式存储，并按天/月归档。
- 返回时限制条数、按热度/密度采样。屏幕一秒能展示的弹幕有限，“全量返回”既浪费又影响观看体验。
- 删除、审核不通过的弹幕要有状态版本；读侧过滤状态，热缓存用消息或短 TTL 尽快收敛。

#### 四、直播广播：连接网关与房间扇出解耦

```text
Danmu Dispatch
  -> Room Router（room_id -> fanout shard）
  -> Fanout Worker
  -> WebSocket Gateway 集群
  -> 客户端连接
```

- WebSocket Gateway 只维护连接和背压，不承担复杂审核/写库；每个连接有发送队列上限。
- 一个超级房间会绑定多个 fanout worker；worker 只向“本机订阅该房间的 Gateway”推消息，避免中心节点逐连接遍历。
- 客户端消息带 `sequence`；断线重连只补最近 N 秒或提示“实时消息不可追溯”，不要无限补历史。
- 慢客户端优先丢低优先级弹幕、合并/采样，再断开；绝不能让一个慢连接反压整个房间。

#### 五、审核、顺序与故障处理

- 审核采用“同步规则拦截 + 异步模型复审 + 人审申诉”。高风险内容先隐藏，审核结果以状态变更事件驱动读侧收敛。
- 房间内以 Kafka 分区 offset 或服务端 sequence 排序；跨分片无法提供绝对全局顺序，客户端按小时间窗口容忍轻微乱序即可。
- Redis 故障时，点播降级为限量读存储或暂时关闭弹幕；直播保留发送和广播的核心链路，关闭历史补偿和非必要特效。
- MQ 积压时，对低等级/重复/机器识别风险弹幕采样或拒绝，并按房间隔离消费，不能让一个热点房间拖垮全局。

**容量与观测：**

- 先估算“发言 QPS、每条平均字节数、在线连接数、热门房间峰值、每个连接的下行带宽”，再定分区数和 Gateway 数。
- 核心指标：发言接受率、审核耗时、Kafka lag、单房间 fanout 延迟、WebSocket 发送队列长度、丢弃率、点播读取 p99、重复率和乱序率。

**面试里推荐这样答：**

> 我会把点播弹幕和直播弹幕拆开。点播按 `video_id + 时间桶` 存储，播放器按当前进度预取未来几十秒，客户端定时展示，避免一次加载整条视频的弹幕；热门 bucket 缓存到 Redis 或 CDN。直播则通过 WebSocket Gateway 维护连接，按 `room_id` 路由到房间分区，再由 fanout worker 扇出到订阅该房间的网关。发送端先做幂等、禁言和风控，进入 Kafka 后异步落库和分发；用分区 offset 保证同房间近似有序。超级房间要拆广播分片，慢客户端按优先级丢弃或采样，不能反压整个房间。审核、删除和举报通过状态事件让读侧最终收敛，关键看发送成功率、MQ 积压、单房间广播延迟和连接队列长度。

### 2. 高并发订单查询接口怎么设计？（拼多多类电商场景）

**目标：** 用户频繁刷新“我的订单”时，查询接口仍要低延迟；状态变更可在短时间内最终一致，但不能越权、不能漏掉刚支付的订单，也不能让缓存击穿拖垮订单库。

**数据与索引：**

- 订单主表按 `buyer_id` 或 `order_id` 分库分表；用户订单列表建立 `(buyer_id, status, created_at DESC, order_id)` 覆盖索引。
- 订单详情、商品快照、物流、售后拆为不同读模型；列表接口只返回卡片字段，详情页再按需拉取。
- 列表使用游标分页：`created_at + order_id`，不要在深分页使用大 `OFFSET`。

```text
Client -> Gateway（鉴权/限流） -> Order Read API
       -> L1 本地缓存 -> Redis 订单卡片/列表缓存
       -> Read Model / 从库 / 搜索索引
       -> 订单、物流、售后聚合（并行且有超时）
```

**缓存和一致性：**

- 订单创建、支付、取消、发货产生 outbox 事件；消费者更新 Redis 和读模型，失败可重放。
- 对“刚支付”这种用户强感知场景，写接口响应可以携带新状态，客户端短暂本地合并；或在短窗口内走主库/版本校验，不能盲信从库。
- 缓存 key 带用户和查询条件，设置随机过期；热点用户使用 singleflight（同一个缓存键只允许一个请求回源重建）或互斥重建，空结果也短暂缓存。
- 缓存挂了时，按用户限流、只查基础订单字段、限制分页深度，读库必须有熔断和排队保护。

**面试里推荐这样答：**

> 我会把“订单列表”和“订单详情”分开建读模型，列表按用户和状态建立覆盖索引，用游标分页，避免深分页扫描。读路径先走本地和 Redis 缓存，未命中再走只读模型；订单状态变更用 outbox 事件异步更新缓存和索引。支付后短时间的可见性是关键，我会让写接口返回新状态，并对短窗口请求做版本校验或读主库。缓存故障时不是直接全量穿透，而是按用户限流、降级字段和限制深分页，保护订单主库。

### 3. 跨境物流状态同步怎么设计？（拼多多 / 电商履约场景）

物流商回调存在乱序、重复、延迟和不同状态码，答案的重点不是“接收 webhook”，而是把外部不可靠事件变成内部可追溯的订单状态。

```text
物流商 Webhook / 主动轮询
  -> 接入层：验签、限流、原始报文落盘
  -> Event Normalize：标准化状态、幂等键、时区转换
  -> Kafka（tracking_no 分区）
  -> State Machine：校验状态迁移、写轨迹与当前态
  -> Outbox -> 订单/通知/售后/数据仓库
```

- 以 `carrier + tracking_no + carrier_event_id` 或报文指纹作为幂等键；原始事件永久或长期留存，便于争议处理和重放。
- 同一运单按 `tracking_no` 分区保证处理顺序，但仍要在状态机中拒绝非法回退，例如“已签收”不能被过期的“运输中”覆盖。
- 状态标准化要有映射版本：物流商的几十种码映射为“揽收、运输、清关、派送、签收、异常”等内部状态，同时保留原始码。
- 回调丢失不能只靠对方重试。对未签收订单建立轮询/补偿任务，按阶段设置不同频率；连续失败进入人工或告警队列。
- 数据库事务内写当前态、轨迹和 outbox；下游通过事件消费，避免在接收回调的同步链路直接调用多个系统。

**面试里推荐这样答：**

> 外部物流回调要按不可靠消息处理：先验签并保存原始报文，再做状态标准化、幂等和异步处理。同一运单按单号分区，状态机校验状态迁移，所以重复和乱序都不会把当前态写错。当前态、轨迹和 outbox 在本地事务内落库，订单、通知等下游异步消费。对于回调缺失，我会对未完成运单做分阶段轮询补偿，并把异常率、状态停留时长和回调延迟做成监控。

### 4. 实时排行榜 / Top K 怎么设计？（直播打赏、热榜、活动榜）

**先问清楚：** 排行榜是全站还是单房间？按金额、次数还是热度？要求强实时、分钟级还是日榜？是否允许撤销/退款？这些决定实现。

- 单房间、实时前 100：消费打赏事件，Redis ZSET 按 `room_id` 维护分数；读取 `ZREVRANGE 0 99 WITHSCORES` 即可。
- 全站海量榜：先按用户或房间分区聚合，局部 Top K 再合并为全局 Top K，不能把所有明细集中到一个 ZSET。
- 滑动窗口热榜：将事件按分钟分桶，分桶内累加，查询时合并最近 N 个桶；过期桶删除。更高吞吐时可用 Flink/Spark（流式计算框架）做窗口聚合并把结果落 Redis。
- 退款、撤销、风控扣分以补偿事件更新，不直接修改历史明细；排行榜展示附带 `as_of_time`，让用户知道数据新鲜度。
- 热点榜单读取缓存，写入通过 MQ 削峰；对同一用户/房间做批量聚合后再写 Redis，避免每一笔交易都造成热 key 写放大。

**面试里推荐这样答：**

> 小范围实时榜我会用 Redis ZSET，按房间分 key，读前 100 是 `O(logN + K)`；全站榜不能集中更新，而是按分区聚合局部 Top K，再合并。热榜用时间桶或流计算维护滑动窗口，退款和风控扣分走补偿事件。展示时标明数据时间，并监控热点 key、消费延迟与榜单刷新延迟。

### 5. 线上接口 p99 从 500 ms 升到 700 ms，怎么排查？（搜广推 / 内容业务场景）

**第一反应不是立刻改代码，而是缩小范围：**

```text
是否所有地域/版本/接口都变慢？
  -> 从何时开始？和发布、流量、配置、上游变更是否相关？
  -> 慢在 Gateway、应用、Redis、DB、RPC、MQ 还是外部依赖？
  -> 是平均值变慢，还是少量长尾请求拉高 p99？
```

**排查顺序：**

1. 看指标面板：QPS、错误率、p50/p95/p99、CPU、GC、线程池队列、连接池等待、网络重传、Redis/DB/RPC 的耗时和命中率。
2. 用 trace 按版本、机房、用户分群，对比变慢前后的关键 span；确认是本服务算得慢，还是某个下游耗时变长。
3. 查变更：代码发布、配置、特征开关、索引/表结构、缓存 TTL、流量来源、热点商品或大客户。
4. 若是数据库，检查慢 SQL、执行计划、锁等待、主从延迟、连接数；若是缓存，检查命中率、热 key、驱逐、网络和连接池；若是应用，检查 GC、CPU 火焰图、线程池和同步锁。
5. 先止血：回滚/关闭开关、扩容、对慢下游熔断降级、缓存预热或限流；根因修复后通过压测和回归验证。

**面试里推荐这样答：**

> 我先确认是整体变慢还是 p99 长尾，再按地域、版本和调用链分桶。通过 trace 定位耗时 span，并结合发布记录、QPS、缓存命中率、线程池、GC、DB 慢 SQL 和下游耗时判断根因。线上优先用回滚、降级、限流和扩容止血，不能一上来就改代码；修复后用压测和同口径指标验证 p99 已恢复，并补齐告警和复盘。

### 6. 用户不断上传文件，如何快速、可靠地分发到服务器集群？（小红书类内容基础设施场景）

**不要把“上传”与“分发”理解成同步复制到所有机器。** 文件先进入可靠的对象存储或内容仓库，服务集群按需拉取、预热或接收元数据通知；只有确有本地副本需求时，才由调度器选择目标节点分发。

```text
Client -> Upload API -> 分片上传 / 校验 -> Object Storage（源文件）
                                      -> 元数据 DB（版本、hash、状态）
                                      -> Kafka：file.ready
                                      -> Scheduler：选目标节点、限速、重试
                                      -> Agent：拉取、校验、原子切换版本
                                      -> Registry：上报可用副本和健康状态
```

- **上传可靠性**：分片带 checksum，服务端合并后再次校验；使用 `upload_id + part_no` 幂等，断线可续传。对象存储写成功且元数据事务/outbox 成功后，文件才进入 `READY`。
- **分发调度**：按机房、剩余磁盘、CPU/网络水位、已有副本和亲和性选择节点；同一大文件限制并发，避免把一个机房的带宽打满。任务状态为 `PENDING（待调度） -> RUNNING（分发中） -> VERIFIED（校验通过） -> ACTIVE（生效）/FAILED（失败）`。
- **一致性**：文件名不可变，使用 content hash 或版本号；节点下载到临时路径，验 hash 后原子 rename/symlink 切换。读服务只读取 `ACTIVE` 版本，避免读到半文件。
- **失败与重试**：任务可重试但按文件/节点幂等；失败指数退避并换节点，连续失败告警。调度器宕机时任务从 DB/Kafka 恢复，Agent 通过心跳和本地 manifest 对账。
- **加速与成本**：热点文件通过 CDN/边缘节点预热；冷文件按需拉取。跨地域采用就近副本和限速队列，不能让大文件分发抢占在线请求带宽。

**面试里推荐这样答：**

> 我会把对象存储作为文件事实源，分发的是带版本和 hash 的元数据任务，而不是在上传请求里同步复制。上传支持分片、断点续传和 checksum；文件进入 READY 后通过 outbox 事件交给调度器。调度器按机房、容量和网络水位选节点，Agent 下载到临时目录、验 hash 后原子切换为 ACTIVE。任务和 Agent 都设计成幂等，失败换节点重试并可对账恢复；热点文件预热到 CDN 或边缘节点，跨地域分发限速，保护在线流量。

## 业务系统与真实故障场景
### 7. 百万用户同时抢 100 台 iPhone，秒杀系统怎么设计？

#### 一、先做总体抽象：这不是“卖 100 台手机”，而是“百万请求竞争 100 个资格”

这道题的矛盾是：输入端可能瞬间有百万级请求，最终真正成功的最多只有 100 个。系统不应该努力把百万请求都送进数据库，而应该完成三件事：

```text
1. 准入：尽早挡掉机器人、重复点击和超出容量的流量
2. 资格预占：从百万请求中原子地选出最多 100 个不同用户
3. 订单结算：把这 100 个资格可靠地变成订单，失败则只回补一次
```

对应的总体架构是：

```text
1 000 000 用户同时点击
        │
        ├─> CDN：活动页、图片、规则静态化
        │
        ▼
LB / Ingress -> Gateway 集群
  鉴权、活动令牌、防刷、用户/IP/设备限频、Pod 本地自保护
        │
        ▼
热点 SKU 全局准入预算（必要时）
  只让 Redis 库存链路能承受的请求进入
        │
        ▼
Redis Lua
  活动校验 + 一人一单 + stock > 0 + stock-- + reservation_id
        │
        ├─ 失败：立即返回“已抢过 / 已售罄 / 请求过多”
        │
        └─ 成功：最多 100 条资格记录
                    │
                    ▼
             可靠事件 / MQ 削峰
                    │
                    ▼
             Order Service 集群
                    │
                    ▼
      MySQL：订单、库存账本、状态机、Outbox
```

先澄清容量口径：**百万用户不等于稳定 100 万 QPS。**要问用户在几秒内点击、每人是否重试、客户端会发几次请求。例如 100 万用户集中在 10 秒内点击一次，平均约 10 万 QPS，但第一秒和客户端重试可能让峰值更高。因此容量设计应同时给出：参与用户数、峰值 QPS、持续时间、请求大小和重试率。

业务语义也要先定清：

- 每个用户最多买一台，重复请求返回同一个结果；
- Redis 抢到的是“购买资格”，不是已经支付成功；
- 资格有支付 TTL，超时未支付是否回补活动库存由业务规则决定；
- 接口先返回 `QUEUED / QUALIFIED / SOLD_OUT` 等明确状态，客户端查询订单结果，不要疯狂重试提交；
- 默认只能做到按服务端到达和处理顺序的近似先到先得；若要求绝对公平，应改成报名后抽签，而不是声称跨网络严格先来先得。

**核心目标：**不超卖、不重复下单；绝大部分无效流量在数据库前失败；Redis、MQ、MySQL 之间短暂不一致时可以恢复和对账。下面再分别展开准入、限流、库存、订单和异常处理。

#### 二、流量怎样从百万用户压到数据库可承受范围？

- **CDN 和静态化：** 活动页、图片、规则提前缓存到 CDN，避免它们占用后端连接；前端按钮置灰、验证码和动态路径只能减少误点，服务端仍要校验。
- **网关限流：** 按用户、IP、设备限频，先挡脚本和重复点击。每个网关实例使用本地令牌桶，保护当前实例，不需要每个请求都访问 Redis。
- **售罄快速失败：** Redis 库存归零后发布售罄事件，让各 Gateway / Seckill Pod 设置短期本地 `sold_out` 标记，后续请求可以在入口直接失败。这个标记只是减压缓存，抢购成功与库存真相仍以 Redis 预占结果为准；补库存或重新开售时要通过带版本的配置事件统一失效，不能让某个 Pod 擅自清除。
- **商品级限流：** 若单个热点 SKU 进入 Redis 的请求仍过多，再用 Redis 全局令牌桶限制所有机器合计的商品 QPS。例如 Redis 库存逻辑安全上限是 5 000 QPS，就不让 10 万 QPS 全部冲进去。
- **MQ 削峰：** Redis 预扣成功后写 MQ（消息队列）；订单服务按数据库可承受的速度消费。MQ 把瞬时洪峰变成稳定写入，但不负责库存正确性。

可以把流量理解为：

~~~text
1 000 000 用户（例如峰值约 100 000 QPS）
  -> CDN / 前端过滤
  -> 网关用户、IP 限流
  -> 商品级限流（必要时）
  -> Redis 库存脚本
  -> 只有抢到库存的少量请求进入 MQ 和 MySQL
~~~

#### 三、令牌桶和各类 Pod 怎么设置？

先回答一个容易混淆的问题：**Gateway 当然可以部署多个 Pod，而且高并发场景下通常会横向扩容。** Kubernetes 中通常是一个逻辑上的 Gateway Service，后面挂多个无状态 Gateway Pod，由 LB / Ingress 分发流量：

```text
                         Kubernetes Service
用户流量 -> LB / Ingress ───────┬──> Gateway Pod 1
                                ├──> Gateway Pod 2
                                ├──> Gateway Pod 3
                                └──> ... Gateway Pod N
```

也可以按机房、业务或活动拆成多个 Gateway 集群，但每个集群内部仍然可以有很多 Pod。**Pod 数量负责扩展计算能力，令牌桶负责限制流量；两者不是一回事。**

##### 3.1 先分清楚三种限流目标

一套秒杀链路里，不是“到处都放同样的令牌桶”，而是每一层保护的对象不同：

```text
100 000 QPS 外部请求
        │
        ▼
┌─────────────────────────────────────────────┐
│ ① 用户 / IP / 设备限频                      │
│ 防刷、防止一个用户重复点击；要求跨 Pod 生效 │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ ② 每个 Gateway Pod 的本地桶                 │
│ 只保护当前 Pod 的 CPU、内存和连接池          │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ ③ 热点 SKU 的全局桶                         │
│ 所有 Pod 共享，保护 Redis 库存链路的总预算   │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
             Seckill Service 多个 Pod
             （每 Pod 还有本地自保护）
                       │
                       ▼
             Redis Lua：资格校验、扣库存
                       │ 只有抢到库存的请求
                       ▼
                      MQ
                       │ 按数据库能力消费
                       ▼
              Order Service 多个 Pod -> MySQL
```

| 限流层 | 状态放在哪里 | 保护对象 | 是否严格控制集群总量 |
| --- | --- | --- | --- |
| 用户 / IP / 设备限频 | Redis 或独立限流服务；如果只做近似防刷，也可本地计数 | 公平性、防刷和重复请求 | 使用共享状态时可以 |
| Gateway Pod 本地桶 | 当前 Pod 内存 | 当前网关实例 | 不可以；只能限制本实例 |
| 热点 SKU 全局桶 | Redis + Lua 或专用分布式限流服务 | 所有实例共享的 Redis / 热点 SKU 处理预算 | 可以 |
| Seckill Pod 本地桶 / 并发上限 | 当前 Pod 内存 | 当前秒杀服务实例及其连接池 | 不可以；只做实例自保护 |
| Order Consumer 并发和消费速率 | 消费者配置、线程池、连接池 | MySQL 写入能力 | 通过总消费并发近似控制；通常不在入口再做令牌桶 |

##### 3.2 本地桶和全局桶究竟有什么区别？

**本地桶：每个 Pod 各有一只，便宜但互相不知道。**

```text
Gateway Pod 1：R=1 000/s，B=200 ─┐
Gateway Pod 2：R=1 000/s，B=200 ─┼─> 理论合计约 N × 1 000 QPS
Gateway Pod 3：R=1 000/s，B=200 ─┘   但受负载是否均匀、Pod 数变化影响
```

- 优点：纯内存操作，速度快，不需要每个请求都访问 Redis。
- 缺点：各 Pod 不共享余额。10 个 Pod 每个放 1 000 QPS，集群理论上就可能放 10 000 QPS；扩到 20 个 Pod 后可能变成 20 000 QPS。
- 适合：保护当前实例，避免单个 Pod 因流量倾斜而 CPU 打满、连接池耗尽。

因此，**用于 Pod 自保护时，`R_local` 应根据“这个 Pod 自己能安全处理多少”来设，而不是简单用集群目标除以 Pod 数。**

```text
R_local = 单 Pod 压测安全 QPS × 安全系数
```

例如单个 Gateway Pod 在 1 500 QPS 时 p99 和 CPU 仍稳定，取 70% 安全系数：

```text
R_local = 1 500 × 70% ≈ 1 000 QPS
```

这样即使负载不均，某个 Pod 也会在自己的安全线附近拒绝请求，不会因为其他 Pod 还有空闲就把自己拖垮。

**全局桶：所有 Pod 共同消费一份额度，精确保护共享下游。**

```text
Gateway Pod 1 ─┐
Gateway Pod 2 ─┼─> Redis / 限流服务中的 sku:1001 共享桶
Gateway Pod 3 ─┘          R_global=4 800/s，B_global=600
                                   │
                          集群合计不能长期超过 4 800 QPS
```

不管 Gateway 和 Seckill Service 有多少 Pod，它们访问同一个 SKU 时都从同一个逻辑桶取令牌。因此扩容 Pod 只会增加处理能力，不会自动放大这个 SKU 的总流量预算。

**全局 SKU 桶放在哪一层？** 逻辑上应放在“进入被保护的 Redis 库存逻辑之前”，物理上有三种常见实现：

```text
方案 A：Gateway 分布式限流插件 -> Seckill Service -> Redis 库存脚本
方案 B：Gateway -> Seckill Service 入口的分布式限流器 -> Redis 库存脚本
方案 C：Gateway -> Seckill Service -> 一个 Lua 同时完成限流 + 资格校验 + 扣库存
```

- Gateway 已经能可信地取得活动 ID 和 SKU，并希望尽早拒绝流量时，可以选方案 A。
- 只有 Seckill Service 才能完成参数、活动状态和路由校验时，可以选方案 B。
- 限流桶和库存位于同一个 Redis 分片、脚本足够短且能接受二者耦合时，可以选方案 C，减少一次 Redis 往返。

三种方案选一种即可。**同一个请求不能在 Gateway 和 Seckill Service 对同一个全局桶各扣一次令牌**，否则实际额度会被重复消耗。本地 Pod 桶仍然可以同时存在，因为它保护的是实例自身，不是同一份全局预算。

全局桶适合保护**真正共享的瓶颈**，例如：

- 某个热点 SKU 的 Redis 库存脚本；
- 第三方支付接口的总调用配额；
- 一组服务共享的数据库写入能力；
- 租户购买的全局 QPS 套餐。

全局桶不能无限滥用，因为每次判断都需要跨网络访问 Redis 或限流服务。只需要保护单个 Pod 时，用本地桶更合适。

##### 3.3 工程实现到底用 `rate`、Sentinel-Go，还是 Redis + Lua？

先给结论：

```text
单个 Pod 的本地令牌桶
  ├─ 需求简单：golang.org/x/time/rate
  └─ 需要动态规则、监控、热点参数、熔断等治理能力：Sentinel-Go

多个 Pod 共享的热点 SKU 全局桶
  ├─ 中小规模、已有 Redis：Redis + Lua
  └─ 大规模统一治理：独立分布式限流服务 / API Gateway 全局限流组件
```

| 方案 | 状态存在哪里 | 适合做什么 | 能否直接保证跨 Pod 总 QPS |
| --- | --- | --- | --- |
| `golang.org/x/time/rate` | 当前 Go 进程内存 | Gateway / Seckill Pod 的本地令牌桶 | 不能 |
| Sentinel-Go 普通流控 | 当前 Go 进程的统计结构 | 本地 QPS、并发数、Warm Up、匀速排队、系统自适应保护 | 不能 |
| Sentinel-Go 热点参数流控 | 当前 Go 进程的热点参数统计结构 | 当前 Pod 内按 SKU、用户等参数分别限流 | 不能 |
| Redis + Lua | 所有 Pod 共享的 Redis | SKU、租户、第三方配额等严格共享预算 | 可以控制共享总量 |
| 独立全局限流服务 | 专门的 Token Server / RLS 集群 | 大规模、多语言、统一规则和配额租约 | 可以，精度取决于实现 |

###### 方案一：`golang.org/x/time/rate`，适合 Pod 本地自保护

Go 官方扩展库 `golang.org/x/time/rate` 提供的 `Limiter` 就是进程内令牌桶。`rate.NewLimiter(R, B)` 中，第一个参数是每秒补充的令牌数，第二个参数是桶容量；Limiter 创建时桶是满的，并且可以被多个 goroutine 并发使用。

Gateway 快速拒绝通常使用 `Allow()`：

```go
package middleware

import (
    "net/http"

    "golang.org/x/time/rate"
)

// 当前 Gateway Pod 最多长期放行 1 000 QPS，允许 200 个瞬时突发请求。
var podLimiter = rate.NewLimiter(rate.Limit(1000), 200)

func RateLimit(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !podLimiter.Allow() {
            w.Header().Set("Retry-After", "1")
            http.Error(w, "too many requests", http.StatusTooManyRequests)
            return
        }

        next.ServeHTTP(w, r)
    })
}
```

这里的 `podLimiter` 只存在于当前进程：

```text
Gateway Pod 1：自己的 rate.Limiter
Gateway Pod 2：自己的 rate.Limiter
Gateway Pod 3：自己的 rate.Limiter

三个 Limiter 之间不共享剩余令牌
```

所以 10 个 Pod 都配置 `R=1 000/s`，集群理论放行量可能接近 10 000 QPS，而不是 1 000 QPS。

`rate.Limiter` 还有三种常用行为：

- `Allow()`：有令牌就通过，没有就立即返回 `false`，适合在线秒杀和 Gateway 快速失败。
- `Wait(ctx)`：没有令牌就等待，并受 `context` 超时控制，适合允许短暂等待的后台任务。
- `Reserve()`：预订未来令牌并得到等待时间，适合调用方自己安排调度。

秒杀入口通常不要无上限地 `Wait()`。大量请求在 Gateway 内等待会占用 goroutine、连接和内存，把“限流”变成“排队拖垮自己”。如果允许排队，也必须有很短的超时和明确的队列上限。

如果要按用户或 SKU 创建很多本地 Limiter，不能简单使用一个永不删除的 `map[string]*rate.Limiter`，否则高基数 key 会持续占用内存。应使用带过期淘汰的缓存、分片 LRU，或者只为已识别出的 Top N 热点创建 Limiter。

###### 方案二：Sentinel-Go，适合需要治理能力的本地限流

Sentinel-Go 不只是一个令牌桶库，它围绕“资源”提供 QPS / 并发限制、Warm Up、匀速排队、热点参数、熔断和系统自适应保护等能力。规则还能通过配置中心动态下发，更适合已有微服务治理体系的项目。

对 Gateway Pod 的本地 QPS 限制，可以这样写：

```go
package main

import (
    "log"

    sentinel "github.com/alibaba/sentinel-golang/api"
    "github.com/alibaba/sentinel-golang/core/base"
    "github.com/alibaba/sentinel-golang/core/flow"
)

func initSentinel() {
    if err := sentinel.InitDefault(); err != nil {
        log.Fatal(err)
    }

    _, err := flow.LoadRules([]*flow.Rule{
        {
            Resource:               "seckill-api",
            TokenCalculateStrategy: flow.Direct,
            ControlBehavior:        flow.Reject,
            Threshold:              1000,
            StatIntervalInMs:       1000,
        },
    })
    if err != nil {
        log.Fatal(err)
    }
}

func handleSeckill() error {
    entry, blockErr := sentinel.Entry(
        "seckill-api",
        sentinel.WithTrafficType(base.Inbound),
    )
    if blockErr != nil {
        return blockErr
    }
    defer entry.Exit()

    return doSeckill()
}
```

`Threshold=1000` 表示当前 Sentinel-Go 进程中，这个资源每秒最多通过约 1 000 次。假设有 10 个 Pod，每个 Pod 都加载这条规则，那么这是“每 Pod 1 000 QPS”，不是“整个集群合计 1 000 QPS”。

Sentinel-Go 还支持热点参数流控。例如把 `skuID` 作为参数传给 `sentinel.Entry(..., sentinel.WithArgs(skuID))`，再通过 `hotspot.LoadRules` 配置 `ParamIndex=0`，就能在当前 Pod 内分别统计不同 SKU 的 QPS：

```go
_, err := hotspot.LoadRules([]*hotspot.Rule{
    {
        Resource:        "seckill-by-sku",
        MetricType:      hotspot.QPS,
        ControlBehavior: hotspot.Reject,
        ParamIndex:      0,    // WithArgs 的第 0 个参数是 skuID
        Threshold:       100,  // 当前 Pod 内，每个 SKU 最多约 100 QPS
        BurstCount:      20,
        DurationInSec:   1,
    },
})

entry, blockErr := sentinel.Entry(
    "seckill-by-sku",
    sentinel.WithArgs(skuID),
)
```

这适合处理“某个 SKU 把当前 Pod 打热”的问题，但仍然是本地状态。10 个 Pod 都配置 100 QPS 时，同一 SKU 的集群理论总量仍可能接近 1 000 QPS。

因此在 Go 项目里可以这样选：

- 只需要一个稳定、轻量的本地令牌桶：优先 `x/time/rate`，代码和依赖都更简单。
- 已经接入 Sentinel-Go，或还需要动态规则、指标、热点参数、Warm Up、熔断、系统保护：使用 Sentinel-Go。
- 需要多个 Pod 对同一 SKU 共享一份严格额度：不能只使用上述本地模式，仍需 Redis + Lua 或专用全局限流服务。

还要注意，Sentinel-Go 的普通 QPS 流控、匀速排队和热点参数流控使用的统计与整形机制并不完全等价于 `x/time/rate` 的经典令牌桶。面试中可以把它们都归为“流量控制方案”，但不要把 Sentinel 的每一种规则都笼统称为令牌桶。

###### 方案三：Redis + Lua，实现热点 SKU 的跨 Pod 全局桶

全局桶需要把 `tokens` 和 `last_refill_time` 放在共享存储中，并用 Lua 原子完成“补充令牌、判断、扣减”。下面是简化实现：

```lua
-- KEYS[1]：例如 rate_limit:{sku:1001}
-- ARGV[1]：R，每秒补充令牌数
-- ARGV[2]：B，桶容量

local rate = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])

-- 使用 Redis 服务器时间，避免不同 Pod 的本地时钟不一致。
local redis_time = redis.call('TIME')
local now = tonumber(redis_time[1]) + tonumber(redis_time[2]) / 1000000

local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'last_refill')
local tokens = tonumber(bucket[1])
local last_refill = tonumber(bucket[2])

if tokens == nil then
    tokens = capacity
    last_refill = now
end

local elapsed = math.max(0, now - last_refill)
tokens = math.min(capacity, tokens + elapsed * rate)

local allowed = 0
if tokens >= 1 then
    tokens = tokens - 1
    allowed = 1
end

redis.call('HSET', KEYS[1],
    'tokens', tokens,
    'last_refill', now)

-- 长时间无请求时自动清理桶；TTL 取装满时间的两倍。
local ttl_ms = math.max(1000, math.ceil(capacity / rate * 2000))
redis.call('PEXPIRE', KEYS[1], ttl_ms)

return allowed
```

所有 Gateway / Seckill Pod 都对同一个 key 执行这段脚本：

```text
Pod 1 ─┐
Pod 2 ─┼─ EVALSHA -> rate_limit:{sku:1001} -> 同一份 tokens
Pod 3 ─┘
```

Lua 在 Redis 中原子执行，不会出现两个 Pod 同时读到最后一个令牌并都扣减成功。生产环境应使用 `SCRIPT LOAD + EVALSHA`，处理脚本缓存丢失后的 `NOSCRIPT` 重载，并记录放行数、拒绝数、Redis p99 和错误率。

如果限流 key 与库存 key 需要放进同一个 Lua 脚本，在 Redis Cluster 中要用相同 hash tag，例如：

```text
rate_limit:{sku:1001}
stock:{sku:1001}
bought_users:{sku:1001}
```

这样相关 key 才会落在同一个 hash slot。是否把“限流 + 资格校验 + 扣库存”合成一个脚本，要在少一次网络往返和脚本耦合、执行耗时之间取舍。

Redis + Lua 也有边界：每个请求都访问 Redis 会增加网络开销，热点 SKU 的桶本身也可能成为 hot key。如果流量达到很高量级，可以让各 Pod 从全局限流服务批量租用一小段本地额度，或使用独立 RLS / Token Server；这样能降低中心节点请求量，但会牺牲一点精确度，并要处理租约过期和故障回收。

###### 实际推荐组合

对于本文的秒杀方案，推荐组合不是“三选一”，而是分层使用：

```text
Gateway Pod
  └─ x/time/rate 或 Sentinel-Go：本地自保护，R=1 000/s、B=200
            │
            ▼
热点 SKU 全局限流
  └─ Redis + Lua / 独立限流服务：共享 R=4 800/s、B=600
            │
            ▼
Seckill Service Pod
  └─ Sentinel-Go 并发隔离或本地 limiter：保护连接池和当前实例
            │
            ▼
Redis 库存 Lua -> MQ -> Order Consumer 并发控制 -> MySQL
```

如果团队没有 Sentinel 体系，`x/time/rate + Redis Lua` 已经足够清晰可靠；如果项目本身已经使用 Sentinel-Go 做规则管理和熔断降级，就用 Sentinel-Go 代替本地 `rate.Limiter`，但全局额度仍由共享组件承担。

相关官方资料：[Go `rate` 包](https://pkg.go.dev/golang.org/x/time/rate)、[Sentinel-Go 流量控制](https://github.com/alibaba/sentinel-golang/wiki/%E6%B5%81%E9%87%8F%E6%8E%A7%E5%88%B6)、[Sentinel-Go 热点参数限流](https://github.com/alibaba/sentinel-golang/wiki/%E7%83%AD%E7%82%B9%E5%8F%82%E6%95%B0%E9%99%90%E6%B5%81)。

##### 3.4 `R` 和 `B` 应该怎么计算？

令牌桶有两个参数：

- `R`：每秒补充多少令牌，决定长期平均放行速率。
- `B`：桶最多存多少令牌，决定空闲一段时间后最多能一次性释放多大的突发。

在任意持续 `T` 秒的时间段内，一个装满的令牌桶最多大约放行：

```text
最大放行量 ≈ B + R × T
```

所以 `B` 不能机械地设置成 `2R`。如果下游只能承受 5 000 QPS，却把 `B` 设置成 10 000，那么桶装满后可能瞬间放出 10 000 个请求，令牌桶反而没有保护住下游。

**设置本地桶：**

```text
R_local = 单 Pod 压测安全 QPS × 60%～80%
B_local = 该 Pod 可承受的短时额外请求量
```

`B_local` 要结合线程/协程池、连接池和允许的排队时间确定。例如 Gateway Pod 长期安全值是 1 000 QPS，只希望吸收约 200 个瞬时请求，就设置 `R=1 000/s、B=200`，而不是为了“允许两秒突发”直接设 `B=2 000`。

**设置全局桶：**

```text
R_global = 被保护下游的集群安全 QPS × 预留系数
```

安全 QPS 必须来自压测和线上观测，不能根据 Gateway 数量倒推。假设 Redis 库存链路压测结果如下：

```text
6 000 QPS：CPU、延迟仍稳定
7 000 QPS：p99 明显上升
8 000 QPS：出现超时
```

为了给故障、流量倾斜和后台任务留余量，可以取 80%：

```text
R_global = 6 000 × 80% = 4 800 QPS
```

如果 Redis 最多允许 6 000 QPS 持续 0.5 秒，而基础速率已经是 4 800 QPS，那么这 0.5 秒内可接受的额外突发大约为：

```text
B_global ≈ (6 000 - 4 800) × 0.5 = 600 个令牌
```

因此可以先设 `R_global=4 800/s、B_global=600`，再通过压测观察 p99、超时率和 Redis CPU 调整。这里的 600 是**额外突发预算**的工程估算；不同令牌桶实现对初始令牌和容量的定义可能不同，落地时要按组件语义换算。

##### 3.5 Pod 数量怎么计算？扩缩容后是否要重算？

Pod 数量同样应该来自单 Pod 压测容量：

```text
Pod 数量 >= 峰值目标 QPS ÷ 单 Pod 安全 QPS
```

然后还要额外预留滚动发布、故障和可用区损失的容量。例如 Gateway 需要承接 80 000 QPS，单 Pod 安全处理 1 000 QPS：

```text
最低需要 80 个 Pod
再预留 25% 容量，可部署约 100 个 Pod
```

各类 Pod 不需要保持固定比例：

- Gateway 按入口 QPS、连接数、CPU 和 p99 扩缩容；
- Seckill Service 按请求 QPS、Redis 延迟、连接池使用率扩缩容；
- Order Service 按 MQ lag、最老消息等待时间、数据库 CPU 和写入延迟扩缩容。

扩缩容后的规则如下：

```text
Pod 自保护模式：
  R_local 由单 Pod 安全容量决定
  扩容后通常不用平分或重算，新增 Pod 使用同样的安全上限

用本地桶近似集群总额度：
  R_local ≈ R_cluster ÷ 当前健康 Pod 数
  扩缩容时必须动态下发，否则集群总额度会漂移

严格全局额度：
  R_global 保存在共享限流器中
  Pod 数变化不改变全局额度，通常无需重算
```

正常情况下，推荐把本地桶用于 Pod 自保护，把严格的共享上限交给全局桶。不要让 HPA 每增减一个 Pod，就改变下游能够承受的真实容量。

##### 3.6 完整数字例子

假设一次秒杀入口峰值是 100 000 QPS，Redis 库存链路的安全容量是 6 000 QPS，数据库只能稳定写入 1 200 个订单/s：

```text
外部 100 000 QPS
    │
    ├─ 用户/IP 限频：同一用户 5 秒最多 2 次，先挡重复点击和脚本
    │
    ├─ Gateway × 100
    │    每 Pod：R_local=1 000/s、B_local=200
    │    作用：任何单个网关都不能超过自己的安全线
    │
    ├─ sku:1001 全局桶
    │    R_global=4 800/s、B_global=600
    │    作用：所有请求路径合计不能持续压过 Redis 预算
    │
    ├─ Seckill Service × 20
    │    每 Pod 压测安全值约 300 QPS，并设置本地并发/连接池上限
    │
    ├─ Redis Lua：一人一单 + 预扣库存
    │    实际库存只有 100 件，最终最多 100 条资格消息进入 MQ
    │
    ├─ MQ：吸收成功订单的短时突发
    │
    └─ Order Service × 8
         每 Pod 约 150 次数据库写入/s，总计约 1 200/s
         数据库变慢时降低消费并发，让消息留在 MQ，不让请求直接压垮 MySQL
```

这里有四个关键结论：

1. 100 个 Gateway Pod 是同一个逻辑网关服务的 100 个实例，完全合理。
2. Gateway 本地桶的 1 000 QPS 是单实例安全线，不负责精确保证集群总量。
3. 热点 SKU 全局桶的 4 800 QPS 才是所有 Pod 共同遵守的 Redis 预算，扩容 Pod 不会把它放大。
4. Order Service 前面已有 MQ 时，主要通过消费并发和数据库连接池做背压，不一定还需要一层请求令牌桶。

##### 3.7 是不是每一层都必须限流？

不是。每增加一层分布式限流，都会增加网络调用、状态维护和故障点，应按瓶颈选择：

- **本地 Pod 桶建议保留：**成本低，可以防止流量倾斜打死单实例。
- **用户 / IP 限频按业务保留：**它解决公平性和防刷，不是容量问题。
- **热点 SKU 全局桶按需开启：**只有网关本地桶的理论合计可能超过 Redis 安全容量，或者必须精确控制某个 SKU 的共享预算时才需要。
- **订单消费者优先使用背压：**已有 MQ 时，根据数据库能力限制消费者总并发；不要入口拒绝已经抢到库存的有效订单。

如果流量已经通过用户限频和 Gateway 本地桶稳定压在 Redis 安全线以内，可以暂时不加 SKU 全局桶，减少一次 Redis 调用。但对于百万 QPS、流量高度倾斜的热点商品，通常不能假设 LB 永远均匀，增加商品级全局预算会更稳妥。

##### 3.8 常见追问

**🟢 追问 1：多个 Gateway Pod 的本地桶加起来，能不能代替全局桶？**

只能近似，不能严格代替。Pod 数和流量分布会变化；若要求集群总量不能超过一个硬上限，应使用共享的全局桶或动态配额系统。

**🟡 追问 2：扩容 Gateway 后，要不要把每个 Pod 的 `R_local` 调小？**

如果本地桶用于保护单 Pod，就不用，它仍应等于单 Pod 安全容量。如果是把全局额度静态平分给各 Pod，就必须重算，但这种做法容易受扩缩容和流量不均影响。

**🟡 追问 3：为什么不把所有限流都放在 Redis？**

因为每个请求都访问 Redis 会增加延迟、成本和新的热点。单实例自保护用内存桶即可，只有跨 Pod 共享的用户、SKU 或第三方配额才需要共享状态。

**🟡 追问 4：`x/time/rate` 和 Sentinel-Go 怎么选？**

只做当前 Pod 的简单令牌桶就选 `x/time/rate`；需要动态规则、热点参数、指标、熔断和系统保护时选 Sentinel-Go。两者默认都不能严格控制多个 Pod 的合计 QPS，全局额度还要依赖共享限流器。

**🔴 追问 5：全局限流器挂了怎么办？**

按业务风险选择 fail-open 或 fail-close。普通浏览请求可以短时退化为更保守的本地限流；秒杀扣库存、支付配额等高风险链路应快速失败或使用本地应急小额度，避免限流器故障时把共享下游打垮。

**面试里推荐这样答：**

> Gateway 是无状态服务，当然可以在一个 Service 后面部署很多 Pod。每个 Gateway Pod 的本地令牌桶按单 Pod 压测安全容量设置，只保护当前实例，不保证集群总 QPS；热点 SKU 的全局桶放在 Redis 或独立限流服务中，所有 Pod 共享，参数按被保护的 Redis 链路容量设置，与 Pod 数无关。比如 Redis 安全容量为 6 000 QPS，留 20% 余量后可设全局 `R=4 800/s`，桶容量再按允许的短时突发计算，不能机械地设成两倍。Seckill Pod 也可以用本地桶或并发上限自保；订单链路已有 MQ 时，主要按数据库能力控制消费并发和连接池。扩容 Pod 会提升计算能力，但不应该自动放大全局下游预算。

#### 四、库存怎么扣，才能不超卖、也不重复下单？

Redis Lua 脚本把以下动作作为一个原子操作执行：检查活动和资格、检查用户是否已抢过、检查库存、库存减一、写预占记录。任何一步失败都不扣库存，因此不会出现两个请求同时抢到最后一件。

可以把核心脚本理解成下面的伪代码：

```lua
-- KEYS[1] = stock:{activity:iphone17}
-- KEYS[2] = buyer_reservation:{activity:iphone17}
-- KEYS[3] = reservations:{activity:iphone17}
-- ARGV[1] = user_id
-- ARGV[2] = reservation_id

local existing = redis.call('HGET', KEYS[2], ARGV[1])
if existing then
    return {2, existing}
end

local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
    return {0, 'SOLD_OUT'}
end

redis.call('DECR', KEYS[1])
redis.call('HSET', KEYS[2], ARGV[1], ARGV[2])
redis.call('HSET', KEYS[3], ARGV[2], ARGV[1])
return {1, ARGV[2]}
```

三个 key 使用相同 Redis Cluster hash tag，保证落在同一个 slot。脚本串行执行，所以库存从 100 最多成功扣减 100 次；用户与 `reservation_id` 的映射也在同一脚本中写入，因此重复点击会返回第一次获得的预占编号，不会再次扣库存。生产代码还要记录活动状态、预占时间和请求幂等号，并为活动数据设置合理的过期与归档策略。

- 每次成功预扣生成唯一的 **reservation_id（库存预占编号）**。
- 订单表对 reservation_id 建唯一索引，并以 **(user_id, sku_id)** 唯一约束兜底一人一单。
- Redis Lua 已能处理商品库存的并发竞争，热点 SKU 再加商品级分布式锁会把请求串行化，通常得不偿失。

#### 五、Redis、MQ 与 MySQL 如何最终一致？

Redis 负责高并发的快速预扣，MySQL 负责订单和库存账本。二者不强行做一个跨库事务，而是让每个预占最终只有两个结果：**成功生成订单，或只回补一次库存。**

~~~text
Redis Lua：stock--，生成 reservation_id
  -> 可靠投递 MQ
  -> 订单服务 MySQL 本地事务：
       写订单 / 预占记录、条件扣减库存、写 outbox
  -> 异步消费者更新其他系统或回补 Redis
~~~

Redis 预扣成功和 MQ 发布不是同一个事务，不能只写成“扣完库存后直接发消息”。常见可靠方案有两种：

1. Lua 在扣库存时同时写 Redis Stream / 预占事件列表，由 Relay 持续读取并投递 MQ，确认 MQ 成功后再标记已转发；
2. Lua 写带状态和 TTL 的 reservation，应用发送 MQ；后台扫描长期处于 `RESERVED_NOT_SENT` 的记录进行重试，最终失败才用 release_id 幂等回补。

无论选哪种，`reservation_id` 都贯穿 Redis 预占、MQ 消息和 MySQL 订单，作为端到端幂等键。API 返回 `QUALIFIED / QUEUED` 只表示已获得资格或正在落单，客户端随后按 reservation_id 查询最终订单状态。

- **Outbox（本地消息表）**：在同一个 MySQL 事务里，除了写订单和库存，还写一条“稍后要发送的事件”记录；事务提交后由后台任务投递 MQ。这样不会出现“订单已提交，但通知丢失”。
- **条件更新**：例如只允许 **UPDATE ... WHERE status = 'RESERVED'** 成功一次。并发的支付回调、超时关单谁先改成功，另一个查询最终状态后退出。
- Redis 预扣后 MQ 或落单失败：按 **reservation_id** 扫描、重试；确认无法落单才发布库存释放事件。Redis 回补脚本也记录已处理的释放编号，重复事件不重复加库存。
- 定时对账以 MySQL 的订单、退款记录和 outbox 为准，发现 Redis 少扣或少回补再修正。

这里要区分两类“归还”：限流令牌代表一次下游处理预算，通常不立即归还；库存代表商品资源，只有已经预扣但最终未下单、超时关闭或退款成功时才回补。

**分布式锁与 RedLock：**

- 秒杀扣库存的热路径依赖 Redis Lua 原子操作和 MySQL 唯一键/条件更新，通常不需要商品级分布式锁。
- 支付、关单、退款可能并发处理同一订单，可加短暂的订单级锁降低冲突；但真正的正确性仍由数据库条件更新和唯一键保证，锁失效也不会写错。
- **RedLock** 是在多个独立 Redis 主节点上获取多数锁的方案，解决的是“锁服务的单点故障”风险；它不是 Redis 与 MySQL 的事务，也不能替代幂等、补偿和对账。

#### 六、支付超时、取消和退款如何回补库存？

先区分未支付取消和已支付退款，不能让任何一个分支直接随意 **stock++**。

~~~text
RESERVED（已预占、待支付） --支付成功--> PAID（已支付）
        |                                    |
        +--超时/取消--> CLOSED（已关闭）      +--发起退款--> REFUNDING（退款中）
                                                        |
                                                        +--支付平台确认--> REFUNDED（已退款）
~~~

- **未支付取消/超时：** 条件更新 **RESERVED -> CLOSED**，在同一个 MySQL 事务里写库存释放 outbox；消费者按 **reservation_id** 去重后回补 Redis。
- **已支付退款：** 先用唯一的 **refund_id（退款编号）** 创建退款记录，订单从 **PAID -> REFUNDING**；支付平台确认后才改为 **REFUNDED**，并写库存释放 outbox。第三方退款调用也携带同一个 **refund_id**，重试不会重复退款。
- 是否回到秒杀库存由规则决定：活动仍开放且允许二次销售，才回补秒杀池；否则只回到常规库存。

#### 七、失败场景怎样恢复？

| 异常 | 处理方式 |
| --- | --- |
| Redis 预扣成功，消息未发出 | 扫描预占记录重试投递；超时未落单则释放库存 |
| MQ 重复投递 | reservation_id 唯一索引，重复消息直接返回已有结果 |
| MySQL 落单或扣库存失败 | 标记该预占失败，发布一次库存释放事件；Redis 按释放编号去重回补 |
| 支付回调与超时关单同时到达 | 条件更新只允许一个状态迁移成功 |
| 退款回调重复 | refund_id 唯一键 + 回补事件去重 |
| Redis 回补失败 | 消费者重试，定时按 MySQL 账本对账修正 |

**面试中可以这样答：**

> 百万用户抢 100 台 iPhone，本质是百万请求竞争 100 个购买资格。我会先用 CDN 静态化，Gateway 集群完成鉴权、防刷、用户限频和单 Pod 自保护；若热点 SKU 的总流量仍超过 Redis 安全容量，再加共享全局准入预算。Redis Lua 原子完成活动校验、一人一单、库存大于零判断、扣减库存和 reservation_id 记录，因此最多只有 100 个不同用户获得资格。成功资格可靠进入 MQ，订单服务再以 reservation_id 幂等写 MySQL，接口返回排队状态而不是直接宣称购买成功。Redis、MQ、MySQL 不强行组成分布式事务，依靠预占记录、Outbox、唯一键、状态机、失败回补和定时对账收敛；支付超时或退款是否回到秒杀库存由活动规则决定。

### 8. 视频点赞系统怎么设计？

**面试官真正想听什么：**

- 你能不能把“用户行为”与“统计计数”拆开
- 你知不知道点赞这种场景的难点不在写库，而在热点和一致性
- 你会不会讲取消点赞、幂等、热点隔离
- 热点隔离：热点 key 隔离不一定只等于“单独放一个 Redis 节点”，本质是把超热点流量和普通流量拆开治理。常见做法包括独立 Redis 实例、独立热点分片、应用层特殊路由，以及在上层增加本地缓存，避免热点 key 把整套缓存系统打爆。

**先定语义：**

- 是否允许重复点赞
- 是否支持取消点赞
- 点赞数是否必须实时精确
- 用户端看到的“已点赞状态”和总数是否允许短暂不一致

**常见拆法：**

1. 用户行为链路
   负责回答“这个用户到底点没点过赞”
2. 总数统计链路
   负责回答“这条视频当前有多少赞”

**典型实现：**

- 用户行为可以落 Redis Set / Bitmap / DB 明细表 / MQ 异步落库
- 总数统计可以先写缓存，再异步汇总刷库
- 热门视频的总数不能只靠单 key 原地自增，容易打爆

**为什么不能简单地“点赞就 update count=count+1”：**

- 高频写直接打 DB，热点视频很容易形成行锁竞争
- 同时还要解决取消点赞、重复点击、重试幂等
- 点赞状态和点赞总数从本质上是两类数据

**关键难点：**

- 重复点赞怎么防
- 取消点赞怎么保证状态一致
- 热门视频单 key 热点怎么扛
- 总数展示和明细状态短时间不一致能否接受

**常见做法：**

- 用业务唯一键或状态机防止重复点赞
- 行为明细和计数异步解耦
- 热门视频做分片计数，最后聚合
- 前台展示允许短时间最终一致

**面试里推荐这样答：**

> 点赞系统我会拆成两条链路：一条是用户行为链路，解决‘这个用户是否点过赞’；另一条是计数链路，解决‘这条内容现在有多少赞’。因为这两个问题的关注点不一样，行为链路更强调状态正确性和防重，计数链路更强调高并发下的吞吐和热点抗压。
>
> 行为链路上，我一般会先确定唯一关系，也就是 (user_id, target_id) 这一对。落地时可以根据规模选型：如果要强一致和可追溯，可以落 MySQL 明细表，并对 (user_id, target_id) 建唯一索引；如果更关注高性能判断用户有没有点过赞，可以在 Redis 里放 Set 或 Bitmap。这样用户点进详情页时，就能快速判断当前用户是否已点赞。
>
> 计数链路上，我不会每次都直接 update DB 的点赞数字，因为热点内容会把数据库行打成瓶颈。更常见做法是先把计数写到 Redis，比如做原子自增；再通过异步任务或者 MQ，把增量批量刷回数据库。这样主链路快，数据库压力也更平滑。
>
> 如果是热门视频，还要考虑热点 key 问题。单个 Redis key 虽然比数据库强很多，但极热点场景下仍可能成为瓶颈，所以可以做分片计数，比如把一个视频的点赞计数拆成多个 shard key，写入时按用户或随机路由到不同分片，读取时再聚合。这样可以把单 key 压力打散。
>
> 另外，点赞和取消点赞不能只看计数，还要保证行为和计数一致。比如用户重复点赞，不能把计数重复加一；取消点赞时，也不能减成负数。所以行为侧必须有幂等判断，可以先判断用户状态，再决定是否更新计数。工程上常见做法是：先原子更新行为状态，再异步发计数变更事件，消费端做幂等汇总。
>
> 如果面试官继续追问异常场景，我会补两点：第一，如果 Redis 计数更新成功但 MQ 投递失败，要有补偿机制，比如本地消息表或者重试；第二，如果缓存计数和数据库计数短暂不一致，我会接受最终一致，因为点赞数本身通常允许短暂延迟，只要用户自己的点赞状态尽量实时准确即可。

### 10. 群聊 / 聊天室怎么设计？

**面试官真正想听什么：**

- 你知不知道聊天系统的核心不是“发消息”，而是长连接、路由、顺序、离线消息
- 你会不会区分单聊、群聊、广播场景
- 你能不能讲清消息链路

**先定需求：**

- 是单聊还是群聊
- 是否要求强顺序
- 是否有离线消息
- 是否需要未读数、撤回、禁言、审核
- 延迟目标是多少

**核心链路建议这样讲：**

1. 长连接接入层
   用户通过 WebSocket / 长连接网关接入
2. 连接管理层
   维护用户 ID 和连接的映射关系
3. 路由层
   按会话 ID 或群 ID 做路由，尽量让同一会话落到同一逻辑分片
4. 存储层
   在线消息实时推送，离线消息持久化
5. 消息扩展能力
   未读数、撤回、禁言、审核、历史拉取

**为什么按群 ID / 会话 ID 路由：**

- 主要是为了降低同一会话的乱序处理成本
- 如果消息到处乱飞，顺序、一致性和状态同步都会变复杂

**关键难点：**

- 海量连接如何维护
- 消息顺序如何保证
- 用户离线后如何补消息
- 未读数怎么统计
- 敏感词和审核链路放在哪

**一个更像后端的回答方式：**

- 在线用户走实时推送
- 不在线则写离线消息表或消息队列
- 同会话消息尽量经过同一路由分片
- 历史消息和实时推送分开考虑，不要混成一套

**面试里推荐这样答：**

> 聊天系统我会拆成长连接网关、连接管理、消息路由、消息存储和离线投递五层。核心难点不是能不能把消息发出去，而是顺序、离线补投递、未读数和海量连接管理。工程上我会按会话 ID 或群 ID 做路由，尽量把同一会话消息收敛到同一路径处理，这样更容易控制顺序和状态一致性。

#### 追问：某个用户 / 某个客户端收消息特别慢，慢消息越来越多怎么办？

这叫 **慢消费者（slow consumer）** 问题。不能因为一个连接读得慢，就让群消息的路由分片、MQ 消费者或 WebSocket 网关一起阻塞；正确做法是把“消息可靠保存”和“向某条在线连接实时写 socket”拆开。

```text
群消息按 group_id 有序写入消息存储 / MQ
                    |
                    +--> 在线快用户：Gateway 发送缓冲 -> socket
                    |
                    +--> 慢用户：个人发送队列达到阈值
                               -> 不再实时堆积完整消息
                               -> 记录 last_delivered_seq / 通知客户端拉取
                               -> 必要时断开连接，重连后按 seq 补消息
```

1. **每连接独立、有界发送队列**：写 socket 只能由该连接自己的 writer goroutine 串行执行；队列必须有字节数和消息数上限，禁止无界 channel / list。这样慢用户只占自己的缓冲，不拖慢同群其他成员。
2. **定义背压策略，而不是默默丢**：强一致聊天正文通常落库后按 `group_id + sequence` 可回拉；在线队列满时停止推实时包，保留最后已确认的 sequence，向客户端发送“需要同步”标识。客户端重连或恢复后执行 `pull(group_id, after_seq)` 补齐。表情、输入状态、在线状态等可丢的弱消息可以 coalesce（合并）或直接丢弃。
3. **分级阈值**：例如队列达到 50% 降低非核心事件，80% 进入只拉不推，100% 关闭连接并写原因码；真正数值由消息大小、客户端网络和网关内存压测决定。不能因为单个连接一直慢而无限占内存。
4. **保证顺序与去重**：服务端生成单调递增的群 sequence；客户端按 sequence 去重、检测缺口并拉取。实时推送只是低延迟路径，持久消息流才是补偿事实源。
5. **观测与治理**：监控单连接 queue bytes、queue age、慢消费者数、断开原因、补拉量、群扇出耗时；按用户 / IP / 客户端版本限速和封禁异常连接。注意不要把 user_id 直接做 Prometheus 高基数标签，可用 Top N 日志或采样追踪定位。

一句话回答：**慢用户不能阻塞群消息主链路；在线推送用每连接有界队列，满了就降级为按 sequence 拉取历史，可靠消息以持久存储为准，弱实时事件可合并或丢弃。**

### 11. 朋友圈 / Feed 流系统怎么设计？推、拉、推拉结合如何实现？

**答案：**

先把数据分成三类：关注关系回答“我关注了谁”，动态表保存“作者发布了什么”，时间线只保存“我的首页应该出现哪些动态 ID”。时间线不要复制完整正文，否则修改、删除动态时要更新大量副本。

```sql
CREATE TABLE follows (
    user_id BIGINT,
    followee_id BIGINT,
    PRIMARY KEY (user_id, followee_id)
);

CREATE TABLE feeds (
    id BIGINT PRIMARY KEY,
    author_id BIGINT,
    content TEXT,
    created_at DATETIME,
    INDEX idx_author_time (author_id, created_at)
);

CREATE TABLE timelines (
    user_id BIGINT,
    feed_id BIGINT,
    score BIGINT,
    PRIMARY KEY (user_id, score, feed_id)
);
```

读取首页时先从时间线取一页 `feed_id`，再批量读取动态详情；热门详情可以放 Redis 或本地缓存。分页使用 `score + feed_id` 游标，避免数据不断新增时深分页产生重复或漏读。

以“用户发布一条动态，粉丝看到时间线”为例，分发有三种选择：

- **推模式（fan-out on write）**：作者发帖后，把动态 ID 异步写入每个粉丝的收件箱 `inbox:{fanoutUserId}`。读时间线只需读取自己的 inbox 再批量取详情，读快；但大 V 发帖会产生海量写放大。
- **拉模式（fan-out on read）**：只保存作者自己的发件箱 `outbox:{authorId}`。用户打开首页时，查询关注列表，分别取每位作者最近动态后按时间或评分归并。写轻；但关注多的用户读放大明显。
- **推拉结合**：普通作者的粉丝规模可控，采用推；大 V 只写自己的 outbox，读者拉取时再合并。用粉丝数阈值、动态热度和在线活跃度决定走哪条路径。

一个可落地的混合流程：

```text
作者发布 -> DB / 内容存储落库 -> Kafka: feed_created
    -> 普通作者分发消费者：批量写粉丝 inbox（可重试、按 event_id 幂等）
    -> 大 V：只维护作者 outbox

用户读首页 -> 读 inbox
    -> 取关注大 V 的 outbox
    -> 合并、去重、按时间/推荐分排序 -> 分页返回
```

工程细节：inbox 通常只保存 `feed_id`、时间和排序字段，内容详情单独存并缓存；分发要异步化且按批次处理；关注/取关、删除动态需要可重放事件或版本号来修正收件箱；分页应使用游标而不是深度 `offset`；热门作者和热点内容还需本地缓存、限流与降级。

**面试回答：**

> 推模式写放大、读快，适合普通用户；拉模式写轻、读放大，适合大 V；生产上通常混合。用户发帖先可靠落库再发事件，普通用户的动态异步 fan-out 到粉丝收件箱，大 V 只维护发件箱；读首页时把 inbox 和大 V 的 outbox 合并排序。这样避开了大 V 的写爆炸，同时保持普通用户读路径足够快。

### 12. 云对象存储的大文件分片上传怎么设计？（S3 / OSS / COS 通用）

**先说清一个常见误区：**生产环境通常不让业务应用服务器接收并拼接所有文件字节。否则一个 500 GB 视频会同时占用应用集群的入口带宽、磁盘和 CPU，应用扩容成本高，还会和在线接口抢资源。更常见的分工是：**业务服务负责鉴权、签发临时上传权限和管理状态；客户端把分片直接上传到对象存储；对象存储完成合并。**

对象存储的 API 名字略有差异，但核心都是：初始化得到 `upload_id`，按 `part_no` 上传分片并获得 `ETag`/校验信息，携带“分片号 + ETag 清单”完成合并；未完成任务必须显式取消或由生命周期规则清理。[S3 Multipart Upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) 和 [OSS 分片上传](https://www.alibabacloud.com/help/en/oss/user-guide/multipart-upload) 都遵循这一模式。

#### 一、先定目标与边界

- 网络中断后只补传缺失分片，不能重传整文件。
- 业务服务能看到进度、失败原因和最终文件状态，但不成为文件流量瓶颈。
- 客户端不能自行指定任意 bucket、对象路径或上传大小，避免越权和存储被滥用。
- 完成请求、分片重传、消息重试都不能生成多个“已完成文件”。
- 文件在校验、病毒扫描或转码完成前不对外可见。

#### 二、完整链路：控制面走业务服务，数据面直传对象存储

```text
Client
  -> POST /uploads：文件名、大小、类型、文件指纹（可选）
  <- upload_id、object_key、part_size、短期 STS / 每片预签名 URL

Client -- 并发 PUT part_no + checksum --> Object Storage
Client <- ETag / checksum ---------------- Object Storage

Client -> POST /uploads/{upload_id}/complete：part_no + ETag 清单
Upload Service -> 校验状态、权限、分片清单 -> CompleteMultipartUpload
Object Storage -> 生成最终对象
Upload Service -> 元数据置为 VERIFYING / PROCESSING
Async Worker -> 全文件校验、病毒扫描、转码/缩略图 -> READY
```

这里的 `object_key` 必须由服务端生成，例如 `tenant/{tenant_id}/uploads/{file_id}/source`，不要直接用用户传来的文件名。浏览器或 App 可使用两种受限凭证之一：

- **预签名 URL**：服务端按 `upload_id + part_no` 生成短时效 URL，客户端只能上传指定分片。
- **STS 临时凭证**：权限策略只允许写本租户、指定前缀和有效期内的对象；适合分片数很多、频繁申请 URL 不方便的场景。

无论哪种，都不能把长期 AccessKey 下发给客户端。

#### 三、初始化、分片与断点续传

初始化接口完成业务校验（登录用户、租户配额、文件大小、类型、业务归属），并创建一条稳定的上传记录：

```text
upload_id, file_id, tenant_id, object_key, file_size, part_size,
expected_part_count, file_fingerprint, status, expires_at, version
```

客户端根据 `part_size` 切片，控制 4～8 个并发上传；弱网时可以降低并发，避免多个大请求互相争抢上行带宽。每片上传完成后保存 `part_no`、字节范围、`ETag` 和分片 checksum。`part_no` 就是分片在最终文件中的顺序，不要只按“先上传完的顺序”合并。

**断点续传不是重新初始化。** 客户端恢复页面或网络后，调用 `GET /uploads/{upload_id}`；服务端返回已确认的分片清单，必要时再向对象存储 `ListParts` 核验。客户端只补传缺失或校验失败的片。重复上传同一 `part_no` 要按覆盖/幂等语义处理，并以本次返回的 ETag 更新记录，不能拿旧 ETag 去完成合并。

**例子：500 GiB 的课程视频。** 若选择 64 MiB 分片，共有 `500 × 1024 ÷ 64 = 8000` 片。用户上传到第 6320 片时断网，恢复后服务端返回已成功的 6319 片和缺失清单；客户端从第 6320 片继续上传。业务服务只处理几 KB 的元数据和签名请求，不会把前面约 395 GiB 的文件再经过应用集群一次。

分片大小不能照搬固定值：过小会产生过多请求、ETag 和元数据；过大则失败时重传成本高、并发度不足。应结合云厂商分片数量/大小限制、平均网络质量、文件大小和压测结果选取，并在初始化时固定下来。

#### 追问：如果是 1 TB 超大文件，或者跨地域传输，方案要多什么？

先澄清单位：面试里 `1 TB` 通常指约 `1000 GB`，而 `1 TiB` 是 `1024 GiB`；设计不是为了口算，而是为了让控制面始终只处理元数据、数据面可以恢复和限速。假设使用 256 MiB 分片，1 TiB 大约是 `1024 × 1024 ÷ 256 = 4096` 片；相比 64 MiB 的 16384 片，元数据和请求数更低，但单片失败的重传代价更高。因此应按网络质量、对象存储分片上限、客户端内存和压测选择 128～512 MiB 一类的范围，而不是将所有文件固定为一个值。

```text
上传端（近源区域）
  -> 就近对象存储 / 边缘加速入口：分片、限速、断点续传
  -> 原区域对象完成并校验 checksum
  -> 服务端异步跨区域复制 / 专线传输
  -> 目标区域校验对象版本 + checksum
  -> 元数据原子切换为 READY，通知下游
```

- **客户端不要整文件读入内存**：使用顺序流式读取或分块读取；每次只保留“并发数 × part_size”大小的 buffer。256 MiB 分片并发 4 个，理论缓冲上限就接近 1 GiB，还要为应用留内存，因此移动端和低配机器通常降低分片或并发。
- **跨地域不要把请求在业务服务中转两次**：优先近源上传、对象存储跨区域复制（CRR）或受控专线；业务 DB 只记录对象版本、目标区域、校验状态。若必须应用间传输，也应走流式转发、分片重试与独立带宽池，不能 `ReadAll` 后再写。
- **端到端完整性**：每片 checksum 防传输损坏，最终以完整对象的可信 checksum / 版本校验；目标端未校验成功前不切换业务引用。大文件的“传完”不等于“可用”。
- **公平与成本**：按租户、用户、任务设并发数和速率配额；低优历史迁移进入可暂停队列，高优在线上传有保底带宽。监控有效吞吐、重传率、分片失败率、未完成上传数量、存储临时空间和跨区费用。

面试收束：**1 TB 不是把分片数调大就结束，而是直传数据面、流式内存边界、断点与校验、跨区复制、限速公平、未完成任务回收一起设计。**

#### 四、完成合并、校验与幂等

客户端不能只说“我传完了”。它提交 `part_no + ETag` 清单后，服务端至少要校验：上传人和租户是否匹配、状态是否仍为 `UPLOADING`、分片数与字节范围是否完整、每个 `part_no` 是否唯一。然后由服务端调用对象存储的完成接口；对象存储按 `part_no` 顺序组合为一个最终对象，不需要应用服务器下载再拼接。

```text
INIT -> UPLOADING -> COMPLETING -> VERIFYING / PROCESSING -> READY
                         |                    |
                         v                    v
                      FAILED                REJECTED
```

- 用条件更新或状态机抢占 `UPLOADING -> COMPLETING`，只有一个请求真正调用完成接口；其他重复请求返回当前状态。
- 如果“完成接口已成功，但业务服务回响应前宕机”，恢复任务通过对象存储的对象状态/版本核实结果，再把记录补为完成，不能直接重新拼一份。
- 分片 checksum 用于校验传输，最终对象最好再做全文件 checksum 或可信元数据校验。**不要把 multipart 的最终 ETag 当作通用文件 MD5**；以 S3 为例，它并不保证是完整对象的 MD5。
- 所谓“秒传”要单独设计：先用可信的完整文件 hash 查找同一租户已存在且有权限复用的对象，再建立引用；不能仅凭客户端报来的 hash 就跳过校验。

#### 五、完成后的异步处理与安全治理

- 最终对象先处于私有前缀或 `VERIFYING` 状态；扫描通过、MIME/大小复核、转码或缩略图生成成功后，元数据才切到 `READY` 并允许下载。
- 以 `upload_id` 为幂等键发布 `file.completed` 事件；下游转码、OCR、索引等消费者可安全重试。
- 上传记录设过期时间。客户端主动取消，或后台定时扫描过期记录并调用 `AbortMultipartUpload`；否则未完成的分片会长期占用空间并可能持续计费。
- 还要限制并发上传数、单用户/租户速率、Content-Type 和大小，记录审计日志；下载走鉴权 URL 或 CDN 签名，不能因“上传成功”就公开 bucket。

**面试里推荐这样答：**

> 我会把上传分成控制面和数据面。控制面由业务服务做登录、配额和对象路径校验，生成 `upload_id` 并下发短时 STS 或预签名 URL；数据面由客户端把分片直接传到 OSS、S3 这类对象存储，避免文件流量经过应用服务器。客户端保存每片的 `part_no`、ETag 和校验值，断线后查询已上传清单，只补缺失分片。所有片完成后，服务端校验清单并用状态机抢占完成权，再调用对象存储的 Complete 接口，由对象存储按分片号合并。完成后还要做全文件校验、病毒扫描和异步处理，未完成上传通过超时任务 Abort 清理。重点是直传、断点续传、完成幂等、完整性校验和权限边界。

### 13. 预约通知 / 延迟通知怎么设计？

**面试官真正想听什么：**

- 你会不会把“定时触发”和“通知发送”拆开
- 你知不知道通知系统的重点是可靠性，不是把消息发出去就算完
- 你能不能讲幂等、重试、取消预约

**先定目标：**

- 到点尽量准时触发
- 重复通知不能发生
- 失败后能重试
- 用户取消预约后不能误发

**核心链路：**

1. 用户预约时，先落预约记录
2. 同时把触发时间交给延迟任务系统
3. 到点后任务系统把事件投递给通知服务
4. 通知服务根据渠道发送站内信 / Push / 短信
5. 发送结果回写，失败重试，超过阈值进入死信或补偿

**延迟任务系统怎么选：**

- 量不大可以定时扫描
- 吞吐更高可以用时间轮
- 已有 MQ 体系时可用延迟队列

**关键难点：**

- 用户取消预约后任务如何失效
- 通知服务超时重试会不会重复发
- 多渠道通知如何保证状态可追踪

**例子：**用户预约“明天 10:00 提醒续费”，9:59:59 又点了取消。即使延迟队列里的任务已经在 10:00 出队，通知服务在真正发短信前仍要按 `task_id` 查到“已取消”状态并结束。这样“取消”不必强依赖从队列里物理删除任务，也不会误发。

**工程回答要补：**

- 每条通知任务都要有唯一 ID，发送逻辑必须幂等
- “预约记录”和“任务状态”要能关联，方便取消和补偿

**面试里推荐这样答：**

> 预约通知我会拆成四段：预约存储、延迟触发、通知执行、失败补偿。用户发起预约时，先落一条预约记录，里面至少包含用户 ID、业务对象 ID、预约触发时间、通知渠道、任务状态和唯一任务 ID；同时把这个任务交给延迟任务系统，比如定时扫描、时间轮，或者基于 MQ 的延迟队列。到触发时间后，延迟系统不直接发通知，而是只负责把“该任务已到期”这个事件投递给通知服务。通知服务收到后，会先根据任务 ID 查状态，做一次幂等校验，确认这个任务没有被取消、没有发送成功过，然后再调用具体渠道去发站内信、Push 或短信。发送成功后回写发送结果和状态；如果发送失败，就按重试策略继续重试，超过阈值进入死信队列或补偿表，后面由人工或补偿任务处理。这样设计的关键点是把“什么时候触发”和“怎么发送”彻底解耦：前者解决定时问题，后者解决渠道可靠性问题。对于用户取消预约，我会把预约记录改成已取消，并让后续执行时再做一次状态校验，这样即使延迟任务已经出队，也不会误发。对于下游超时或重复投递，我会依赖任务唯一 ID 和发送幂等来保证‘最多只成功一次’，并把整个链路的状态都落库，保证后续可查、可重试、可补偿

### 14. 缓存一致性怎么保证？

**面试官真正想听什么：**

- 你知不知道这题没有银弹
- 你会不会先谈一致性目标，再谈方案
- 你能不能讲出极端情况下的补偿

**第一句话就要说：**

- 绝大多数互联网业务追求的是**最终一致**，不是强一致

**为什么这点重要：**

- 如果你一上来说“保证绝对一致”，面试官通常会继续追到你答不下去
- 正确做法是先问清楚业务能接受多大延迟、读旧值后果多严重

**常见方案：**

1. `cache-aside`
   - 读：先查缓存，miss 再查 DB，再回填
   - 写：先写 DB，再删缓存
2. 延迟双删
   - 适合处理并发读写窗口问题
3. MQ 异步补偿
4. 订阅 binlog / CDC 驱动缓存更新

**关键难点：**

- 删缓存失败怎么办
- 并发读写时会不会把旧值重新写回缓存
- 缓存和 DB 分别成功 / 失败的组合场景怎么收口

#### CDC + Outbox：怎样可靠地把数据库变更发成消息？

**CDC（Change Data Capture，变更数据捕获）**是一种把数据库变更从 binlog 中读出来、再变成事件的机制；它不是单一产品。Canal 是阿里开源的 MySQL binlog 订阅实现，Debezium、Flink CDC 也能做类似事情。

**Outbox（本地消息表）**则是在 MySQL 里与业务表一起提交的一张消息暂存表。比如创建订单时，在**同一个本地事务**中写入订单和一条 `order.created` 事件：

~~~text
orders + outbox（event_id、event_type、payload）
              -> MySQL COMMIT
              -> binlog
              -> CDC 发现新增 outbox 记录
              -> Kafka
              -> 下游消费者
~~~

这样不会出现“订单已提交，但准备发出的消息因为进程崩溃而丢失”。使用 CDC 后，通常不必由后台任务不断轮询 `SELECT * FROM outbox WHERE status = 'pending'`；CDC 可以持续监听 binlog 并投递。不过仍要保留失败重试、积压监控和对账。

**CDC 不负责幂等。** CDC/Kafka 通常是至少一次投递，同一事件可能重复到达。消费者必须按 `event_id` 去重：例如第一次收到 `evt-888` 扣积分并记录该 ID；再次收到同一 ID 时直接忽略，不能再扣一次。

#### CDC + Redis：怎样让缓存最终一致？

对“价格更新后缓存应失效”这类允许短暂读旧值的场景，业务只需更新 MySQL，CDC 将变更驱动到缓存侧：

~~~text
UPDATE product SET price = 99 WHERE id = 1001
  -> binlog -> Canal / Debezium / Flink CDC
  -> Kafka -> 缓存消费者
  -> DEL product:1001
  -> 下一次读请求从 MySQL 加载新值并回填缓存
~~~

同一份 CDC 事件还可以分发给 Elasticsearch 索引、数据仓库等下游。缓存消费者同样要幂等：重复删除同一个 key 没问题；若选择“直接更新缓存”，则要带数据版本，避免乱序旧事件把新值覆盖。

**一句话区分：** Outbox 保证“数据库成功后，待发送的业务事件有可靠落点”；CDC 把数据库变化可靠捕获成事件；Kafka 负责传输；消费者幂等防止重复事件造成重复业务操作。

#### 外部接口成功，但本地缓存更新失败怎么处理？

先区分**业务事实**和**缓存副本**。例如扣减库存的第三方接口已经返回成功，但应用本地缓存没有更新：不能因为缓存失败就认定扣减失败，也不能立刻用新请求号再扣一次。

1. 先把第三方调用结果用业务单号/幂等键可靠落库；若响应丢失或结果不确定，优先按该幂等键查询第三方状态。
2. 本地缓存失败时，优先删除/失效这个缓存键，异步重试删除或回填；下一次读取可以从事实源恢复，TTL 只是兜底。
3. 如果第三方明确支持同一幂等键重复调用并返回同一结果，可以带**同一个**键重试；重试目标是确认或补齐本地状态，不是再执行一次业务。
4. 用 outbox、MQ 或定时对账补偿“第三方已成功但本地状态未落好”的记录，并告警。缓存不应成为唯一事实源。

**更稳的回答方式：**

- 主方案是 cache-aside
- 再根据业务写频率、一致性要求和链路复杂度决定是否加延迟双删、MQ 补偿或 binlog 驱动
- 最后一定补一句：TTL 是兜底，不是主策略

**面试里推荐这样答：**

> 缓存一致性这题我会先确认业务要的是强一致还是最终一致。大部分互联网业务我会优先用 cache-aside，也就是先写库再删缓存；如果并发读写窗口比较明显，再加延迟双删、消息补偿或者 binlog 驱动更新。这个题的重点不是背某一个方案，而是你能不能说清楚一致性要求、失败场景和补偿策略。

### 15. 热点 key 怎么治理？

**面试官真正想听什么：**

- 你是不是知道热点 key 不只是 Redis 问题，而是整条链路问题
- 你会不会把热点识别、流量分散、缓存层次都讲出来

**热点 key 的本质：**

- 某个 key 的访问量远高于其他 key，导致单点成为瓶颈

**治理手段可以分四类讲：**

1. 提前识别
   监控热点 key、热榜数据、活动流量
2. 多级缓存
   本地缓存 + Redis + DB
3. 流量分散
   key 分片、热点隔离、读副本
4. 流量治理
   限流、降级、预热

**为什么本地缓存常常有效：**

- 很多热点流量其实是同一批数据被反复读取
- 如果每次都打 Redis，Redis 本身就会变成热点中心

**关键难点：**

- 本地缓存带来一致性问题
- key 分片后聚合更复杂
- 热点变化快，预热可能跟不上

**面试里推荐这样答：**

> 热点 key 治理我不会只盯 Redis。更完整的思路是：先通过监控识别热点，再用本地缓存和多级缓存兜住最热流量，必要时做 key 分片和热点隔离，最后配合限流和降级守住主链路。这个题的关键是把“热点识别、流量分散、缓存层次、失败兜底”连成一套。**

### 16. 某个时间点 Redis QPS 突然暴涨，怎么定位是哪个 key？

**先说结论：**

你说的“Grafana 找时间点 → Trace 找 HTTP 请求 → 根据请求和代码找到 Redis key”是合理的排查链路，尤其适合没有现成 key 维度监控的系统。它能先回答“哪个接口、哪个业务参数、哪个版本把流量打到了 Redis”。

但它通常不能单独证明“就是某一个具体 key 的 QPS 最高”：Trace 会采样，Redis span 默认也未必记录 key；即使记录，也不能把原始 key 直接当 Prometheus label，否则高基数指标会先把监控系统打坏。企业内部 Redis SDK 如果已经提供命令拦截器、埋点或 Top N 能力，应该优先用它做 key 级定位，再用 Trace 做业务归因。

#### 一、先确认是不是 Redis 层的突发，而不是监控错觉

先在 Grafana 固定告警前后 5～15 分钟的时间窗，并按实例、分片、命令类型拆开看：

- `instantaneous_ops_per_sec`、入站/出站带宽、连接数、CPU、网络、命令耗时和 p99；
- `GET` / `MGET` / `HGETALL` / `EVAL` 等命令的调用量是否同时上涨；
- 是所有分片都涨，还是只有一个 shard / 一个副本涨；
- 缓存命中率、应用入口 QPS、某个路由或租户的 QPS 是否在同一时间跳变。

如果只是某个 Redis 分片 QPS 上升，而应用入口没变，优先怀疑热 key、重试风暴、读流量被错误路由到主节点，或本地缓存失效。如果所有 Redis 分片和入口 QPS 一起上升，则可能是活动、爬虫、发布或上游流量变化。

#### 二、首选：在企业 Redis SDK 中做“Key Top N”观测

面试官说“内部 Redis 用 SDK，肯定有监控”，这个方向是对的，但要补一句：**先确认 SDK 监控的粒度。** 很多 SDK 默认只报实例、命令和错误率；能直接给出热 key Top N，或者至少能在 Hook / Interceptor 中取到命令和 key，才可以精确定位。

SDK 在每次调用 Redis 时都知道命令和 key，可以在客户端侧聚合一个短时间窗口内的 Top N：

```text
SDK Hook
  -> 识别命令、key、调用方、HTTP 路由、Trace ID
  -> key 归一化：product:detail:12345 -> product:detail:{id}
  -> 以原始 key 或 key_hash 做窗口 Top N 统计
  -> 上报：调用次数、错误率、耗时、读写字节数
```

上报时应分两层：

- **低基数 Metrics** 放到 Prometheus / Grafana，例如 `redis_requests_total{cluster, command, key_namespace, caller_service}`。`key_namespace` 可以是 `product:detail`、`user:profile`，不能直接放完整 key。
- **精确 key 的 Top N** 进入日志、Trace 补充事件或专门的热点分析服务。例如记录 `time_window`、`key_template`、`key_hash`、`command`、`count`、`caller_service`、`route`。只有排障人员在有权限的情况下，才把 `key_hash` 映射回原始 key；key 里可能含用户 ID、手机号等敏感信息，不能默认明文全量采集。

高 QPS 场景不要给每个 key 建一个计数器再全部上报。SDK 可以用固定窗口的 Top K 聚合，或使用 Count-Min Sketch、Space-Saving 这类“近似统计出现次数最多项目”的算法，最后只上报前几十个 key。这样既能发现“谁最热”，又不会制造高基数监控问题。批量命令、Pipeline、Lua 脚本也要正确解析 key 参数；否则只记录 `MGET` / `EVAL` 而不记录实际 key，定位结果会失真。

#### 三、没有 Key Top N 时：你的 Grafana → Trace 方案怎么落地

```text
Grafana：14:05 某 Redis 分片 QPS 从 2 万升到 20 万
  -> 找同一时间窗口 QPS 增长最快的 HTTP route / RPC method / tenant
  -> Trace 对比正常和异常请求，确认 Redis span 和重试次数
  -> 查看该接口的业务参数、缓存 key 构造规则和代码版本
  -> 临时提高该路由的 trace 采样或 SDK 调试采样
  -> 用采样结果的 key_hash / Top N 验证具体热 key
```

例如 `/api/v1/product/12345/detail` 在 14:05 的 QPS 暴涨，Trace 显示它 90% 的耗时都在 `GET product:detail:12345`，同时 SDK 采样的 Top N 也把该 key 排在第一，才能比较有把握地定性为 `product:detail:12345` 热 key。若只有一次 Trace 看到这个 key，还不能说明它导致了全局 QPS 上升，可能只是一个偶然请求。

这条链路还有两个常见坑：

- Trace 常按比例采样，突发开始时可能恰好没有样本。应按告警时间窗对可疑路由临时提高采样率，或使用 tail sampling 保留 Redis 调用次数异常、耗时异常的请求。
- 不要把完整 Redis key 默认写进 Trace。可以记录 key 模板、哈希值和业务对象类型；确有排障需要时，再在受控时间窗内开启原始 key 日志并设置短 TTL。

#### 四、服务端和旁路工具能做什么，不能做什么

- `INFO commandstats`、`INFO stats` 可以确认是哪类命令在涨，但 Redis 原生命令统计**不按 key 计数**。
- `SLOWLOG` 用来找慢命令，不适合找“QPS 很高但每次都很快”的热读 key。
- `redis-cli --hotkeys` 可以在使用 LFU 淘汰策略时，基于访问频率采样找候选热 key；它适合低风险时段的辅助验证，不应在高峰期把它当实时排障主手段。
- `MONITOR` 会把所有命令实时输出，流量大时对 Redis 和客户端都有明显额外开销。除非是在隔离副本、短时间、明确限流的应急场景，否则不要对繁忙主库直接执行。
- 如果所有调用强制经过 Redis Proxy / Service Mesh，也可以在代理层做同样的命令和 key Top N 聚合；没有统一入口时，SDK 侧更可靠。

`SCAN`、`MEMORY USAGE`、`--bigkeys` 用于找大 key，不会告诉你一个 key 在告警窗口内被访问了多少次，不能用它们定位热 key。

#### 五、定位的同时先止血

不要等完全确认 key 才行动。只要已确认是某个路由或业务对象引起的突发，就可以先：

1. 对路由、租户或业务对象限流，关闭非核心字段和高频轮询；
2. 把稳定的读数据短 TTL 放进应用本地缓存或 CDN，降低 Redis 回源；
3. 对可接受旧数据的读流量切只读副本，并观察复制延迟；
4. 对确认的热 key 做预热、隔离实例或分片计数；如果是重试风暴，先修正超时、退避和熔断。

止血后补充告警：单分片 QPS、单命令 QPS、SDK Key Top N、某个 namespace 的流量倾斜、调用方/路由 Top N、Redis 重试率和本地缓存命中率。这样下一次就不必从 Trace 反推。

**面试里推荐这样答：**

> 我会先在 Grafana 固定异常时间窗，确认是哪个 Redis 分片、哪类命令和哪条业务链路的 QPS 上升。企业内部如果 Redis SDK 有 Hook 或监控，我优先让 SDK 在客户端聚合短窗口 Key Top N：Prometheus 只打 key namespace、命令和调用方这些低基数维度，完整 key 用哈希后的 Top N 进入受控日志或热点分析系统，避免高基数标签拖垮监控。没有这层能力时，我会用 Grafana 找到同时间增长的 HTTP 路由，再通过 Trace 和代码里的 key 构造规则缩小范围，并临时提高该路由的采样，用 key_hash 验证具体 key。`SLOWLOG` 只能查慢命令，`SCAN` 和大 key 工具也不能反映访问 QPS，`MONITOR` 在繁忙主库上风险很高。定位期间会先对可疑路由限流，并加本地缓存或副本读给 Redis 止血。

### 17. 接口或服务的 QPS 突然爆高，怎么排查？

先固定异常时间窗，按“入口、维度、原因、影响”缩小范围：

1. **入口是否真的变大：** 对比 Gateway、LB、应用实例的 QPS，确认是外部流量增加，还是监控口径、内部重试造成的放大。
2. **按维度切分：** 看 HTTP route / RPC method、状态码、调用方、租户、地域、版本、实例。一个路由或一个租户突然陡增，通常比“全站都涨”更容易定位。
3. **查来源和调用链：** 从 access log、Trace、发布与配置变更中判断是活动、爬虫、定时任务、死循环轮询、上游重试，还是本服务超时后触发的重试风暴。
4. **看资源是否同步恶化：** CPU、连接池、线程池/goroutine、Redis/DB/RPC QPS、错误率和 p99。如果入口没涨而下游请求翻倍，优先查重试、N+1 调用和循环消费。
5. **先止血：** 对可疑 route、租户或 IP 限流；关闭非核心轮询/功能，熔断慢下游，必要时回滚发布或扩容。止血和定位可以并行。

**例子：**支付回调超时后，网关和客户端各重试 3 次；原本 1 万 QPS 的请求可能迅速变成数万次下游调用。此时入口业务请求数未必同比例上涨，但错误率、超时率和同一 `request_id` 的重复次数会明显上升。修复重点是统一幂等键、重试预算和退避，而不是只加机器。

**面试里推荐这样答：**

> QPS 爆高时我先固定时间窗，确认增长发生在入口还是服务内部，再按路由、调用方、租户、地域和版本分桶。通过 access log 和 Trace 判断是活动流量、爬虫、发布变更，还是超时重试造成的放大；再结合 CPU、线程池、连接池、下游 QPS、错误率和 p99 看影响范围。线上先对可疑维度限流、降级和熔断止血，不能等根因完全确认后才保护系统。

### 18. 多机房 / 多实例流量怎么均匀分配？

**面试官真正想听什么：**

- 你会不会区分“实例负载均衡”和“跨机房调度”
- 你知不知道“绝对均匀”不一定最优
- 你能不能讲出健康检查和故障切流

**先分两个层次：**

1. 单机房内实例调度
2. 多机房之间流量调度

**常见手段：**

- 四层 / 七层负载均衡
- 权重路由
- 就近接入
- 健康检查和自动摘除
- 一致性哈希
- 会话亲和

**为什么不一定追求绝对均匀：**

- 如果业务有本地缓存、会话状态或连接状态，过于随机的均匀分布反而会降低命中率
- 所以很多场景要在“均匀分布”和“局部粘性”之间平衡

**关键难点：**

- 机房故障切流时如何避免雪崩
- 跨机房延迟和数据一致性怎么权衡
- 有状态连接如何迁移

**例子：**上海用户通常优先进入上海机房，既减少网络延迟，也更容易命中该机房的本地缓存。上海机房故障时，流量不要在一秒内全部切到北京：先按可用容量逐步调大北京的权重，同时扩容、限流并关闭非核心接口。对已经建立的 WebSocket 连接，允许断开后重连到新机房，而不是强行迁移连接状态。

**面试里推荐这样答：**

> 多机房流量分配我会先分成实例级和机房级两层来看。实例层更关注负载均衡和健康检查，机房层更关注就近接入、权重调度和故障切流。如果业务有本地缓存或长连接，我不会一味追求绝对随机均匀，而是会适度保留会话亲和，在命中率和负载均衡之间做取舍。

### 19. 服务超时、网络波动、重试风暴怎么处理？

**面试官真正想听什么：**

- 你知不知道重试不是免费午餐
- 你会不会把超时、幂等、退避、熔断一起讲
- 你有没有“避免故障放大”的思维

**先讲原则：**

- 重试是恢复手段，不是默认加速器
- 没有边界的重试，往往会把小故障放大成大故障

**一套完整方案应该包括：**

1. 明确的超时控制
   每一层调用都有边界
2. 幂等设计
   不然重试本身就会造成副作用
3. 指数退避和抖动
   避免一窝蜂重试
4. 熔断
   下游明显异常时，不再持续压测它
5. 降级
   关键功能保主链路，非关键功能先让步
6. 限流
   防止系统在故障期间被进一步打穿

**关键难点：**

- 超时值设太小，误伤正常请求
- 超时值设太大，线程 / goroutine 被长时间占住
- 没幂等时重试会重复扣款、重复下单、重复发消息

**例子：**支付服务调用下游后在 2 秒超时，但下游其实在 2.1 秒已经扣款成功。上游重试时若带同一个业务请求号，下游应返回第一次的成功结果，而不是再扣一次款；若大量请求都在 2 秒同时超时，重试还要加随机退避，否则会在 2 秒后集体再冲击一次已经变慢的下游。

**面试里推荐这样答：**

> 面对服务超时和网络波动，我不会只说“加重试”。更完整的思路是：先给每层调用设清晰超时边界，再保证请求幂等，然后用指数退避重试、熔断、限流和降级一起控制故障扩散。重试只能在“可重试 + 幂等 + 有边界”的前提下使用，否则它本身就会变成故障放大器。

### 20. 登录业务怎么保证通信安全和数据安全？

**面试官真正想听什么：**

- 你会不会区分通信安全、身份认证、数据存储、风控审计
- 你会不会答成“上 HTTPS 就完了”

**推荐拆成四层：**

1. 通信安全
   HTTPS / TLS，避免窃听和中间人攻击
2. 身份认证
   token / session / 签名 / 多因素认证
3. 数据安全
   密码加盐强哈希，敏感字段加密与脱敏
4. 风控与审计
   验证码、限流、设备指纹、异地登录提醒、审计日志

**密码存储一定要答到位：**

- 绝不能明文存储
- 也不建议简单做 `md5(password)`
- 更稳的做法是使用带盐的强哈希算法，比如：
  - `bcrypt`
  - `scrypt`
  - `Argon2`

**关键难点：**

- 登录接口本身就是暴露面最大的入口之一
- 除了密码，还要关注 token 泄露、撞库、暴力破解、会话劫持

**面试里推荐这样答：**

> 登录安全我会分成通信安全和数据安全两层来讲。通信层通过 HTTPS 保证链路不被窃听和篡改；数据层里，密码必须用带盐的强哈希算法存储，不能明文也不能简单 md5。除此之外，还要配合限流、验证码、设备指纹、异地登录提醒和审计日志。这个题的高分点是把“传输、认证、存储、风控、审计”连成一套，而不是只说一个 HTTPS。

### 21. 支付 / 订单状态机怎么设计？

**答案：**

状态机的重点是“状态可枚举、流转受约束、重复事件幂等”。

- 常见状态：待支付、支付中、支付成功、支付失败、已取消、已退款、已关闭。
- 每个外部事件只能触发合法流转，例如待支付可以变支付成功或取消，支付成功不能再变待支付。
- 支付回调可能重复到达，所以要用业务单号、支付单号、唯一索引和状态判断保证幂等。
- 回调处理要验签、校验金额、校验商户订单号，再更新本地状态。
- 支付状态更新、支付流水与 outbox 事件应在同一个 MySQL 本地事务中写入；CDC 从 binlog 捕获这条 outbox 记录后投递 Kafka，通知发券、积分、物流等下游。下游按 `event_id` 幂等消费，不能因为消息重投就重复发券或扣积分。

### 22. 如何防止重复支付或重复提交？

**答案：**

- 前端按钮置灰只能减少误触，不能作为核心保证。
- 后端要用请求号、业务唯一键、支付单唯一索引、状态机判断保证幂等。
- 对外部支付回调，要以支付平台交易号和本地订单号做唯一约束。
- 如果引入分布式锁，也只能作为并发互斥辅助手段，最终仍要靠状态机和唯一约束兜底。

### 23. 项目里并发很大、订单量突然上来时，你会怎么扛？

**面试官真正想听什么：**

- 你会不会先讲瓶颈分析，而不是一上来就说“加机器”
- 你能不能把流量入口、应用层、缓存层、数据库层拆开讲
- 你知不知道“先止血，再扩容，再重构”的思路

**先定目标：**

- 先保证核心链路不挂
- 先保写入成功，再谈复杂功能
- 避免局部热点拖垮整个系统

**回答顺序建议这样讲：**

1. **先定位瓶颈在哪一层**

   - 网关扛不住
   - 应用线程池 / goroutine 爆了
   - Redis 热 key
   - MySQL 慢 SQL / 锁竞争
   - MQ 积压

2. **入口先做止血**

   - 限流
   - 熔断
   - 降级
   - 非核心功能先关掉

3. **把重操作异步化**

   - 下单、发券、通知、统计尽量解耦到 MQ
   - 主链路只保最关键成功结果

4. **热点隔离**

   - 热门商品、热门用户、热点配置单独隔离
   - 防止单点热点把整个系统拖垮

5. **数据库层做兜底**

   - 补索引
   - 限制大事务
   - 读写分离
   - 必要时做分库分表

**trade-off 要主动补一句：**

- 不是所有问题都该靠数据库硬扛
- 也不是所有问题都能马上靠分库分表解决
- 很多时候第一步是削峰、限流、异步化，而不是直接做大手术

**面试里推荐这样答：**

> 如果订单量突然上来，我不会直接说加机器，而是先按层定位瓶颈：入口、应用、缓存、数据库、消息队列分别看。短期先靠限流、降级、异步化和热点隔离止血，优先保住下单主链路；中期再补数据库索引、优化慢 SQL、拆大事务；如果增长是长期的，再考虑分库分表和更大的架构调整。这个题的关键不只是扩容，而是知道先保什么、先挡什么、先拆什么。

### 24. 如果用户量本身很大，系统要怎么设计得更稳？

**面试官真正想听什么：**

- 你会不会把“高并发”和“高用户量”区分开
- 你知不知道读多写少和写多读多的治理方式不同
- 你会不会讲容量规划和分层设计

**先定问题：**

用户量大，不一定等于每时每刻并发都大。
所以这题要先拆成：

- 总用户量大
- 在线用户量大
- 瞬时并发大

**系统设计思路：**

1. **分层承压**

   - 静态资源走 CDN
   - 热读请求优先走缓存
   - 重写操作尽量异步化

2. **存储分层**

   - 热数据和冷数据分开
   - 在线查询链路和历史归档链路分开

3. **服务拆分**

   - 核心链路和非核心链路拆开
   - 用户系统、订单系统、搜索系统不要混成一个大服务

4. **容量规划**

   - 不是“用户量 1000 万”就结束
   - 要继续估：
     - 日活
     - 峰值 QPS
     - 单用户请求频率
     - 数据增长速度

不要从单体一步跳到“全套微服务 + 分库分表”。更合理的演进是每个阶段先解决已经被监控和压测证明的瓶颈：

| 阶段 | 先做什么 | 为什么 |
| --- | --- | --- |
| 100 万用户 | 索引优化、主从读写分离、Redis 缓存、应用无状态扩容 | 此时通常先解决慢 SQL、热点读和单机容量 |
| 1000 万用户 | 按业务边界拆服务，非核心链路异步化，增加 CDN、热点隔离和容量压测 | 流量和团队规模上升后，需要隔离故障与发布影响 |
| 1 亿用户 | 按访问路径做数据分片，建设路由层、全局 ID、冷热分离和多机房容灾 | 单库容量、热点分片和机房故障开始成为长期约束 |

**例子：**一个订单系统从日活 20 万增长到 2000 万。第一阶段先把订单列表的慢 SQL 和索引修好，再用缓存承担重复查询；峰值写入增加后，把短信、积分、推荐从下单事务拆到 MQ；确认单库订单表已经成为持续瓶颈后，才按 `user_id` 分片，并提前设计路由版本、增量同步和灰度切流。这个顺序比一开始就分库分表风险更低，也更容易定位每次改造带来的收益。

#### 追问：如果你做的项目规模扩大 100 倍，最先会炸在哪里？

不要脱离数据直接说“数据库一定会炸”。先用压测、容量模型和监控找**最短板**：入口 QPS、单请求 CPU / 内存、连接池等待、缓存命中率与热 key、DB 的慢 SQL / 锁 / 写入 IOPS、MQ 积压、下游配额以及单机网卡带宽。哪项先到 70%～80% 水位，哪项就是优先治理对象。

回答时可以按“预测 → 止血 → 演进”讲：

1. **预测：**用当前峰值 QPS、请求大小、读写比和增长率估算 100 倍后的连接数、带宽、存储和分区数，并压测验证，而不是拿平均 QPS 估容量。
2. **短期止血：**限流、排队、缓存、降级、异步化、连接池与 goroutine 上限，优先保护登录、下单、支付等主链路。
3. **长期演进：**按已经验证的热点拆分无状态服务，读写分离或分片，按 key 分区 MQ，隔离大客户 / 大任务 / 热 key，并在每次扩容后验证 P99、错误率和成本。

例如一个原本单实例同步处理文件的服务，放大 100 倍后最早可能不是 CPU，而是上传连接、对象存储带宽或下游解析队列；此时先做分片直传、异步解析和队列背压，比盲目把业务实例扩 100 倍更有效。

**高分点：**

- 真正大规模系统不是靠单点参数调优扛出来的
- 而是靠“缓存、异步、隔离、分层、容量规划”一起做

**面试里推荐这样答：**

> 用户量大时，我会先把“总量、在线量、瞬时并发”拆开看，因为它们对应的架构压力不一样。整体设计上会走分层承压：静态资源走 CDN，热点请求走缓存，重操作异步化；数据上做冷热分离，服务上做核心链路和非核心链路拆分。真正稳定的大规模系统，不是靠某一个数据库参数或线程池参数解决，而是靠分层、隔离和容量规划一起兜住。

- 你是不是只会说“数据量很大”
- 你能不能把量级、链路、瓶颈和优化点一起讲

### 26. 如果文件非常大、内存有限，你会怎么处理？

**面试官真正想听什么：**

- 你知不知道“不能把整个文件一次性读进内存”
- 你会不会讲分块、流式处理、外部排序这类思路

**核心原则：**

- 不要一次性全量读入内存
- 要按块处理
- 中间结果必要时落磁盘

**常见做法：**

1. **流式读取**

   - 一边读一边处理
   - 适合日志解析、文本扫描、哈希计算

2. **分块处理**

   - 把大文件拆成多个 chunk
   - 每块单独处理，再汇总结果

3. **外部算法**

   - 如果数据量远超内存，就用外部排序、分桶、临时文件归并

**高分点：**

- 你要主动说明：这类题本质上是“用磁盘换内存”
- 不要假装所有问题都能靠内存 map 解决

**面试里推荐这样答：**

> 文件特别大、内存有限时，核心原则就是不要整文件读进内存，而是改成流式读取和分块处理。如果问题需要全局排序或全局聚合，就要接受“用磁盘换内存”，采用外部排序、分桶或归并的思路。这个题考的不是 API，而是你有没有大数据量下的资源约束意识。

### 27. 500G 文件、内存只有 8G，这类海量数据题怎么回答才不慌？

**面试官真正想听什么：**

- 你能不能先判断“内存肯定不够”
- 你会不会讲外部排序、分桶、哈希拆分、归并
- 你能不能先说思路，再看具体题型

**万能回答框架：**

1. **先判断约束**

   - 500G 远超 8G，不能全量进内存

2. **再判断题型**

   - 如果是排序：外部排序
   - 如果是去重 / 聚合：分桶 + 局部处理
   - 如果是查 TopK：小根堆 + 分块扫描
   - 如果是匹配组合：哈希分片后局部求解

3. **最后讲工程细节**

   - 临时文件怎么落盘
   - 分桶规则怎么定
   - 如何保证最终归并正确

**举一个最通用的说法：**

> 这类海量文件题我会先承认“内存一定不够”，所以不能按常规算法直接做，而要转成外部算法。排序就做外部排序，先分块排序再归并；如果是查找或聚合，就先按哈希或范围做分桶，把大问题拆成多个内存可处理的小问题。核心思想是分而治之，用磁盘换内存。

**面试里推荐这样答：**

> 500G 文件配 8G 内存，这种题第一反应不是想“怎么调参数塞进去”，而是立刻切换到外部算法思路。先按题型分类：排序就外部排序，聚合就分桶，TopK 就分块扫描配堆，匹配组合就先哈希拆分。高分点在于你先明确资源约束，再给出分治和落盘方案，而不是直接写普通内存算法。

### 28. 分布式任务调度应该怎么做？

**面试官真正想听什么：**

- 你会不会把“什么时候触发”和“谁来执行”拆开。
- 多实例、节点宕机、网络抖动时，是否会重复跑、漏跑或并发跑。
- 是否理解**无法只靠分布式锁实现真正的 exactly-once**，要用幂等、重试和对账兜底。

**先定目标：**

- 到点尽量触发，并明确错过调度（misfire）是补跑一次、跳过，还是合并执行。
- 任务同一调度周期只创建一个执行实例。
- 执行失败可重试，节点故障后可接管。
- 任务状态、耗时、重试和积压可观测。

#### 一、先拆成“任务定义”和“任务实例”

```text
Job 定义：每天 02:00 跑一次结算
  -> 本次调度时间到达
  -> Task 实例：job_id + scheduled_at = 2026-09-03 02:00
  -> 被一个 executor 抢到并执行
```

- **Job 定义**保存 cron / 下次触发时间、参数、超时、重试策略、并发策略和启停状态。
- **Task 实例**保存本次 `scheduled_at`、状态、执行节点、尝试次数、开始 / 结束时间和错误原因；对 `(job_id, scheduled_at)` 建唯一约束，防止多个调度器重复创建同一轮任务。
- 高频海量延迟任务可用时间轮或延迟队列；普通 cron 任务用带 `(status, next_run_at)` 索引的数据库扫描通常已足够。

#### 二、调度与执行解耦

```text
多个 scheduler
  -> 找到到期 Job，创建唯一 Task 实例
  -> 投递 MQ / 任务队列
多个 executor
  -> 原子抢占 Task 实例
  -> 执行业务，记录成功 / 失败
```

调度器可以用 leader 选举、分片扫描，或成熟调度中心（如 XXL-JOB、Kubernetes CronJob）来减少重复扫描；但高可用不能只依赖“只有一个节点在跑”。即使两个 scheduler 因切换同时创建任务，唯一约束也要把重复创建挡住。

执行器通过**数据库状态抢占**领取任务，避免持有分布式锁执行长任务。例如只有 `READY` 状态才能原子切换为 `RUNNING`；更新成功的节点才拥有执行权。任务很长时还要续租心跳：租约过期后可被其他节点接管，同时用执行版本 / fencing token 防止旧节点恢复后继续写入结果。

#### 三、重复、失败和宕机怎么处理

| 问题 | 处理方式 |
| --- | --- |
| 调度器重复触发 | `(job_id, scheduled_at)` 唯一约束；重复插入视为已创建。 |
| executor 执行中宕机 | `RUNNING` 任务的租约超时后重置或转交；接管前检查执行版本。 |
| MQ 重投、超时后不确定是否已执行 | 按**至少一次**投递设计；业务用 `task_instance_id`、业务唯一键或状态机保证幂等。 |
| 任务失败 | 限次指数退避重试；超过上限进入失败 / 死信状态并告警，不要无限重试。 |
| 上一轮未完成、下一轮又到点 | 按业务选择禁止并发、排队、覆盖或合并；例如账务结算通常禁止并发，指标汇总可合并窗口。 |

> 分布式调度的正确目标通常是“至少一次调度 + 幂等执行”，不是承诺绝对只执行一次。比如发优惠券时，以 `user_id + campaign_id` 建唯一约束；重复 Task 即使跑两次，也只能发一张券。

#### 四、一个结算任务的完整链路

```text
02:00 到达
  -> scheduler 创建 (settlement, 02:00) 的 READY 实例
  -> 唯一约束去重后投递任务队列
  -> executor A 原子抢占为 RUNNING，并定期续租
  -> 以 task_instance_id 写幂等账务记录
  -> 成功：SUCCEEDED；失败：按退避时间回到 READY
  -> 重试耗尽：FAILED + 告警；之后由人工 / 补偿任务处理
```

**观测和运维：**至少监控到期未创建数、队列积压、任务延迟、运行时长、成功率、重试次数、租约超时接管次数和失败任务数；任务参数、执行日志和状态迁移都应可查询。时区、夏令时、发布暂停、批量补跑和数据对账也要有明确策略。

**面试里推荐这样答：**

> 分布式任务调度我会拆成 Job 定义、Task 实例、调度、执行和补偿五层。到点先创建以 `job_id + scheduled_at` 唯一的任务实例，再由多个 executor 原子抢占执行；调度与执行解耦，节点宕机通过租约和心跳接管。因为 MQ 重投和超时会带来重复，我按至少一次投递设计，业务必须以任务 ID 或业务唯一键保证幂等。失败采用限次退避重试、死信和告警；还要定义错过调度和上一轮未完成时是否补跑、并发或合并。重点不是 cron API，而是去重、接管、幂等和可观测闭环。

### 29. 如何设计一个支撑 10 万 QPS 的路径规划服务？

**答案：**

先确认边界：10 万 QPS 是全局还是单城市，目标 p99、实时路况时效、地图更新频率、是否有货车限行或多途经点等个性化约束。不同答案会导致完全不同的容量和缓存设计。

```text
客户端 -> Gateway（鉴权、限流、城市路由）
       -> 区域路径规划集群（无状态横向扩容）
       -> 静态路网快照 + 实时路况 Overlay
       -> 本地/分布式路径缓存

地图编辑/路况流 -> Kafka -> 区域状态服务 -> 版本化快照与 Overlay
```

- 静态道路拓扑按城市或地理网格分片，版本化后加载到本地内存或 mmap；路径引擎按区域横向扩容。
- 实时路况通过 Kafka 更新到对应区域的内存 Overlay，不每次请求都查数据库。
- 使用分层/预处理算法，例如主干路索引、Contraction Hierarchies 或 MLD，把在线搜索限制在局部区域和少量候选路径。
- 缓存 key 至少包含起终点网格、出发时间桶、`map_version` 和 `traffic_version`；命中旧版本不能直接返回。
- 热点城市独立资源池；依赖或路况流异常时可降级为静态路况、较粗路线或短 TTL 缓存结果。

**例子：**早高峰北京到上海的跨城路线请求非常集中。入口先按城市与网格路由，命中“起点网格 + 终点网格 + 5 分钟时间桶”的缓存；未命中才进入路径引擎。事故事件只更新受影响区域的 traffic overlay 并递增 `traffic_version`，相关缓存自然失效，不需要全量清空。这样热点请求主要在缓存层完成，路径引擎只处理长尾和个性化请求。

**面试回答：**

> 10 万 QPS 的关键不是单纯加机器，而是区域分片、静态路网本地化、实时路况流式 Overlay、版本化缓存和热点隔离。读链路尽量不查 DB；在线算法只做必要的局部搜索，热点 OD 对走缓存。我要持续看 p99、缓存命中率、路况版本延迟、单城市流量倾斜和路线成功率，并准备静态路况降级。

### 30. 分布式系统中，如何保证地图数据最终一致性？

**答案：**

最终一致性不是“发一条 MQ 就结束”，而是可靠投递、顺序/版本、消费幂等、版本发布和对账的闭环。地图编辑数据以主库为事实源，实时路况以事件流为事实源；两类数据都要显式带版本。

```text
地图编辑事务：主库更新 + Outbox 事件同一事务提交
  -> CDC / Relay 投递 Kafka
  -> 索引、缓存、搜索、路径引擎分别消费
  -> 按 feature_id + version 幂等更新
  -> 构建完成后原子切换 map_version
```

- Outbox/CDC 解决“数据库已提交但消息没发出”的双写问题。
- Kafka 按 `feature_id` 分区，保证同一道路要素的事件顺序；消息包含 `event_id`、`feature_id`、`version`、操作类型和时间。
- 消费者用去重表或唯一约束去重，只接受更高版本；删除使用 tombstone，避免旧消息把已删除道路重新写回。
- 地图索引构建完成后通过 manifest/版本指针原子发布，读服务在一个请求内固定使用同一 `map_version`，不能读到半新半旧数据。
- 失败事件进入重试/死信队列；定时用主库快照与索引、缓存、下游数据做行数、版本和抽样路径对账。

**例子：**一条道路在 10:00 被封闭，主库把 `road_123` 更新为 `version=42`，并写入 Outbox。CDC 投递 Kafka 后，路径引擎先构建带 `version=42` 的区域 overlay，校验成功才切换版本指针。重复消息因为版本相同被忽略；若旧的 `version=41` 迟到，也会被版本比较丢弃。直到新版本发布前，用户仍会读旧快照，但不会读到一半新、一半旧的路线数据。

**面试回答：**

> 我会以主库和版本化事件为事实依据：主库更新与 Outbox 同事务提交，CDC 可靠投递 Kafka；消费者按要素 ID 保序、按事件 ID 去重、按版本单调更新；索引和缓存按 map_version 原子发布。失败走重试、死信和对账。这样允许短暂读旧数据，但保证最终收敛，并避免重复、乱序和半版本发布。

### 31. TB 级文件如何合并？文件之间无序、每个文件内部有序怎么办？

**先确认题意：**

- 文件之间无序，表示不能简单按文件名拼接；例如 `file-01` 的最大值可能比 `file-02` 的最小值大。
- 每个文件内部有序，表示每个文件都是一个已排序的 run，例如按用户 ID、时间戳或整数升序。
- TB 级数据无法整体读入内存，因此本质是 **多路归并（k-way merge）+ 流式读取 + 外部存储**。

#### 一、核心思路：维护每个文件的当前最小值

假设有 1000 个文件，每个文件内部按 `user_id` 升序：

```text
file A: 1, 10, 20, 50, ...
file B: 2,  8, 30, 40, ...
file C: 3,  7, 25, 60, ...
```

不能先读完 A 再读 B，因为输出会变成 `1, 10, 20, 50, 2...`，全局不再有序。正确做法是从每个文件读一条记录，放进一个大小为 `k` 的最小堆：

```text
初始堆: [A:1, B:2, C:3]

弹出 A:1 -> 写入结果文件 -> 从 A 再读 10 -> 入堆
弹出 B:2 -> 写入结果文件 -> 从 B 再读 8  -> 入堆
弹出 C:3 -> 写入结果文件 -> 从 C 再读 7  -> 入堆

结果: 1, 2, 3, 7, 8, 10, 20, 25, 30, 40, 50, 60 ...
```

- 每次堆顶一定是所有“尚未输出数据”中最小的一条，因此顺序正确。
- 弹出一条后，只需要从同一个文件再读一条补回堆，不会把整个文件读到内存。
- 时间复杂度是 `O(N log k)`，`N` 是总记录数，`k` 是参与归并的文件数；堆本身只占 `O(k)` 条记录的内存。

#### 二、TB 数据落地时的完整流程

```text
多个已排序输入文件
  -> 每文件一个顺序读 buffer
  -> 最小堆维护各文件当前记录
  -> 大 buffer 顺序写临时结果文件
  -> 多轮归并
  -> 最终全局有序文件
```

**1. 一次不要打开过多文件。**

- 1000、1 万个文件直接同时打开，可能超过文件描述符上限，也会让每个 buffer 太小、磁盘随机读增多。
- 设置归并路数 `k`，例如内存、文件描述符和磁盘吞吐允许时每轮合并 64 或 128 个文件。
- 第一轮将原文件分成若干组，每组归并出一个临时有序文件；第二轮再归并这些临时文件，直到只剩一个结果文件。

**2. 读写都用大 buffer，避免逐行系统调用。**

- 每个输入文件使用顺序读取 buffer，例如 1～8 MB；输出文件也使用较大的顺序写 buffer。
- 具体 buffer 和 `k` 的大小按可用内存、FD 上限、磁盘类型和压测结果确定。可用内存不能只除以 `k`，还要给堆、解析对象、输出 buffer 和系统页缓存留余量。
- 归并过程几乎都是顺序读和顺序写，适合磁盘吞吐；不要在循环中反复 seek 或频繁打开关闭文件。

**3. 数据格式决定解析和稳定性。**

- 固定长度二进制记录可直接按 key 读取，CPU 开销小；CSV/JSON 需要解析字段，可能先转换为更适合归并的中间格式。
- key 相同怎么办要提前定义：保留全部记录、按时间戳二次排序、去重保留最新版本，还是聚合计数。
- 如果需要稳定排序，堆比较器除业务 key 外再比较 `source_file_id + sequence_no`，保证相同 key 的输出顺序可预测。

#### 三、Go 风格伪代码

```go
type Item struct {
    Key      int64
    Value    []byte
    FileID   int
    Sequence int64
}

// heap 中每个元素都是一个文件当前尚未输出的最小记录。
for _, file := range files {
    if item, ok := readNext(file); ok {
        heap.Push(h, item)
    }
}

for h.Len() > 0 {
    item := heap.Pop(h).(Item)
    writeBuffered(output, item)

    if next, ok := readNext(files[item.FileID]); ok {
        heap.Push(h, next)
    }
}
```

生产代码还要处理文件校验、解析错误、临时文件命名、磁盘满、进度 checkpoint 和中断恢复，不能只写这段核心循环。

#### 四、失败恢复与工程边界

- 每轮归并输出到临时路径，写完后校验记录数、字节数、首尾 key 或 checksum，再原子 rename 为完成文件；不要直接覆盖最终结果。
- manifest 记录输入文件列表、归并轮次、临时输出、checkpoint 和校验值。任务失败后可从上一个完成轮次恢复，不必从 TB 原始文件重新开始。
- 输入文件若仍在追加，必须先按版本/水位线冻结快照，否则“合并期间文件继续变大”会让结果不可重复。
- 多磁盘、多机器时可以先按 key range 做分区，每个分区独立归并；边界 key 要统一规则，最终再按分区顺序拼接。若输入不按 range 切分，分布式 shuffle 的成本可能远高于本地归并。

**面试里推荐这样答：**

> 每个文件内部有序但文件之间无序时，我会做 k 路外部归并。每个文件只顺序读一个 buffer，把各文件当前最小记录放到最小堆；每次弹出堆顶写入输出，再从同一文件补一条。这样全局顺序正确，时间复杂度是 `O(N log k)`，内存只需要 `O(k)` 条记录和读写 buffer。TB 级数据不能无限打开文件，所以会按 64 或 128 路分批归并、多轮产出临时文件；同时用 manifest、checksum 和原子 rename 做断点恢复。相同 key 的去重或稳定顺序要在比较器和业务规则中提前定义。

### 32. 100 个指标有些延迟、服务崩了甚至没有指标，怎么设计告警？

#### 先用一句人话说清这道题

这题要解决的不是“给 100 个数字都设一个阈值”，而是：**当监控图上没有数字时，我怎样区分“业务真的没有发生”“服务挂了”“监控系统没采到”这三件完全不同的事？**

先记住最小结论：

> 我会把告警分成四类：用户是否真的受影响、服务是否还活着、关键业务数据是否新鲜、监控系统自己是否正常。没有数据绝不直接当成 0；服务挂掉用服务存活告警和外部探测发现，业务数据迟到则单独报“数据迟到”。

#### scrape、up 到底是什么？先把名词翻译成人话

| 名词 | 全称 / 中文 | 你可以怎样理解 |
| --- | --- | --- |
| Metric（指标） | 一段可持续记录的数字。 | 例如订单成功数、接口错误数、CPU 使用率、请求耗时。 |
| Prometheus | 常见的监控系统。 | 它像一个定时来抄表的监控员，把各服务暴露的数字收集起来。 |
| Target（采集目标） | 被 Prometheus 采集的一个实例或地址。 | 例如 order-api 的某台机器。 |
| Exporter / metrics endpoint | 指标暴露程序 / 指标地址。 | 服务常在 metrics 地址输出数字；没有原生指标的 MySQL、Redis 也可借 Exporter 代为暴露。 |
| **scrape（拉取采集）** | Prometheus 主动定时访问 Target 的 metrics 地址。 | 每 15 秒去问一次：“你现在 CPU、QPS、错误数是多少？”这个“去问并抄下来”的动作就叫 scrape。 |
| **up** | Prometheus 自己生成的采集是否成功标记。 | up 等于 1：刚才能连上该 Target 并成功拿到指标；up 等于 0：这次没拿到，可能服务挂了、网络不通或指标地址坏了。 |
| Alert rule（告警规则） | 判断是否异常的条件。 | 例如“连续 2 分钟 up 等于 0”或“5 分钟错误率超过 5%”。 |
| Alertmanager | 告警通知器。 | 把触发的规则发到飞书、短信、电话；负责去重、合并和升级。 |
| Freshness（新鲜度） | 最后一条数据距离现在有多久。 | 订单成功数最后更新时间已经是 10 分钟前，就说明数据可能迟到或丢失。 |
| 黑盒 / 合成探测 | 从服务外部模拟真实用户访问。 | 监控机定时请求登录页或创建一笔测试订单；即使服务自己完全不再上报指标，也能发现故障。 |

**最容易说错的一句：**up 等于 1 不是“业务健康”，只代表“监控员刚才成功抄到表”。例如订单接口返回 500、订单成功数一直为 0，但指标地址还能访问时，up 仍可能是 1。

#### 用一个订单服务看完整最小链路

~~~text
order-api 服务
  输出：订单成功数、5xx 数、接口耗时、CPU 等指标
                 ▲
                 │ 每 15 秒主动访问一次；这就叫 scrape
                 │
Prometheus（监控员）
  ├─ 这次成功拿到数据：记录 up 等于 1
  ├─ 这次连不上或拿不到数据：记录 up 等于 0
  ├─ 保存指标并按规则判断
  ▼
Alertmanager（通知器） -> 飞书 / 短信 / 电话

另一台独立探针：
  定时请求 order-api 的健康接口或执行一笔测试下单
  即使 order-api 已彻底挂掉、不再输出指标，也能报警
~~~

#### 初学者答这道题，只要先分四类

| 要回答的问题 | 最简单的告警信号 | 发生后怎么做 |
| --- | --- | --- |
| 用户是否受影响？ | 下单/支付测试失败、5xx 错误率高、接口很慢。 | 高优先级通知值班；这是最接近真实故障的信号。 |
| 服务是否还活着？ | 所有关键实例连续一段时间 up 等于 0，或外部 HTTP 探测失败。 | 告警服务失联；不要把它当成“订单为 0”。 |
| 业务数据是否迟到？ | 最后一笔订单事件 / 最后一次成功统计距今超过约定时间。 | 报“数据迟到”，检查消息积压、消费者和采集链路。 |
| 监控系统是否还活着？ | Prometheus / 告警通知器没有心跳、规则没有执行、通知发送失败。 | 告警监控平台本身；否则会出现“系统挂了但没人收到告警”。 |

因此，100 个指标不要配 100 个电话告警。每个服务先选 1～2 个能直接代表用户受损的指标做紧急告警；CPU、连接池、缓存命中率等多数指标用于定位面板或普通通知。再额外给“服务失联”“数据迟到”“监控失联”各设一条独立规则。

#### 进阶版：为什么“没有数据”不能直接当成 0？

**先纠正一个危险做法：把“没有数据”当成 0。**

例如订单成功数没有上报，可能是订单为 0，也可能是应用挂了、Exporter 挂了、Prometheus 抓取失败、远程写积压、标签变了或查询写错。把它一律当 0 会同时造成漏报和误报。告警设计必须把“业务症状”“被观测对象健康度”“监控链路健康度”“数据新鲜度”分开。

```text
业务系统 / Exporter
      | scrape / push（带 source_timestamp）
      v
Prometheus / Agent -> remote write / TSDB -> Alert rule -> Alertmanager
      |                    |                    |
      |                    |                    +--> 告警是否送达？
      |                    +--> 写入 backlog / ingest lag？
      +--> target up？最新样本距今多久？

外部黑盒探测（独立区域） -> DNS / TCP / HTTP / 关键交易探测
```

#### 一、给每类信号定义“正常延迟”，不要要求所有指标实时

| 信号 | 例子 | 正常新鲜度 | 设计原则 |
| --- | --- | --- | --- |
| 在线服务指标 | QPS、5xx、CPU、请求延迟 | 秒到 1 分钟级 | 用 scrape 时间和 `up` 判断；适合实时告警。 |
| 事件 / 流式指标 | Kafka 消费量、支付事件 | 秒到数分钟 | 同时看事件发生时间和处理/入库时间，监控 consumer lag。 |
| 批处理指标 | 每日对账、离线特征、财务汇总 | 小时到天级 | 以 job deadline / watermark（已处理到的事件时间）告警，不能拿 1 分钟延迟规则套它。 |
| 推理 / Agent 任务 | 队列长度、Run 成功率、模型耗时 | 秒到分钟级 | 同时看请求入口、队列积压、worker 存活与结果产出，避免只看单一吞吐。 |

每条关键事件尽量保留两个时间：`event_time`（业务真正发生的时间）与 `ingest_time`（平台收到 / 入库的时间）。两者差值就是数据延迟；只看采集时间会把“旧事件刚补进来”误判为实时数据。

#### 二、三类告警要分开路由

```text
1. 服务真的坏了？        -> 症状告警：错误率、延迟、关键交易失败、黑盒探测失败
2. 服务看不见了？        -> 目标告警：up=0、最后成功 scrape 时间过旧、实例数异常
3. 监控自己坏了？        -> 可观测性告警：采集/远写/规则评估/告警投递延迟与失败
```

| 告警类型 | 典型条件 | 等级与动作 |
| --- | --- | --- |
| 症状告警 | `5xx`、SLO burn rate、p99、关键下单 / 支付合成探测异常，且数据新鲜 | 直接 page；这是用户实际受损的强信号。 |
| TargetMissing | 关键服务 `up=0`、实例全部消失、最后样本超过 freshness SLO | page 或高优先级通知；同时标明“服务失联，业务指标不可信”。 |
| TelemetryLag | remote write backlog、consumer lag、最后样本时间落后于阈值 | 先 ticket / 通知监控值班；超过关键窗口升级 page。 |
| MonitorBlind | Prometheus / Alertmanager 自身不可用、告警发送失败、整个区域没有心跳 | 高优先级 page；依赖独立的外部探针或第二套监控面发现。 |

关键服务的可用性不要只依赖它自己暴露的 `/metrics`。例如外部探针从另一个可用区定期做 DNS、TCP、HTTP 和一笔只读/合成交易；即使目标进程完全挂掉、不再暴露任何指标，探针仍能报警。监控系统自身也要有跨区域 heartbeat，避免“Prometheus 整体挂了，因此没有任何告警”的静默失败。

#### 三、延迟指标怎样避免误报，又不掩盖真实事故？

1. **新鲜度作为告警前置条件**：业务阈值告警只有在数据新鲜时才能判定为“业务异常”；数据不新鲜时不要静默，而是切换到 `TelemetryLag` / `TargetMissing` 告警。
2. **按数据类型设置 watermark**：例如实时 API 指标允许 2 分钟新鲜度，Kafka 指标允许 5 分钟，日报在次日 10:00 前未到才告警。阈值来源是正常延迟 p95/p99 + 业务 SLO，不是所有表统一 60 秒。
3. **使用 `for`、多窗口与抑制关系**：短暂 scrape 抖动可用 `for: 2m` 防抖；当 `TargetMissing` 已触发时，抑制该实例衍生出的几十条 CPU / QPS 无数据噪声；但不能抑制外部黑盒失败或核心业务失败。
4. **延迟恢复不等于事故恢复**：数据补到监控平台后应标记回填区间，告警系统可以重算报表，但不应因为一条迟到的“正常”样本自动宣称此前事故不存在。事故闭环以当时的 SLI、外部探针和人工确认时间线为准。

#### 一个 100 指标系统的实际策略

不要为 100 个指标各配一个 pager。先将它们归因到少量服务目标：可用性、延迟、错误、饱和度、数据正确性和观测新鲜度。每个目标选 1～2 个强症状指标做 page，其余做诊断面板或 ticket。

```text
order-api
  Page：合成下单失败 + 5xx burn rate（新鲜数据）
  Page：关键实例全 up=0 / 外部 HTTP 探测失败
  Ticket：DB pool wait、GC、单个慢 SQL、缓存命中率下降
  Observability：metrics_last_seen_age、scrape_error、remote_write_lag
```

这样某些指标延迟时，值班同学能一眼区分：是业务变差、服务失联，还是我暂时看不见服务。面试回答可收束为：

> 我不把无数据当成 0，而是把业务症状、目标存活、监控链路和数据新鲜度分成独立告警。实时指标用 `up` 和 freshness SLO，离线指标用 event time 与 watermark；服务完全挂掉依赖跨区域黑盒 / 合成探测，监控平台故障依赖独立 heartbeat。指标迟到时触发 TelemetryLag，而不是静默或误判业务为 0；再用 `for`、分级和告警抑制控制噪声。

### 33. 很久没操作系统，点击按钮或空白处却跳到登录页：怎么判断和设计？

**先给结论：**这很可能和登录态过期有关，但“点击空白处”本身不会让 Token 自动失效。它通常只是**触发了某段检查逻辑或一个被遮住的点击处理器**。排查时要先确定是前端主动跳转，还是某个接口返回未登录后被全局拦截器跳转。

#### 一、先区分四种常见原因

| 现象 | 更可能的原因 | 怎样确认 |
| --- | --- | --- |
| 长时间不动，点击任意按钮后跳登录 | Access Token 已过期；本次按钮操作请求接口，接口返回 401，前端全局响应拦截器清理登录态并跳转。 | 浏览器 Network 保留请求记录，查看跳转前最后一个接口的状态码和响应体。 |
| 页面刚打开或未发请求，倒计时一到就跳 | 前端定时器、路由守卫或前端解析 Token 的过期时间，主动登出。 | 搜索 logout、router.replace、navigate、setTimeout、token exp 等调用点。 |
| 只有点击“空白处”才跳 | 空白位置实际被全屏遮罩层、透明链接或父级点击事件覆盖；也可能注册了 document 级别的 click 监听。 | DevTools 元素检查该坐标命中的节点；在 Event Listener Breakpoints 中断在 mouse/click。 |
| 点击空白后紧接着跳 | 点击触发了刷新 Token、心跳、权限校验或懒加载请求；该请求 401 后统一跳转。 | 对比“点击前后”的 Network 请求，检查是否有 refresh、profile、permission、heartbeat。 |

HTTP 401 的语义是“当前请求缺少有效认证”；Token 过期、被服务端吊销、Cookie 未携带、时钟偏差都可能导致它。403 更常用于“已经认证，但没有权限”。不要只凭“跳到了登录页”就武断断言一定是 Token 过期。

#### 二、一条典型的跳转链路

~~~text
用户点击按钮 / 空白区域
          │
          ├─► 点击处理器发起 API、刷新 Token 或做路由鉴权
          │                         │
          │                         ▼
          │                    服务端返回 401
          │                         │
          └──────────────────► 全局响应拦截器
                                      │
                         清理本地 Token / Session
                                      │
                                      ▼
                         router.replace(登录页)
~~~

这里的全局拦截器便于统一处理真正失效的登录态，但必须避免把**任何** 401 都粗暴踢回登录页：例如刷新 Token 的并发请求、一个无权限的子资源、网络代理错误，都需要按接口类型和错误码分别处理。

#### 三、“点空白就跳转”通常是怎样实现的？为什么不推荐滥用？

前端可以在 document 上监听 click，也可以让一个 position: fixed 的全屏遮罩层接收点击；点击事件还会从子节点向父节点冒泡。因此一个父容器的“未登录则跳登录”逻辑、透明的 Link、未关闭的 Modal backdrop（模态框遮罩）都可能让用户觉得自己点了空白。

这类机制适合“点击遮罩关闭弹窗”或“闲置后首次操作时弹出续期提示”，**不适合**把任意空白点击直接当作登出动作。更好的会话超时设计是：

1. 记录用户活动，如键盘、鼠标、触摸、页面可见性变化；每次活动只重置前端的“空闲提示”计时器。
2. 空闲快到期时弹窗提示“还有 2 分钟过期”，用户可续期；不要无提示地跳走。
3. 真正登录态以服务端校验为准：Access Token 过期后，尝试一次受控的 Refresh Token 刷新；刷新失败或服务端明确返回未登录，才清理状态并跳登录。
4. 全局点击监听必须在组件卸载时移除；遮罩关闭时设置正确的 pointer-events，避免透明层意外拦截页面。

#### 四、实际排查步骤

1. 打开 DevTools，Network 勾选 Preserve log，复现“点击空白后跳转”；找跳转前最后一个请求，确认是否是 401、403、重定向还是根本没有请求。
2. 在 Sources 的 Event Listener Breakpoints 勾选 Mouse > click，以及 History / Navigation；代码会停在真正执行跳转的调用栈。
3. 用元素选择器检查空白点实际命中的 DOM；重点看透明遮罩、父级 Link、z-index、pointer-events 和 document 上的监听器。
4. 查看 Token 的 exp、浏览器 Cookie 的 Expires / SameSite，以及服务端日志中的认证失败原因；注意浏览器与服务器时钟差。
5. 修复后验证四件事：未过期时空白点击不跳；即将过期有明确提示；刷新成功可继续；刷新失败只跳一次且能回到原访问页。

**面试可直接答：**

> 长时间无操作后点击就跳登录，我先不假设是 Token 过期，而是看跳转前有没有 401。如果点击触发接口、接口因 Access Token 过期返回 401，再被全局拦截器清登录态并路由跳转，这是正常链路。若只是点空白就跳，优先怀疑 document 级 click、父级事件冒泡或透明遮罩层，而不是认证本身。设计上我会把“用户空闲提示”和“服务端登录态失效”分开：空闲先提醒并允许续期，真正退出以刷新失败或服务端明确未认证为准，并通过 Network、事件断点和服务端认证日志定位。

### 34. 一次 HTTPS 请求从 DNS、TCP/TLS、HTTP 到 Reverse Proxy 和上游服务的完整链路是什么？

**先给全图：**一次请求不是“浏览器直接调用业务服务”。DNS 负责把域名变成可访问的地址；TCP/TLS 建立一条安全传输通道；HTTP 承载业务请求；反向代理在服务端入口完成路由和治理，再把请求转给真正处理业务的上游服务。

~~~text
浏览器
  │  1. DNS：api.example.com -> IP
  │  2. TCP 三次握手
  │  3. TLS：协商密钥、验证证书
  │  4. HTTP 请求：Host / Path / Header / Body
  ▼
CDN / WAF / 四层 LB（可选）
  ▼
Reverse Proxy：Nginx / Envoy / Gateway
  │  TLS 终止、鉴权、限流、路由、负载均衡、超时、日志
  ▼
上游服务实例
  │  应用中间件 -> 业务逻辑 -> Cache / DB / RPC / MQ
  ▼
响应按原链路返回；连接通常通过 keep-alive 或 HTTP/2 复用
~~~

#### 一、逐层解释

| 阶段 | 做什么 | 典型失败与排查点 |
| --- | --- | --- |
| DNS 解析 | 浏览器、操作系统、本地递归解析器依次查缓存；未命中时由递归 DNS 查询权威 DNS，得到 A/AAAA 或 CNAME 记录及 TTL。 | DNS 超时、缓存旧记录、CNAME 配错、IPv6 不可达。看 DNS 查询耗时和解析出的 IP。 |
| TCP 三次握手 | 客户端发送 SYN，服务端返回 SYN-ACK，客户端再 ACK，双方确认收发能力并建立连接。 | 连接超时、SYN backlog 满、网络丢包、安全组/防火墙、LB 不健康。 |
| TLS 握手 | 客户端发 ClientHello；服务端选择协议和密码套件、返回证书；客户端校验证书域名和可信链；双方用 ECDHE 等密钥交换协商出对称会话密钥。HTTP/2 通常借 ALPN 协商出来。 | 证书过期或域名不匹配、SNI 配置错、TLS 版本/套件不兼容、握手耗时高。 |
| HTTP 请求 | 在已加密的连接中发送方法、路径、Host、鉴权信息、Cookie、请求头和请求体。HTTP/1.1 可长连接复用；HTTP/2 可在一条连接上多路复用。 | 4xx 多为请求、鉴权、限流问题；5xx 可能在代理或上游；关注 request id。 |
| 反向代理 | 服务端入口代表**服务端**接收客户端请求，再根据 Host、Path、权重或服务发现结果选择上游。可做 TLS 终止、WAF、鉴权、限流、压缩、连接池、重试、熔断和访问日志。 | 502 常见为无法连上或上游提前断开；504 常见为代理等上游超时；还要看路由和健康检查。 |
| 上游业务服务 | 解析请求、执行业务逻辑，可能继续访问缓存、数据库和其他 RPC 服务；将状态码、响应头和响应体返回。 | 线程池/连接池耗尽、慢 SQL、下游超时、GC、代码异常；用 Trace 定位具体 Span。 |

**Reverse Proxy（反向代理）与正向代理不要混：**正向代理代表客户端访问外部，例如公司代理服务器；反向代理代表服务端接收外部流量，例如 Nginx / Envoy，客户端通常不知道真实上游实例。

#### 二、两个容易被忽略的工程点

1. **代理到上游通常是另一跳连接。**客户端与 Nginx 的 TLS 可以在 Nginx 处终止；Nginx 再通过 HTTP、HTTPS 或 gRPC 连接上游。因此要分别配置客户端读写超时、代理到上游的连接/首包/总超时，不能只配一个大超时。
2. **客户端 IP 和协议要可信地传递。**代理会添加 Forwarded 或 X-Forwarded-For、X-Forwarded-Proto 等头；上游只能信任自己控制的入口代理写入的这些头，不能直接信任外部客户端传来的伪造头。

HTTP/3 是一个例外：它运行在 QUIC（基于 UDP）之上，握手和传输不再是传统 TCP 加 TLS 的两段式；但面试题若明确问 TCP/TLS，就按上图回答即可。

**面试可直接答：**

> 我会从 DNS、建连、加密、协议和服务端转发五层讲。域名先经缓存和递归 DNS 解析到 IP，然后 TCP 三次握手；HTTPS 再完成 TLS 证书校验和会话密钥协商，之后才在连接里发送 HTTP 请求。请求先到 CDN、LB 或 Nginx/Envoy 这类反向代理，代理负责 TLS 终止、鉴权、限流、路由和负载均衡，再用另一条到上游的连接转发。上游服务执行业务并访问 DB/RPC，响应原路返回。排障时我会把 DNS、TCP connect、TLS、TTFB、代理耗时和应用 Trace 分开看，才能知道慢在哪里。

### 35. etcd 的 Lease、Watch、服务发现缓存怎么设计？Watch 断开或实例刚注册但未 Ready 怎么办？

etcd 常被用作一致的注册表，但它不是每个请求都要查询的“实时路由数据库”。正确用法是：**etcd 保存服务实例的权威注册状态；客户端或代理把它同步成本地服务发现缓存，再从本地缓存做负载均衡。**

#### 一、Lease 和服务注册

Lease（租约）可以理解成带 TTL（Time To Live，存活时间）的“临时所有权”。服务启动后向 etcd 申请一个租约，把实例注册键绑定到租约；进程持续 KeepAlive（续租）。若进程崩溃、网络永久中断或不再续租，TTL 到期后 etcd 自动删除这批键，其他客户端就会收到实例下线事件。

~~~text
实例 order-10 启动
   │
   ├─ grant lease：TTL = 10 秒
   ├─ put /services/order/order-10 = {ip, port, zone, state}
   │     └─ 绑定该 lease
   └─ 每隔几秒 KeepAlive

进程崩溃 / 无法续租
   │
   ▼
TTL 到期，etcd 删除注册键
   │
   ▼
Watch 客户端收到 DELETE，从本地 endpoint cache 移除该实例
~~~

TTL 不是越短越好：过短会把短暂 GC、网络抖动误判为下线；过长又会让故障实例残留太久。常见做法是秒级到几十秒级 TTL，KeepAlive 间隔明显小于 TTL，并结合上游连接失败和健康检查快速摘除。

#### 二、服务发现缓存的正确初始化与更新

不能只先 Watch 再说“我已经有缓存了”。可靠顺序是一次 Range 全量读取加带 Revision（版本号）的 Watch：

~~~text
1. Range：读取 /services/order/ 前缀，得到实例全集和 revision = R
2. 用全集原子替换本地 endpoint cache
3. Watch：从 R + 1 开始监听同一前缀
4. 收到 PUT / DELETE，按 revision 顺序更新缓存快照
5. 调用请求只读取本地不可变快照并做负载均衡
~~~

这样既不会漏掉“全量读取之后、开始 Watch 之前”的变更，也不会让正常请求每次都压到 etcd。高并发客户端读取缓存可使用 copy-on-write（复制后替换）或读写锁，避免更新 Watch 结果时读到一半的数据。

#### 三、Watch 断开、慢消费者或压缩怎么办？

Watch 是一条流式连接，不应被认为永远可靠。网络中断、服务端重启、客户端消费太慢都可能导致它结束；而且 etcd 会压缩过旧历史，客户端从太老 revision 恢复时会得到 compaction（历史已压缩）错误。

处理流程应是：

1. 发现 Watch 结束、被取消或收到 compaction 错误后，用指数退避重连，防止大量客户端同时冲击 etcd。不能仅凭 revision 数字跳跃判断漏事件，因为其他 key 的写入也会推进全局 revision。
2. **不要只从旧位置盲目续 Watch。**先重新做一次前缀 Range，拿到最新全量实例和新 revision，用它原子重建本地缓存。
3. 再从新 revision 加一开始 Watch；如果报 compaction，更必须全量重建。
4. 重连期间可在一个明确的 max-stale（最大可容忍陈旧时间）内继续使用上一次缓存，并同时依赖连接失败快速摘除；超过窗口或缓存为空，则按业务选择失败快返、切流或降级，不能无限相信旧地址。
5. 记录 Watch 延迟、最后成功 revision、缓存实例数、重连次数和过期缓存命中，作为服务发现自身的监控。

#### 四、实例刚注册但还没 Ready，绝不能立即接流量

“进程存在”不等于“可以服务”。实例可能端口刚监听、配置还没加载完、连接池未建立、缓存未预热、模型未加载，或依赖尚未满足。若在启动第一秒把它注册为可选地址，负载均衡就会把真实请求打过去，产生启动抖动。

推荐把生命周期拆开：

~~~text
STARTING
  -> 已监听端口、加载配置、建立必要依赖、完成 warm-up
  -> readiness check 通过
READY：写入 /services/order-ready/order-10，或把 state 改为 READY
  -> 被代理 / 客户端纳入可选 endpoints

DRAINING：先从 ready 集合移除，不再接新请求
  -> 等待在途请求、超时兜底
STOPPED：撤销 lease 或停止续租
~~~

注册表可以保存全部实例，但服务发现消费者只订阅或筛选 READY 实例。若使用 Kubernetes，Pod 的 readinessProbe 以及 EndpointSlice 通常承担相似职责；etcd 注册也必须遵循同一原则。

**面试可直接答：**

> etcd 的 Lease 用来让注册自动过期：实例把注册键绑定租约并持续 KeepAlive，进程失联后 TTL 到期自动删键。客户端启动时先 Range 拉全量和 revision，再从 revision 加一 Watch，把事件更新到本地 endpoint cache，业务请求只读缓存。Watch 断开、revision 太旧或收到 compaction 时不能假装缓存仍然正确，我会退避重连、全量 Range 重建缓存后再 Watch，并限定旧缓存的 max-stale。实例启动不能一注册就接流量，必须在配置、依赖、预热和 readiness 通过后才进入 READY 集合；下线时先进入 DRAINING、摘除新流量、等待在途请求，再撤销租约。

### 36. 固定窗口、滑动窗口、令牌桶、漏桶分别是什么？网关为什么常用令牌桶？

限流的目标不是简单“拒绝请求”，而是在突发流量、爬虫或下游故障时，把系统的并发、平均速率和排队时延控制在可承受范围。先确定限流维度：全局、路由、租户、用户、IP、设备或热点资源；再决定超限是拒绝、排队、降级还是要求客户端稍后重试。

| 算法 | 核心规则 | 优点 | 缺点 / 适合场景 |
| --- | --- | --- | --- |
| 固定窗口 | 将时间切成 1 秒或 1 分钟等固定桶；桶内计数未超阈值就放行。 | 实现最简单，Redis INCR 加过期时间即可。 | 有边界突刺：某窗口末尾放满 N 个，下个窗口开头又放 N 个，极短时间可过 2N。适合粗粒度配额。 |
| 滑动窗口日志 | 保存最近一段时间每次请求的时间戳，只统计窗口内记录。 | 最精确地限制“任意连续窗口”。 | 内存、清理和排序成本高；高 QPS 不适合每请求一条记录。 |
| 滑动窗口计数 | 把窗口分成多个小桶，求最近 N 个桶之和，必要时对当前桶加权。 | 比固定窗口平滑，成本远低于完整日志。 | 仍是近似，桶越细成本越高。适合用户/API 的分布式配额。 |
| 令牌桶 | 以固定速率 R 补充令牌，桶最多存 B 个；请求取到令牌才放行。 | 平均速率受控，同时允许最多 B 的短时突发；通常 O(1) 且易本地实现。 | 不能单独保证下游输出绝对匀速；全局一致限流需要共享状态或一致路由。 |
| 漏桶 | 请求先进入有界队列，按固定速率向下游“漏出”。 | 输出更平滑，能保护只能稳定处理固定速率的下游。 | 排队会增加延迟；队列满了仍要丢弃；不适合网关把大量用户请求长期堆住。 |

~~~text
令牌桶：                       漏桶：
每秒补 R 个令牌                请求进入有界队列
桶最多存 B 个                  固定速率流出

突发 N 个请求                  突发 N 个请求
  -> 有令牌就立即通过            -> 大多先排队
  -> 用完则拒绝/稍后重试         -> 队列满则拒绝
~~~

#### 网关为什么常用令牌桶？

网关面对的是正常用户的短暂突发，例如页面刷新会并发请求用户信息、订单、配置和图片接口。若只按完全匀速的漏桶放行，会把这些正常突发排队，直接拉高用户延迟；令牌桶则允许积累的 B 个令牌瞬时消化一小段突发，同时长期平均不超过 R，兼顾体验与保护。

网关还常用令牌桶，因为它：

1. **开销低。**每请求只做一次基于时间差的补充和原子扣减，本地限流不需要每次访问 Redis。
2. **参数直观。**R 是长期 QPS 预算，B 是允许的突发量；可按路由、用户、IP、租户设置不同配置。
3. **易与容量联动。**根据后端实例数、连接池、下游容量和 SLO 推导 R 与 B；超限直接返回 429 和 Retry-After，或按优先级降级。
4. **支持分层。**每个网关实例先做本地令牌桶挡住大部分流量；确实需要全局资源上限时，再对热点 SKU、支付通道等使用 Redis / 专用限流服务做分布式令牌桶。

**面试可直接答：**

> 固定窗口最简单但有窗口边界双倍突发；滑动窗口更平滑，精确日志成本高，分桶计数是常用折中。令牌桶按固定速率补令牌，既限制长期平均 QPS，又允许桶容量范围内的短时突发；漏桶按固定速率出队，输出最匀但会把突发排成延迟。网关通常选令牌桶，因为用户请求本来就有短突发，令牌桶能兼顾体验和后端保护，而且本地实现 O(1)、参数 R 和 B 好调；全局额度再叠加 Redis 或限流服务。

### 37. 超时、重试、熔断、降级的顺序与区别是什么？为什么不能无脑重试 POST？

**先纠正一个说法：**它们不是一条请求上永远严格串行的四步。超时是每次调用的时间边界；重试是对少数可恢复失败的补救；熔断是依赖维度的共享状态机；降级是无法正常服务时的业务替代方案。它们共同构成韧性设计，但职责不同。

| 机制 | 解决什么 | 典型动作 | 不能解决什么 |
| --- | --- | --- | --- |
| 超时 | 不让一次调用无限等待，释放 goroutine、连接和线程池。 | 到 deadline 取消调用并返回超时。 | 不会让下游恢复，也不能判断请求是否已在下游成功。 |
| 重试 | 网络瞬断、连接被重置、临时过载等短暂故障。 | 在预算内、带退避和抖动地再次尝试。 | 对持续故障只会放大流量；无幂等时会重复副作用。 |
| 熔断 | 某个下游已持续失败，避免所有请求都去等待它。 | 错误率或慢调用超过阈值后 Open，快速失败；稍后 Half-Open 少量探测，恢复后 Close。 | 不会提供业务结果；需要配合降级或替代路径。 |
| 降级 | 系统仍要以较低能力服务用户。 | 返回缓存/默认值、关闭推荐、只保主链路、排队或提示稍后再试。 | 不应伪造关键业务成功，例如支付已完成。 |

#### 一、一次请求的推荐运行时顺序

~~~text
入口：鉴权、限流、总 Deadline
       │
       ▼
调用下游前：检查熔断器是否 Open
       │ Open
       ├────────────► 直接降级 / 快速失败
       │ Closed 或 Half-Open
       ▼
在本次调用的剩余时间预算内发起一次尝试
       │
       ├─ 成功 ───────────────────► 返回
       ├─ 可重试的临时错误 ─► 退避 + 抖动 + 重试预算仍足够？ ─► 再尝试
       └─ 不可重试 / 预算耗尽 ───────────────────────────────► 降级或失败

多次失败会反馈给熔断器；达到阈值后，后续请求走 Open 分支。
~~~

几个关键规则：

1. **先定总 Deadline，再切子预算。**例如入口总预算 800ms，网关、业务逻辑、下游调用和可能的一次重试都要从这 800ms 中分配；不能每层各配 800ms，否则最外层已经超时，内层还在白白工作。
2. **重试必须限层、限次、限时。**通常只在一个明确层级重试，避免客户端、网关、服务 A、服务 B 都重试三次，把一次请求放大为数十次。使用指数退避、随机抖动和 retry budget（重试预算）。
3. **只重试可恢复且幂等的错误。**例如连接尚未建立、明确的临时网络失败、部分 429/503；参数错误、权限错误和大多数 4xx 不应重试。对 429 应尊重 Retry-After。
4. **熔断不是降级。**熔断器负责“不要继续打坏下游”；降级决定“用户此刻看到什么”。例如推荐服务熔断后可以返回缓存热榜；支付服务熔断后只能明确提示处理中或稍后重试，不能伪造支付成功。

#### 二、为什么不能无脑重试 POST？

POST 只是 HTTP 方法，不天然等于“不能重试”；关键在于这个 API 是否有**副作用**和**幂等契约**。创建订单、扣款、发券、发送消息常用 POST。最危险的场景是：

~~~text
客户端 POST /payments
   │
服务端已成功扣款、已写数据库
   │
响应在网络中丢失 / 客户端超时
   ▼
客户端不知道服务端是否成功，直接再发一次 POST
   ▼
可能重复扣款、重复下单、重复发消息
~~~

安全做法是：

1. 客户端为同一业务意图生成 Idempotency-Key（幂等键），所有重试携带**同一个**键，不能每次重新生成。
2. 服务端以幂等键或业务唯一键建立唯一约束，在事务内记录处理状态和最终结果；重复请求返回第一次结果或“处理中”，不再重复执行副作用。
3. 超时后优先按业务单号查询最终状态；只有 API 合同明确支持幂等键、重试条件和返回语义时才自动重试。
4. 若调用第三方支付 / 短信等外部系统，也把同一幂等键透传，并准备状态查询、回调、对账和补偿，不把“HTTP 超时”当成“业务失败”。

**面试可直接答：**

> 超时是调用边界，防止资源无限等待；重试用于少量短暂故障，但必须有幂等、次数、退避和总时间预算；熔断是下游持续异常后的快速失败状态机；降级是熔断或资源不足时给用户的替代能力。运行时先在入口定总 deadline，调用下游前看熔断器，单次调用超时后只对可恢复且幂等的错误做有限重试，失败再降级。POST 不能无脑重试，因为服务端可能已经扣款或落库，只是响应丢了；必须用同一个幂等键、数据库唯一约束和状态查询把重复请求收敛成同一次业务。
