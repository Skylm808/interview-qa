# 设计模式面经合集

> 目标：不只背出模式定义，还能讲清参与者、调用时序、适用边界和常见坑。

---

## 1. 观察者模式（Observer Pattern）是什么？

**定义：**观察者模式建立一种一对多依赖关系：当主题对象（Subject，也叫 Publisher，发布者）的状态发生变化时，它会主动通知所有订阅它的观察者（Observer，也叫 Subscriber，订阅者），让它们各自更新。

它解决的是：**一个事件发生后，多个后续动作都要跟着发生，但触发方不想依赖每个具体处理方。**

### 一、先用订单支付成功举例

假设订单服务在支付成功后，库存要扣减、积分要发放、通知要发送。如果订单服务直接依次调用三个具体模块，后续再加“生成发票”就得不断修改订单代码。

~~~text
没有观察者：
订单服务 -> 库存服务
        -> 积分服务
        -> 通知服务
        -> 每新增一个动作，都要修改订单服务

观察者模式：
订单服务（Subject） -- 发布 PaymentSucceeded 事件 -->
      ├─ 库存观察者：扣减库存
      ├─ 积分观察者：发积分
      └─ 通知观察者：发送通知
~~~

订单服务只需要知道“我在发布支付成功事件”，不需要知道现在到底有几个后续处理器。

### 二、四个参与者分别做什么？

| 角色 | 职责 | 订单例子 |
| --- | --- | --- |
| Subject / Publisher（主题 / 发布者） | 保存订阅者列表；状态变更时发出通知。 | 订单或支付模块。 |
| Observer / Subscriber（观察者 / 订阅者） | 定义接收通知的接口。 | 事件处理器接口。 |
| Concrete Subject（具体主题） | 维护真实状态，变化时调用通知逻辑。 | PaymentService。 |
| Concrete Observer（具体观察者） | 实现收到通知后的具体业务。 | 库存、积分、通知处理器。 |

以 Go 的接口表达，核心不复杂：

~~~go
type PaymentObserver interface {
    OnPaymentSucceeded(orderID string)
}

type PaymentService struct {
    observers []PaymentObserver
}

func (s *PaymentService) Subscribe(o PaymentObserver) {
    s.observers = append(s.observers, o)
}

func (s *PaymentService) PaySucceeded(orderID string) {
    // 先完成支付状态变更；真实系统还要保证事件可靠投递
    for _, o := range s.observers {
        o.OnPaymentSucceeded(orderID)
    }
}
~~~

### 三、它的优点和代价

| 优点 | 代价 / 风险 |
| --- | --- |
| 发布者和订阅者解耦；新增订阅者通常不用改发布者。 | 调用链变隐式，排障时不如直接调用直观。 |
| 很适合 UI 状态刷新、领域事件、缓存失效通知。 | 同步通知时，慢观察者会拖慢发布者。 |
| 可按需订阅 / 取消订阅，扩展性好。 | 忘记取消订阅可能导致内存泄漏。 |
| 可将一个变化分发给多个处理器。 | 观察者失败、执行顺序、重复通知和并发安全都要定义。 |

### 四、观察者模式、发布订阅、MQ 不要混为一谈

| 对比 | 经典观察者模式 | 发布订阅 / MQ |
| --- | --- | --- |
| 典型位置 | 同一进程内的对象协作。 | 跨进程、跨服务的事件通信。 |
| 发布者是否直接知道订阅者 | 通常持有观察者接口或列表。 | 通常只知道 Topic，由 Broker 管理订阅关系。 |
| 调用方式 | 常为同步方法调用，也可异步。 | 常为异步投递，可持久化、重试、消费确认。 |
| 适合 | 本地事件、界面刷新、模块内扩展点。 | 订单事件、通知、日志流、削峰解耦。 |

可以把 MQ 看成“更分布式、更可靠的事件分发机制”，但它增加了最终一致性、重复消费、顺序和可观测性问题；不要为了本地一次简单回调引入 MQ。

### 五、面试追问：生产中怎么写得稳？

1. **先定同步还是异步。**同步适合必须马上完成的轻量校验；耗时通知、积分、搜索索引等通常异步化。
2. **先提交事实源，再可靠发布事件。**涉及数据库时，用 Outbox（本地消息表）或 CDC（变更数据捕获）避免“订单已提交但事件没发出去”。
3. **订阅方要幂等。**消息可能重复投递；库存、积分等以业务事件 ID 去重。
4. **隔离失败与慢处理器。**不要让一个发短信失败回滚已成功的支付；设置超时、重试、死信和告警。
5. **处理并发与注销。**遍历订阅者时避免同时修改列表；需要时复制快照、加锁或使用线程安全容器。

**面试可直接答：**

> 观察者模式是一对多的通知机制：主题对象状态变化后，通知所有订阅者，各订阅者完成自己的处理。它的价值是让发布者不依赖库存、积分、通知这些具体模块，新增处理器只要订阅事件即可。进程内它常是同步回调；跨服务时更接近基于 Topic 的发布订阅和 MQ，但要额外解决可靠投递、幂等、顺序和失败隔离。生产上我会先写事实源，再通过 Outbox 或 MQ 发布事件，并让每个订阅者可重试且幂等。
